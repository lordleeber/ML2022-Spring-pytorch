第 1 章　資料與 ε 的換算：0–255 的 8，在模型眼裡是多少

攻擊在模型看到的數字上進行，限制卻寫在 PNG 的像素上。兩者之間隔著 ToTensor 與 Normalize 兩道轉換，攻擊完還要走回去：乘回標準差、加回平均、剪到 0–255、四捨五入成整數。這一章把這條來回的路走一遍，看 ε = 8 為什麼在程式裡寫成 8/255/std，以及「程式印出的準確率」和「交出去的 PNG 的準確率」為什麼可能不同。

1.1　200 張圖在磁碟上的樣子

Kaggle 的壓縮檔解開後是 data/，底下 10 個以類別命名的資料夾，每個 20 張 PNG，檔名是「類別名稱＋編號」，例如 dog/dog2.png。AdvDataset 把它們讀進來：

這幾行藏了三個值得注意的地方。

類別編號來自資料夾名稱的字母順序。第 28 行把資料夾排序後，用 enumerate 的順序當類別編號：airplane 是 0、automobile 是 1……truck 是 9。可是代理模型在 CIFAR-10 上訓練時，類別編號是 CIFAR-10 自己定的。兩者要一致，模型的輸出才對得上標籤。它們剛好一致：CIFAR-10 的官方順序就是 airplane、automobile、bird、cat、deer、dog、frog、horse、ship、truck，正好是字母順序。這是巧合，不是程式保證的：如果資料集是 CIFAR-100、或類別用中文命名，同一段程式就會默默給出錯誤的標籤，原圖準確率會掉到接近亂猜，而且程式不會報錯。

檔名是字串排序，不是數字排序。第 29 行的 sorted 比的是字串，所以每一類的順序是 airplane1、airplane10、airplane11、……、airplane19、airplane2、airplane20、airplane3……。dog/dog2.png 因此排在第 111 個（從 0 算起），而不是你可能以為的第 101 個。這對結果沒有影響，因為每張圖都帶著自己的名字走（第 32 行的 names），最後依名字存回同一個位置；但如果你想用索引去找「第幾張圖」，就要小心。

names 是相對路徑。os.path.relpath 把 ./data/dog/dog2.png 變成 dog/dog2.png，存檔時接在輸出資料夾後面（1.6 節），交出去的資料夾結構就和 data/ 一模一樣。JudgeBoi 靠這個結構判斷每張圖的正確類別。

__getname__ 這個方法名稱長得像 Python 的特殊方法（前後兩個底線），其實不是：Python 沒有叫 __getname__ 的協定，它只是一個普通方法，hw10.py 第 25 行直接呼叫它。PEP 8 建議不要自己發明這種名字，因為將來 Python 可能真的定義同名的特殊方法。

1.2　ToTensor 與 Normalize：模型看到的數字

PNG 讀進來是 32×32×3 的 0–255 整數。ToTensor 做兩件事：把形狀從 (高, 寬, 通道) 換成 PyTorch 慣用的 (通道, 高, 寬)，再除以 255 變成 0–1 的浮點數。Normalize 再對每個通道減去平均、除以標準差。平均與標準差寫在 config.py：

這組數字是 CIFAR-10 訓練集 5 萬張圖每個通道的平均與標準差（取到小數點後三位）。pytorchcv 的模型訓練時用的就是這樣的正規化，所以攻擊與評估也必須用同一組，模型看到的輸入分布才和訓練時一致。.view(3, 1, 1) 把三個數排成 (3, 1, 1) 的形狀，和 (B, 3, 32, 32) 的圖片相乘時會自動廣播（broadcast）到每一個像素。

正規化之後，數字的範圍不再是 0–1。量了這 200 張圖：三個通道的最小值是 −2.43、−2.42、−2.22，最大值是 2.52、2.60、2.75。為什麼不對稱？因為一個通道的最小值是 (0 − 平均) ÷ 標準差，最大值是 (1 − 平均) ÷ 標準差，平均不在 0.5，兩邊就不一樣長。這件事在 1.5 節會變得重要：合法像素在模型眼中的範圍，每個通道都不同。

1.3　ε = 8 為什麼寫成 8/255/std

限制是寫在 0–255 的像素上：|a − p| ≤ 8，p 是原圖的像素、a 是改過的像素。攻擊卻是在正規化之後的空間裡做的：程式改的是 N(T(p))，T 是 ToTensor（除以 255）、N 是 Normalize（減平均、除標準差）。兩個空間之間的距離是一個固定的比例：

| N(T(a)) − N(T(p)) | = | (a/255 − mean)/std − (p/255 − mean)/std | = | a − p | ÷ (255 × std)

平均在相減時消掉了，只剩下除以 255 和除以標準差。所以「像素上差 8」對應到「正規化空間裡差 8 ÷ (255 × std)」，這就是第 16 行的 8/255/std。因為三個通道的標準差不同，ε 也是三個不同的數：

通道stdε（正規化空間）= 8/255/std
R0.2020.155310
G0.1990.157651
B0.2010.156082

epsilon 是一個形狀 (3, 1, 1) 的張量，攻擊函式裡的 epsilon * grad.sign() 與 x + epsilon 都靠廣播把每個通道的 ε 套到對應的像素上。

常見錯誤：忘了除以 std

如果寫成 epsilon = 8/255（0.0314），在正規化空間裡走 0.0314，換回像素是 0.0314 × 255 × std ≈ 1.6。三個通道分別是 1.616、1.592、1.608：比允許的 8 小了約 5 倍。圖片完全合法，JudgeBoi 不會報錯，只是攻擊弱很多。第 2 章的 ε 掃描裡，resnet110 在 ε = 1 與 ε = 2 時白箱準確率是 0.735 與 0.665，遠不如 ε = 8 的 0.590。反過來，如果攻擊在 0–1 的空間裡做、卻除了 std，就會超過 8 被退件。所以 notebook 在這一格寫著「Don't change the settings here」。

另一個做法是把正規化從資料轉換搬進模型裡：資料只做 ToTensor（0–1），模型的第一層是「減平均、除標準差」。這樣攻擊就在 0–1 的空間裡做，ε 就是單純的 8/255，剪回合法範圍也只是 clamp(0, 1)。現在的對抗攻擊函式庫（例如 torchattacks、RobustBench 的模型）大多採用這個慣例，第 4 章會再提到它的好處。

1.4　攻擊之後：走回 PNG

攻擊函式回傳的 x_adv 還在正規化空間裡，而且是浮點數。gen_adv_examples 一邊量代理模型的準確率，一邊把每個 batch 換回可以存成 PNG 的整數：

第 86–89 行把 ToTensor 與 Normalize 倒著做一遍：乘回 std、加回 mean，回到 0–1；剪到 [0, 1]；乘 255；四捨五入成整數；把形狀從 (B, C, H, W) 換回 (B, H, W, C)。第 90 行用 np.r_ 把每個 batch 接起來，最後得到 (200, 32, 32, 3) 的陣列。

來回一趟會不會有誤差？把 200 張原圖經過 transform 再倒回來，和原本的整數最多差 1.5 × 10⁻⁵，四捨五入之後完全相同。所以沒有被攻擊改到的像素，存回去一定是原值。被改到的像素，原值是整數、改動在 ±8 以內，四捨五入之後也不會超過 8：L∞ 的限制在存檔後仍然成立（1.6 節實際檢查）。

讀這段程式時會注意到幾個命名上的殘留：量的是攻擊後的準確率，變數卻叫 train_acc、train_loss（從訓練迴圈複製過來的）；第 76 行的 adv_names = [] 從頭到尾沒有用到。.data 在 .detach() 之後也是多餘的。這些不影響結果。

1.5　程式印出的準確率，量的不是交出去的圖

關鍵在第 81 行：yp = model(x_adv) 量的是攻擊函式剛回傳的 x_adv——還沒有剪到合法範圍、也還沒有四捨五入的浮點數圖片。可是交出去的是第 86–88 行處理過的整數。兩者在兩個地方不同：

  • 超出 0–255 的像素被剪掉。攻擊函式只保證「離原圖不超過 ε」，從來沒有保證「是合法的像素」。原圖裡已經是 255 的像素再加 8，在浮點數圖片裡是 263，存檔時被剪回 255。這 200 張圖的 614,400 個像素值裡，有 5,920 個本來就是 255、2,633 個本來就是 0；FGSM 之後有 13,754 個超出範圍（其中 4,305 個被剪回原值，等於完全沒改；9,449 個只改了 1–7），I-FGSM 之後有 7,628 個。
  • 四捨五入。I-FGSM 每步走 0.8，累積起來常常是 1.6、2.4 這種非整數（1.6 節）。存檔時變成 2，比浮點數圖片多改或少改了一點。

結果：resnet110 的 FGSM，程式印出 0.595，把 fgsm/ 的 PNG 讀回來重新量是 0.590。差了一張圖。差距很小，但方向不一定：實驗 A 的 97 組單一代理攻擊裡（第 2–4 章），有 41 組的「印出」與「PNG」不同，最多差 0.02（4 張圖）；PNG 比較高的 25 組、比較低的 16 組。換句話說，剪掉與四捨五入有時幫了攻擊、有時害了攻擊，沒有固定方向。 所以本書所有的實驗都量存成 PNG 之後的準確率（docs/tools/hw10_exp.py 存檔後重新讀檔評估），程式印出的只當參考。

現在的做法：在攻擊迴圈裡就剪到合法範圍

比較嚴謹的實作會在每一步之後，除了剪回 ε 球，也剪回合法的像素範圍：在 0–1 空間裡是 x_adv.clamp(0, 1)；在正規化空間裡要對每個通道用不同的上下界（1.2 節量到的 −2.43 到 2.52 這類數字）。這樣攻擊產生的就是真的能存成圖片的東西，量到的準確率也就是交出去的準確率；還剩四捨五入一項，可以在最後一步之後再量一次。這也是把正規化搬進模型裡（1.3 節）的另一個好處：合法範圍永遠是 [0, 1]。

1.6　存檔後檢查：每個像素到底改了多少

交件前最該做的檢查是 L∞：讀回每一張 PNG，和原圖逐像素相減，看最大的絕對值是不是 ≤ 8。本書的工具 docs/tools/hw10_eval_dir.py 做了這件事（並用指定的模型量準確率）：

fgsm: 200 images, max |adv - benign| = 8                «1»

resnet110_cifar10 on ifgsm: acc = 0.00500, loss = 17.28956
  1. 1兩種攻擊的 L∞ 都剛好是 8，沒有超過。
  2. 2PNG 的準確率 0.590，比程式印出的 0.595 低一張圖（1.5 節）。loss 也不同：2.49183 對 2.48333。

更有意思的是「改了多少」的分布。把 614,400 個像素值的 |改過的值 − 原值| 數一數：

|差|012345678
FGSM4,3051,8451,6781,2551,1761,0341,0451,416600,646
I-FGSM89,0451,575154,965124,72298291,50065,06818,63667,907

FGSM 的分布很好懂：每個像素都往梯度的正負號方向走滿 8（梯度剛好等於 0 的像素一個都沒有），所以 97.8% 是 8；不是 8 的那些，全部是原值太靠近 0 或 255、被剪掉一部分（1–7）或全部（0）的像素。

I-FGSM 的分布則有一個奇怪的形狀：2、3、5、6 很多，1、4、7 很少。原因是步長。每一步走 ±0.8，20 步之後淨移動是 0.8 ×（往上的步數 − 往下的步數）。往上加往下等於 20，兩者的差一定是偶數，所以淨移動只可能是 0、±1.6、±3.2、±4.8、±6.4、±8.0——四捨五入後正好是 0、2、3、5、6、8。會出現 1、4、7，是因為碰到 ε 球的邊界被剪掉之後，奇偶就被打亂了（例如走到 8.8 被剪回 8，再往回走一步是 7.2，四捨五入成 7），或是被 0–255 剪掉。另一個值得注意的數字是 0 的那 89,045 個：上上下下走了 20 步，最後回到原點。I-FGSM 只把 11% 的像素值推到 ε 的邊界，FGSM 則把 98% 推到邊界。改得「比較少」，在白箱上卻強得多——第 2、4 章會解釋為什麼。

1.7　存檔：create_dir

先把整個 data/ 複製成 fgsm/（只是為了得到同樣的資料夾結構），再用攻擊後的圖逐張覆蓋。astype(np.uint8) 把浮點數轉成 0–255 的無號整數；前面已經剪過、四捨五入過，所以轉換不會截斷或繞回（如果沒剪，263 轉成 uint8 是溢位，常見的結果是繞回 7）。存成 PNG 是無損壓縮，讀回來的像素值和存進去的完全相同；如果存成 JPEG，壓縮本身就會改變像素，把精心算出來的雜訊抹掉一大半——第 7 章會看到，這正是 JPEG 能當防禦的原因。

第 95 行有一個陷阱：資料夾已經存在時，什麼都不清。如果上一次的輸出還在，而且這次的 adv_names 和上次不同（例如你改了資料、或只攻擊了一部分圖片），舊的檔案就會留在資料夾裡，打包時一起交出去。zip 也不會檢查兩個串列一樣長：adv_examples 比較短時，多出來的名字就保留原圖。範例程式每次都處理全部 200 張，所以不會出事；改寫的時候要記得先刪掉舊資料夾。

本章重點

  • 類別編號來自資料夾名稱的字母排序，剛好和 CIFAR-10 的官方順序相同；檔名是字串排序（dog2 是第 111 張）。
  • ToTensor 除以 255、Normalize 減平均除標準差；正規化後每個通道的合法範圍不同，大約是 −2.4 到 2.5–2.75。
  • 像素上的 ε = 8，在正規化空間裡是 8/255/std，三個通道約 0.155–0.158。只寫 8/255 會讓攻擊弱 5 倍。
  • gen_adv_examples 印出的準確率量的是沒剪、沒四捨五入的浮點數圖片；交出去的 PNG 要剪到 0–255、四捨五入。resnet110 的 FGSM：印出 0.595、PNG 0.590。本書一律量 PNG。
  • FGSM 把 98% 的像素值推到 ±8；I-FGSM 的步長 0.8 讓改動集中在 0、2、3、5、6、8，只有 11% 在邊界上。

自我測驗

1. 一個像素的原值是 252，FGSM 要它 +8。在正規化空間裡算出來的值換回像素是多少？存成 PNG 之後呢？它在 1.6 節的表裡被算在 |差| 等於多少的那一欄？

正規化空間裡是 260（換回像素的浮點數），超出 255；存檔時第 86 行剪到 1.0（即 255），所以 PNG 裡是 255，|差| = 3，算在「3」那一欄。代理模型在第 81 行看到的卻是 260，這就是印出的準確率與 PNG 不同的來源之一。

2. 如果 CIFAR-10 的類別名稱改成中文資料夾（飛機、汽車、鳥……），AdvDataset 會出什麼問題？怎麼修？

中文字串的排序（依 Unicode 碼位）和 CIFAR-10 的類別順序不同，類別編號會對錯，模型的「正確答案」全部錯位，原圖準確率會掉到接近亂猜，程式卻不會報錯。修法是明確寫出類別清單（例如 report.py 的 classes），用 classes.index(資料夾名稱) 當編號，不要依賴排序。

3. 某人把 epsilon = 8/255/std 改成 epsilon = 8/std。交到 JudgeBoi 會發生什麼事？

正規化空間裡的 8/std 換回像素是 8 × 255 = 2,040，遠超過 8。FGSM 會把幾乎每個像素推到 0 或 255（存檔時被剪掉），圖片變成一片雜訊，L∞ 遠大於 8，JudgeBoi 會退件。這是推算，本書沒有實際交件。

4. I-FGSM 的步長改成 1.0（每步走 1 個像素值）、步數 20，你預期 1.6 節的 |差| 分布會變成什麼樣子？

淨移動是 1 ×（往上 − 往下），差一定是偶數，所以沒有被剪到的像素只會落在 0、2、4、6、8；奇數（1、3、5、7）只會出現在碰過 ε 邊界或 0–255 邊界的像素上。這是推論，本書沒有實際跑步長 1.0 的組（第 4 章跑了 0.2、0.4、0.8、1.6、3.2、8）。

5. 為什麼「把 Normalize 搬進模型裡」能讓攻擊程式變簡單？

資料只做 ToTensor，攻擊在 0–1 的空間裡進行：ε 就是 8/255（三個通道相同）、合法範圍就是 [0, 1]，每一步 clamp(0, 1) 就能保證圖片合法，不必記得乘回 std、加回 mean，也不會出現 1.5 節那種「量的不是交出去的東西」。代價是模型多一個小小的前處理層。

延伸閱讀

  • Alex Krizhevsky，Learning Multiple Layers of Features from Tiny Images（2009）：CIFAR-10 的技術報告，第 3 章描述資料怎麼收集與標註。
  • torchvision 文件 Normalize 與 ToTensor：兩者的精確定義。
  • Harry Kim，torchattacks：常用的 PyTorch 對抗攻擊函式庫；它要求輸入在 [0, 1]，正規化放在模型裡（1.3、1.5 節的慣例）。

第 1 章　10 張圖與一個太有把握的模型

1.2　checkpoint.pth 裡裝了什麼

第 0 章 0.2 節的〈參數之外：BN 的 buffer〉說過，存檔裡的模型權重不只 14,162,827 個參數，還有 BN 的 buffer。現在直接打開檔案看。下面的指令從 repo 根目錄出發、先 cd HW09 再執行，本章之後的指令也都在 HW09/ 裡跑（checkpoint.pth 要先照 0.4 節放好）；python -c "…" 的用法和第 0 章相同，整段貼進終端機即可。字串裡的 \" 是因為整段 Python 包在 shell 的雙引號裡，裡面的雙引號要跳脫：

$ cd HW09
$ ../.venv/bin/python -c "
import torch
ck = torch.load(\"checkpoint.pth\")
print(type(ck).__name__, list(ck.keys()))
print(\"epoch\", ck[\"epoch\"])
sd = ck[\"model_state_dict\"]
print(len(sd), list(sd.keys())[:6])
opt = ck[\"optimizer_state_dict\"]
print(list(opt.keys()), len(opt[\"state\"]))
print({k: v for k, v in opt[\"param_groups\"][0].items() if k != \"params\"})
"

這段程式裡沒有 .cuda()，但還是需要 GPU：checkpoint 裡的張量當初是在 GPU 上存的，記錄的裝置是 cuda:0，torch.load 預設會把它們放回原來的裝置。實測用 CUDA_VISIBLE_DEVICES="" 假裝沒有 GPU 再跑，會停在 torch.load：

RuntimeError: Attempting to deserialize object on a CUDA device but torch.cuda.is_available() is False. If you are running on a CPU-only machine, please use torch.load with map_location=torch.device('cpu') to map your storages to the CPU.

錯誤訊息已經給了解法：改成 torch.load(\"checkpoint.pth\", map_location=\"cpu\")，強制把張量讀到 CPU，實測這樣就能在沒有 GPU 時載入。explain_cnn.py:289 沒有加 map_location，這也是 Part 1 離不開 GPU 的原因之一。有 GPU 時的實測輸出：

dict ['epoch', 'model_state_dict', 'optimizer_state_dict']  «1»
epoch 208  «2»
81 ['cnn.0.weight', 'cnn.0.bias', 'cnn.1.weight', 'cnn.1.bias', 'cnn.1.running_mean', 'cnn.1.running_var']  «3»
['state', 'param_groups'] 48  «4»
{'lr': 0.001, 'betas': (0.9, 0.999), 'eps': 1e-08, 'weight_decay': 0, 'amsgrad': False}  «5»
  1. 1torch.load 讀回來的是一個普通的 Python dict，三個 key：訓練到第幾個 epoch、模型的 state_dict、優化器的 state_dict。state_dict 是 PyTorch 存模型的標準格式：一個「名字 → 張量」的對照表。
  2. 2存檔時的 epoch 編號是 208。這個數字在本作業不會用到，下面會拿它和優化器的步數對照。
  3. 3model_state_dict 有 81 個 entry，這裡印出前 6 個名字。名字就是屬性路徑：cnn.0.weight 是 model.cnn[0].weight（第一個卷積層的權重）；cnn.1.* 是 model.cnn[1]，也就是第一個 BN，它除了 weight、bias 兩個參數，還有 running_mean、running_var 兩個 buffer。
  4. 4optimizer_state_dict 分成 state（每個參數各自的狀態）與 param_groups（超參數）。state 有 48 個 entry。
  5. 5超參數是 Adam 的典型設定：學習率 0.001、betas (0.9, 0.999)、eps 1e-8、沒有 weight decay、沒有開 AMSGrad。所以這個模型是用 Adam 優化器訓練的。

81 與 48 怎麼來

81 可以從第 0 章的逐層表數出來：5 個 stage 裡一共有 11 個卷積層，每個卷積層後面各接一個 BN，最後是 2 個 Linear。模型裡有參數或 buffer 的層只有這三種（num_batches_tracked 是 BN 記錄「看過幾個 batch」的計數器，第 0 章介紹 buffer 時提過）：

11 個 Conv2d × 2（weight、bias）= 22
11 個 BatchNorm2d × 5（weight、bias、running_mean、running_var、num_batches_tracked）= 55
2 個 Linear × 2（weight、bias）= 4
合計 22 + 55 + 4 = 81

ReLU、MaxPool、Dropout 沒有任何要存的東西，所以不出現在 state_dict 裡。load_state_dict 做的事，就是拿這 81 個名字去對模型自己的 81 個名字，一個一個把張量複製進去；名字和形狀全部對上，才會回報 <All keys matched successfully>。如果存檔少了某個名字，或多出模型沒有的名字，預設會直接報錯，而不是默默略過。

48 則是只數「參數」：Adam 只替要訓練的張量保存狀態，buffer 不用梯度訓練，所以沒有。11 × 2 + 11 × 2 + 2 × 2 = 48，正好等於模型的 48 個參數張量。每個 entry 裡有三樣東西：

  • step：這個參數被更新過幾次。
  • exp_avg：梯度的移動平均（Adam 的一階動量）。
  • exp_avg_sq：梯度平方的移動平均（Adam 的二階動量）。

（每個 entry 的內容上面的指令沒有印出，是本書另外逐一檢查的；下面「舊版 PyTorch 留下的痕跡」裡的 step 值與 key 也一樣。）後兩個的形狀和對應的參數完全一樣，例如第一個 entry 的 exp_avg 是 (128, 3, 3, 3)，和 cnn.0.weight 相同。也就是說，每一個參數，Adam 都另外存了兩份一樣大的張量。這就是檔案為什麼這麼大。

170 MB 的組成

逐個張量把 bytes 加起來（float32 每個數 4 bytes、int64 每個數 8 bytes）：

內容怎麼算bytes
模型參數14,162,827 × 4（float32）56,651,308
BN 的 running_mean／running_var5,120 × 4（float32）20,480
BN 的 num_batches_tracked11 × 8（int64）88
model_state_dict 小計56,671,876
Adam 的 exp_avg + exp_avg_sq2 × 56,651,308113,302,616
兩者合計169,974,492
檔案實際大小第 0 章 0.4 節170,002,879
差額存檔格式本身（pickle 結構、key 名稱等；pickle 是 Python 把物件存成檔案的內建格式）28,387

本書逐個張量檢查過，state_dict 裡的 dtype 只有 float32 和 int64 兩種。5,120 是 11 個 BN 的通道數總和 2,560 再乘 2（mean 與 var 各一份），和第 0 章算 buffer 數量時用的是同一組數字。

模型（forward 會用到） 梯度的累積（Adam 的動量）

為什麼訓練時要連優化器一起存？因為 Adam 每一步的更新量取決於過去梯度的累積。如果訓練中斷、只存了模型權重，重新開始時動量從 0 起算，訓練曲線會跳一下。把 optimizer_state_dict 一起存，就能從中斷處無縫接著訓練。這對 HW3 的訓練有用，對 HW09 這種只做推論的作業則完全是多餘的重量。

舊版 PyTorch 留下的痕跡

仔細看 optimizer_state_dict，還能看出這個檔案是用比較舊的 PyTorch 存的（存檔的確切版本無從得知）：

  • param_groups 只有 lr、betas、eps、weight_decay、amsgrad、params 六個 key；新版還會多出 maximize、foreach、capturable 等設定。
  • step 存成 Python 的 int 32395；新版存成張量。
  • state 的 key 是很大的整數，例如 140436588276144，而不是新版的 0 到 47。（從數值大小看，像是存檔當時參數物件在記憶體裡的位址；這是推測，沒有另外查證。）

這些差異都不影響本作業，因為腳本只讀 model_state_dict，從頭到尾沒碰優化器的部分。

step 的 32395 還能拿來推一件事：32395 = 155 × 209。以下是推論，沒有其他資料佐證：如果 epoch 從 0 開始數，存檔時的 epoch 208 就是第 209 個 epoch；每個 epoch 更新 155 次，209 個 epoch 正好 32,395 步。而 HW3 的訓練集有 9,866 張圖，若 batch size 是 64（這兩個數都是 HW3 的設定，不在本 repo 裡，無法在這裡核對），一個 epoch 正好是 ⌈9866 ÷ 64⌉ = 155 個 batch。數字對得上，但這只是吻合，不是證明。

現在的做法：推論用的權重只存 state_dict，載入時用 weights_only

這個 checkpoint 是「訓練中途存檔」的格式，適合接續訓練。如果只是要把模型交給別人做推論，現在的慣例是只存模型本身：torch.save(model.state_dict(), path)。照上表推算，這樣只剩 model_state_dict 的 56.7 MB 左右，大約是原本的三分之一（這是由上表推得，本書沒有另外存檔量過）。

另一個變化在載入端。torch.load 底層用的是 Python 的 pickle，pickle 檔在載入時可以執行任意程式碼，載入來路不明的檔案有安全風險。PyTorch 2.6 起，torch.load 的 weights_only 參數預設改成 True，只允許載入張量、dict、數字這類基本型別。explain_cnn.py:289 沒有指定這個參數，所以在本書的 torch 2.11 上用的就是 True；這個檔案裡只有 dict、tensor、int、float、tuple，照樣載得進來，也沒有任何警告。另一個常見的選擇是 Hugging Face 推出的 safetensors 格式，它只存張量，根本不含可執行的內容（第 0 章 0.3 節提到的 BERT 權重檔 model.safetensors 就是這種格式）。

為什麼不用普通的字串排序

上面第二行顯示，這 10 個檔名用 sorted 的字串排序，結果和 my_key 排出來的完全一樣。那 my_key 有什麼用？原因是字串排序是逐字元比較的，類別一旦有兩位數就會排錯。這個模型的資料集（HW3 用的 food-11）有 11 個類別，編號 0 到 10，類別 10（Vegetable/Fruit）就是兩位數；只是這 10 張圖裡剛好沒有它。用三個假的檔名試試（不需要真的有這些檔案，這裡只排序字串）：

$ ../.venv/bin/python -c "
names = ['1_2.jpg', '10_3.jpg', '2_1.jpg']
print(sorted(names))
key = lambda n: int(n.replace('.jpg','').split('_')[1]) + 1000000 * int(n.split('_')[0])
print(sorted(names, key=key), [key(n) for n in sorted(names, key=key)])
"

這裡的 key 和第 51 行的 my_key 算法相同，只是寫成一行的 lambda。實測輸出：

['10_3.jpg', '1_2.jpg', '2_1.jpg']  «1»
['1_2.jpg', '2_1.jpg', '10_3.jpg'] [1000002, 2000001, 10000003]  «2»
  1. 1字串排序把 10_3.jpg 排在最前面。比較 10_3 和 1_2：第一個字元都是 1；第二個字元一邊是 0、一邊是 _，而 '0' 的字元碼比 '_' 小，所以 10_3 先。類別 10 就被排到類別 1 前面了。
  2. 2my_key 把檔名換成一個整數：類別 × 1,000,000 + 編號。1_2 → 1,000,002、2_1 → 2,000,001、10_3 → 10,000,003，當數字比就是「先比類別、類別相同再比編號」。

這個技巧有個前提：編號必須小於 1,000,000，否則編號會「溢位」到類別那一段（例如類別 1、編號 1,000,000 會變成 2,000,000，和類別 2、編號 0 撞在一起）。HW3 的資料量遠小於這個數，所以沒問題。Python 裡更直接的寫法是讓 key 回傳一個 tuple，例如 (int(類別), int(編號))，tuple 會先比第一個元素、相同再比第二個，不必挑一個夠大的倍數。

1.4　讀圖：FoodDataset 與 getbatch

有了路徑和標籤，第 294 行建立 FoodDataset。這個類別繼承 PyTorch 的 Dataset；Dataset 是 PyTorch 表示「一組資料」的基本類別，子類別只要實作 __len__（有幾筆）和 __getitem__（取出第 i 筆），PyTorch 的其他工具就能用它。這一份另外加了一個 getbatch：

__init__ 不讀任何圖片，只記下路徑、標籤，並決定之後要用哪一套轉換（transform）。transforms.Compose([...]) 把幾個轉換串成一個，依序套用。兩套轉換：

  • trainTransform（第 15–20 行）：縮放後再隨機左右翻轉、隨機旋轉 ±15 度。這是 HW3 訓練時的資料增強（data augmentation）：每次讀到同一張圖都稍微不一樣，讓模型不要死記圖片。
  • evalTransform（第 21–24 行）：只縮放、轉張量，沒有任何隨機成分。

第 25 行依 mode 選一套。explain_cnn.py:294 傳的是 mode='eval'，整個 HW09 也只在這裡建過 FoodDataset，所以 trainTransform 在本作業從來沒用到，它是從 HW3 沿用過來的。這很重要：如果用了隨機翻轉、旋轉，每次執行拿到的圖都不一樣，解釋圖也就無法重現。

真正讀圖發生在 __getitem__（第 30–34 行）：用 PIL（Python 最常用的圖片處理套件，現在的套件名稱是 Pillow）的 Image.open 打開第 index 張圖，套上轉換，連同標籤一起回傳。getbatch（第 37–44 行）則是對每個 index 呼叫一次 __getitem__，最後用 torch.stack 把 10 個 (3, 128, 128) 的張量沿著新的第 0 維疊成 (10, 3, 128, 128)，用 torch.tensor 把 int list 變成張量。第 36 行的註解說明了它的用途：拿圖來視覺化。訓練時一般用 PyTorch 的 DataLoader 自動分批；這裡只有固定的 10 張，手動取一批就夠了。

Resize 與 ToTensor 做了什麼

第 0 章圖 0.1 的輸入方框寫著「縮放成 128×128、像素值 0–1」，就是這兩個轉換：

  • transforms.Resize(size=(128, 128))：把圖縮放到 128×128。注意 size 給的是 (高, 寬) 兩個數，這時 Resize 會把圖直接拉成這個尺寸，不保持長寬比。（如果只給一個數，例如 Resize(128)，才會保持長寬比，把短邊縮到 128。）
  • transforms.ToTensor()：PIL 圖片是 0–255 的整數（uint8），維度排成 高 × 寬 × 通道；ToTensor 把它轉成 0.0–1.0 的 float32，並把維度換成 通道 × 高 × 寬，也就是 PyTorch 要的 (C, H, W)。

10 張圖裡有 4 張不是正方形，Resize 對它們的水平、垂直縮放比例不同：

1.7　eval 與 train：forward 也會改到模型

上一節的指令有一行 model.eval()。第 0 章說過它的基本作用：BN 改用長期平均、Dropout 關掉。這裡補一個第 0 章沒提到的細節：在 train 模式下做 forward，會改寫模型本身。

原因在 BN。train 模式的 BN 用「這一批」的平均與變異數做正規化，同時把這一批的統計量混進長期平均（running_mean、running_var），讓長期平均跟著訓練資料更新。這個更新在 forward 裡就發生了，不需要 backward，也不需要優化器；包在 torch.no_grad() 裡照樣會更新，因為 no_grad 只管梯度、不管 buffer。實測把上一節的指令改成 model.train()，對同樣 10 張圖做 forward：

  • 預測（argmax）仍然 10 張全對；
  • 但 logit 和 eval 模式相比最多差了 18.9（Dropout 隨機丟掉了數值，BN 改用這 10 張圖的統計量）；
  • 而且 BN 的 running_mean、running_var 被這 10 張圖更新了。之後再切回 eval，用的已經是被改過的長期平均，輸出也跟著變了，回不到原本的結果。

換句話說，在 train 模式下 forward 一次，就把從 checkpoint.pth 載入的 buffer 弄髒了，要重新 load_state_dict 才能還原。這件事沒有附上可以照貼的指令，是本書另外量的。

回頭看 explain_cnn.py：nn.Module 剛建好時預設是 train 模式，而主程式在 explain_cnn.py:288–290 建模型、載入權重之後沒有呼叫 model.eval()。它沒出事，是因為主程式在載入之後沒有做任何 forward，而每一個解釋方法都在開頭自己呼叫 model.eval()：LIME 的 predict 裡（第 42 行）、Saliency map（第 80 行）、SmoothGrad（第 121 行）、Filter explanation（第 169 行）、Integrated Gradients（第 230 行）。這是寫解釋程式的基本規矩：先 model.eval()，再做任何 forward。如果你自己加了一段 forward（例如想印出預測），要記得放在 model.eval() 之後。

1.8　這個「太有把握」會跟著你走完 Part 1

回到目錄頁那句話：10 張全對而且幾乎都是 100% 確定，後面每一章都會用到這個事實。本節只預告它出現在哪裡，細節留給各章。

  • 第 3 章 Saliency map：梯度小到幾乎是 0。Saliency map 對 loss 取梯度，而 cross-entropy loss 對 logits 的梯度是「softmax 機率減掉 one-hot 標籤」。p(標籤) 已經是 1.0000、其他類別都是 0.0000，這個差幾乎每一項都是 0，傳回輸入的梯度也就極小。1.6 節的表裡 1 − p 從 0 到 10−3 不等，差了好幾個數量級，第 3 章會看到這個差距怎麼反映在熱圖上，以及最沒把握的圖 2 為什麼是例外。
  • 第 2 章 LIME：程式餵給 LIME 的是 logits。LIME 每次會把圖上大約一半的 superpixel 換成平均色，看模型的輸出怎麼變。如果看的是機率，有幾張圖（圖 1、2、3、5）就算遮掉一半，機率也幾乎都還在 0.99 以上，分不出哪一塊比較重要；logits 則仍會隨遮掉的部分上下變動（原圖的標籤 logit 7.8 到 23.0、領先幅度 7.3 到 37.9，還有很大的空間）。explain_cnn.py 的 predict（第 45–46 行）直接回傳 model(...) 的輸出，沒有做 softmax。這對 LIME 的結果有什麼影響，第 2 章拿圖 0 實際比較兩種版本。
  • 第 5 章 Integrated Gradients 也是對目標類別的 logit 取梯度，所以那一章會再用到本章的 logit 數字（以及 1.6 節「小數第 3 位會變」的提醒）。

  • 類別寫在檔名 <類別>_<編號>.jpg 裡。os.listdir 不保證順序，所以要排序；my_key 用「類別 × 1,000,000 + 編號」當數字比，避免字串排序在類別 10 時排錯。排序後的位置就是圖 0–9。
  • FoodDataset(mode='eval') 只做 Resize(128, 128) 與 ToTensor：不保持長寬比（圖 1、3、9 被橫向擠窄）、值域 0–1、形狀 (3, 128, 128)；getbatch 疊成 (10, 3, 128, 128)。
  • normalize 把整個陣列線性拉到 0–1；save_fig 存圖、關圖、印一行 saved …。
  • 模型對 10 張圖全對；p(標籤) 除了圖 2（0.9986）都是 1.0000，第 1、2 名的 logit 差 7.3 到 37.9。這會讓第 3 章的梯度極小，也讓第 2 章「餵 logits 還是機率」變得重要。
  • train 模式的 forward 會改寫 BN 的 buffer；解釋模型前一定要先 model.eval()。

自我測驗

1. 如果在 food/ 裡多放一張 10_10.jpg（Vegetable/Fruit），用 my_key 排序後它會是第幾張？如果把第 53 行改成普通的 imgnames.sort() 呢？

用 my_key：它的 key 是 10 × 1,000,000 + 10 = 10,000,010，比其他 10 張都大，排在最後，成為圖 10；圖 0–9 不受影響，labels 變成 [0, 1, 1, 2, 2, 3, 5, 6, 8, 9, 10]。用字串排序：10_10.jpg 和 1_1.jpg 比到第二個字元時，'0' 比 '_' 小，所以它會排在 0_0.jpg 之後、1_1.jpg 之前，變成圖 1，原本的圖 1–9 全部往後挪一號，題目的編號就全錯了。（實測：在 food/ 的複本裡多放一張 10_10.jpg，my_key 版把它排在第 10 個、labels 是 [0, 1, 1, 2, 2, 3, 5, 6, 8, 9, 10]；改成 imgnames.sort() 之後它排在第 1 個，labels 變成 [0, 10, 1, 1, 2, 2, 3, 5, 6, 8, 9]。）

2. 如果把 checkpoint 改存成只有 model.state_dict()，檔案大約多大？explain_cnn.py 要改哪一行才讀得進去？

大約 56.7 MB（model_state_dict 的 56,671,876 bytes，再加上一點存檔格式的開銷），約原本的三分之一（由 1.2 節的表推得）。第 290 行 checkpoint['model_state_dict'] 要改成直接用 checkpoint，因為讀回來的已經是 state_dict 本身，不再是外面包一層的 dict。

3. 圖 2 的 p(標籤) 是 0.9986，第 2 名 Dessert 是 0.0007。為什麼 1 − p 是 1.38e-03，而不是 0.0007？

1 − p(標籤) 是「其他 10 個類別的機率總和」，不只第 2 名。第 2 名分到約 0.0007（e−7.262 ≈ 0.0007），其餘 9 個類別合起來又分到差不多一樣多，加起來約 0.0014。

4. 你在自己的機器上把圖 0 單獨送進模型，得到標籤 logit 10.331，書上卻寫 10.333。哪裡出錯了？

沒有出錯。本章的 10.333 是 10 張一起算的結果；單獨一張算時，GPU 會用不同的卷積演算法，浮點數加總順序不同，小數第 3 位就會變（實測 10.3332 對 10.3312）。比較 logit 時要用同樣的批次組成。

5. 有人把 1.6 節指令裡的 model.eval() 刪掉，反正預測還是 10 張全對。這樣有什麼問題？

預測雖然仍然全對，但 logit 和 eval 模式最多差 18.9：Dropout 會隨機丟值，BN 改用這 10 張圖自己的統計量，所以每次跑的數字都不一樣。更麻煩的是，train 模式的 forward 會把這 10 張圖的統計量寫進 BN 的 running_mean／running_var，即使之後再切回 eval，結果也回不去了，要重新載入 checkpoint 才能還原。torch.no_grad() 擋不住這個更新。

第 2 章　訓練迴圈與指標

六種方法共用同一個 train() 和同一個 evaluate()，差別只在傳進去的 lifelong 物件。這一章逐行讀這兩個函式：一步之內 forward、懲罰項、update()、backward() 的順序；報告要你描述的那個指標到底在算什麼、會漏掉什麼；怎麼把它拆成逐任務的矩陣，算出 ACC 與 BWT。最後量一件不在任何說明裡的事：光是「評估」這個動作，就會改變之後的訓練。

2.1　train() 的骨架

train() 一次只負責一個任務。參數裡最重要的三個：

  • dataloader：這個任務的訓練資料（469 個 batch，第 1 章）。
  • lll_object 與 lll_lambda：lifelong learning 物件和它的權重 λ。lll_object 只需要提供兩個方法：penalty(model) 傳回懲罰項，update(model) 在每一步被呼叫一次。train() 完全不知道它是 EWC 還是 SI，這是六種方法能共用同一個迴圈的原因（第 3 章讀這個介面）。
  • test_dataloaders：要評估哪些任務。呼叫的地方傳的是 test_dataloaders[:train_indexes+1]，也就是「到目前為止學過的任務」，2.4 節的主角。

外層迴圈跑 epochs_per_task（10）個 epoch，內層迴圈跑完一個 epoch 的所有 batch；每個 epoch 結束評估一次，把一個數字加進 acc_per_epoch。函式傳回這 10 個數字。呼叫它的 run_baseline 用 extend 把五個任務的 10 個數接成 50 個，就是第 0 章印出的那一串。

兩個 tqdm.auto 進度條都設了 leave=False，跑完就從終端機上清掉，這是第 0 章的輸出只剩串列的原因。log_step=1 這個參數在函式裡從來沒有用到。

2.2　一步之內的順序

內層迴圈的每一步（第 17–26 行）做這些事：

  1. forward：outputs = model(imgs)，得到 (128, 10) 的 logits。
  2. 分類 loss：nn.CrossEntropyLoss，對一個 batch 取平均。
  3. 懲罰項：lll_object.penalty(model)，再乘上 λ 加進去。各方法的懲罰項都長成 Σ Ωᵢ (θᵢ − θ*ᵢ)²：每個參數離「上一個任務結束時的值」θ* 多遠，乘上它的重要度 Ω，全部加起來。
  4. update()：讓 lifelong 物件在每一步看一眼模型。baseline、EWC、MAS、SCP 的 update 什麼都不做，只有 SI 和 RWalk 用它累積資訊。
  5. 清梯度、backward、更新：optimizer.zero_grad()、total_loss.backward()、optimizer.step()。

有兩個細節值得停下來看。

第 20、22 行：total_loss 和 loss 是同一個張量

total_loss = loss 不會複製張量，只是讓 total_loss 這個名字也指向 loss 指向的那個物件。接著第 22 行的 += 對 PyTorch 張量是原地（in-place）運算，直接修改那個物件。所以執行完第 22 行，loss 和 total_loss 都是「分類 loss 加懲罰項」。這裡剛好沒有造成錯誤：backward() 用的就是加總後的值，第 28 行印出的也是加總後的值（進度條上的 Loss 包含了懲罰項）。但如果有人在第 22 行之後想印「純分類 loss」，拿 loss 就會拿錯。要分開記，得寫成 total_loss = loss + lll_lambda * lll_loss（產生新張量）。

baseline 的 λ 是 0.0，penalty 仍然每一步都會算：它走過八個參數張量、把 0 × (θ − θ*)² 加總，乘上 0.0 再加進去。結果是 0，只是白算。

第 23–24 行：update() 在清梯度之前

update() 被呼叫的時候，這一步的 backward() 還沒做，optimizer.zero_grad() 也還沒做。所以參數的 .grad 裡留著的是上一步的梯度，參數本身則是上一步 optimizer.step() 更新過的值。SI 正是要「上一步的梯度」乘上「上一步造成的參數變化」，這個順序是刻意的，第 6 章會逐行驗證。

每個任務重建一次 Adam

每個任務訓練完，迴圈做兩件事：建一個新的 lifelong 物件（第 46 行，把「這個任務結束時的權重」與「這個任務的資料」交給它，第 3 章起逐一讀），以及建一個新的 Adam（第 49 行）。Adam 會替每個參數記住梯度的移動平均（一階動量）和梯度平方的移動平均（二階動量），用來調整每個參數的步長。重建 optimizer 等於把這些記憶清空，新任務從「沒有動量」開始。這是持續學習程式的常見做法：上一個任務的動量指向上一個任務的方向，帶進新任務沒有意義。學習率維持 1e-4，沒有任何排程。

2.3　evaluate()：沒有 no_grad，也回不到 train 模式

它做的事很直接：對測試集的每個 batch 算 logits，torch.max(…, 1) 沿著類別那一維取最大值，傳回 (最大值, 索引)，索引就是預測的類別；猜對的個數除以總數。第 51 行用 torch.ones_like(labels).sum() 數這個 batch 有幾張，等於 labels.size(0)，只是繞了一圈。（這個函式用 4 格縮排，train 用 2 格，看得出是不同人寫的。）

有兩件事和一般的寫法不同：

  • 沒有 torch.no_grad()。評估時不需要梯度，但沒有包在 no_grad 裡，PyTorch 仍會為 forward 建立計算圖、保留中間結果。一個 batch 是 8,192 張，這會多佔一些 GPU 記憶體和時間，但不影響數字：outputs.data 取的是不帶計算圖的值，也沒有人對它呼叫 backward()，所以參數的 .grad 不會被動到。
  • model.eval() 之後沒有切回 model.train()。train() 只在開頭（第 9 行）呼叫一次 model.train()；第 1 個 epoch 結束評估之後，模型就一直停在 eval 模式，第 2–10 個 epoch 都是在 eval 模式下訓練的。eval 與 train 模式只影響 Dropout 與 BatchNorm 這類層，這個模型兩種都沒有（第 0 章），所以結果不受影響。但同樣的程式換成有 Dropout 或 BatchNorm 的模型，就會在不知不覺中關掉它們。

改模型時別忘了這兩行

作業規定不准改架構，所以這兩個問題在作業裡是無害的。但這是「看起來能跑、換個設定就悄悄出錯」的典型：要把這套迴圈用在別的模型上，評估要包 with torch.no_grad():，評估完要切回 model.train()（或在每個 epoch 開頭呼叫）。

2.4　作業的指標：已學任務的平均準確率

報告的第二部分（0.5 分）要你描述學習曲線用的指標。從 train() 第 30–35 行讀出來是這樣：

學完第 t 個任務的第 e 個 epoch 之後：
指標 = (1/t) · Σj=1..t accj　，accj = 模型在任務 j 測試集（10,000 張）上的準確率 × 100

也就是說，學習曲線上的每一個點，是「目前為止學過的每個任務」各自的測試準確率的算術平均，還沒學到的任務不算。學任務 1 時是 1 個任務的準確率，學任務 2 時是 2 個的平均，到任務 5 才是全部 5 個的平均。每個任務的權重相同（都是 10,000 張，所以和「把已學任務的測試集合起來算一個準確率」一樣）。

這個指標同時反映兩件事：舊任務還記得多少，和新任務學得多好。兩者混在一個數字裡，看不出是哪一個在變。本書的實驗工具在每個 epoch 結束時，另外對全部五個任務各算一次準確率（用事先轉好的測試張量，不經過 DataLoader，所以不會動到亂數，2.6 節）。這樣每種方法都有一個 50 × 5 的表。把 baseline 的這張表畫出來：

這張圖把一條曲線拆成了五條，有幾件事一眼就看得到：

  • 新任務學得很快。每換一個任務，那個任務的準確率在第一個 epoch 就跳到 97% 左右（任務 2–5 在第 11、21、31、41 個 epoch 分別是 97.11、97.31、97.18、97.35）。
  • 舊任務掉得也很快，而且不會停。任務 1 學完時 98.03，學任務 2 的第一個 epoch 就掉到 94.17，之後每換一個任務再往下掉一截，最後剩 35.43。
  • 還沒學的任務也在動。學任務 1 時，任務 2 跟著到了 90% 左右（第 1 章：轉 20° 的圖和原圖很像）；學任務 2 時，任務 3 從 55.66 升到 90.62。學一個任務會順便讓「角度相近」的任務變好，讓「角度遠」的任務變差。

回到第 0 章留下的問題：學習曲線在換任務時那一階的落差，有多少是遺忘？可以這樣拆：假設舊任務完全沒有忘、維持換任務前的準確率，再加上新任務實際的準確率，算出一個「沒有遺忘時的指標」。實際指標比它低多少，就是遺忘造成的；它比換任務前低多少，就是「新任務還不夠好」造成的：

報告怎麼寫

描述指標時，把三件事講清楚就夠了：(1) 每個 epoch 結束評估一次；(2) 只評估到目前為止學過的任務（第 t 個任務期間是任務 1..t），各自在完整的測試集上算準確率；(3) 取算術平均、乘以 100。可以再補一句它的限制：分母會隨任務變多，新任務的準確率和舊任務的遺忘混在同一個數字裡，看不出個別任務忘了多少。

2.5　逐任務矩陣、ACC 與 BWT

持續學習的論文通常不畫作業那條曲線，而是報一個 T × T 的準確率矩陣：第 i 列是「學完任務 i 之後」，第 j 行是「在任務 j 的測試集上」。baseline 的矩陣（取每個任務最後一個 epoch，即第 10、20、30、40、50 個）：

學完之後 ＼ 測在任務 1任務 2任務 3任務 4任務 5
任務 198.0390.5355.6625.6814.02
任務 293.0898.0890.6256.1325.39
任務 369.6694.5698.3291.2257.60
任務 448.8170.5893.1098.2990.58
任務 535.4351.6373.1394.4098.37

讀法：對角線（粗體）是「剛學完這個任務時」的準確率；對角線左下是學完之後的舊任務，從上往下看就是遺忘的過程；對角線右上是還沒學的任務。作業的指標只用到對角線和左下三角，而且還把每一列平均掉了。

從這張矩陣定義兩個常用的數字（Lopez-Paz 與 Ranzato 在 GEM 的論文裡提出，之後成為這個領域的標準報法）。設 R[i][j] 是上表第 i 列、第 j 行，共 T = 5 個任務：

ACC = (1/T) · Σj=1..T R[T][j]　　　　（最後一列的平均）
BWT = (1/(T−1)) · Σj=1..T−1 ( R[T][j] − R[j][j] )　（舊任務「最後」減「剛學完」的平均）
  • ACC（average accuracy）：學完全部任務之後，在每個任務上的平均準確率。baseline 是 (35.43 + 51.63 + 73.13 + 94.40 + 98.37) / 5 = 70.59。它和作業指標的最後一個點是同一個數，因為到了任務 5，「已學任務」就是全部任務。
  • BWT（backward transfer）：學後面的任務對前面的任務有什麼影響。負的代表遺忘，正的代表後來的學習反而幫了舊任務。baseline 是 [(35.43 − 98.03) + (51.63 − 98.08) + (73.13 − 98.32) + (94.40 − 98.29)] / 4 = −34.53：舊任務平均掉了 34.5 個百分點。

兩個數字要一起看。ACC 高可能是因為記得多，也可能是新任務學得特別好；BWT 接近 0 可能是因為記得住，也可能是因為什麼都沒學會（剛學完就不高，自然掉不多）。第 5 章的 MAS 就是後一種情況的例子：它的 BWT 是 −13.97，看起來遺忘少很多，但它的對角線從 97.9 一路降到 89.7，新任務學不好。所以本書每種方法都會同時報 ACC、BWT 和對角線。

另一個常見的量叫 forgetting（Chaudhry 等人在 RWalk 的論文提出）：每個舊任務「歷史上最好的準確率」減「最後的準確率」，再取平均。baseline 的每個舊任務都是剛學完時最好，所以它就是 −BWT，四個任務分別忘了 62.60、46.45、25.19、3.89，平均 34.53。越早學的任務忘得越多：任務 1 和任務 5 的角度差最大（第 1 章）。

每種方法的 ACC 與 BWT 已經整理在目錄頁的成績表；本書的實驗工具 docs/tools/hw14_exp.py 把整個 50 × 5 的表存在 hw14_runs.jsonl 的 matrix 欄位，第 3 章起的每一張圖都從這裡畫。

2.6　評估也會改變訓練

最後一件事不在任何說明裡。train.py 建測試資料的 DataLoader 時用了 shuffle=True（第 0 章 train.py 第 248 行）。測試資料打不打亂，對準確率沒有影響：加總起來都是那 10,000 張。但打亂需要亂數，而這些亂數和訓練資料的打亂、模型初始化，取自同一個全域亂數產生器。

每次從 DataLoader 拿一個新的迭代器時，PyTorch 會先從全域產生器抽一個數，當作這一輪資料讀取的基礎種子；如果 shuffle=True，抽樣器還會再抽一個數來決定排列。實測（在 CPU 上，用一個小資料集，比對抽了幾次數之後的產生器狀態）：

動作從全域亂數產生器抽了幾次
走過一次 shuffle=True 的 DataLoader2
走過一次 shuffle=False 的 DataLoader1
用 tqdm.auto.tqdm(...) 包住再走一次 shuffle=True 的 DataLoader（train() 第 16 行的寫法）3
tqdm.auto.trange(10)0

第三列多出來的一次，是因為在一般 Python 環境下 tqdm.auto.tqdm 實際上是 tqdm_asyncio，它在建立時就先對 DataLoader 呼叫一次 iter()，多建了一個沒用到的迭代器。（同樣的現象在 HW03 的教材裡也遇過。）

所以每個 epoch 的亂數用量是：訓練 3 次，加上評估「每個已學任務 2 次」。評估用掉的亂數會讓下一個 epoch 的訓練資料以不同的順序出現。為了量這個影響有多大，本書加跑了一組：baseline、種子 0，只把測試資料改成 shuffle=False（實驗工具的 --test_noshuffle），其他完全相同。注意這不會讓評估完全不用亂數，每個測試集仍抽 1 次，只是少抽 1 次：

設定任務 1 學完任務 2任務 3任務 4任務 5（ACC）BWT
測試資料 shuffle=True（原版）98.0395.5887.5177.7070.59−34.53
測試資料 shuffle=False97.7895.1288.0378.4770.86−34.15
參考：原版換種子 0–4ACC 67.56 – 70.73−38.32 – −34.22

兩組的第 1 個 epoch 完全相同（92.58），因為在第一次評估之前，兩者用掉的亂數一樣；從第 2 個 epoch 起就分岔了（94.63 對 94.86）。最後的 ACC 差 0.27。這個差距本身不重要，它和換一個種子造成的差異（67.56 到 70.73，差 3.17）是同一類東西：都是「資料順序不同」。重要的是它說明了兩件事：

  • 「只改評估」不是中性的修改。把評估的批次大小、打不打亂、評估的頻率改掉，訓練結果都會變。要比較兩個方法，它們的評估方式要一模一樣，或者讓評估完全不碰全域亂數。
  • 差距要和種子之間的差異比。baseline 光是換種子，ACC 就在 67.56–70.73 之間。兩個方法差 1 個百分點，在只跑一個種子的情況下說明不了什麼。第 3 章會用這五個種子定出 baseline 的範圍，第 8 章用同樣的方式比較所有方法。

現在的做法：評估不碰訓練的亂數

現在的寫法會把評估和訓練的亂數分開：評估包在 torch.no_grad() 或更嚴格的 torch.inference_mode() 裡；測試資料不打亂；需要亂數的 DataLoader 傳入自己的 torch.Generator（DataLoader(..., generator=g)），它的抽樣與基礎種子就改從 g 取，不再動到全域產生器。持續學習的研究則多半用現成的框架（例如 Avalanche）來管理任務序列與評估，ACC、BWT、forgetting 這些指標由框架統一計算，各篇論文的數字才能互相比較。

本章重點

  • train() 一次訓練一個任務 10 個 epoch；每一步：forward → CE loss → 加上 λ·penalty → update() → 清梯度、backward、step。update() 在清梯度前呼叫，看到的是上一步的梯度（SI 要的就是這個）。每個任務結束都重建 lifelong 物件和 Adam。
  • total_loss = loss 加上原地的 +=，讓 loss 也變成加總後的值；evaluate() 沒有 no_grad，且之後模型一直停在 eval 模式，這個模型沒有 Dropout／BatchNorm 所以結果不受影響。
  • 作業的指標：每個 epoch 結束，對已學過的任務各算測試準確率，取平均乘 100。分母隨任務增加，新任務與舊任務混在一起；新任務一個 epoch 就到 97% 左右，所以這個指標會低估遺忘（換到任務 4 時，曲線掉 4.96，遺忘 7.37）。
  • 逐任務矩陣 R[i][j]；ACC = 最後一列平均（baseline 70.59，等於作業指標最後一點），BWT = 舊任務「最後 − 剛學完」的平均（baseline −34.53）。兩者要和對角線一起看。
  • 評估會用掉全域亂數（打亂的 DataLoader 每走一次抽 2 次，不打亂也抽 1 次；tqdm.auto 包住訓練資料再多 1 次）。只把測試資料改成不打亂，baseline 的 ACC 從 70.59 變成 70.86；換種子的範圍是 67.56–70.73。

自我測驗

1. 學任務 3 的第 5 個 epoch 結束時，train() 會呼叫幾次 evaluate()？印出的那個數是怎麼算的？

3 次：test_dataloaders 是 test_dataloaders[:3]，任務 1、2、3 各一次。印出的是三個準確率的算術平均乘以 100。任務 4、5 的測試集不會被評估。

2. 進度條上顯示的 Loss 包含懲罰項嗎？

包含。第 20 行 total_loss = loss 讓兩個名字指向同一個張量，第 22 行的 += 是原地修改，所以第 28 行的 total_loss.item() 是分類 loss 加上 λ 乘懲罰項。對 baseline（λ = 0）兩者相同，對其他方法則不同。

3. 如果這個模型有一層 nn.Dropout(0.5)，train() 會出什麼問題？

第 1 個 epoch 結束評估時呼叫了 model.eval()，之後沒有任何地方切回 model.train()，所以第 2 個 epoch 起訓練時 Dropout 都是關掉的，等於只有第 1 個 epoch 有 Dropout。這題是依程式推論，本書沒有實際跑（作業的模型沒有 Dropout）。

4. 方法 A 的 ACC 是 72.0、BWT 是 −20；方法 B 的 ACC 是 72.0、BWT 是 −32。兩者的 ACC 一樣，差別在哪裡？

A 舊任務掉得比較少，但最後的平均一樣，代表 A 剛學完每個任務時的準確率（對角線）比較低：它記得住，但學不好新任務。B 學每個任務都學得很好，但忘得多。這就是穩定性（stability）與可塑性（plasticity）的取捨，第 5 章的 MAS 是偏向 A 的例子。

5. 本書的實驗工具在每個 epoch 結束時對五個任務都多評估一次。為什麼這樣做不會改變訓練結果？

因為它不經過 DataLoader：五個測試集在一開始就轉成張量放在 GPU 上（旋轉是確定性的，不用亂數），評估時直接把張量送進模型，包在 torch.no_grad() 裡，結束後恢復原本的 train／eval 狀態。不抽亂數、不動 .grad，所以第 0 章驗證過：加了這個額外評估，印出的 300 個數和原版逐位元相同。

第 6 章　SI：把訓練路徑上的貢獻累加起來

EWC 和 MAS 都在任務結束後，另外走一遍資料來算重要度。Synaptic Intelligence 不需要這一步：它在訓練的每一步記下「這個參數這一步動了多少，對 loss 下降貢獻了多少」，任務結束時把累加的結果整理成重要度。這是六種方法裡唯一真正用到 update() 的（RWalk 沿用它）。這一章讀 update() 為什麼要放在 backward() 之前、資料怎麼藏在模型的 buffer 裡傳給下一個物件，再實測它累加出來的東西：分母裡的 ε 完全蓋過了參數的變化量。

6.1　想法：loss 下降的功勞，分給每個參數

訓練一個任務時，參數沿著一條路徑從 θ(0) 走到 θ(T)，loss 從 L(0) 降到 L(T)。把 loss 的總變化寫成沿路徑的積分，再拆成每個參數各自的部分：

L(T) − L(0) = ∫ ∇L · dθ ≈ Σt Σi gi(t) · Δθi(t)
ωi = − Σt gi(t) · Δθi(t)　（參數 i 對 loss 下降的貢獻）

gi(t) 是第 t 步的梯度，Δθi(t) 是第 t 步參數的變化。梯度下降讓參數往梯度的反方向走，所以 −g · Δθ 通常是正的；一個參數一路上對 loss 下降貢獻越多，ωi 越大。任務結束時，SI 把 ωi 除以這個參數在整個任務中總共移動了多少（的平方），再加上一個小常數 ξ 避免除以 0：

Ωi += ωi / ( (θi(T) − θi(0))² + ξ )

直覺是：一個參數只移動了一點點，卻貢獻了很多 loss 下降，它就很重要，之後別動它。程式裡 ξ 叫做 epsilon，設為 0.1。

這個做法有兩個好處：不需要任務結束後再走一遍資料（ω 是訓練時順便算的），而且它用的是訓練當下的梯度，不必另外定義 Fisher 或輸出敏感度。投影片 p.22 的提示 Accumulated loss change in each update step 說的就是 ω。至於「需不需要 label」：SI 本身不另外用 label，但它累加的梯度來自訓練的 loss，訓練需要 label，所以間接用到了。

6.2　update()：每一步記下「梯度 × 變化」

第 88 行就是 ω 的累加：W[n] 加上 −p.grad × (p − p_old)。要讓這一行算對，p.grad 和 p − p_old 必須是同一步的梯度與變化。第 2 章 2.2 節讀過 train() 一步的順序：

第 t 步：forward → loss → penalty → update() → zero_grad → backward（算出 g(t)）→ step（θ 變成 θ(t)）
第 t+1 步：forward → loss → penalty → update() ← 這時 .grad 是 g(t)，p 是 θ(t)，p_old 是上一次 update 記下的 θ(t−1)

所以在第 t+1 步呼叫 update() 時，.grad 還留著第 t 步的梯度（zero_grad 在 update 之後才做），p − p_old 正是第 t 步 optimizer.step() 造成的變化。兩者配成一對，第 90 行再把目前的參數記成新的 p_old。update() 放在 zero_grad() 與 backward() 之前，不是隨手寫的，是這個配對成立的條件：如果放在 backward() 之後、step() 之前，.grad 會變成在 θ(t) 這個位置新算的梯度 g(t+1)，配上第 t 步的變化：梯度不再是「造成這一步變化的那一個」，而是走完這一步之後的位置的梯度。兩者都是一階近似，但原本的寫法讓 g 與 Δθ 來自同一個 batch，這一點 6.4 節會用到。

邊界情況：整個訓練的第一步，模型還沒做過 backward，p.grad 是 None，第 87 行跳過累加，只記下 p_old。之後每個任務的第一步，.grad 是上一個任務最後一步留下的梯度，但新物件的 p_old 就是目前的參數（_init_ 第 34 行），變化是 0，所以這一步貢獻 0。也就是說每個任務的最後一步不會被算進 W，一個任務 4,690 步中少算一步，影響可以忽略。

還有兩個細節：p.grad 是 total_loss 的梯度，包含懲罰項（第 2 章 2.2 節），所以 W 累加的是「分類 loss 加懲罰項」的下降，不只是分類 loss；Δθ 是 Adam 走的那一步，不是 −學習率 × 梯度，但 ω 的定義只需要「實際走了多少」，和用哪種 optimizer 無關。

為什麼要 register_buffer

第 89 行每一步都把 W[n] 用 register_buffer 存進模型。原因在 run_si 的結構：每個任務結束時建立一個新的 si 物件（下面的第 155 行），而 W 是存在舊物件的 self.W 裡的。舊物件沒有被傳給新物件，新物件要拿到 W，只能透過兩者共有的東西：模型。所以程式把 W、上一個任務結束時的參數、累積的重要度，都當成 buffer 掛在模型上，參數名稱裡的 . 換成 __（buffer 的名稱不能有 .），例如 fc1__weight_W。

這個做法能跑，但有副作用。實測：建立第一個 si 物件後模型多了 8 個 buffer，做過一次 update 後是 16 個，第二個物件建立後是 24 個（8 個參數 × 3 種：_W、_SI_prev_task、_SI_omega）。buffer 會進到 state_dict()，模型的 state_dict 從 8 項變成 32 項；把它存檔之後，想載入一個全新的 Model() 會出現 RuntimeError: Error(s) in loading state_dict for Model（多出來的 key）。另外每一步都對 8 個參數各呼叫一次 register_buffer，是不必要的開銷：self.W[n] 是原地累加的，第一次登記之後，buffer 指向的就是同一個張量。比較乾淨的寫法是讓新物件直接接收舊物件（或它的 W），不經過模型。

這個類別的 docstring 引用的是 EWC 的論文（Kirkpatrick 等，2017），不是 SI 的論文（Zenke、Poole、Ganguli，2017），應該是複製 EWC 類別時沒有改。

6.3　任務結束：把 W 變成重要度

兩個分支：

  • dataloader 是 None（第 63–69 行，訓練開始前的第一個物件）：重要度全 0，並把目前的參數登記成 _SI_prev_task，當成任務 1 的起點 θ(0)。
  • 否則（第 41–61 行，任務結束時）：從 buffer 讀出這個任務的起點 p_prev 和累加的 W，算出參數在整個任務中的變化 p_change，omega_add = W / (p_change² + ε)，加到之前累積的 _SI_omega 上（第一次沒有這個 buffer，getattr 丟出 AttributeError，就從 0 開始）。最後把目前的參數登記成下一個任務的起點，把新的重要度存回 buffer。

這裡 dataloader 只是一個旗標：程式只檢查它是不是 None，從來沒有走過它的資料。這是 SI 不需要額外一輪資料的具體證據。寫法 != None 在 Python 裡能用，慣例是寫 is not None（!= 會呼叫物件的比較方法，對 DataLoader 沒差，但對張量之類的物件會出問題）。

和 EWC、MAS 不同，SI 的重要度沒有重複累加：每個任務只把自己的 omega_add 加到前一份累積值上一次（第 55 行），不是把整個歷史清單再加一遍。所以第 4 章 4.4 節的 bug 在 SI 不存在（實驗工具的 --guards 選項也只對 EWC、MAS、RWalk、SCP 有作用）。

懲罰項（第 72–81 行）和其他方法相同：Σ Ω (θ − θ_prev)²，θ_prev 是上一個任務結束時的參數。

6.4　實測：ε 蓋過了參數的變化

SI 的公式看起來很合理，但分母 (Δ² + ε) 裡兩項的大小要實際看了才知道。本書用 docs/tools/hw14_si_inspect.py 照原樣跑一次 SI（種子 0，印出的 50 個數和 A 組 SI 種子 0 逐位元相同），在每個任務結束、新物件建立之前，讀出模型 buffer 裡的 W 與參數變化 Δ：

三件事：

  • ε 完全主導分母。每個參數在一整個任務裡移動的距離都很小（中位數 0.002–0.008，最大 0.134），Δ² 全部小於 ε = 0.1，95% 以上甚至小於 ε 的百分之一。所以 W / (Δ² + ε) 幾乎就是 W / 0.1 = 10 W：Ω 增量的總和 270.2 正好約是 W 總和 27.09 的 10 倍。SI「除以參數移動距離」的那一半公式在這份作業裡沒有作用，重要度就是「累加的 −g·Δθ」乘 10。反過來，如果把 ε 拿掉，任務 1 結束時的 Ω 增量總和會變成 1.4 × 1011（有些參數幾乎沒動），ε 的大小決定了 SI 的行為。學習率 1e-4 的 Adam 讓參數移動得很少，這是 Δ² 這麼小的原因；ε 的合適大小和參數的尺度、學習率都有關，作業沿用了 0.1 這個值。
  • W 沒有任何負值，146 萬個參數裡 5–12% 是 0。單一步的 −g·Δθ 可能是負的（Adam 的一步是梯度的移動平均，方向不一定和這一步的梯度相同），但累加 4,690 步之後全都是非負的。等於 0 的參數主要是 fc1 裡連到「永遠是黑色的邊角像素」的權重：輸入是 0，梯度就是 0。
  • W 的總和遠大於 loss 實際的下降。任務 1 結束時 W 總和是 27.09；但一個從隨機初始化開始的十類分類器，訓練 loss 從約 ln 10 ≈ 2.30 降到接近 0，總共最多降 2.3 左右。如果 W 是 loss 下降的精確分解，總和應該接近 2.3。多出來的十倍來自小批次梯度的雜訊：每一步的 g 是這個 batch 的梯度，Δθ 也是用這個 batch 的梯度算出來的，兩者的雜訊同方向，乘起來總是正的，一路累加上去。後來的研究也指出，SI 的重要度在實務上很大一部分反映的是梯度雜訊的大小，而不是真正的 loss 貢獻。

λ = 1 時五個種子的 ACC 是 74.50、73.97、74.06、75.30、74.05，平均 74.38 ± 0.56；BWT −29.52 ± 0.68。比 baseline（69.47 ± 1.40）好約 5 個百分點，比 EWC 的作業設定（71.61 ± 0.45）好約 3 個百分點。注意第 0 章參照執行裡 SI 是 71.98：參照執行六種方法共用一條亂數流，SI 排在第四個跑，拿到的初始權重與資料順序都和 A 組不同，換一條亂數流就差了 2.5 個百分點。

成本方面，SI 把 EWC「任務結束後多跑一個 epoch」的成本，換成「每一步多做一次逐元素運算」：每一步對 8 個參數張量各算一次乘法、一次累加、一次 clone()，一個任務 4,690 步。它還要多存兩份和模型一樣大的東西（W 與 p_old），加上 buffer 裡的起點參數與累積的 Ω，比 EWC 的「一份重要度加一份舊權重」多。在這個小模型上兩者都感覺不到；換成大模型時，每一步都要碰一次全部參數的做法，成本會和訓練本身同一個量級。

現在的做法：從訓練軌跡估重要度

SI「訓練時順便記錄，不另外走資料」的想法很省，但 6.4 節看到的兩個問題（ε 的尺度要配合學習率與參數大小、累加量被梯度雜訊主導）讓它在實務上比 EWC、MAS 更難調。現在直接使用 SI 的場合不多；它的概念在別處延續，例如用訓練過程中參數的移動量或梯度統計（Adam 的二階動量本身就是梯度平方的移動平均）來判斷哪些參數「對這個任務很敏感」，在模型合併（model merging）時決定各個微調結果裡哪些參數要保留。另外，像本章這樣把狀態寄存在模型的 buffer 裡、讓存檔多出一堆 key 的做法，現在多半改成把方法的狀態放在獨立的物件（或 optimizer 的 state）裡，存檔時分開存。

本章重點

  • SI 的重要度：訓練時每一步累加 −g·Δθ 得到 W（參數對 loss 下降的貢獻），任務結束時 Ω += W / (Δ² + ε)，Δ 是參數在整個任務中的變化，ε = 0.1。不需要額外走一遍資料。
  • update() 在 zero_grad、backward 之前被呼叫，.grad 是上一步的梯度、p − p_old 是上一步造成的變化，兩者正好配對；放到 backward 之後就會錯開一步。
  • W、起點參數、累積的 Ω 都用 register_buffer 寄存在模型上，給下一個 si 物件讀；副作用是 state_dict 從 8 項變成 32 項，無法直接載入新的 Model。dataloader 只當旗標用。docstring 引錯論文。SI 沒有重複累加的問題。
  • 實測：Δ² 全部小於 ε（95% 以上小於 ε/100），所以 Ω ≈ 10 W；W 全部非負，總和 27 遠大於 loss 實際的下降（約 2.3），多出來的是小批次梯度的雜訊。
  • λ 掃描：0.1 → 71.68、1 → 74.50、10 → 78.20、100 → 82.61；作業設定下五個種子 74.38 ± 0.56。

自我測驗

1. 如果把 train() 裡的 lll_object.update(model) 移到 optimizer.step() 之後，SI 的 W 會累加什麼？

update() 在 step() 之後被呼叫時，.grad 是這一步剛算出的梯度 g(t)，p − p_old 是這一步 step() 造成的變化，兩者其實也配成一對（同一步的梯度與它造成的變化）。差別在於原本的寫法是在下一步開頭才算；移到 step() 之後，每個任務的最後一步也會被算進去，第一步則一樣。如果放在 backward() 之後、step() 之前，則是新梯度配上一步的變化（6.2 節）。這題是依程式推論，本書沒有實際跑。

2. SI 的 __init__ 收到 dataloader=train_dataloaders[train_indexes]，它會走過這些資料嗎？

不會。_calculate_importance() 只檢查 self.dataloader != None 來決定走哪個分支，從來沒有 iterate 它。SI 的重要度完全來自訓練時 update() 累加的 W。

3. 把 epsilon 從 0.1 改成 0.001，SI 的重要度大約會變成幾倍？

依 6.4 節的實測，Δ² 有 95% 以上小於 0.001（ε/100），所以這些參數的分母從約 0.1 變成約 0.001 加上 Δ²，重要度大約放大到 50–100 倍，移動距離較大的少數參數放大得少一些。效果類似把 λ 放大很多倍。本書沒有實際跑 ε = 0.001。

4. 為什麼 SI 不會有 EWC、MAS 那種「舊任務的重要度被重複累加」的問題？

SI 每個任務只把新算出的 omega_add 加到前一份累積值（存在 _SI_omega buffer）上一次。EWC、MAS 則把每個舊物件的「已經包含所有歷史」的重要度存進 prev_guards 清單，新物件再把整份清單加總，歷史就被重複加了。

5. 用 torch.save(model.state_dict(), 'si.pth') 存下跑完 SI 的模型，再用 Model().load_state_dict(torch.load('si.pth')) 載入，會發生什麼？怎麼解決？

會出現 RuntimeError：state_dict 裡多了 24 個 fc1__weight_W、fc1__weight_SI_prev_task、fc1__weight_SI_omega 之類的 buffer，新的 Model 沒有這些 key（本章實測 load 失敗）。可以用 load_state_dict(..., strict=False) 忽略多出來的 key，或存檔前只挑出參數（例如用 {n: p for n, p in model.named_parameters()}）。

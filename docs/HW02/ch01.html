  1. 1這一句有 500 格，每格 39 個 float32。2007-149877-0023 是 train_split.txt 的第一行，後面幾章會一直拿它當例子。
  2. 2第 0 格的前 6 個數字。這些數字本身沒有直觀的意思，重要的是下面兩行。
  3. 3沿著時間軸（500 格）取平均，前 4 維都是 10⁻⁷ 量級，也就是 0（float32 的誤差）。
  4. 4沿著時間軸取標準差，都是 1。

第 3、4 行說明這份資料已經做過正規化：每一維在這一句裡平均 0、標準差 1。投影片第 11 頁寫的「39-dim MFCC w/ CMVN」就是這件事，CMVN（Cepstral Mean and Variance Normalization）是語音處理裡常用的正規化：把每一維減掉平均、除以標準差。本書把 4,286 句全部檢查過：每一句、每一維的平均絕對值都不超過 4.6 × 10⁻⁷，標準差都落在 0.99999994 到 1.00000012 之間。也就是說，CMVN 是每一句各自做的，用的是這一句自己的平均與標準差。所以程式裡完全沒有再做正規化，也不需要。

39 這個數字在 MFCC 的慣例裡通常是「13 個係數，加上它們隨時間的一階差分與二階差分」，但投影片只寫了 39 維，沒有說明組成，本書不往下推。對讀程式來說，只要知道「每一格是 39 個已經正規化過的數字」就夠了。

第 0 類是什麼？資料沒有標明。但有一個很強的線索：4,286 句裡有 4,281 句的第一格是第 0 類、4,244 句的最後一格是第 0 類，而且像 2007-149877-0023 這樣，開頭一整段都是它。一句話的頭尾通常是還沒開口或已經講完的空白，所以第 0 類很可能是靜音（silence）。這是推測，本書之後提到它時都會寫「第 0 類」，不直接叫它靜音。

1.5　一個音素持續幾格

投影片第 8 頁的論點是：每格只有 25 ms，一格不足以代表一個完整的音素，一個音素通常橫跨好幾格，所以要把相鄰的格子拼起來。資料可以直接驗證這句話。把每句標籤裡「連續相同的數字」當成一段（segment），例如上面的 6 個 29 是一段、10 個 39 是一段：

段數平均長度中位數前 90% 的段最多最長短於 11 格的段
276,0109.58 格7 格16 格305 格73.12%

一段的中位數是 7 格。最長的 305 格是第 0 類（4014-186175-0000 裡的一段）；前五長的段全是第 0 類。不過不是只有第 0 類會很長：第 1 類也有一段長達 270 格（8098-278278-0003），資料沒有說明它是什麼，本書不猜。最後一欄最值得注意：將近四分之三的段短於 11 格。本 repo 每次看 11 格（前後各 5 格），所以這個視窗裡常常不只一個音素。用 2007-149877-0023 的第 50 格（0 起算）當例子：

這張圖說明了兩件事。第一，拼接是有用的：中心格自己的 39 個數字可能模糊不清，但它前面連著 5 格 29，模型有更多證據判斷「這裡是 29」。第二，邊界附近最難：第 50 格和第 51 格的視窗幾乎一樣（11 格裡有 10 格重疊），答案卻不同，模型得從那一兩格的差別判斷邊界在哪裡。

最後提醒一個容易算錯的地方：投影片說每格 25 ms，但不能把中位數 7 格直接換算成 7 × 25 = 175 ms。語音特徵通常每隔一小段時間（frame shift）取一格，格與格之間會重疊，所以每格的長度不等於格與格的間隔；投影片沒有給 frame shift，這份資料無法換算成真實時間。

1.6　以「句」為單位切 train/val

preprocess_data 讀完標籤之後，決定這次要讀哪些句子：

訓練集和驗證集都從 train_split.txt 的 4,286 句裡切出來，做法是：

  1. 第 57 行用固定的種子 train_val_seed（預設 1337）設定 Python 內建 random 模組的亂數；
  2. 第 58 行把 4,286 句的順序打亂；
  3. 第 59 行算切點：int(4286 × train_ratio)；
  4. 第 60 行：要 'train' 就取切點之前，要 'val' 就取切點之後。

train.py 呼叫兩次 preprocess_data（一次 'train'、一次 'val'），每次都從頭讀檔、用同一個種子打亂，所以兩次得到的順序完全相同，切出來的兩份不會重疊，合起來剛好是全部 4,286 句。這是靠「每次都重設種子」才成立的；如果拿掉第 57 行，兩次打亂的順序不同，訓練集和驗證集就會互相混到。

還有一個要注意的參數：函式宣告的預設值是 train_ratio=0.8（第 42 行），但 train.py 呼叫時明確傳了 config.py 的 train_ratio = 0.9，所以實際用的是 0.9。原版範例程式的 config 是 0.8，本 repo 改成 0.9，多拿一成的句子去訓練。照抄這幾行，就能在程式外重現同一個切分。存成 c1c.py：

import random
usage_list = open('libriphone/train_split.txt').readlines()
random.seed(1337)
random.shuffle(usage_list)
percent = int(len(usage_list) * 0.9)
train = [u.strip('\n') for u in usage_list[:percent]]
val = [u.strip('\n') for u in usage_list[percent:]]
print(len(usage_list), percent, len(train), len(val))
print(val[:3])
spk = lambda ids: {u.split('-')[0] for u in ids}
print(len(spk(train)), len(spk(val)), len(spk(val) - spk(train)))

['5049-25947-0112', '1898-145724-0020', '6019-3185-0096']  «2»
250 184 0  «3»

  2. 2驗證集的前三句。之後要找「驗證集裡的某一句」都可以從這裡挑。
  3. 3用 id 的第一段（說話者）數人數：訓練集 250 位說話者、驗證集 184 位，而驗證集裡「訓練集沒出現過的說話者」是 0 位。

第 3 行是這個切分的重要性質：驗證集的每一位說話者，在訓練集裡都出現過，只是說的句子不同。測試集也一樣：本書核對過，測試集的 231 位說話者全部出現在 train_split.txt 裡。所以驗證集量的是「熟悉的聲音、沒聽過的句子」，和測試集同一種情況，用它來估計測試集的表現是合理的。（換一個問題：如果要量「模型對完全沒聽過的人表現如何」，就得按說話者切，這份作業不需要。）

為什麼不能把 264 萬格直接打亂再切

直覺上，把所有格子打亂、取一成當驗證集也可以。但第 2 章會看到，本 repo 每一格都帶著前後各 5 格：第 t 格和第 t+1 格的 11 格裡有 10 格是同一批資料。如果按「格」隨機切，驗證集的每一格，它隔壁的格子幾乎都在訓練集裡，模型等於看過了九成以上的答案，驗證準確率會虛高。以句為單位切，一句的所有格子一起進訓練集或一起進驗證集，就沒有這個問題。這是處理序列資料時最基本、也最容易被忽略的一條規則。

第 66 行把每一行結尾的 \n 去掉，第 67 行印出 ch00 看過的那一行 [Dataset] - …。測試模式走第 61–62 行，直接讀 test_split.txt，不打亂也不切；順序不能動，因為 prediction.csv 的 Id 就是照這個順序編的（第 6 章）。函式接下來的部分（第 69 行以後）把這些句子的 .pt 讀進來、拼接、疊成一個大 tensor，那是第 2 章的主題。

第 57 行還有一個副作用值得知道：random.seed(1337) 設的是 Python 內建 random 模組的全域亂數狀態，呼叫一次 preprocess_data 就會被重設一次。本 repo 的其他地方都用 PyTorch 的亂數（打亂 batch、初始化權重、dropout），沒有用到 Python 的 random，所以這裡不會影響訓練；但在自己的程式裡借用這個函式時，要記得它會改掉 random 的狀態。

1.7　投影片和資料對不上的一個數字

投影片第 10 頁寫：「Training: 4268 preprocessed audio features with labels (total 2644158 frames)」。總格數 2,644,158 和資料完全一致，句數卻寫 4,268；實際上 train_split.txt、train_labels.txt 和 feat/train/ 三者都是 4,286。兩個數字只是中間兩位對調，應該是筆誤。測試集的「1078 … total 646268 frames」則完全一致。

這種小地方本身不影響作業，但它是一個好習慣的練習：投影片、README、註解裡的數字，都要拿資料或程式實際核對一次。第 4 章會看到更嚴重的例子：config.py 說模型有 1 層，實際上有 10 層。

本章重點

  • libriphone/：三個文字檔加 feat/train/（4,286 個 .pt）、feat/test/（1,078 個）。檔名是「說話者-章節-句號」。wc -l 會少算 split 檔的最後一行。
  • 一個 .pt 是 (T, 39) 的 float32 tensor；每一句各自做過 CMVN（每一維平均 0、標準差 1），程式不必再正規化。T 從 139 到 998，總共 2,644,158 格；測試集 646,268 格。
  • train_labels.txt 一行一句、一格一個 0–40 的整數，被讀成 label_dict；標籤數與格數逐句相等。
  • 41 類很不平均：第 0 類佔 17.42%（很可能是靜音，資料沒標明），最少的第 20 類只有 0.05%。驗證集上「全部猜 0」的準確率是 0.177261。
  • 一段音素中位數 7 格，73.12% 的段短於 11 格，所以 11 格的視窗常跨過音素邊界。
  • train/val 以句為單位切：種子 1337 打亂，int(4286 × 0.9) = 3,857 句訓練（2,379,588 格）、429 句驗證（264,570 格）。驗證與測試集的說話者全部出現在訓練資料裡。
  • 投影片的「4268」句是筆誤，實際是 4,286 句。

自我測驗

1. wc -l libriphone/train_split.txt 印出 4285，但程式說有 4,286 句。哪個對？為什麼會差一？

4,286 對。wc -l 數的是換行字元，而這個檔的最後一行 1624-168623-0053 後面沒有換行字元，所以少算一行。readlines() 不需要換行字元就能讀到最後一行，程式拿到的是完整的 4,286 句，也和 feat/train/ 的 4,286 個檔對得上。

2. 如果 train.py 呼叫 preprocess_data 時沒有傳 train_ratio，訓練集和驗證集各有幾句？

會用函式預設的 0.8：int(4286 × 0.8) = 3,428 句訓練、858 句驗證。本書實測，這樣切出的驗證集有 527,790 格（訓練集 2,116,368 格），是本 repo 驗證集的兩倍左右。這正是原版範例程式的切法，第 7 章跑範例程式時用的就是它。

3. 一個永遠只猜第 0 類的「模型」，在本 repo 的驗證集上準確率是多少？為什麼這個數字值得記住？

0.177261（驗證集 264,570 格裡有 46,898 格是第 0 類）。它是多數類別基準：任何有在學東西的模型都應該明顯超過它。如果訓練出來的模型準確率卡在 0.177 附近，很可能是它只學會了猜最多的那一類。

4. 為什麼不把 2,644,158 格全部打亂，隨機取一成當驗證集？

本 repo 每一格都帶著前後各 5 格，相鄰兩格的 11 格裡有 10 格相同。按格隨機切，驗證集的每一格幾乎都有鄰居在訓練集裡，模型等於看過大部分內容，驗證準確率會虛高。以句為單位切，同一句的格子全部在同一邊，就不會互相洩漏。

5. 一段音素的中位數是 7 格，每格 25 ms，所以一個音素大約持續 175 ms，對嗎？

不能這樣算。25 ms 是一格涵蓋的長度，但特徵是每隔一段時間（frame shift）取一格，格與格通常互相重疊，所以格數乘以 25 ms 不等於持續時間。投影片沒有給 frame shift，這份資料無法換算成真實時間；能說的只有「中位數 7 格、73.12% 的段短於 11 格」。

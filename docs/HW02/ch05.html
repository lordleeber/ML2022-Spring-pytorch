第 5 章　訓練迴圈：11 格一起算 loss，只看中間那格

train.py 的後半段是一個標準的 PyTorch 訓練迴圈，但有一個不標準的地方：模型對 11 格都有輸出，loss 用全部 11 格算，準確率卻只看中間那格。本章逐行讀完訓練與驗證兩段，確認印出來的驗證準確率是不是真的，並把第 0 章那 20 行輸出畫成曲線來讀。

5.1　same_seeds：為什麼重跑會得到一模一樣的結果

第 0 章看到，重跑一次 train.py，得到的 model.ckpt 和原本的逐位元組相同。這要歸功於 train.py:35 呼叫的 same_seeds：

  • 第 108–111 行：固定 PyTorch 在 CPU 與 GPU 上的亂數。訓練中用到亂數的地方有三個：模型權重的初始值（第 38 行建模型時）、訓練集每個 epoch 的打亂順序（第 3 章）、LSTM 層間的 dropout。三者都用 PyTorch 的亂數，所以這幾行全管到了。
  • 第 112 行：固定 NumPy 的亂數。本 repo 的訓練沒有用到 NumPy 的亂數，這行留著無妨。
  • 第 113–114 行：cuDNN 是 NVIDIA 的深度學習函式庫，PyTorch 在 GPU 上跑 LSTM 時就是交給它。benchmark = False 表示不要每次都試跑幾種演算法挑最快的（挑出來的結果可能每次不同）；deterministic = True 表示只用「同樣輸入一定得到同樣輸出」的演算法。有些 GPU 演算法為了快，加總的順序不固定，結果會在最後幾位小數上飄動，這兩行把它關掉。

呼叫的位置也有講究。same_seeds 在第 35 行，晚於第 31–32 行建 DataLoader，但早於第 38 行建模型。第 3 章說過，打亂順序是在開始迭代時才決定，所以它仍然管得到；權重初始化則一定要在它之後，才會每次相同。另外，切 train/val 用的是 Python 的 random 與另一個種子 1337（第 1 章），和這裡無關。

5.2　loss 與 optimizer

第 0 章讀過 train.py:38–41：建模型、印出來，然後是這兩行：

    criterion = nn.CrossEntropyLoss()
    optimizer = torch.optim.AdamW(model.parameters(), lr=learning_rate)
  • nn.CrossEntropyLoss()：分類問題的標準 loss。輸入是每一筆的 41 個 logits（還沒 softmax）和正確類別的編號；它內部先做 softmax，再取正確類別那一項機率的負對數，最後對所有筆數取平均（預設 reduction='mean'）。模型對正確類別越有把握，loss 越接近 0。
  • torch.optim.AdamW：Adam 加上「和梯度分開處理」的 weight decay。lr=learning_rate 是 config.py 的 0.0001；其餘用預設值，本書實測 betas=(0.9, 0.999)、eps=1e-08、weight_decay=0.01。

train.py 自己沒有 import torch.nn as nn，卻能用 nn 和 torch：開頭的 from model import *、from utils import * 會把那兩個模組裡的名字（包括它們 import 的 nn、torch）全部帶進來。這種星號 import 讓人很難看出一個名字從哪裡來，現在一般不建議這樣寫。

5.3　訓練一個 batch

第 46–49 行把四個累加器歸零，第 52 行 model.train() 打開訓練模式（dropout 生效）。第 53–58 行是第 3 章讀過的取 batch、搬上 GPU、改形狀。接下來分成兩件事。

更新權重：11 格一起算 loss

第 60 行先把上一步留下的梯度清掉，第 61 行做 forward，outputs 是 (64, 11, 41)。第 63–64 行是本 repo 的關鍵改動：

  • outputs.view(-1, 41)：(64, 11, 41) 攤成 (704, 41)，704 = 64 × 11。攤平的順序是第 0 筆的第 0–10 步、第 1 筆的第 0–10 步……
  • labels.view(-1)：(64, 11) 攤成 (704,)，順序完全一樣。所以第 k 個 logits 和第 k 個標籤指的是同一筆、同一步。

第 66 行把 704 組（logits, 標籤）交給 CrossEntropyLoss，取 704 個 loss 的平均。對模型來說，等於每個 batch 有 704 個題目要答，不是 64 個；其中只有 64 個是「中間格」，另外 640 個是每筆前後各 5 格自己的標籤。第 67–68 行反向傳播、更新權重。

為什麼要讓 11 格都算 loss？評分只看中間格，其餘 10 格的答案理論上用不到；但多算這 10 格，等於每個 batch 多了 10 倍的監督訊號，而且每一步的 h 都被要求「認得出這一格是什麼音」，這對中間格有沒有幫助，可以直接比較。第 7 章把第 66 行改成只算中間格（criterion(outputs[:, 5, :], labels[:, 5])），其餘不變，同樣跑 5 個 epoch：

loss 怎麼算epoch 1epoch 2epoch 3epoch 4epoch 5
11 格都算（本 repo）0.57620.59930.61070.62130.6276
只算中間格0.52700.56620.58700.59790.6094

（中間格的驗證準確率。）每一個 epoch，11 格都算的版本都領先 0.018 到 0.049。在這個模型、這個規格下，多算的那 10 格確實幫了中間格。

量準確率：只看中間格

第 71–72 行（標著 # new）把 outputs 和 labels 都換成中間那一步：concat_nframes // 2 = 5。outputs[:, 5, :] 已經是 (64, 41)，後面的 .view(outputs.shape[0], -1) 不改變任何東西，只是保險。第 75 行 torch.max(outputs, 1) 沿著第 1 維（41 類）找最大值，回傳（最大值, 最大值的位置）；只要位置，也就是預測的類別，所以用 _ 丟掉第一個。第 76 行數這個 batch 答對幾個，累加到 train_acc；第 77 行把 loss 加到 train_loss。.item() 把只有一個元素的 tensor 變成 Python 數字，.detach() 切斷和計算圖的連結（這裡只是比較大小，不需要梯度）。

注意這裡的 outputs 是第 61 行算的，也就是更新權重之前的輸出，而且是在 dropout 開著的情況下算的。所以 Train Acc 不是「這個 epoch 結束時，模型在訓練集上的準確率」，而是「這個 epoch 一邊學、一邊量」的平均。5.6 節會再回來看這件事。

5.4　驗證與存檔

驗證段和訓練段幾乎一樣，差在三個地方：

  1. 第 82 行 model.eval()：關掉 dropout。驗證時要量的是模型真正的能力，不要隨機丟掉一半的數值。
  2. 第 83 行 torch.no_grad()：不記錄計算圖、不算梯度，省記憶體也省時間。
  3. 沒有 zero_grad、backward、step：只量，不學。

第 96 行一樣用 11 格算 val loss，第 99–105 行一樣只用中間格算 val acc。第 107–109 行印出第 0 章看到的那一行，四個數字分別是：

印出的欄位算法意思
Train Acctrain_acc / len(train_set)答對的中間格總數 ÷ 2,379,588
Loss（train）train_loss / len(train_loader)37,182 個 batch 的 loss 平均（每個 batch 的 loss 是 704 格的平均）
Val Accval_acc / len(val_set)答對的中間格總數 ÷ 264,570
loss（val）val_loss / len(val_loader)4,134 個 batch 的 loss 平均

第 112–115 行：這個 epoch 答對的個數比過去最好的多，就存檔並印出 saving model with acc …。比較用的是 >，所以「一樣好」不會存；印出的值只有 3 位小數，epoch 那一行是 6 位。torch.save(model.state_dict(), model_path) 只存權重（一個「參數名稱 → tensor」的字典），不存模型的結構、也不存 optimizer 的狀態，所以 predict.py 要先建一個一樣的模型再把權重填進去（第 6 章）。

第 116–124 行是沒有驗證集時的分支（train_ratio = 1 才會走到），只印訓練的兩個數字、最後存最後一個 epoch；本 repo 的設定不會用到。第 126–127 行刪掉 DataLoader、回收記憶體。

5.5　印出來的 Val Acc 是真的嗎

這個問題值得每份作業都問一次。同一個 repo 的 HW01，印出的驗證 loss 是 1.661，最佳 checkpoint 在整個驗證集上一次算完卻是 2.069：驗證集被打亂、各 batch 平均再平均、再從幾千次量測裡挑最好的，三件事加起來讓印出的數字比真實值好看很多。HW02 的寫法有沒有同樣的問題？

本書把 model.ckpt（第 15 個 epoch，印出 0.641955）載入，在整個驗證集上一次算完：中間格答對 169,842 / 264,570 = 0.641955，和印出的值完全一致。原因有四條：

  1. 驗證集不打亂（train.py:32，shuffle=False）。而且對準確率來說，順序本來就無關：第 3 章實測打亂後準確率一位都不差。
  2. 累加的是答對的個數，最後除以總筆數（第 104、108 行），不是「每個 batch 的準確率」再平均。最後一個只有 58 筆的 batch，在總和裡的份量剛好是 58 筆，不多也不少。
  3. 驗證時 dropout 關閉、不算梯度（第 82–83 行），每次量的都是同一個確定的模型。
  4. 只從 20 次量測裡挑最好的。驗證集同時被拿來挑 epoch，所以 0.641955 對「完全沒看過的資料」來說略為樂觀；但它本身就是那個 checkpoint 在整個驗證集上的真實準確率，而且 20 次裡最好的（第 15 個 epoch）和第 20 個 epoch（0.641936）只差 0.00002，挑選的影響很小。

val loss 就沒有這麼乾淨：第 108 行把 4,134 個 batch 的平均 loss 再平均，最後那個 58 筆的 batch 和其他 64 筆的 batch 份量一樣。本書用同一個 checkpoint 實測：照 train.py 的算法是 1.299442（和第 15 個 epoch 印的值相同），按筆數加權是 1.299457，差 0.000015，可以忽略。

還有一個容易誤讀的地方：印出的 val loss 是 11 格的平均，不是中間格的。只算中間格的 val loss 是 1.197084，比印出的 1.299 低；第 4 章看過，前面幾步看到的上下文少、準確率低，loss 也高，把平均拉上去了。所以「val loss」和「val acc」在這份程式裡量的是不同的東西：前者是 11 格，後者只有中間格。

現在的做法：把「挑 epoch」和「報分數」分開

用同一個驗證集挑模型又報分數，報出來的分數會略為樂觀。比較嚴謹的做法是切成三份：訓練集、用來挑 epoch 與超參數的驗證集、最後只用一次的測試集（這份作業的 Kaggle 測試集就扮演第三份的角色）。另外，PyTorch 現在提供 torch.use_deterministic_algorithms(True)，一次要求所有運算都用確定性的實作，比只設 cuDNN 的兩個旗標涵蓋得更完整。

5.6　20 個 epoch 的曲線

把第 0 章那 20 行輸出的 Train Acc 和 Val Acc 畫出來：

這張圖有三個值得讀的地方。

前 6 個 epoch，Train Acc 比 Val Acc 低。第 1 個 epoch 是 0.495 對 0.576。這不是「模型在驗證集上比較強」，而是兩個數字量的條件不同：Train Acc 是在 dropout 開著（一半的層間數值被丟掉）的情況下量的，而且是一邊學一邊量，前面的 batch 是用還很差的權重量的；Val Acc 是 epoch 結束、權重最好的時候、dropout 關掉量的。兩者不能直接比。

第 7 個 epoch 起，Train Acc 反超並持續上升，Val Acc 停住。Train Acc 從 0.639 一路爬到 0.691；Val Acc 在第 11 個 epoch 達到 0.640 之後，就在 0.639 到 0.642 之間打轉。val loss 在第 11 個 epoch 最低（1.291020），之後慢慢升到 1.316。模型在訓練集上越來越好、在驗證集上卻沒有進步，這就是過擬合：它開始記住訓練資料的細節，而這些細節對新的句子沒有幫助。

最佳的 epoch 是第 15 個，但差距很小。第 11–20 個 epoch 的 Val Acc 最大和最小只差 0.0027。如果改用「val loss 最低」來挑，會挑到第 11 個 epoch（Val Acc 0.640451）。照這條曲線，跑到第 11 個 epoch 左右就可以停了，後面 9 個 epoch（約一小時）幾乎沒有收穫。這種「驗證指標連續幾個 epoch 沒進步就停」的做法叫 early stopping，HW01 的程式有，本 repo 沒有。

停在 0.642 的原因，第 4 章已經給了一部分答案：中間格看不到後 5 格。第 7 章會在同一個規格下比較各種改法，看哪一種最能推動這個數字。

本章重點

  • same_seeds 固定 PyTorch 的 CPU／GPU 亂數，並讓 cuDNN 只用確定性的演算法；它管到權重初始化、每個 epoch 的打亂順序與 dropout，所以 checkpoint 可以逐位元組重現。
  • loss：CrossEntropyLoss；optimizer：AdamW（lr 1e-4、weight_decay 預設 0.01）。
  • loss 把 (64, 11, 41) 和 (64, 11) 攤平成 704 組一起算；準確率只取中間第 5 步。11 格都算 loss 的版本，5 個 epoch 內每個 epoch 都比只算中間格高 0.018–0.049。
  • Train Acc 是 dropout 開著、一邊學一邊量的，不能和 Val Acc 直接比。
  • 印出的 Val Acc 沒有偏差：不打亂、累加答對個數再除以總數、eval 模式。實測 0.641955 和整個驗證集一次算完相同。印出的 val loss 是 batch 平均再平均（差 0.000015），而且是 11 格的平均，不是中間格的。
  • 第 11 個 epoch 起 Val Acc 停在 0.639–0.642，val loss 回升，Train Acc 繼續升：過擬合。最佳是第 15 個 epoch；本 repo 沒有 early stopping。

自我測驗

1. 一個 64 筆的 batch，criterion 拿到的 logits 和標籤各是什麼形狀？最後一個只有 4 筆的 batch 呢？

64 筆時：output_flatten 是 (704, 41)、labels_flatten 是 (704,)，704 = 64 × 11。最後一個 batch 只有 4 筆：(44, 41) 和 (44,)。view(-1, 41) 和 view(-1) 的 -1 讓兩種情況都能算。

2. 第 1 個 epoch 印出 Train Acc 0.495127、Val Acc 0.576195。為什麼訓練集的準確率反而比較低？

兩者量的條件不同。Train Acc 在 model.train() 下量，dropout 會隨機丟掉層間一半的數值；而且它是整個 epoch 一邊更新權重一邊累加的，前面的 batch 用的是剛初始化、還很差的權重。Val Acc 在 epoch 結束後、model.eval() 下量，用的是這個 epoch 最後的權重、dropout 關閉。所以不能拿這兩個數字判斷有沒有過擬合；要比，得在 eval 模式下用同一組權重重新量一次訓練集。

3. 如果把第 66 行改成只用中間格算 loss，5 個 epoch 後中間格的驗證準確率會變好還是變差？

變差。第 7 章實測（其餘設定完全相同）：只算中間格，5 個 epoch 中最好是 0.609449；原本 11 格都算，第 5 個 epoch 是 0.627588。每一個 epoch 都落後 0.018 到 0.049。

4. 如果存檔的條件改成「val loss 比過去都低就存」，最後 model.ckpt 會是第幾個 epoch？它的 Val Acc 是多少？

照第 0 章的 20 行輸出，val loss 最低的是第 11 個 epoch（1.291020），之後都沒有更低，所以會是第 11 個 epoch，Val Acc 0.640451，比第 15 個 epoch 的 0.641955 低 0.0015。（這題是從輸出紀錄讀出來的：因為訓練過程完全由種子決定，改存檔條件不會改變每個 epoch 的數字，只會改變存哪一個。）

5. 印出的 val loss 是 1.299442，按筆數加權是 1.299457。差在哪裡？只算中間格的 val loss 又是多少？

印出的值是 4,134 個 batch 各自的平均 loss 再平均，最後那個只有 58 筆的 batch 份量和其他 64 筆的一樣；按筆數加權則讓它只佔 58 筆的份量，兩者差 0.000015。另外，兩個數字都是 11 格的平均；只算中間格的 val loss 是 1.197084。

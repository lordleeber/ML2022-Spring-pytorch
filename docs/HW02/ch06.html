第 6 章　預測與 prediction.csv

predict.py 只有 56 行：讀測試集、載入第 5 章存下的最佳權重、逐批預測中間格、寫成 Kaggle 要的 CSV。本章逐行讀完，弄清楚 Id 和句子、音框的對應關係，並打開寫出來的 prediction.csv，看模型到底猜了什麼，哪些類別它幾乎從來猜不對。

6.1　讀測試集、載入權重

第 6–9 行和 train.py 一樣，用星號 import 把四個模組的名字全部帶進來（第 5 章）。config.py 也被 import，所以 concat_nframes、batch_size、model_path 這些名字都和訓練時同一份設定。這很重要：拼接的格數、模型的大小都必須和訓練時一模一樣，權重才填得進去，也才有意義。

  • 第 19–20 行：split='test'，preprocess_data 走測試模式（第 1 章）：讀 test_split.txt、不打亂、不讀標籤，拼接之後只回傳特徵 (646268, 429)。沒有傳 train_ratio，測試模式也用不到它。
  • 第 21 行：LibriDataset(test_X, None)，沒有標籤，所以 __getitem__ 只回傳特徵（第 3 章）。
  • 第 22 行：shuffle=False。6.3 節會看到，這一行不能改。
  • 第 25–26 行：先建一個和訓練時結構相同的 Classifier，再把 model.ckpt 裡的權重填進去。第 5 章說過，torch.save(model.state_dict(), …) 只存了「參數名稱 → tensor」的字典，沒有存結構，所以一定要先有一個同樣的模型。如果 model.py 被改過（例如改成 3 層），名稱或形狀對不上，load_state_dict 就會報錯。

第 0 章跑過一次：stdout 只有四行（DEVICE: cuda、測試集 1,078 句、[INFO] test set、特徵形狀 (646268, 429)），整支程式 27.05 秒，峰值記憶體 2.1 GB。

6.2　逐批預測

和第 5 章的驗證段幾乎一樣：model.eval() 關掉 dropout、torch.no_grad() 不算梯度、view 成 11 格、取中間第 5 步、torch.max 取分數最大的類別。差別在於測試集沒有標籤，所以沒有 loss、也沒有準確率，只把每一批的答案收集起來。

第 29–30 行的 test_acc、test_lengths 宣告了卻沒有用到：測試集沒有標籤，根本算不了準確率。原版範例程式就有這兩行，是從某個「測試集有標籤」的版本留下來的殘骸，刪掉也不影響任何事。

第 31、46 行收集答案的方式值得多看一眼。pred 一開始是空陣列，每一批都用 np.concatenate 接上這一批的 64 個答案。np.concatenate 每次都會配置一個新陣列、把舊的內容全部複製過去，所以第 k 批要複製大約 64 × k 個數字；10,098 批加起來，複製的總量和批數的平方成正比。另外，pred 雖然宣告成 int32，接上 test_pred（PyTorch 的 int64 轉成的 NumPy 陣列）之後，型別會變成 int64。

這個寫法有多慢？本書用同樣的批數與批量模擬（10,097 批 64 個加一批 60 個，總共 646,268 個整數，不需要 GPU），比較「每批 concatenate 一次」和「先收進 list、最後 concatenate 一次」：

646268 int64 4.980 s | 646268 0.0012 s True

逐批接要 4.98 秒（再跑一次 5.06 秒），最後接一次只要 0.0012 秒，兩種結果完全相同，型別也確實變成 int64。predict.py 總共 27 秒，這一行大約就佔了 5 秒。

現在的做法：收進 list，最後接一次

迴圈裡要累積結果時，先 preds.append(test_pred.cpu()) 收進 list，迴圈結束後 torch.cat(preds) 或 np.concatenate(preds) 一次接起來，複製量和總長度成正比，不會隨批數平方成長。如果結果還要留在 GPU 上做後續運算，用 torch.cat 也可以省下每批搬回 CPU 的動作。

6.3　寫檔：Id 是什麼

第 48–51 行的說明文字是原版 notebook 留下的（「從左邊的檔案區下載」指的是 Colab 的介面）。第 53–56 行寫檔：第一行標題 Id,Class，接著每一格一行，Id 是 pred 裡的位置 i，Class 是預測的類別。寫檔用的是 with open(...)，離開區塊時會自動關檔（第 1 章「現在的做法」講的寫法，這裡有照做）。

Id 只是一個流水號，它怎麼對應到「哪一句的哪一格」？靠的是順序：preprocess_data 照 test_split.txt 的順序一句一句讀、把每一句的格子依序接在後面（第 2 章），DataLoader 又不打亂，所以 pred 的順序就是「第 1 句的第 0 格、第 1 格……第 1 句的最後一格、第 2 句的第 0 格……」。前三句的對應（實測）：

test_split.txt 的順序句子 id格數Id 範圍
第 1 句1963-142776-00228180–817
第 2 句1841-150351-0006657818–1474
第 3 句481-123720-00822201475–1694

1,078 句接完，最後一個 Id 是 646,267。Kaggle 那邊有一份同樣順序的正確答案，逐行比對 Class。這也說明了為什麼測試集不能打亂：第 1 章 preprocess_data 的測試模式不打亂句子，第 22 行的 shuffle=False 不打亂格子，兩者只要有一個打亂，Id 就對不上正確答案，分數會掉到接近亂猜，而程式不會報任何錯。

6.4　打開 prediction.csv

寫出來的檔案有 646,269 行（標題 1 行加 646,268 格），結尾有換行字元。開頭與結尾：

Id,Class
0,0
1,0
…
646266,0
646267,0

第一句的開頭和最後一句的結尾都猜第 0 類。第 1 章說過，第 0 類很可能是句首句尾的靜音，這個結果和那個推測一致。

整個檔案的類別分布：41 類都有出現。最多的是第 0 類 126,222 格（19.53%）、第 31 類 40,981 格（6.34%）、第 2 類 37,541 格（5.81%），排名和第 1 章訓練資料的前三名相同。最少的是第 1 類，只被猜了 64 次；其次是第 20 類 166 次、第 17 類 554 次。

測試集沒有標籤，猜得對不對要上傳 Kaggle 才知道。但同一個模型在驗證集上的行為可以拿來參考。本書用 model.ckpt 在整個驗證集上統計中間格：

類別（驗證集裡的格數）與準確率
最準的 5 類第 0 類（46,898）0.964、第 2 類（13,538）0.822、第 23 類（4,690）0.784、第 11 類（2,676）0.762、第 39 類（9,395）0.752
最差的 5 類第 1 類（1,856）0.000、第 22 類（712）0.166、第 17 類（664）0.191、第 38 類（1,649）0.236、第 18 類（1,315）0.294

幾個觀察：

  • 第 0 類幾乎全對（0.964），而且被猜得太多：驗證集裡真正的第 0 類佔 17.73%，模型猜第 0 類的比例是 19.59%。測試集上它猜第 0 類的比例（19.53%）也同樣高於訓練資料裡的 17.42%。類別不平均時，模型傾向多猜最常見的那一類（第 1 章）。
  • 第 1 類一格都沒猜對：驗證集有 1,856 格第 1 類，準確率 0。它不是最少的一類（第 20、17、22 類更少），第 1 章卻看過它有一段長達 270 格的紀錄，資料沒有說明第 1 類是什麼。模型為什麼完全學不會它，本書沒有進一步追查；在測試集上它只被猜了 64 次，和驗證集的結果一致。
  • 最常見的錯誤是成對出現的：驗證集上最常見的錯誤是把第 8 類猜成第 2 類（1,993 次），而第 2 類猜成第 8 類也有 1,050 次；第 25 類與第 37 類互相猜錯各 1,381 次和 1,228 次。這些很可能是聽起來相近的音素，但資料沒有給類別名稱，無法確認。

這些數字也告訴我們 0.642 是怎麼組成的：最常見的第 0 類貢獻了大量的「答對」，而一些少見的類別幾乎拿不到分。第 7 章比較改良方法時，看的仍然只是整體準確率，這一節的觀察可以當作「整體準確率之外還能看什麼」的例子。

6.5　重跑會不會改到 git 追蹤的檔案

第 0 章說過，HW02/prediction.csv 雖然符合 .gitignore 的 *.csv，卻因為比 .gitignore 早進 repo 而仍被追蹤。predict.py 每次都把結果寫到同一個路徑，覆蓋這個檔案。

用 repo 附的 model.ckpt 重跑，本書實測寫出來的檔案和被追蹤的版本逐位元組相同，所以 git status 看不出任何變化。這也間接證明了 repo 裡那份 prediction.csv 就是這個 checkpoint 的輸出。但只要你重新訓練過（改了任何設定，或在不同的顯示卡上跑），權重不同，預測就不同，這個檔案就會出現在 git status 的修改清單裡。做實驗時可以在 HW02/ 的複本裡跑，或是事後用 git checkout HW02/prediction.csv 還原。

本章重點

  • predict.py 用和訓練時相同的 config.py 與 model.py：先建模型，再 load_state_dict 填入 model.ckpt 的權重。
  • 預測只取中間第 5 步的最大分數類別；test_acc、test_lengths 宣告了沒用。
  • 逐批 np.concatenate 的複製量隨批數平方成長，模擬實測約 5 秒（最後接一次只要 0.0012 秒），結果也從 int32 變成 int64。
  • Id 是所有測試句依 test_split.txt 順序接起來的格號（第 1 句 Id 0–817、第 2 句 818–1474……），所以句子和格子都不能打亂。
  • 預測裡第 0 類佔 19.53%，比訓練資料的 17.42% 多；驗證集上第 0 類準確率 0.964，第 1 類 0.000，最常見的錯誤是第 8 類與第 2 類互相猜錯。
  • 用 repo 附的 checkpoint 重跑，prediction.csv 逐位元組不變；重新訓練之後就會出現在 git status。

自我測驗

1. prediction.csv 裡 Id 為 818 的那一行，是哪一句的第幾格？

第 2 句 1841-150351-0006 的第 0 格。第 1 句 1963-142776-0022 有 818 格，佔掉 Id 0–817，所以第 2 句從 818 開始。

2. 把 predict.py 第 22 行改成 shuffle=True，程式會報錯嗎？Kaggle 分數會怎樣？

不會報錯，程式照樣寫出 646,268 行。但每一批拿到的是隨機的格子，pred 的第 i 個答案不再是第 i 格的預測，Id 和答案的對應被打亂，分數會掉到接近隨便猜的水準。（這題依程式邏輯推論，本書沒有實際上傳 Kaggle。）

3. test_acc 和 test_lengths 是做什麼用的？

什麼都沒做：宣告之後沒有任何一行用到它們。測試集沒有標籤，本來就算不了準確率。它們是原版範例程式留下的殘骸，刪掉不影響結果。

4. 為什麼 pred 宣告成 np.int32，最後卻是 int64？逐批 np.concatenate 有什麼代價？

test_pred 來自 torch.max，是 int64；np.concatenate 接上 int32 和 int64 時，結果取能容納兩者的 int64。代價是每接一次都要複製整個舊陣列，總複製量隨批數平方成長。本書以同樣的批數模擬：逐批接 4.98 秒，最後接一次 0.0012 秒。

5. 驗證集上模型猜第 0 類的比例是多少？和真實比例相比，代表什麼？

模型猜第 0 類的比例是 19.59%，驗證集真實的第 0 類是 17.73%，多猜了將近 2 個百分點。類別不平均時，模型傾向把不確定的格子猜成最常見的類別。第 0 類本身的準確率因此很高（0.964），代價是其他類別的一些格子被誤判成第 0 類。

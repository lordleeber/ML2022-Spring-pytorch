第 3 章　Dataset、DataLoader 與形狀之旅

第 2 章結束時，訓練集是兩個大 tensor：(2379588, 429) 的特徵和 (2379588, 11) 的標籤。本章看它們怎麼被包成 Dataset、由 DataLoader 切成一個個 64 筆的 batch，最後在 train.py 裡用一行 view 變成 LSTM 要的 (64, 11, 39)。全章的主角是「形狀」：每一步都把形狀印出來看。

3.1　LibriDataset：把兩個 tensor 包成「可以用索引取一筆」的物件

PyTorch 的 Dataset 是一個約定：只要一個類別提供 __len__（有幾筆）和 __getitem__（給一個編號，回傳那一筆），DataLoader 就知道怎麼從裡面取資料。data_loader.py 只有這一個類別：

  • __init__（第 7–12 行）：把特徵存成 self.data；有標籤的話，存成 self.label。第 10 行的 torch.LongTensor(y) 是把標籤轉成 int64 的舊式寫法；preprocess_data 給的 y 本來就是 int64，所以這一行不會複製，本書實測轉換前後兩者共用同一塊記憶體。
  • __getitem__（第 14–18 行）：第 idx 筆就是特徵的第 idx 列和標籤的第 idx 列。測試集沒有標籤（predict.py 傳 None），只回傳特徵。
  • __len__（第 20–21 行）：特徵有幾列，就有幾筆。

「一筆」是什麼？第 2 章說過：一筆 = 一格，連同它前後各 5 格的特徵（429 個數字）與 11 個標籤。不是一句。所以訓練集有 2,379,588 筆，不是 3,857 筆。用驗證集實際取一筆來看，存成 c3a.py（放在 HW02/ 裡）：

from torch.utils.data import DataLoader
from utils import preprocess_data
from data_loader import LibriDataset

val_X, val_y = preprocess_data(split='val', feat_dir='./libriphone/feat', phone_path='./libriphone',
                               concat_nframes=11, train_ratio=0.9)
val_set = LibriDataset(val_X, val_y)
x, y = val_set[0]
print(len(val_set), x.shape, x.dtype, y.shape, y.dtype)
print(y)
loader = DataLoader(val_set, batch_size=64, shuffle=False)
print(len(loader))
batches = list(loader)
print(batches[0][0].shape, batches[0][1].shape)
print(batches[-1][0].shape, batches[-1][1].shape)
print(batches[-1][0].view(-1, 11, 39).shape)
$ ../.venv/bin/python c3a.py 2>/dev/null

現在的做法：TensorDataset

有標籤時，LibriDataset 做的事和 PyTorch 內建的 torch.utils.data.TensorDataset(X, y) 一樣：把幾個第一維一樣長的 tensor 綁在一起，第 i 筆就是每個 tensor 的第 i 列。自己寫一個類別的好處是可以處理「沒有標籤」的測試集；如果只是包 tensor，直接用 TensorDataset 就好。

3.2　DataLoader：一次 64 筆

DataLoader 每次被迭代（for batch in loader）時，做三件事：決定這一輪的順序、每次按順序取 batch_size 個編號、對每個編號呼叫 __getitem__ 再把結果疊成一個 batch。疊的方式是把 64 個 (429,) 疊成 (64, 429)，64 個 (11,) 疊成 (64, 11)，這一步叫 collate，預設行為就是沿著新的第 0 維堆起來。

第 27–28 行的 del 和 gc.collect()，第 2 章已經說過：Dataset 還握著同一個 tensor，刪掉的只是名字，記憶體不會因此釋放。

每個 epoch 的 batch 數：

集合筆數batch 數（64 筆一批）最後一批shuffle
訓練2,379,58837,1824 筆True
驗證264,5704,13458 筆False
測試（predict.py）646,26810,09860 筆False

第 0 章 stderr 上那兩條每個 epoch 都會出現的進度條 37182/37182、4134/4134，數的就是這兩個 batch 數。一個 epoch 要做 37,182 次參數更新，這是訓練慢的直接原因；原版範例程式用 batch_size = 512，同樣的資料只要八分之一的次數。

訓練集打亂，驗證集不打亂

shuffle=True 表示每個 epoch 開始迭代時，都重新決定一個隨機順序，所以每個 epoch 看到的 batch 組合都不一樣。打亂的單位是「筆」，也就是格：同一個 batch 裡的 64 筆通常來自 64 個不同的句子、不同的位置。這沒有問題，因為每一筆已經自帶前後 5 格的上下文，模型不需要知道它和隔壁那筆在原本的句子裡是不是相鄰。

這個隨機順序是用 PyTorch 的全域亂數決定的，而且是在每個 epoch 開始迭代時才決定，不是在建 DataLoader 的時候。所以第 35 行的 same_seeds(seed) 雖然寫在第 31 行之後，仍然管得到打亂的順序：第一次迭代發生在第 53 行，那時亂數已經固定了。第 0 章看到「重跑一次得到逐位元組相同的 checkpoint」，這是原因之一（第 5 章會把 same_seeds 整個讀一遍）。

驗證集是 shuffle=False，每次都照原本的順序。對驗證準確率來說，順序其實無關：train.py 是把每個 batch 答對的個數加起來，最後除以總筆數，加法的順序不影響結果。第 5 章檢查「印出來的驗證準確率是不是真的」時，這會是理由之一。

3.3　形狀之旅：(64, 429) → (64, 11, 39)

訓練迴圈每拿到一個 batch，先做這幾行：

第 54 行把 batch 拆成特徵和標籤；第 55–56 行搬到 GPU（device 是 "cuda"）；第 58 行把 (64, 429) 改成 (64, concat_nframes, input_dim_lstm) = (64, 11, 39)。驗證迴圈的第 84–89 行是一模一樣的四步。

為什麼一行 view 就夠？view 不搬動任何資料，只是換一種方式解讀同一串數字：把每一列的 429 個數字，每 39 個切一段，切成 11 段。第 2 章說過，一列裡的數字是「第 t−5 格的 39 個、第 t−4 格的 39 個、……」依序排的，所以每 39 個一段，切出來的第 j 段剛好就是第 t−5+j 格。用真的資料驗證，存成 c3b.py：

import torch
from utils import concat_feat
f = torch.load('libriphone/feat/train/2007-149877-0023.pt')
row = concat_feat(f, 11)[50]
print(row.shape)
a = row.view(11, 39)
print(all(torch.equal(a[j], f[45 + j]) for j in range(11)))
b = row.view(39, 11)
print(torch.equal(b[0], f[45, :11]), torch.equal(b[:, 0], f[45]))
$ ../.venv/bin/python c3b.py
torch.Size([429])  «1»
True  «2»
True False  «3»
  1. 1取 2007-149877-0023 拼接後的第 50 列，也就是第 1 章圖 1.1 的那個視窗。
  2. 2view(11, 39) 的第 j 段，和原始特徵的第 45+j 格完全相同，11 段全部成立。所以 LSTM 拿到的第 0 格是第 45 格、第 5 格是第 50 格（中心）、第 10 格是第 55 格。
  3. 3如果寫反成 view(39, 11)：它把 429 個數字每 11 個切一段，切出 39 段。第一段是第 45 格的前 11 維（True），而把每一段的第一個數字湊起來，也不等於第 45 格（False）。形狀一樣能算，程式不會報錯，但每一段都是把不同格、不同維的數字混在一起，模型學到的是沒有意義的東西。

形狀對了不代表內容對了，這是 view／reshape 最常見的陷阱：只要元素總數相同，任何形狀都改得過去。這裡能用一行 view，是因為第 2 章的 concat_feat 剛好把資料排成了「格在外、維在內」的順序。

LSTM 怎麼看這個 (64, 11, 39)

第 0 章的模型裡，LSTM 設了 batch_first=True（model.py:12）。這個參數決定 LSTM 怎麼解讀三個維度：

  • batch_first=True：(batch, 時間步, 每步的特徵) = (64, 11, 39)。64 筆各自獨立，每筆是一串 11 個時間步，每步 39 個數字。
  • batch_first=False（PyTorch 的預設）：(時間步, batch, 特徵)。如果沒有設 True，同一個 (64, 11, 39) 會被當成 64 個時間步、11 筆、每步 39 個數字，形狀照樣算得過去，意思卻完全錯了。

所以「形狀對了不代表內容對了」這件事，在 view 之後又出現了一次：資料排成 (64, 11, 39)，模型也必須同意第 1 維才是時間。這兩個條件本 repo 都滿足。LSTM 拿到之後怎麼沿著那 11 個時間步一步一步讀，是第 4 章的主題。

每個 batch 才搬上 GPU

整個訓練集放在主機記憶體裡（第 2 章，約 4 GB），每次只把一個 batch 搬上 GPU：特徵 64 × 429 × 4 = 109,824 bytes、標籤 64 × 11 × 8 = 5,632 bytes，很小。模型本身的兩千萬個參數則在第 38 行 .to(device) 時就一次搬上去，之後一直留在 GPU 上。DataLoader 沒有設 num_workers，所以取資料、疊 batch 都在主程式裡做；資料已經是記憶體裡的 tensor，取一列只是索引，不需要讀檔或解碼。

本章重點

  • LibriDataset 實作 __len__ 與 __getitem__：一筆 = 一格（429 個特徵、11 個標籤），不是一句。測試集沒有標籤，只回傳特徵。
  • torch.LongTensor(y) 對已經是 int64 的 y 不會複製。
  • batch 64：訓練 37,182 批（最後 4 筆）、驗證 4,134 批（最後 58 筆）、測試 10,098 批（最後 60 筆）。
  • 訓練集每個 epoch 重新打亂（以格為單位），順序在迭代開始時才用全域亂數決定，所以 same_seeds 寫在建 DataLoader 之後也有效。驗證集不打亂，順序不影響準確率。
  • view(-1, 11, 39) 能把一列拆回 11 格，是因為 429 個數字按「格在外、維在內」排列；寫成 view(39, 11) 形狀一樣算得過，內容卻是錯的。-1 讓不滿 64 筆的最後一批也能改形狀。
  • batch_first=True 讓 LSTM 把第 1 維（11）當成時間步。

自我測驗

1. len(train_set) 是多少？是句數還是格數？

2,379,588，是格數。__len__ 回傳特徵的列數，而 preprocess_data 一格產生一列。訓練集的句數是 3,857，在 LibriDataset 裡已經看不到句子的邊界了。

2. 把 train.py:58 的 -1 換成寫死的 64，第一個 epoch 會在哪裡出事？

前 37,181 個 batch 都是 64 筆，沒有問題；最後一個 batch 只有 4 筆，特徵是 (4, 429) 共 1,716 個數字，無法變成 64 × 11 × 39 = 27,456 個，view 會報錯，訓練停在第一個 epoch 的最後一步。（這題是依 view 的規則推論，本書沒有實際改程式去跑。）

3. 驗證集也設 shuffle=True，印出的 Val Acc 會變嗎？

不會。train.py 把每個 batch 答對的個數加總後除以總筆數；模型在 eval() 模式下對每一筆的預測和順序無關（dropout 關閉、各筆獨立計算），總和也和加法順序無關。會變的只有 val loss 的最後幾位小數：val loss 是「每個 batch 的平均」再平均，batch 怎麼分組會影響它（第 5 章）。本書用 model.ckpt 實測：shuffle=False 時準確率 0.6419548701666856、loss 1.299442；shuffle=True 時準確率完全相同、loss 1.299462。另一個副作用是打亂會用掉全域亂數：實測固定種子後直接取一個亂數得到 0.4962…，先迭代一次 shuffle=True 的驗證集再取，得到 0.3074…。在訓練中這會讓下一個 epoch 訓練集的打亂順序跟著改變，之後的訓練結果就不會和原本逐位相同了。

4. 第 0 章 stderr 的進度條是 37182/37182。如果把 batch_size 改成 512，會變成多少？

2,379,588 ÷ 512 = 4,647 餘 324，所以是 4,648 個 batch，最後一批 324 筆。這正是第 7 章跑原版範例程式（batch 512）時一個 epoch 的步數；參數更新的次數只剩原本的八分之一左右。

5. 一個 batch 裡的 64 筆，可能來自同一句嗎？可能是同一句裡相鄰的兩格嗎？這會造成問題嗎？

都可能，訓練集有 2,379,588 筆，打亂之後碰巧抽到同一句、甚至相鄰的格子並不奇怪，只是機率不高。這不會造成問題：每一筆都自帶前後 5 格的上下文，模型對每一筆的預測是獨立算的，它不知道也不需要知道兩筆之間的關係。要避免的是同一句同時出現在訓練集和驗證集（第 1 章），而那已經由「以句為單位切分」保證了。

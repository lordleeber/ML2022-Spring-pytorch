第 4 章　訓練迴圈與驗證

train.py 的後半段：固定亂數、一個 epoch 的訓練、驗證、寫 log、存 checkpoint。程式本身是標準的 PyTorch 寫法，但細節裡藏了四件值得追的事：印出的驗證準確率是怎麼平均的、為什麼 log 檔永遠是空的、一個進度條怎麼改變了亂數順序，以及為什麼「每次跑都一模一樣」。

4.1　固定亂數：每次跑都一模一樣

訓練裡有很多地方用到亂數：模型的初始權重、DataLoader 打亂的順序、第 6 章的隨機增強。第 31–34 行把 NumPy、PyTorch（CPU）與每張 GPU 的亂數產生器都設成同一個起點 6666，之後每次「抽」出來的數字序列就固定了。Python 內建的 random 雖然在第 20 行 import 了，但整份程式沒有用到它，所以沒有設種子。

光固定亂數還不夠。cuDNN（NVIDIA 的深度學習函式庫，PyTorch 在 GPU 上做卷積時呼叫它）對同一個卷積有好幾種演算法，有些用平行累加，加法的順序每次不同，浮點數的捨入誤差也就不同，結果會在小數點後很多位出現差異。第 29 行要求只用確定性（deterministic）的演算法；第 30 行關掉 benchmark 模式——開著時，cuDNN 會在第一次遇到某種形狀時把幾種演算法都試跑一遍、挑最快的，挑中的那一個每次可能不同。

效果在第 0 章已經看到：2026-10-03 與 2026-10-05 在不同資料夾裡跑的兩次，submission.csv 逐位元組相同；第 2 章 OMP_NUM_THREADS=1 的那一次，sample_best.ckpt 也和原本逐位元組相同。代價是一點速度：確定性演算法不一定是最快的。（本書沒有實際比較關掉這兩行時的速度與差異。）

現在的做法：一行 seed_everything

今天常見的是把這幾行包成一個函式，連 Python 的 random 一起設，並加上 torch.use_deterministic_algorithms(True)：它不只管 cuDNN，遇到任何沒有確定性版本的 GPU 運算都直接報錯，而不是悄悄給出不同的結果。PyTorch Lightning 的 seed_everything 就是這樣一個函式。另外，DataLoader 可以傳一個自己的 generator，讓打亂的順序不受其他地方抽亂數的影響——4.6 節會看到為什麼這很重要。

4.2　一個 epoch 的訓練

這是 PyTorch 訓練迴圈的標準五步，逐行看：

  • 第 90 行 model.train()：切到訓練模式。上一個 epoch 結尾切成了 eval（第 139 行），所以每個 epoch 開頭都要切回來；BatchNorm 在兩種模式下的算法不同（第 3 章 3.3 節）。
  • 第 96 行：從 train_loader 一次拿一個 batch，外面包了 tqdm 畫進度條。這個看起來無害的包裝會改變亂數順序，4.6 節專門追它。
  • 第 103–104 行：把圖片與標籤搬上 GPU，做 forward，得到 (256, 11) 的 logits。第 99 行被註解掉的 imgs.half() 是改用半精度的嘗試，沒有用。
  • 第 108 行：算 cross entropy loss（4.3 節）。
  • 第 111 行 optimizer.zero_grad()：把上一步留在每個參數上的梯度清掉。PyTorch 的梯度是累加的，不清就會和上一步的梯度加在一起。
  • 第 114 行 loss.backward()：反向傳播，算出 loss 對 12,833,803 個參數各自的梯度，存在每個參數的 .grad 裡。
  • 第 117 行：梯度裁剪（4.3 節）。回傳值 grad_norm 存了起來，但後面沒有用到。
  • 第 120 行 optimizer.step()：Adam 用梯度更新參數（4.3 節）。
  • 第 124–125 行：這個 batch 的準確率。logits.argmax(dim=-1) 取每張圖 11 個分數裡最大的位置，torch.eq 和標籤逐一比較，得到 256 個 True／False，轉成 1.0／0.0 再取平均。第 123 行被註解掉的是原版的寫法，意思完全一樣；本 repo 把它拆成兩行，並在第 104 行先把標籤搬上 GPU，避免搬兩次。
  • 第 128–132 行：記下每個 batch 的 loss 與準確率，一個 epoch 結束後取平均印出來。loss.item() 把 GPU 上的一個數字取回 CPU 變成 Python 的 float；acc 則直接把 GPU 上的 tensor 放進 list，最後 sum 出來的 train_acc 也是一個 GPU 上的 tensor，f-string 的 :.5f 照樣能印。

印出的訓練準確率有兩個要注意的地方。第一，它是邊訓練邊量的：第 1 個 batch 是用剛初始化的權重量的，第 39 個 batch 是用更新了 38 次之後的權重量的，平均起來代表的是「這個 epoch 過程中」的表現，不是 epoch 結束時的模型。第二，它是在 train 模式下量的，BatchNorm 用的是 batch 的統計量（第 3 章看到這在早期差很多）。所以第 0 章的「Train acc 0.31425、Valid acc 0.17568」不能直接比。

4.3　loss、優化器與梯度裁剪

CrossEntropyLoss

第 78 行的 nn.CrossEntropyLoss() 對每張圖做兩步：先對 11 個 logits 做 log-softmax，變成 11 個機率的對數；再取出正確類別那一個、加負號。一個 batch 的 loss 是這 256 個值的平均。第 107 行的註解說「不需要先做 softmax，它會自動做」，指的就是第一步，所以第 3 章的模型最後一層沒有 softmax。如果模型完全不知道答案、11 類的機率都是 1/11，loss 就是 ln 11 ≈ 2.398。本書實測第一個訓練 batch（剛初始化的權重）的 loss 是 2.4209，就在這附近；第 0 章第 1 個 epoch 的平均 1.95937 已經比它低了。

Adam 與 weight decay

第 81 行的 torch.optim.Adam(model.parameters(), lr=0.0003, weight_decay=1e-5)：Adam 為每個參數記住梯度的移動平均（方向）與梯度平方的移動平均（大小），用前者除以後者的平方根來決定每一步走多遠，所以每個參數有自己的有效學習率。lr=0.0003 是整體的步伐大小，3e-4 是 Adam 常見的預設附近的值。

weight_decay=1e-5 是一種正則化：每一步都把參數往 0 拉一點點，讓權重不要長得太大。要注意 torch.optim.Adam 的 weight decay 是把 1e-5 × 參數 加進梯度裡，再交給 Adam 的自適應縮放；因為縮放會因參數而異，這和「直接把參數縮小一點」不是同一件事。

現在的做法：AdamW 與學習率排程

2019 年的 AdamW 把 weight decay 和梯度分開，直接對參數做衰減（decoupled weight decay），效果比較符合「L2 正則化」的原意，今天訓練 CNN 與 Transformer 大多用 torch.optim.AdamW，weight decay 常設在 0.01–0.05。另外，這份程式的學習率從頭到尾固定在 0.0003；現在通常會搭配排程（scheduler），例如先暖身（warmup）再用 cosine 慢慢降到接近 0。第 8 章的 200 個 epoch 長跑也沒有用排程，這是可以再往上爬的方向之一。

梯度裁剪：max_norm=10

第 117 行的 clip_grad_norm_ 把所有參數的梯度看成一個超長的向量，算它的長度（L2 norm）；如果超過 10，就把整個向量等比例縮到長度 10，方向不變；沒超過就什麼都不做。它是防止某一步梯度突然爆大、把參數一下子推到很遠的保險。這個保險在這份程式裡用到了嗎？本書在實驗工具裡記下每一步裁剪前的梯度長度（印出的每一行仍與 train.py 相同），5 個 epoch 共 195 步：

4.4　驗證：被打亂的驗證集與「平均再平均」

和訓練迴圈幾乎一樣，差在三處：第 139 行切到 eval 模式；第 154 行的 torch.no_grad() 告訴 PyTorch 不必為 backward 記錄計算過程，省記憶體也省時間；沒有 backward 與 step，權重不會改變。第 159 行的 loss 寫在 no_grad 外面，但它的輸入 logits 已經不帶梯度資訊，所以結果一樣。第 138 行的註解提到 dropout，這個模型其實沒有 dropout，那是從其他作業的範本帶過來的說明。

關鍵在第 171–173 行。註解說「整個驗證集的平均 loss 與準確率，就是記錄下來的值的平均」——這句話不完全對。valid_accs 裡有 14 個數字，前 13 個各是 256 張圖的準確率，最後一個只是 102 張圖的準確率（3,430 = 13 × 256 + 102，第 2 章），把 14 個數字直接平均，等於讓那 102 張圖的每一張都多了 2.5 倍的權重。真正「整個驗證集的準確率」是：

真實準確率 = 答對的總張數 ÷ 3,430　　≠　　(acc₁ + acc₂ + … + acc₁₄) ÷ 14

而且第 64 行的驗證集是 shuffle=True：每個 epoch 分到最後那一批的 102 張圖都不一樣，印出的數字就會隨分批方式上下晃動，即使模型完全相同。

偏差有多大

本書在實驗工具裡，用同一次驗證同時累加「答對的總張數」，算出每個 epoch 的真實準確率（不多抽任何亂數，印出的每一行仍與 train.py 相同）：

結論是：這份程式的偏差很小，大約 ±0.2 個百分點，不影響本書引用 train.py 印出的數字；第 8 章比較各組時，一律另外列出真實值。偏差小的原因有三個：最後一批 102 張只占 3%，多給它的權重有限；一個 batch 有 256 張，每批的準確率本身就不太跳；而且 train.py 只拿這個數字來決定「存不存 checkpoint」，挑選的次數不多。HW01 的教材裡，同一類「印出的驗證指標」和真實值差了很多（印出 1.661、真實 2.069）；同一種寫法會不會出問題，要看資料、batch 大小與挑選的方式，只能實測。

但它還是會讓「最佳 epoch」選錯

偏差小不代表沒有影響。train.py 用印出的數字和 best_acc 比，比較大就存檔。當兩個 epoch 的真實準確率只差 0.1 個百分點時，±0.2 的晃動就足以讓程式存下比較差的那一個。第 8 章的長跑裡，印出的最佳是第 187 個 epoch 的 0.76669，真實值 0.76501——每一組都會同時列出這兩個數字。

4.5　永遠是空的 log 檔與存檔

第 180 行 with open(f"./{exp_name}_log.txt", "a"): 以附加模式打開 sample_log.txt，但沒有用 as f 把檔案取個名字；第 181 行的 print 也沒有寫 file=f。print 預設寫到標準輸出，也就是螢幕。所以這兩行的效果是：打開檔案（檔案不存在就建立一個空的）、在螢幕上印一行、關閉檔案。第 0 章看到的兩個現象都從這裡來：每個驗證結果在螢幕上印了兩次（第 176 行一次、這裡一次，這裡多了 -> best），而 sample_log.txt 是 0 bytes。原版 notebook 就是這樣寫的。修正只要改兩個地方：

with open(f"./{exp_name}_log.txt", "a") as f:
    print(f"[ Valid | ... ] ... -> best", file=f)

（這是本書寫的示意，... 的部分照原本。本書沒有實際改 train.py 去跑。）

第 187–196 行存檔與提前停止（early stopping）：

  • 印出的 valid_acc 比目前最好的 best_acc 大，就印一行、把模型的 state_dict()（所有參數與 BatchNorm 的 buffer，第 3 章）存成 sample_best.ckpt，覆蓋舊的。第 189 行的註解說「只存最好的，避免輸出超過容量」，指的是 Kaggle 的輸出上限（投影片第 23 頁：20 G）。
  • 第 188 行 Best model found at epoch {epoch} 用的是迴圈變數 epoch，從 0 起算；同一個 epoch 的其他行都印 epoch + 1。第 0 章的 stdout 因此出現 [ Valid | 005/005 ] 與 epoch 4 指的是同一個 epoch。
  • 沒進步就把 stale 加 1；連續超過 patience（300）個 epoch 沒進步就 break 停止訓練。5 個 epoch 根本走不到 300；第 8 章 200 個 epoch 的長跑也走不到。第 195 行的 improvment 是原版就有的拼字錯誤。
  • best_acc 初始是 0（第 85 行），而 valid_acc 是 GPU 上的 tensor，valid_acc > best_acc 比出來也是一個 tensor，if 會自動把它轉成 True／False。第一次存檔之後，best_acc 本身也變成了 tensor。

注意訓練結束時，記憶體裡的 model 是最後一個 epoch 的權重，不一定是最好的；最好的在 sample_best.ckpt 裡，所以 test.py 要重新載入它（第 5 章）。

4.6　一個進度條改變了亂數順序

本書寫實驗工具 docs/tools/hw03_exp.py 時，第一版把訓練迴圈原樣搬過去，只拿掉了 tqdm 進度條（不需要畫進度）。種子一樣、模型一樣、資料一樣，第 1 個 epoch 的訓練 loss 卻從 train.py 的 1.95937 變成 1.97084。逐步比對之後發現：建模型那一刻的亂數狀態相同、初始權重相同，但第一個 batch 的圖片不同——train.py 第一個 batch 的前 8 個標籤是 [3, 9, 2, 7, 8, 3, 1, 2]，工具是 [8, 9, 9, 0, 9, 7, 10, 3]。差別只在第 96 行與第 146 行的 tqdm(...)。

為什麼

train.py:19 是 from tqdm.auto import tqdm。tqdm.auto 會自動挑一個適合目前環境的進度條；在一般的 Python 腳本裡（不是 notebook），它挑的是 tqdm.asyncio.tqdm_asyncio，一個也支援 async for 的版本。tqdm 4.70.1 的 tqdm/asyncio.py 裡，它的建構子是這樣寫的：

    def __init__(self, iterable=None, *args, **kwargs):
        super().__init__(iterable, *args, **kwargs)
        self.iterable_awaitable = False
        if iterable is not None:
            if hasattr(iterable, "__anext__"):
                ...
            else:
                self.iterable_iterator = iter(iterable)
                self.iterable_next = self.iterable_iterator.__next__

（取自已安裝的 tqdm 4.70.1，中間兩個分支以 ... 省略。）為了支援 async for，它在建構時就先呼叫一次 iter(iterable)，建立一個 iterator 存起來。但 train.py 用的是一般的 for，走的是父類別 tqdm 的 __iter__，它會再呼叫一次 iter(self.iterable)。對 DataLoader 來說，每次 iter() 都會建立一個新的資料迭代器，而建立迭代器時，PyTorch 會從全域亂數產生器抽一個數字當這個迭代器的種子（torch 2.11 的 dataloader.py 第 708 行附近的 .random_(generator=loader.generator)，本書用追蹤 Tensor.random_ 的方式確認過）。所以每個 epoch 的訓練與驗證各多抽了一個亂數，之後所有的亂數——下一個 epoch 的打亂順序、第 6 章的隨機增強——全部錯開。

用一個 10 筆的小例子就能重現（本書實測）：torch.manual_seed(1) 之後直接從 DataLoader(list(range(10)), batch_size=10, shuffle=True) 取第一個 batch 是 [4, 2, 0, 6, 8, 7, 9, 1, 5, 3]；同樣的種子、先包一層 tqdm 再取，是 [9, 7, 8, 3, 5, 1, 2, 0, 4, 6]。即使設了 tqdm(..., disable=True) 關掉進度條，建構子裡那次 iter 一樣會執行，所以本書的實驗工具最後就是用 tqdm(..., disable=True) 包住兩個迴圈，才和 train.py 逐位元一致。

回收第 2 章的伏筆：num_workers=4 為什麼改變了結果

第 2 章把 num_workers 改成 4，訓練快了 4 倍，第 5 個 epoch 的驗證準確率卻從 0.55541 變成 0.48967；拿掉進度條之後，0 與 4 個 worker 的結果又完全相同。現在可以解釋了：

  • num_workers=0 時，單行程的迭代器在建立時只抽「迭代器種子」那一個數字；決定打亂順序的那次抽取，要等第一次真的取資料時才發生。tqdm 丟掉的那個迭代器從來沒被取過資料，所以只多抽了一個數字。
  • num_workers=4 時，多行程的迭代器在建立時就會啟動 4 個子行程、並預先派出前幾個 batch 的工作，打亂順序在這一刻就抽好了。tqdm 丟掉的那個迭代器因此多抽走了一份打亂順序，還白白開了 4 個子行程。

兩種情況多抽的亂數個數不同，後面的亂數就錯開成不同的樣子，訓練結果也就不同。（本書沒有逐行追進 PyTorch 多行程迭代器的程式碼；這一段是依「有進度條時 0 與 4 個 worker 結果不同、拿掉進度條後完全相同」的實測，加上多行程迭代器會預先派工的行為推得的。）worker 數本身不改變結果，是「進度條 × worker」的組合改變了它。

教訓：會抽亂數的東西要有自己的產生器

這件事不是 bug——結果仍然可重現，只是「加一個進度條」或「改 worker 數」這種看起來和模型無關的修改，會讓實驗變成另一組亂數。要讓打亂順序不受干擾，可以給 DataLoader 一個專用的產生器：DataLoader(..., generator=torch.Generator().manual_seed(6666))，它就只從這個產生器抽，其他地方抽多少亂數都不影響它。比較兩種設定時，也要確認除了你想比的那一項，亂數的消耗方式沒有跟著變。

本章重點

  • 第 28–34 行固定 NumPy、PyTorch、CUDA 的種子 6666，並要求 cuDNN 用確定性演算法、關掉 benchmark；實測重跑的 checkpoint 與 submission.csv 逐位元組相同。
  • 訓練五步：model.train() → forward → zero_grad → backward → 裁剪 → step。印出的訓練準確率是邊訓練邊量、在 train 模式下量的。
  • 初始 loss 約 ln 11 = 2.398（實測第一個 batch 2.4209）。Adam lr 3e-4，weight_decay=1e-5 是加進梯度的 L2，不是 AdamW。梯度裁剪 max_norm=10 在前 5 個 epoch 的 195 步裡一次都沒有觸發（最大 9.962）。
  • 驗證準確率是 14 批各自的準確率直接平均，最後一批 102 張被多給了權重，驗證集又被打亂；實測偏差約 ±0.2 個百分點，第 5 個 epoch 印出 0.55541、真實 0.55394。
  • with open(...) 沒有 as f、print 沒有 file=f：log 印到螢幕上兩次，sample_log.txt 永遠是 0 bytes。Best model found at epoch {epoch} 從 0 起算。patience 300 在本書的所有實驗裡都用不到。
  • tqdm.auto 在腳本裡是 tqdm_asyncio，建構時多呼叫一次 iter(loader)，每個迴圈多抽一個亂數；搭配 num_workers>0 時還多抽走一份打亂順序。所以加不加進度條、worker 數多少，都會改變訓練結果。

自我測驗

1. 把第 111 行的 optimizer.zero_grad() 刪掉，會發生什麼事？

每一步的梯度會一直累加在 .grad 上：第 2 步用的是第 1、2 步梯度的和，第 39 步用的是 39 步的和。梯度越來越大，梯度裁剪很快就會開始每一步都觸發，但方向是所有歷史梯度的總和，不是當下這個 batch 的方向，訓練會很糟。（這題是推論，本書沒有實際刪掉去跑。）「刻意不清、累加幾步再更新」是有用的技巧，叫做 gradient accumulation（投影片第 34 頁），但要搭配每幾步才 step 與 zero_grad 一次。

2. 某個 epoch 的驗證，前 13 批的準確率都是 0.55，最後 102 張那一批是 0.75。印出的 acc 是多少？真實的準確率是多少？

印出的是 (13 × 0.55 + 0.75) ÷ 14 = 0.56429。真實的是 (13 × 256 × 0.55 + 102 × 0.75) ÷ 3,430 = (1,830.4 + 76.5) ÷ 3,430 = 0.55595。最後一批特別好時，印出的數字比真實值高了 0.8 個百分點；本書實測的晃動比這個小，因為各批的準確率沒有差這麼多。

3. 要讓 log 真的寫進 sample_log.txt，最少要改哪幾個地方？

第 180、183 行的 with open(...) 後面加 as f，第 181、184 行的 print(...) 加上 file=f，共四處。這樣螢幕上就不會再印第二次，每個 epoch 的驗證結果會附加到檔案裡；因為是 "a" 模式，重跑時會接在舊內容後面，不會覆蓋。

4. 只把第 96 行的 tqdm(train_loader) 改成 train_loader（第 146 行不動），第 1 個 epoch 的訓練 loss 會不會變？

會。建立模型之後，第一個被抽的亂數是第 96 行那個迭代器的種子。改掉之後第 96 行只建立一次迭代器，少抽一個數字，打亂訓練集的那次抽取就拿到不同的數字，第一個 batch 的內容不同，第 1 個 epoch 的 loss 就變了。本書實驗工具的第一版兩處都拿掉，第 1 個 epoch 的訓練 loss 是 1.97084；只拿掉一處的版本本書沒有實際跑，數字會是第三種。

5. 印出的訓練準確率在第 30 個 epoch 達到 1.00000（第 8 章的 base40），代表模型在訓練集上 100% 正確嗎？

幾乎是，但嚴格來說它是「這個 epoch 過程中、train 模式下、39 批各自的準確率直接平均」：每一批都全對，平均才會是 1.00000，所以第 30 個 epoch 的每一個 batch 確實都全對了。它不等於「epoch 結束時的模型、在 eval 模式下」的準確率，那需要另外量；第 8 章會看到，這時驗證集只有 0.67，模型已經把訓練集背起來了。

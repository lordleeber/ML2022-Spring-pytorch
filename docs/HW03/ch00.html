第 0 章　任務、環境與模型總覽

先弄清楚作業要什麼、規則禁止什麼、分數怎麼算；再看一眼模型——一張 128×128 的彩色圖片，經過 5 個卷積區塊和 3 層全連接，變成 11 個分數；最後把 train.py 和 test.py 實際跑一遍，逐行讀它們印出來的東西。

0.1　作業要做什麼

HW03 是一個影像分類（image classification）問題：輸入一張食物照片，輸出它屬於 11 類中的哪一類。投影片第 2 頁列了這份作業的三個目標：用卷積神經網路（convolutional neural network，CNN）解影像分類、用資料增強（data augmentation）提升表現、認識殘差（residual）這類常見的影像模型技巧。資料來自 food-11 資料集，投影片第 3 頁給的數量是：

Testing set3,347沒有交給 Kaggle 評分

本書在本機數過，三個資料夾的張數和投影片一致。11 類各是什麼食物、每一類有幾張，是第 1 章的主題。

規則：不准用預訓練模型（投影片第 4 頁）

這份作業有三條和技術有關的禁令：不准試圖找出測試集的原始標籤、不准用外部資料、不准用預訓練模型（pretrained model）。投影片第 8 頁再強調一次：可以用 torchvision.models 或 timm 裡現成的模型結構，但要設 pretrained=False，權重必須從亂數開始訓練。第 4 頁甚至特別寫了「預訓練非常有效，比賽結束後你可以自己試」。這條規則決定了整份作業的風格：所有改良都要在「一萬張圖、從零開始」的條件下完成。目錄頁的「現在的做法」框說明了為什麼今天很少這樣做。

0.2　模型總覽：3 × 128 × 128 個數字，經過 5 個卷積區塊變成 11 個分數

本 repo 的模型在 classifier.py，類別名稱是 Classifier，和原版範例程式的模型一模一樣（只差 forward 裡兩個中間變數的名字）。這一節只看整體：有哪些層、資料的形狀怎麼變、參數在哪裡。每一層內部怎麼算，留給第 3 章逐行拆。

整個模型是兩個 nn.Sequential：第 10 行起的 self.cnn 和第 36 行起的 self.fc。nn.Sequential 是一個容器，把裡面的層依序串起來，資料從第一層流到最後一層。助教在每一行後面用註解寫了那一層的輸出形狀（例如 [64, 128, 128]），格式是「通道數, 高, 寬」，不含 batch 那一維；本章圖 0.1 會把它們畫出來，0.2 節最後讓 PyTorch 實際數一次。

四種層，各做一件事

  • nn.Conv2d(in, out, 3, 1, 1)：二維卷積（convolution）。用 out 個 3×3 的小濾波器（filter）在圖上滑過，每個濾波器在每個位置看「3×3 個像素 × in 個通道」，算出一個數字，所以輸出有 out 個通道。後兩個數字是步長（stride）1 和補邊（padding）1：一次移一格、四周補一圈 0，所以高和寬不變。第 7 行的註解寫了這五個參數的順序。
  • nn.BatchNorm2d(C)：批次正規化（batch normalization）。把每個通道的數值調成平均 0、標準差 1 左右，再乘上、加上兩個可學習的數。它在訓練與評估時的行為不同，第 3、4 章會講這件事為什麼重要。
  • nn.ReLU()：激活函數，負數變 0、正數不變。沒有參數。
  • nn.MaxPool2d(2, 2, 0)：最大池化（max pooling）。把每 2×2 個格子取最大的一個，所以高和寬各減半，通道數不變。沒有參數。

Conv → BN → ReLU → MaxPool 四層一組，本書叫它一個卷積區塊，共 5 個。每過一個區塊，圖的邊長減半（128 → 64 → 32 → 16 → 8 → 4），通道數加倍或持平（3 → 64 → 128 → 256 → 512 → 512）。最後得到 512 張 4×4 的「特徵圖」，第 47 行 view(zzz, -1) 把它攤平成一條 512 × 4 × 4 = 8,192 個數字的向量（zzz 是 batch 大小，-1 讓 PyTorch 自己算剩下那一維），交給 self.fc 的三層全連接（nn.Linear）：8,192 → 1,024 → 512 → 11。最後的 11 個數字還沒經過 softmax，叫做 logits；分數最大的那一類就是模型的答案。

參數量：先手算，再讓 PyTorch 數

三種有參數的層，各有一條公式。設輸入通道 cin、輸出通道 cout、卷積核 3×3：

Conv2d 的參數 = cout × (cin × 3 × 3)（權重）+ cout（偏差 bias）
BatchNorm2d(C) 的參數 = 2C（每個通道一個縮放 weight、一個平移 bias）
Linear(i, o) 的參數 = i × o（權重）+ o（偏差）
  • 區塊 1：64 × (3 × 9) + 64 = 1,728 + 64 = 1,792；BN 2 × 64 = 128。合計 1,920。
  • 區塊 2：128 × (64 × 9) + 128 = 73,728 + 128 = 73,856；BN 256。合計 74,112。
  • 區塊 3：256 × (128 × 9) + 256 = 294,912 + 256 = 295,168；BN 512。合計 295,680。
  • 區塊 4：512 × (256 × 9) + 512 = 1,179,648 + 512 = 1,180,160；BN 1,024。合計 1,181,184。
  • 區塊 5：512 × (512 × 9) + 512 = 2,359,296 + 512 = 2,359,808；BN 1,024。合計 2,360,832。
  • fc：8,192 × 1,024 + 1,024 = 8,389,632；1,024 × 512 + 512 = 524,800；512 × 11 + 11 = 5,643。
  • 合計：卷積部分 1,920 + 74,112 + 295,680 + 1,181,184 + 2,360,832 = 3,913,728；全連接部分 8,389,632 + 524,800 + 5,643 = 8,920,075；全部 12,833,803，大約一千三百萬個。

注意卷積層的參數和圖的大小無關：同一組 3×3 的濾波器在整張圖上重複使用，圖是 128×128 還是 1000×1000，區塊 1 都是 1,792 個參數。全連接層就不同了，fc 第 1 層的 8,192 個輸入是「512 個通道 × 4 × 4 個位置」，每一個位置、每一個通道都有自己的權重，所以這一層就占了全部參數的 65%。這件事在第 7 章會更極端：Q2 的殘差網路沒有池化，攤平後有 262,144 維，第一層全連接就有 6,711 萬個參數。

和手算一致。recurse=False 讓每個模組只數「直接屬於自己」的參數，所以 cnn、fc 這兩個容器本身被跳過，ReLU 和 MaxPool 沒有參數也被跳過，剩下的 13 行就是全部有參數的層。PyTorch 把 Conv2d(3, 64, 3, 1, 1) 印成 kernel_size=(3, 3), stride=(1, 1), padding=(1, 1)，因為一個整數會被展開成「高、寬」兩個方向。

BatchNorm 除了這些可學習的參數，還存了每個通道的「移動平均」與「移動變異數」，這兩樣不是參數、不會被訓練，PyTorch 叫它們 buffer。存下來的 checkpoint sample_best.ckpt 是 51,360,932 bytes，比 12,833,803 個 float32 × 4 bytes = 51,335,212 多一點點，多出來的就是這些 buffer 和每個參數的名稱。

  4. 4同一行又印了一次，多了 -> best。這一行原本應該寫進 sample_log.txt，但程式寫錯了，字印到了螢幕上，log 檔永遠是空的（第 4 章逐行說明）。
  5. 5驗證準確率創新高，存下 sample_best.ckpt。這裡的 epoch 0 是從 0 起算的，和上面三行的 001 指的是同一個 epoch。
  6. 6最後一個 epoch：驗證準確率 0.55541。5 個 epoch 每一個都比前一個好，所以每個 epoch 都存了一次，最後留在 sample_best.ckpt 裡的是第 5 個 epoch 的權重。

stderr 上另外有 tqdm 畫的進度條：每個 epoch 兩條，訓練一條數到 39、驗證一條數到 14，那是一個 epoch 的 batch 數（第 2 章）。除了進度條，沒有任何警告訊息。

看第 4 個 epoch：訓練 loss 從 1.375 降到 1.188，驗證 loss 卻從 1.553 升到 1.586，驗證準確率只多了 0.5 個百分點；到第 5 個 epoch 驗證 loss 又降回 1.319。只跑 5 個 epoch，曲線還在劇烈跳動，看不出有沒有過擬合（overfitting）。第 8 章會把同一份程式跑到 40 個 epoch，曲線就清楚了。

跑多久：本書在 GPU 上沒有任何其他程式時，用 /usr/bin/time -v 量完整的 train.py：wall clock（牆上時鐘實際經過的時間）3 分 0.70 秒，平均一個 epoch（含驗證）約 36 秒。同一份紀錄裡，CPU 時間是 3,101.94 秒，CPU 使用率 1723%——也就是平均有 17 個 CPU 核心在忙。一個只靠 GPU 訓練的程式為什麼會用掉這麼多 CPU？因為 num_workers=0 時，每一張 JPEG 的解碼、縮放、轉成 tensor 都在主程式裡做，第 2 章會量這部分占了多少時間。

同樣的程式，同樣的結果

repo 裡被忽略的 sample_best.ckpt 與 submission.csv 是 2026-10-03 跑出來的；本書 2026-10-05 在另一個資料夾裡再跑一次，印出的每一行都和上面相同，產生的 submission.csv 和它逐位元組相同。原因是 train.py:28-34 固定了亂數種子，並要求 cuDNN 使用確定性（deterministic）的演算法（第 4 章）。所以只要環境相同，你跑出來的每一行數字都會和上面一樣；換了顯示卡或套件版本，小數點後幾位才可能不同。

表裡 0.55541 後面的「真實值 0.55394」是什麼意思？train.py 印的驗證準確率是「每個 batch 各算一次準確率，再把 14 個數字平均」，而最後一個 batch 只有 102 張、卻和 256 張的 batch 算一樣的權重，加上驗證集被打亂，每次跑分批的方式都不同。本書用存下來的最佳權重，把整個驗證集 3,430 張一次算完，答對 1,900 張，準確率 0.55394，和印出來的只差 0.15 個百分點。第 4 章會把這件事拆開來看，並說明為什麼這裡的差距很小（HW01 的教材裡，同樣的寫法差了很多）。

驗證集不是 Kaggle 的測試集

表裡有兩種數字：基準線是 Kaggle 測試集上的分數，本 repo 是本機驗證集上的準確率。兩者是不同的資料，所以只能說「在驗證集上，本 repo 落在 simple 和 medium 之間」，不能說它通過了哪一條 Kaggle 基準線；repo 裡也沒有任何上傳 Kaggle 的紀錄。助教的 simple baseline 是原版範例程式（batch 64、3 個 epoch）的分數，本 repo 跑 5 個 epoch，在驗證集上比它高一些，這個方向是合理的，但幅度不能拿來比。

從 0.555 到 medium 的 0.732，投影片給的方法是「資料增強 + 訓練更久」。這兩件事分別在第 6 章和第 8 章實作：第 8 章會在同一套規格（40 個 epoch）下，把原版、加增強、殘差網路等改法並排比較，再跑一次 200 個 epoch 的長跑。

本章重點

  • HW03 是 11 類食物的影像分類：訓練 9,866 張、驗證 3,430 張、測試 3,347 張，評估指標是 accuracy。不准用預訓練模型，權重必須從亂數開始。
  • Kaggle 四條基準線：simple 0.50099、medium 0.73207、strong 0.81872、boss 0.88446；每往上一級都要「訓練更久」。報告兩題：Q1 資料增強（第 6 章）、Q2 殘差連接（第 7 章）。
  • 模型是 5 個卷積區塊（Conv 3×3 → BN → ReLU → MaxPool 2×2）加 3 層全連接，(3, 128, 128) → (512, 4, 4) → 8,192 → 1,024 → 512 → 11。
  • 參數 12,833,803 個（手算與 PyTorch 一致）：卷積部分 3,913,728，全連接部分 8,920,075，其中 fc 第 1 層 8,389,632 個就占 65%。
  • 兩支腳本都要在 HW03/ 裡用 ../.venv/bin/python 執行，需要 NVIDIA GPU；資料、checkpoint、log、預測檔都被 .gitignore 擋在 repo 外。
  • train.py 5 個 epoch 實測 3 分 0.70 秒，最佳是第 5 個 epoch，印出驗證準確率 0.55541（整個驗證集一次算 0.55394）；結果可以逐位元組重現。每個驗證結果印兩次、log 檔是空的，原因在第 4 章。

自我測驗

1. 一個 batch 進模型時是 (256, 3, 128, 128)，經過第 3 個卷積區塊之後是什麼形狀？攤平之後呢？

每個區塊的 MaxPool 讓邊長減半，3 個區塊後邊長是 128 ÷ 2³ = 16，通道是第 3 個區塊的卷積輸出 256，所以是 (256, 256, 16, 16)。攤平要等 5 個區塊都走完：(256, 512, 4, 4) 經過 view(zzz, -1) 變成 (256, 8192)。

2. 手算區塊 2 的卷積層有幾個參數。如果把它的卷積核從 3×3 改成 5×5（padding 改成 2），會變成多少？輸出形狀會不會變？

3×3 時是 128 × (64 × 9) + 128 = 73,856。改成 5×5：128 × (64 × 25) + 128 = 204,800 + 128 = 204,928，約 2.8 倍，因為權重和卷積核的面積成正比。padding 跟著改成 2，輸出的高寬仍然不變，所以形狀還是 (128, 64, 64)，後面的層都不受影響。（這題只手算，本書沒有實際改模型去跑。）

3. 在 repo 根目錄直接執行 .venv/bin/python HW03/train.py 會怎樣？

import 沒有問題（Python 會把腳本所在的 HW03/ 加進模組搜尋路徑），但 dataset_dir = "./food11" 是相對路徑，相對於 repo 根目錄就找不到。實測最後一行是 FileNotFoundError: [Errno 2] No such file or directory: './food11/training'，出錯的位置是 dataset.py 第 17 行 os.listdir(path)。這個錯誤發生在建 FoodDataset 的時候，還沒碰到 GPU。要先 cd HW03 再執行。

4. 5 個 epoch 裡，Best model found … 印了幾次？印出的 epoch 編號是哪幾個？最後 sample_best.ckpt 存的是第幾個 epoch 的權重？

5 次，因為每個 epoch 的驗證準確率都比前一個高（0.17568 → 0.43092 → 0.47906 → 0.48411 → 0.55541）。印出的編號是 epoch 0 到 epoch 4，因為那一行用的是迴圈變數 epoch 本身（0 起算），其他行用的是 epoch + 1。最後存的是第 5 個 epoch（印成 epoch 4）的權重。

5. 為什麼全連接層占了 69.5% 的參數，卷積層只占 30.5%？如果輸入圖片改成 256×256、其他都不改，模型會怎樣？

卷積層的參數只和通道數、卷積核大小有關，和圖的大小無關；fc 第 1 層的輸入是攤平後的 512 × 4 × 4，每個位置都有自己的權重，所以 8,192 × 1,024 這一層就有 839 萬個參數。輸入改成 256×256 時，5 次池化後是 8×8，攤平成 512 × 8 × 8 = 32,768 維，但 nn.Linear(512 * 4 * 4, 1024) 寫死了 8,192，所以 forward 走到 self.fc 會因為形狀不合而出錯。要嘛把 transform 縮回 128，要嘛改 fc 第 1 層的輸入大小（那一層會變成 3,355 萬個參數）。（這題是推論，本書沒有實際跑。）

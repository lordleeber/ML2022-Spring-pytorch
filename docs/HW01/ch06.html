花了多少時間？本機實測整支 predict.py 約 2.5 秒（大部分是 import torch、初始化 GPU 這類固定開銷），其中讀 CSV、切分、選特徵合計約 0.025 秒。所以這段繞路慢不了多少，第 0 章稱它「多餘」，問題不在速度，而在下面兩件事。

問題一：預測要依賴訓練資料

predict.py 只要預測測試集，卻非得找到 covid.train.csv 不可。把它交給別人、搬到另一台機器上執行，就得連訓練資料一起帶過去。本機實測，在 repo 根目錄（而不是 HW01/）執行 .venv/bin/python HW01/predict.py，第一個失敗的就是第 25 行讀訓練資料：

FileNotFoundError: [Errno 2] No such file or directory: './covid.train.csv'

路徑 ./covid.train.csv 是相對於「執行時所在的目錄」（第 5 章 5.2 節講 models/ 時的同一件事），所以 predict.py 和 train.py 一樣必須在 HW01/ 裡執行。程式在讀檔時就停了，不會留下半份 pred.csv。

問題二：117 是「現在」算的，不是「訓練時」的

這是更根本的問題。第 39 行的 117，是 predict.py 執行當下依照 config 與 select_feat 重算出來的；它和 model.ckpt 訓練時用的特徵一致，只是因為兩支程式剛好讀同一份 config、呼叫同一個函式。兩者之間沒有任何東西在檢查「是不是同一套特徵」。

第 7 章改進模型時，你會去改 select_feat 或 config（例如拿掉 id 欄）。只要改了之後沒有重新訓練就執行 predict.py，會出現兩種情況：

  • 欄數變了：例如改成 116 欄，第 39 行就建出 My_Model(116)，第 40 行載入 117 欄的權重時報第 4 章 4.8 節那個 size mismatch for layers.0.weight 錯誤。這種情況至少會大聲失敗。
  • 欄數沒變、欄位換了：例如把某一欄換成另一欄，總數還是 117。形狀完全對得上，load_state_dict 不會抱怨，模型卻會把學給 A 欄的權重乘在 B 欄上。第 2 章 2.4 節說過這種錯「程式不會報錯，只會默默給出錯的預測」。這種情況完全安靜。

兩種情況的根源相同：建模型需要的資訊，沒有跟著權重一起存。下一節看怎麼補。

附帶一提，predict.py 沒有呼叫 same_seed，對結果沒有影響。切分用的是 train_valid_split 自己的 torch.Generator（第 2 章），不看全域 seed；第 39 行建模型時抽到的亂數初始權重（第 4 章 4.4 節），下一行就全部被覆蓋；預測過程本身不用任何亂數。本機實測連續執行兩次，pred.csv 的 md5（一種檔案內容的指紋，內容差一個位元組，指紋就完全不同）都是 46a0484b5d4eff1d72c9dd06923e65bb：預測是確定性的。

6.3　更好的做法：讓 checkpoint 自己帶著 input_dim

第 4 章 4.8 節的「現在的做法」框提過方向：存檔時不只存 state_dict，而是存一個字典，把建模型需要的設定一起放進去。這裡把它展開。

先確認：存字典，新版 torch.load 讀得回來嗎

目錄頁說過，PyTorch 2.6 起 torch.load 的 weights_only 預設為 True：只允許載入 tensor 與基本容器。本書用的 torch 2.11 實測如下：

  • torch.load 的函式簽名（def 那一行列出的參數與預設值）裡，weights_only 的預設值寫的是 None，但執行時的效果就是 True：載入一個含自訂類別物件的檔案，會報 UnpicklingError: Weights only load failed. ...，加上 weights_only=False 才讀得進來。
  • 白名單裡的型別照樣能載入，例如 collections.Counter（標準函式庫裡用來計數的 dict）。
  • repo 的 model.ckpt（一個 OrderedDict，也就是會記住 key 插入順序的 dict，6 個 key）用預設值能載入，所以第 40 行沒寫 weights_only 也照常運作。
  • {'input_dim': 117, 'state_dict': ...} 這種「整數加 state_dict」的字典，用預設值也能載入。

UnpicklingError 的 unpickling 指的是 Python 的 pickle 格式：torch.save 用它把物件序列化（轉成一串可以寫進檔案的位元組，第 5 章 5.7 節）。pickle 可以存任意 Python 物件，載入時也就可能執行任意程式碼，所以來路不明的檔案很危險；weights_only 就是只放行 tensor、數字、字串、list、dict 這類「純資料」的限制。最後一點是本節要的：把 input_dim 和 state_dict 包成字典，新版預設的安全載入照樣接受。

現在的做法：checkpoint 帶著重建模型需要的一切

以下是示意寫法，本書沒有改 repo 的程式，也沒有實際執行這段。存檔端（train.py 第 88 行）：

torch.save({
    'input_dim': x_train.shape[1],
    'feat_idx': feat_idx,              # 用了哪幾欄（需要讓 select_feat 把它傳回來）
    'state_dict': model.state_dict(),
}, config['save_path'])

載入端（取代 predict.py 第 25–34 行與第 39–40 行）：

ckpt = torch.load(config['save_path'], map_location=device, weights_only=True)  # map_location：第 4 章 4.8 節
test_data = pd.read_csv('./covid.test.csv').values
x_test = test_data[:, ckpt['feat_idx']]
model = My_Model(input_dim=ckpt['input_dim']).to(device)
model.load_state_dict(ckpt['state_dict'])
  • 不必再讀訓練資料。predict 只需要權重檔與測試集，圖 6.1 的上排整段消失。
  • 存 feat_idx，才擋得住 6.2 節的「安靜的錯」。只存 input_dim，只能保證欄數一致；存下用了哪幾欄，預測時直接照著取，欄位就不可能對錯。feat_idx 是整數 list，屬於 weights_only 放行的基本容器（本機只實測了含 input_dim 的那種字典）。
  • 標準化（第 1 章「現在的做法」）一旦加進來，訓練集算出的平均與標準差也是「預測時必須原樣重用」的東西，同樣該放進這個字典。第 5 章 5.7 節的「存檔時連同訓練狀態一起存」是同一個想法：checkpoint 存的是「之後要用到的一切」，不只是權重。

不改存檔格式的折衷：從權重形狀反推

如果不想動 train.py，還有一個辦法：input_dim 其實已經藏在 model.ckpt 裡了。第 4 章 4.3 節看過，layers.0.weight 的形狀是 (輸出, 輸入) ＝ (16, 117)，第二個維度就是 input_dim。所以：

state_dict = torch.load(config['save_path'])
model = My_Model(input_dim=state_dict['layers.0.weight'].shape[1]).to(device)
model.load_state_dict(state_dict)

這樣也不必讀訓練資料。代價是程式碼必須知道「第一層的參數叫 layers.0.weight」，model.py 的結構一改（例如在最前面加一層），這行就得跟著改；而且它只救得了欄數，救不了「欄位換了」那種錯。存字典是比較完整的做法，反推形狀是應急。

6.4　第 36–40 行：建 test loader、載回權重

第 36–37 行在第 3 章 3.4 節讀過：只傳 x 的 Dataset 每筆只回傳一個 tensor；shuffle=False 是正確性的要求，6.6 節會量化打亂的後果。第 39–40 行在第 4 章 4.8 節讀過：建一個和 train.py 第 126 行同樣的模型（少了行尾註解），torch.load 讀出 state_dict，load_state_dict 依名字複製進去。把三章的說法接起來，載回權重的完整流程是：

  1. 訓練時（第 5 章 5.7 節）：每次 valid loss 創新低，torch.save(model.state_dict(), ...) 覆寫 model.ckpt。訓練結束時，檔案裡是第 1483 個 epoch 那一份。
  2. 預測時重建骨架（第 39 行）：用同樣的 input_dim 建 My_Model，搬上 GPU。這時權重是新抽的亂數。
  3. 填回數字（第 40 行）：讀出 6 個 key 的字典，依名字把 2,033 個數字（第 4 章 4.3 節算過的參數總數）複製進去。名字與形狀必須完全對上，否則報錯（第 4 章 4.8 節）。

第 40 行還有一個前提：檔案要存在。本機實測，把 models/model.ckpt 移走再執行，前面的讀檔、切分、印形狀都照常完成，到第 40 行才失敗：

FileNotFoundError: [Errno 2] No such file or directory: './models/model.ckpt'

也就是說，predict.py 永遠載入「最近一次 train.py 存下的最佳」。第 5 章動手做第 4 項提醒過：改了設定重新訓練，model.ckpt 就被覆寫；之後執行 predict.py，pred.csv 反映的是新的那一份。本章所有數字都以 1.661 那一份 model.ckpt 為準：訓練時印出的最佳 valid loss 是 1.661，拿到 539 筆上一次算完的真實 valid MSE 是 2.0685（兩者的差距見第 3 章 3.5 節）。

6.5　predict()：一批一批算，再接成一條

這個函式和第 5 章 5.6 節的驗證迴圈幾乎是同一個樣子：先 model.eval()（第 11 行），迴圈裡 .to(device) 搬上 GPU（第 14 行），在 torch.no_grad() 裡做 forward（第 15–16 行）。eval 與 no_grad 各管什麼，5.6 節講過；這裡只看和驗證迴圈不同的地方。

  • 第 13 行只拿 x。驗證迴圈是 for x, y in valid_loader；測試集的 Dataset 沒有 y，每個 batch 就是一個 tensor（第 3 章 3.2 節），所以這裡只寫 for x in ...。迴圈外包了 tqdm，那就是 6.2 節 stderr 的那條進度條。
  • 沒有 loss。沒有答案可比，預測值就是全部的產出，第 17 行把它收集起來。

第 17 行：.detach() 多餘，.cpu() 不可少

pred 是 GPU 上的 (256,) tensor（第 4 章 4.5 節的形狀，經過 squeeze(1)）。第 17 行對它做兩件事再放進 list：

  • .detach()：取出不連著計算圖的版本。但它在 no_grad 區塊裡算出來，本來就沒有計算圖：本機實測 pred.requires_grad 是 False。所以這個 detach 和第 5 章 5.5 節 train loss 那裡的一樣，多餘但無害。
  • .cpu()：把 tensor 從 GPU 記憶體複製回主記憶體（第 3 章 3.4 節：搬上 GPU 是複製，搬回來也是）。這一步不可少，原因在第 18 行。

第 18 行：torch.cat 接起來，.numpy() 轉成 NumPy

迴圈結束時，preds 是 5 個 tensor 組成的 list。本機實測它們的形狀依序是 (256,)、(256,)、(256,)、(256,)、(54,)，都在 cpu、都是 float32，正是第 3 章 3.3 節 test loader 的 256 × 4 ＋ 54。第 18 行做兩件事：

  • torch.cat(preds, dim=0)：沿著第 0 維把 5 個 tensor 首尾相接（第 4 章動手做用過它把 train 與 valid 上下接起來），得到一個 (1078,) 的 tensor。順序就是 list 的順序，也就是 loader 給 batch 的順序。
  • .numpy()：轉成 NumPy 陣列。本機實測結果是 ndarray，形狀 (1078,)，dtype float32（第 3 章：模型的參數與運算都是 float32，輸出自然也是）。

.numpy() 只能用在 CPU 上的 tensor：NumPy 陣列住在主記憶體，讀不到 GPU 記憶體。本機實測，對 GPU 上的 tensor 直接呼叫會報錯，錯誤訊息自己就把解法講出來了：

TypeError: can't convert cuda:0 device type tensor to numpy. Use Tensor.cpu() to copy the tensor to host memory first.

（host memory 就是主記憶體，相對於 GPU 這個 device。）predict() 選擇每個 batch 算完就先搬回 CPU，再在 CPU 上接起來；也可以先在 GPU 上 cat、最後一次搬回，HW01 這麼小的資料量兩種寫法沒有差別。

在 GPU 上 在 CPU（主記憶體）上

最後回傳的是 NumPy 陣列，而不是 tensor。這是一個分界：從這裡開始，寫檔、統計都在 CPU 上用一般的 Python 與 NumPy 處理，不再需要 PyTorch。

6.6　save_pred()：pred.csv 的每一行

七行，逐行看：

  • 第 41 行用 with open(file, 'w') as fp: 以寫入模式開檔：檔案不存在就建立，存在就清空重寫，所以每次執行 predict.py 都會蓋掉上一份 pred.csv。with 區塊結束時自動關檔（第 5 章 5.6 節的 with torch.no_grad() 是同一種語法：進入時做一件事、離開時做收尾）。這一行少了一個參數，6.8 節專門談。
  • 第 42 行建立 csv.writer，Python 標準函式庫 csv 模組的寫入器。它負責 CSV 格式的細節：欄位之間放逗號、欄位內容本身有逗號或引號時，用引號把整個欄位包起來，免得被誤認成分隔符號、每列結尾放行尾字元。utils.py 第 3 行 import csv 就是為了它。
  • 第 43 行 writerow 寫一列：表頭 id,tested_positive。這兩個欄名是 Kaggle 規定的提交格式，答案欄的名字和訓練資料的最後一欄相同。
  • 第 44–45 行對每個預測寫一列 [i, p]。enumerate 給出 0、1、2…當 id（第 3 章 3.4 節），p 是陣列裡的一個 float32 數字，怎麼變成字串在 6.7 節。

  2. 2注意 4.1526003 有 8 位數字，8.850631 只有 7 位。不是四捨五入到固定位數，原因在 6.7 節。
  3. 3最後一個 id 是 1077，所以 id 從 0 數到 1077，正好 1,078 個。最後兩筆的預測都超過 30，比訓練資料裡任何一個答案都高，6.9 節會回來看。

本機也用 pd.read_csv('pred.csv') 讀回來檢查：欄位是 ['id', 'tested_positive']，1,078 列，tested_positive 是 float64（pandas 讀小數的預設型別），數值和模型在 x_test 上的輸出一致（np.allclose 為 True，「在浮點誤差內相等」，第 1 章的 np.isclose 的整個陣列版本）。檔案格式沒有問題。

id 對得上嗎：第 3 章的前提，實測確認

第 3 章 3.4 節說，enumerate 的 i 能當 id，前提是 loader 依原始順序給資料。其實還有第二個前提：測試集本身的 id 欄要正好是 0、1、2…依序排列。如果 covid.test.csv 的列是亂序的，或 id 從 1 開始，enumerate 的 i 就和檔案裡的 id 不一致。本機實測，測試集的 id 欄正好是 0 到 1077 依序排列（和 0 到 1077 的整數序列 np.arange(1078) 用 np.array_equal 逐個比較，完全相同）。兩個前提都成立，pred.csv 的第 i 列就是測試集 id i 的預測。

save_pred 沒有讀測試集的 id 欄，而是自己從 0 數起，這是一種「剛好成立」的寫法。更穩的做法是直接把 x_test 的第 0 欄（也就是 id 欄，第 2 章 select_all 的結果）寫出去，見 6.8 節的「現在的做法」。

如果 test loader 打亂了：從 1.00 變成 120

第 3 章說，test loader 若打亂，每個預測值都算對了，卻被貼上錯的 id，「成績會差到像亂猜」。現在可以量化這句話，只是要先解決一個問題：測試集沒有答案，算不出真正的 MSE。

本章借用一把替代的尺：測試集第 4 天的陽性率（第 101 欄，pandas 欄名 tested_positive.3）。目錄頁的 baseline 表裡，「直接抄第 4 天」當預測，在驗證集上的真實 MSE 是 1.313：第 4 天和真正的答案（第 5 天）相當接近。所以拿預測和第 4 天算 MSE，雖然不是成績，卻能看出預測「離一個合理的參考值有多遠」。下面寫成 MSE(預測, 第 4 天)。

本機實測，把模型的 1,078 個預測照 pred.csv 的順序和第 4 天比，MSE(預測, 第 4 天) 是 1.0045；把 1,078 個預測本身隨機重排（用以 0 為 seed 的 NumPy 亂數產生器 np.random.default_rng(0) 產生排列），模擬「每個預測被貼上隨機的 id」，變成 120.0056，大了一百多倍。

120 有多糟？拿它和最笨的預測比：每一筆都猜同一個數字，猜第 4 天的平均值。這樣的 MSE(預測, 第 4 天) 就是第 4 天陽性率的變異數（variance，每個值和平均的差平方後再平均，衡量一組數字散得多開；第 5 章 5.10 節「永遠猜平均」的 MSE 和驗證集答案的變異數幾乎相等，就是這個道理）。本機實測測試集第 4 天的變異數是 59.6773。打亂後的 120 大約是它的 2 倍：比「每筆都猜平均」還糟一倍。

為什麼剛好是 2 倍左右？打亂之後，每一筆的預測和它被配到的第 4 天是兩個互不相干的數字，各自都在平均附近散開，散開的程度都約是變異數；把差拆成「預測離平均多遠」減「第 4 天離平均多遠」（兩者的平均都約 15.17，見 6.9 節，所以可以用同一個平均）：平方展開後，兩項各自的平方平均起來各是一份變異數；交叉項是兩者的乘積，配對既然是隨機的，正負互相抵銷、平均約為 0。所以總和約是兩份變異數。所以第 3 章的「像亂猜」說得還太客氣：打亂 id 的提交，比亂猜一個常數還差。

6.7　數字怎麼變成字串：float32 的最短表示

pred.csv 裡的 8.850631 和 4.1526003，位數不一樣多。如果是固定四捨五入到小數第幾位，應該一樣長；如果是印出全部精度，應該更長。它們是怎麼來的？

第 45 行的 p，是對一個 float32 的 NumPy 陣列做 enumerate 取出的元素，型別是 NumPy 的 float32 純量（np.float32），不是 Python 內建的 float。csv.writer 遇到非字串的值，會先把它轉成字串，這裡等於 str(p)。而 NumPy 把 float32 轉字串的規則是：印出能唯一還原成同一個 float32 的最短十進位數字。

拆開來說。第 3 章講過，float32 只有約 7 位有效數字：它能精確表示的數字是一格一格的，相鄰兩格之間的數都存不了。8.850631 這個十進位字串，讀回 float32 時會落在唯一的一格上，正是模型算出的那一格；少一位（8.85063）就會落到別格，多一位則沒有必要。4.1526003 也一樣，只是在 4 附近，要 8 位數字才足以指名那一格。所以位數不固定，取決於那個值附近格子的疏密。

對照組：同一個預測若先轉成 float64 再印，是 8.850630760192871。後面那串 0760192871 不是模型多算出來的精度，而是 float32 那一格的值用 float64 完整寫出來的樣子（第 3 章 y_train[0] 從 3.7109291 變成 3.7109291553497314 是同一件事）。寫成最短表示 8.850631，資訊一點也沒少：讀回 float32 是完全同一個數。

這對成績有影響嗎？沒有。pred.csv 寫下的就是模型算出的 float32 值本身；Kaggle 讀進去算 MSE 時，和完整精度的差異遠小於預測本身的誤差（真實 valid MSE 2.07，第 3 章）。值得知道的是另一件事：檔案裡的位數不代表模型的精度。模型只算到 float32，寫成 16 位小數是假的精確，寫成 7、8 位才是誠實的。

6.8　行尾：CRLF 與 newline=''

「一行結束」在檔案裡是一兩個看不見的位元組，叫行尾（line ending）。歷史上有兩種主流：

  • LF（line feed，換行），一個位元組，Python 字串裡寫成 \n。Linux 與 macOS 的文字檔用它。
  • CRLF（carriage return ＋ line feed，歸位加換行），兩個位元組，寫成 \r\n。Windows 的文字檔用它，許多網路協定也規定用它。

本機是 Linux，直覺上 pred.csv 應該是 LF。但本機實測，用二進位模式（'rb'，原封不動地讀位元組、不轉換行尾，指令見 6.10 節第 2 項）讀出檔案開頭：

b'id,tested_positive\r\n0,8.850631'

開頭的 b'...' 表示這是 bytes（位元組串，檔案裡原原本本的位元組），不是一般字串。表頭後面是 \r\n：每一行的結尾都是 CRLF，即使是在 Linux 上產生的。原因是 csv.writer 預設的行尾設定（lineterminator）就是 '\r\n'，不管在哪個作業系統。CSV 格式的規範 RFC 4180 規定行尾是 CRLF，csv 模組照規範寫；pandas 讀回來也完全正常（6.6 節）。在 Linux 上，這個檔案一切正常。

問題在 Windows：\r\r\n

問題出在第 41 行開檔的方式。Python 以文字模式開檔（'w' 沒有 b）時，寫入的每個 \n 會被換成「這個作業系統的行尾」：Linux 上維持 \n，Windows 上換成 \r\n。csv.writer 寫出的 \r\n 裡也有一個 \n，於是在 Windows 上它又被換一次：

檔案裡的位元組 多出來的 \r

\r\r\n 對許多工具來說是「一個 \r 結束一行，接著 \r\n 又結束一行」，中間夾了一個空行。用一般的文字工具看，pred.csv 就像每行之間都多了空白行；某些 CSV 讀取程式會把它讀成多出來的空列。

解法是 Python csv 模組文件明文建議的：開檔時加上 newline=''。這個參數告訴文字模式「不要轉換行尾」，讓 csv.writer 寫什麼就是什麼。第 41 行改成 with open(file, 'w', newline='') as fp:，任何系統上的結果都是圖 6.3 第一列的 CRLF。讀 CSV 時也一樣，文件建議用 newline='' 開檔再交給 csv.reader。

現在的做法：寫 CSV 的兩種寫法

  • 繼續用 csv 模組，就加上 newline=''，這是它的固定搭配，少了它就是本節的問題。HW01 在 Linux 上不受影響，但同一份程式在 Windows 上執行就會踩到。
  • 已經在用 pandas，就讓 pandas 寫。例如 pd.DataFrame({'id': x_test[:, 0].astype(int), 'tested_positive': preds}).to_csv('pred.csv', index=False)：id 直接取自測試集的 id 欄（6.6 節說的「更穩的做法」），index=False 避免 pandas 多寫一欄列號，行尾也由 pandas 自己處理。這行是示意，本書沒有實測它的輸出。

另外兩個實測把 id 的影響直接隔離出來：

  • 把 id 換掉：把原版模型在測試集上的 id 全部改成 1349（約是訓練集 id 的中位數）再預測，預測的平均只改變 +0.1305，MSE(預測, 第 4 天) 從 1.0045 變成 0.8888。id 確實有影響，但只有零點幾，解釋不了平均高出 5 的差距。
  • 拿掉 id 的模型也一樣：它在測試集上有 65 筆預測超過 30.3046，最大 44.8734，和原版的 61 筆、44.7035 同一個量級。沒有 id 的模型照樣預測出超過 30 的值。

（第 4 章說 id 在第一層的加權總和裡份量最大，這裡又說換掉 id 只影響零點幾，兩者不矛盾：前者量的是第一層內部的份量，後者量的是把 id 從測試集的 0–1077 換成訓練範圍中段的 1349 之後，最終預測移動多少。）

外推：在沒見過的範圍裡做預測

在訓練資料涵蓋的範圍之外做預測，叫外推（extrapolation）；在範圍之內則是內插（interpolation）。模型從沒見過答案超過 30.3 的例子，卻要對第 4 天已經 46.95 的那一列給出第 5 天的值。它的做法是把在範圍內學到的「第 5 天大約等於第 4 天再加一點」這個關係，延伸到範圍外：ReLU 對每個單元只做兩件事之一：原樣放行或輸出 0（第 4 章）。輸入往同一個方向一路變大時，走到夠遠之後，哪些單元放行、哪些輸出 0 就不再改變，整個網路便等於一串固定的 Linear 疊在一起，也就是一個線性函數。所以在訓練範圍之外，預測會沿著直線延伸：第 4 天越高，預測就跟著越高。

這次的外推大方向是合理的：前一天已經 46.95%，隔天多半不會一下掉回 30% 以下，預測 44.7 比「卡在訓練集最大值」合理得多。但它同時提醒一件事：驗證集量不到這種情況。驗證集是從訓練資料隨機切出來的（第 2 章），答案範圍和訓練集一樣，最大只到 29.8157（第 2 章的 y_valid 範圍）。模型在高陽性率時期表現如何，驗證集完全沒測到；Kaggle 的成績卻全部來自這段時期。目錄頁說「驗證方式要符合資料的性質」、第 1 章建議按時間切分，原因就在這裡。

改進模型（拿掉 id、標準化、按時間驗證、換優化器）是第 7 章的事，本章點到這裡。

    應該印出 state_dict 的型別 OrderedDict、6 個 key，以及第一層權重的第二個維度 117：不讀任何 CSV，就拿到了 predict.py 第 25–34 行花力氣算出的那個數字。這裡沒寫 weights_only，用的是 6.3 節驗證過的預設（效果為 True）。

本章重點

  • predict.py 的第 23–34 行和 train.py 第 103–114 行逐字相同，讀入、切分、選特徵五樣東西，只用到 x_test 與 x_train.shape[1]。這段繞路只花約 0.025 秒，問題不在速度，而在預測依賴訓練資料，以及 117 是「現在」重算的，和訓練時用的特徵之間沒有任何檢查。
  • 更好的做法是把 input_dim（最好連 feat_idx）和 state_dict 包成字典存進 checkpoint；torch 2.11 的 weights_only 預設實際等於 True，這種字典照樣能載入，含自訂類別的檔案則報 UnpicklingError。不改存檔格式的折衷：從 layers.0.weight 的形狀 (16, 117) 反推。
  • predict() 和驗證迴圈同一個樣子，但沒有 y、沒有 loss。第 17 行的 detach 多餘，.cpu() 不可少：GPU 上的 tensor 不能直接 .numpy()。5 個 batch 接成 (1078,) 的 float32 陣列。
  • pred.csv：表頭加 1,078 行，15,799 bytes，id 用 enumerate 從 0 數起；測試集的 id 欄正好是 0–1077 依序，所以對得上。test loader 若打亂，MSE(預測, 第 4 天) 從 1.0045 變成 120.0056，約是變異數 59.6773 的 2 倍：比每筆都猜平均還糟。
  • 數字寫成 float32 的最短表示（8.850631、4.1526003），位數不固定，但讀回去是同一個 float32。位數不代表精度。
  • csv.writer 一律寫 CRLF，Linux 上也是；save_pred 開檔沒加 newline=''，在 Windows 上會變成 \r\r\n。用 csv 模組寫檔就固定加 newline=''。
  • 測試集是陽性率更高的時期（第 4 天平均 15.17、最大 46.95）。模型的預測跟著第 4 天走，61 筆超過訓練集答案的最大值 30.3046：這是外推，不是 id 造成的。隨機切出的驗證集量不到這段時期的表現。

自我測驗

1. 有人想省掉切分，把 predict.py 第 26 行刪掉，第 39 行改成 My_Model(input_dim=train_data.shape[1])。會發生什麼事？

第 25 行讀進來的 train_data 是 2699 × 118，包含最後一欄答案，所以 shape[1] 是 118，不是 117。第 39 行建出 My_Model(118)，第 40 行載入時，layers.0.weight 的形狀 checkpoint 是 (16, 117)、模型是 (16, 118)，報第 4 章 4.8 節那種 size mismatch 錯誤（這是依 4.8 節的實測推論，118 這個版本本書沒有實際執行）。input_dim 是「選完特徵之後」的欄數，所以 predict.py 才非得把 select_feat 也跑一遍。

2. 把 predict.py 第 17 行改成 preds.append(pred)（不 detach、不 cpu），哪一行會出錯？錯誤訊息怎麼說？

第 17 行與 torch.cat 都不會出錯：5 個 GPU 上的 tensor 照樣能接起來，結果也在 GPU 上。出錯的是第 18 行的 .numpy()：TypeError: can't convert cuda:0 device type tensor to numpy. Use Tensor.cpu() to copy the tensor to host memory first.。少了 detach 則不會有任何影響，因為 no_grad 裡算出的 pred 本來就沒有計算圖。

3. 為什麼把預測打亂之後，MSE(預測, 第 4 天) 會接近第 4 天變異數的 2 倍，而不是 1 倍？

「每筆都猜平均」時，誤差只來自第 4 天自己的散開，一份變異數。打亂後，預測和被配到的第 4 天是兩個互不相干的數，而且預測本身也散得和第 4 天差不多開（兩者平均都約 15.17，6.9 節）。兩個獨立散開的量相減，差的平方平均是兩份變異數相加，所以約 2 倍：59.6773 × 2 ≈ 119，實測 120.0056。

4. 同學在 Windows 上執行 predict.py，用文字編輯器打開 pred.csv，發現每一行之間都多了空白行。原因是什麼？要改哪一行？

csv.writer 每行寫 \r\n，而 utils.py 第 41 行以文字模式開檔、沒加 newline=''，Windows 的文字模式又把其中的 \n 換成 \r\n，每行結尾變成 \r\r\n，被讀成兩次換行。改第 41 行：with open(file, 'w', newline='') as fp:。

5. pred.csv 裡有一筆寫成 4.1526003，有 8 位數字；第 3 章說 float32 只有約 7 位有效數字。多出來的那一位是假的嗎？

不是假的，也不是多出來的精度。NumPy 印出的是「能唯一還原成同一個 float32 的最短十進位數字」。在 4.15 附近，float32 的格子排得比較密，只寫 7 位不足以指名模型算出的那一格，所以要 8 位。「約 7 位」是平均的說法，實際需要幾位依數值而定，最多要 9 位（這是 float32 格式的性質，不是本書的實測）。

6. 61 筆預測超過訓練集答案的最大值。這代表模型壞了嗎？為什麼還是值得擔心？

不代表壞了：那些列的第 4 天陽性率本身就超過 30，預測跟著第 4 天走是合理的方向；拿掉 id 的模型也有 65 筆。值得擔心的是，模型在這個範圍裡是在外推，訓練時從沒見過這麼高的答案，驗證集（隨機切自訓練資料，最大 29.8）也完全測不到它在這裡準不準，而 Kaggle 的成績正是在這段時期上算的。

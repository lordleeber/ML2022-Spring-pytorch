5.2　準備工作：loss、優化器、SummaryWriter、models 目錄

第 29 行：criterion，量「錯多少」的尺

criterion（評判標準）是一個 nn.MSELoss 物件。它和模型一樣是 nn.Module，所以也是用「呼叫物件」的方式使用：criterion(pred, y) 回傳 pred 與 y 的均方誤差，也就是第 0 章 0.1 節的 MSE 公式。reduction='mean' 是對 batch 裡每一筆的平方誤差取平均（第 3 章 3.5 節比較過 'mean' 與 'sum'），而且這正是預設值，寫出來只是讓人一眼看見。註解「不要修改這個」是作業規定：Kaggle 用 MSE 評分（第 0 章 0.1 節），訓練時最小化的東西就該是 MSE。

這裡的 nn 是經由 from model import * 借來的（第 0 章 0.8 節），train.py 自己沒有 import torch.nn。

第 34 行：優化器，負責「改權重」的人

loss 只告訴你錯多少；真正動手改 2,033 個參數的是優化器（optimizer）。第 34 行建立的是 torch.optim.SGD，三個引數各有意義：

  • model.parameters()：要它負責哪些參數。第 4 章 4.2 節說過，這會沿著模型的名冊列出全部 6 個參數 tensor（共 2,033 個數字）。優化器把它們記在自己身上，之後每次 optimizer.step() 就去改這些 tensor。沒交給它的參數，它不會改。
  • lr=config['learning_rate']：學習率（learning rate），每一步要走多大，HW01 是 1e-5（0.00001）。5.4 節會看到它在公式裡的位置，5.10 節看它改大改小的後果。

5.3　epoch 迴圈與 model.train()

第 45 行的 epoch 從 0 數到 2999；印出來時都寫成 epoch+1，所以畫面上是 1 到 3000。

第 47 行 model.train() 把模型切成訓練模式。它做的事很單純：把模型和所有子模組的 training 旗標設成 True。有些層在訓練與評估時行為不同（第 4 章提過的 Dropout，以及 BatchNorm），它們看這個旗標決定怎麼算；Linear 與 ReLU 不看。所以對 HW01 來說它不改變任何計算：本機實測，同一個 batch 在 model.train() 與 model.eval() 下的輸出完全相同（torch.equal 為 True）。本機也實測，模型剛建立時 model.training 就已經是 True，預設就是訓練模式。

那為什麼每個 epoch 都要寫？因為這個 epoch 的結尾會呼叫 model.eval()（第 71 行），把旗標切成 False；下一個 epoch 開頭若不切回來，後面的訓練就全在評估模式下進行。在 HW01 這不會出事，但模型裡一旦加了 Dropout（第 7 章改模型時可能會加），訓練就會悄悄變成「沒有 Dropout 的訓練」。train() 與 eval() 成對出現、每個 epoch 都切換，是 PyTorch 訓練迴圈的固定寫法。

第 48 行準備一個空 list，收集這個 epoch 每個 batch 的 loss。第 51 行用 tqdm 把 train_loader 包起來：tqdm(...) 回傳的東西照樣可以用 for 迭代，一次給一個 batch，只是每給一個就順便更新進度條。leave=True 讓跑完的進度條留在畫面上，所以第 0 章看到的是每個 epoch 一條；position=0 是有好幾條進度條同時存在時的排列位置，這裡只有一條。

5.4　訓練五步驟：一個 batch 怎麼讓模型變好一點

這七行是整本書的核心。每個 epoch，這個迴圈跑 9 次（train 有 9 個 batch，第 3 章），每跑一次模型的 2,033 個參數就改一次。要讀懂這七行，得先知道它們在追求什麼：梯度。

梯度是什麼

第 4 章 4.3 節給過一句話的定義：梯度是「這個參數往哪個方向改一點，loss 會降多少」。展開來說：

挑模型裡的某一個參數 w，其他 2,032 個都不動，只把 w 加上一個很小的量 ε，loss 會跟著變一點。在 ε 很小的時候，loss 的變化量大約和 ε 成正比：

loss 的變化 ≈ g × ε
g 叫做 loss 對 w 的偏導數（partial derivative），也就是 w 這個方向上的「斜率」

g 是正的，表示 w 變大 loss 會變大，所以應該把 w 調小；g 是負的，就該調大；g 的絕對值越大，表示 loss 對 w 越敏感。把 2,033 個參數各自的 g 收集起來，就是 loss 對整個模型的梯度（gradient）。在 PyTorch 裡，每個參數的梯度存在它的 .grad 屬性，形狀和參數本身相同：layers.0.weight 是 (16, 117)，它的 .grad 也是 (16, 117)，一個參數對應一個斜率。

有了梯度，「讓 loss 變小」就有了最直接的作法：每個參數都往自己斜率的反方向走一小步。

w ← w − lr × g

這就是梯度下降（gradient descent），lr 就是第 34 行的學習率。為什麼只走「一小步」？因為斜率只描述 w 附近的情況：走遠了，地形可能已經不同，原本往下的方向可能變成往上。lr 決定了一步走多遠，5.10 節會看到走太遠的後果。

剩下的問題是：2,033 個斜率怎麼算？一個一個去加 ε 試，要跑 2,033 次 forward，太慢。PyTorch 用的方法是自動微分（autograd）：forward 時記下每一步運算，backward 時沿著記錄倒著走一遍，一次算出全部的梯度。下面五個步驟就是這件事的流程。

控制：清空與更新的動作 GPU 上的運算 loss（預測與答案的差距）

以下逐步拆開。本機照 train.py 的順序（same_seed → 切分 → DataLoader → 建立模型）準備好一切，拿第 1 個 epoch 的第 1 個 batch 一步一步執行、每步之後檢查狀態；所以下面的數字就是 train.py 真正跑的那第一步。

① 第 54 行 optimizer.zero_grad()：清掉上一步的梯度

第一步是清除。PyTorch 的 backward 不會覆寫 .grad，而是把新算出的梯度加到原有的值上。本機另做了一個實驗（不是下面那第一步的狀態）：模型不動，對同一個 batch 算兩次 loss、做兩次 backward，中間不清，最後一層 bias 的 grad 從 −57.9991 變成 −115.9982，剛好 2 倍。所以每個 batch 開始前要先清掉上一個 batch 留下的梯度，否則這一步會帶著之前所有 batch 的梯度總和去更新。

「清掉」在今天的 PyTorch 是把 .grad 設成 None，不是填 0（zero_grad 的 set_to_none 參數預設為 True，省掉一次寫 0 的工夫）。本機實測，還沒做過任何 backward 時 layers.0.weight.grad 就是 None，呼叫 zero_grad() 之後仍是 None。

為什麼不乾脆讓 backward 每次覆寫？因為「累加」有它的用處：記憶體放不下大 batch 時，可以連續對幾個小 batch 做 backward、讓梯度累加起來，再 step 一次，效果接近一個大 batch。代價就是平常每一步都得自己清。

② 第 55–56 行：搬上 GPU，算出預測

第 55 行兌現了第 2、3、4 章的說法：資料在這裡才搬上 GPU。DataLoader 交出的 x、y 在 CPU（第 3 章 3.4 節：pin_memory 只換一種記憶體，device 仍是 cpu）；模型在第 126 行已經搬上 GPU。一次運算的所有 tensor 必須在同一個裝置上（第 4 章 4.5 節），所以每個 batch 都要先搬。x.to(device) 回傳的是 GPU 上的新 tensor（複製，第 3 章），必須用 x, y = … 接住。整個 train loader 只有 2,160 筆，其實可以一開始全部搬上 GPU，但「每個 batch 搬一次」是通用寫法：資料大到 GPU 放不下時也能用。

第 56 行 pred = model(x) 就是第 4 章圖 4.2 的整條呼叫鏈，輸出 (256,) 的預測。這裡多了一件第 4 章沒講的事：forward 的同時，PyTorch 在記帳。因為參數的 requires_grad 是 True（第 4 章 4.3 節），凡是用到它們的運算，PyTorch 都會記下「這個結果是由哪個運算、從哪些輸入算出來的」。這些記錄連起來，叫計算圖（computational graph）：起點是參數與輸入，經過 Linear、ReLU、squeeze，一路連到 pred。

本機實測，pred.requires_grad 是 True，pred.grad_fn 是 SqueezeBackward1。grad_fn 指向「產生這個 tensor 的那個運算」在計算圖裡的節點：pred 是 squeeze(1) 算出來的（model.py 第 24 行），所以是 Squeeze。名字裡的 Backward 表示這個節點知道「反向時該怎麼算」。

③ 第 57 行：算 loss

loss = criterion(pred, y) 算出這個 batch 的 MSE，計算圖也延伸到 loss。本機實測，第 1 個 batch 的 loss 逐字是：

tensor(508.8512, device='cuda:0', grad_fn=<MseLossBackward0>)

三個資訊：值 508.8512（還沒訓練的模型，平均每筆偏了 √509 ≈ 22.6 個百分點）；它在 GPU 上；它由 MSE 運算產生，是計算圖的終點。loss.item() 是 508.8511657714844，和自己用 ((pred-y)**2).mean() 算的完全相同，MSELoss 沒有任何神秘之處。第 2 個 batch 的 loss 是 136.3234：第 1 步之後，模型已經好了很多。

注意 loss 是一個 0 維 tensor（第 3 章），一個數字。這很重要：梯度是「這一個數字」對每個參數的斜率，backward 只能從一個數字出發。這也是 reduction='mean' 的另一層意義：把 256 個平方誤差合成一個數。

④ 第 58 行 loss.backward()：反向算出所有梯度

loss.backward() 從 loss 出發，沿計算圖倒著走回每個參數。每經過一個節點，就用該運算的局部斜率把梯度往前傳一層：loss 對 pred 的斜率，乘上 pred 對最後一層輸出的斜率，再乘上那一層對它的權重的斜率……這種「斜率一層一層相乘」的規則是微積分的連鎖律（chain rule），用在神經網路上的這套倒著算的方法叫反向傳播（backpropagation）。走完之後，每個參數的 .grad 都有了值。本機實測第 1 個 batch backward 之後：

backward 做完，計算圖就被釋放了（中間結果佔的記憶體跟著還回去）。本機實測，對同一張圖再 backward 一次會報錯，開頭是：

RuntimeError: Trying to backward through the graph a second time (or directly access saved tensors after they have already been freed).

所以前面「backward 兩次、梯度變 2 倍」的實驗，第二次要重新 forward、重新算 loss，建一張新圖。訓練迴圈每個 batch 本來就會重新 forward，正好每次一張新圖、用完即丟。

為什麼 id 欄的梯度特別大

第一層的輸出是 out[n, j] = Σi x[n, i] · W[j, i] + b[j]（第 4 章圖 4.1）。W[j, i] 動一點 ε，out[n, j] 就動 x[n, i] · ε：這個權重的局部斜率就是它乘的那個輸入 x[n, i]。連鎖律再把它乘上「下游」（從這一層往 loss 那一端）傳回來的斜率；loss 是 batch 裡 256 筆誤差的平均，每一筆都經由這個權重影響 loss，所以梯度是每一筆的貢獻加總（再除以 256），所以第一層權重的梯度，和它所乘那一欄的數值大小大致成正比。第 1 章 1.4 節說「梯度和那欄的數值大小成正比」，說的就是這一步。

本機實測第 1 個 batch：

id 欄其他 116 欄的平均倍數
這個 batch 的平均 |x|1348.715.75約 86 倍
第一層 weight 梯度的平均 |g|2602.0824.13約 108 倍

兩個倍數在同一個量級，不完全相等，因為梯度還乘上了下游傳回來的斜率，每筆資料各不相同。bias 沒有乘任何輸入（等於乘 1），所以第一層 bias 的梯度小得多（範數 8.78 對 weight 的 15824.6）。

同一個式子也解釋了第 4 章 4.7 節「死掉的 ReLU 回不來」：ReLU 在輸入為負時輸出固定是 0，它的局部斜率是 0；連鎖律一路相乘，傳到那個單元的權重時就是 0，step 時那些權重一動也不動。

⑤ 第 59 行 optimizer.step()：依梯度改權重

step() 走過第 34 行交給它的每個參數，讀它的 .grad，依 SGD 的規則修改參數。有 momentum 時，PyTorch 的 SGD 對每個參數多存一個同形狀的 momentum buffer（記在 optimizer 身上，不在模型裡），規則是：

buf ← 0.9 × buf ＋ grad
w ← w − lr × buf
第一步時 buf 還不存在，直接令 buf ＝ grad

本機逐步驗證了這兩行：第一步之後 buffer 等於這一步的 grad（torch.allclose 為 True）；第二步照上面的公式手算，和 PyTorch 實際的結果吻合。buf 是梯度的累積：每一步把舊的 buf 打九折、再加上新的梯度。梯度方向一致時，buf 會越積越大（一直同方向時最多累積到約 1 ÷ (1 − 0.9) = 10 倍的梯度，這是公式推得的上限，不是實測），步伐跟著變大；方向來回擺盪時，正負互相抵銷，步伐變小。它像一顆有慣性的球：被同一個方向一直推就加速，被左右亂推就不太動。每一步只看一個 batch 的梯度帶著雜訊（SGD 的「隨機」），momentum 等於把最近幾十步的梯度平均起來用。

第一步：id 欄的權重一步走完整個初始範圍

第一步沒有歷史可言，buf 就是 grad，所以第一步就是最樸素的 w ← w − 1e-5 × grad。本機實測，第一步權重的變化量 Δw 和 −lr × grad 最大只差 7.45e-09（浮點數誤差）。

把數字代進去：第一層 weight 最大的 |g| 是 8688.2920，乘上 1e-5 是 0.0869。本機實測第一步第一層最大的 |Δw| 正是 0.0869，而且就在 id 欄。第 4 章 4.4 節看過，第一層的初始權重在 ±0.0925 之內：只走一步，id 欄的權重就移動了幾乎一整個初始範圍，其他欄的梯度小了約百倍，移動量也小了約百倍。第 4 章 4.7 節看到訓練完的 id 權重平均 |w| 是 0.22643、遠超出初始範圍，起點就在這裡：id 欄從第一步開始就被推得最猛。

反過來看，lr = 1e-5 這個看起來小得出奇的值，其實是被 id 欄逼出來的：梯度動輒幾千，學習率只要大一點，一步就會走出很遠（5.10 節的 lr 1e-4 就是這樣壞掉的）。輸入標準化之後，梯度的量級會正常得多，學習率也就能用比較常見的大小——這是第 7 章的事。

現在的做法：五步驟不變，周邊多了幾樣

  • 五步驟本身沒有過時。2026 年手寫 PyTorch 訓練迴圈，核心仍是 zero_grad → forward → loss → backward → step。zero_grad 放在 backward 之前任何位置都可以，常見的另一種寫法是放在 step 之後。
  • 優化器的預設選擇多半是 AdamW。它替每個參數依梯度的歷史自動調整步幅，對輸入尺度、學習率都比 SGD 寬容。SGD＋momentum 仍然常用，但很少是第一個嘗試的。換優化器是作業 strong 基準線的提示之一，第 7 章實測。
  • 梯度裁剪（gradient clipping）。在 backward 與 step 之間加一行 torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm)，梯度的總範數超過上限時等比例縮小，防止某一步走得太遠。第 1 個 batch 第一層 weight 的梯度範數就有一萬多，這類情況正是它的用途。

第 67 行：mean_train_loss 量的是什麼

第 67 行把 9 個 batch 的 loss 加總除以 9，和第 3 章 3.5 節讀過的 valid loss（第 81 行）是同一種「平均的平均」：train 最後一個 batch 只有 112 筆，卻和 256 筆的 batch 佔一樣的份量。但 train loss 還有一個 valid loss 沒有的特性：9 個 batch 的 loss 來自 9 個不同的模型。每個 batch 先算 loss、再 step，所以第 k 個 batch 的 loss 是「被前 k−1 步改過的模型」量的，量完這個模型又被改了一次。mean_train_loss 是整個 epoch 裡一路變化的模型的平均表現，不是任何一個固定模型的 MSE。

第 1 個 epoch 最能看出這一點：第一個 batch 的 loss 是 509，第 9 個是 60.4，平均出來的 train loss 是 134.2442；而 epoch 結束時（已經更新 9 次的模型）量到的 valid loss 是 107.2155。train loss 比 valid loss 高，不是模型在驗證集上表現比較好，而是 train loss 包含了 epoch 開頭那幾個還很差的模型。

訓練後段每一步改得很少，這個落差就小了。本機實測，第 1483 個 epoch 印出的 train loss 是 1.8014；把那個 epoch 結束時存下的 checkpoint 拿到整個訓練集上一次算完，真實 MSE 是 1.7938，差距只有 0.008。對照驗證集：同一個 checkpoint 的真實 valid MSE 是 2.0685（第 3 章）。

5.7　存最佳模型：創新低才存

第 85 行比較這個 epoch 的 valid loss 和目前的最低紀錄，嚴格小於才算創新低。是的話：更新紀錄（第 86 行）、存檔（第 88 行）、印一行（第 89 行）、把連續沒進步的計數歸零（第 90 行）；不是的話計數加 1（第 92 行）。

第 88 行存的是 model.state_dict()，第 4 章 4.3 節看過的那個「名字 → tensor」字典，6 個 key，共 2,033 個數字。torch.save 把它序列化寫進 ./models/model.ckpt，每次都寫同一個路徑，所以新的最佳會覆蓋舊的最佳，訓練結束時檔案裡只有最後一次創新低的模型。只存 state_dict、不存整個模型物件，是 PyTorch 官方建議的做法：檔案裡只有數字，載入時由 model.py 重建結構再填回去（第 4 章 4.8 節、第 6 章），程式碼改了路徑或類別也不受影響；存整個模型物件則會在檔案裡記下「這個物件屬於哪個模組的哪個類別」，載入時要能找到一模一樣的類別，改名或搬檔就讀不回來。第 89 行用 {:.3f} 只印到小數第三位，所以 log 裡是 Saving model with loss 1.661...，而上一行的 Epoch 那行有四位 1.6611。

為什麼要「最佳時存」，而不是訓練完存最後一個？因為最後一個不一定最好：本機實測，最後一個 epoch（第 1883 個）的 valid loss 是 2.5030，比第 1483 個的 1.6611 高得多。用驗證集挑一個最好的時間點，是在不知道「訓練多久才剛好」的情況下最直接的辦法。

每個 epoch 的 valid 分組，來自 PyTorch 全域產生器（第 3 章 3.4 節）；same_seed 固定了起點，所以 train.py 每個 epoch 用的分組可以完整重建。本機照原流程重建了全部 1,883 個 epoch 的 valid 打亂順序，拿第 1483 個 epoch 存下的 checkpoint 去量：用第 1483 個 epoch 的分組，正好重現 1.6611，證明重建是對的。接著讓同一個模型配上全部 1,883 種分組：

更有說服力的是對照組。本機把學習率改成 1e-6 重新訓練（5.10 節）：學習率小了 10 倍，模型的軌跡完全不同，存檔 76 次，但最佳也落在第 1483 個 epoch（印出 1.818），也在第 1883 個 epoch 停止。拿它的 checkpoint 去量，第 1483 個 epoch 的分組量到 1.8176，在它自己的 1,883 種分組裡排第 5 低（中位數 2.2278）。

為什麼兩次訓練會選中同一個 epoch？因為每個 epoch 的分組只由全域產生器決定：train 與 valid 的打亂每個 epoch 各抽一次亂數，抽多少和學習率無關，所以兩次訓練在第 k 個 epoch 拿到的是一模一樣的分組。第 1483 個 epoch 的分組對兩個不同的模型都特別「友善」，兩次訓練便都在那裡創下紀錄，又都在 400 個 epoch 後停止。「最佳 epoch」有相當一部分是被分組決定的，不是被模型決定的。這也具體說明了第 3 章那句副作用：被存下的 checkpoint，不一定是真實表現最好的那一個。

現在的做法：存得更完整，挑得更誠實

  • 先把量法修好。第 3 章 3.5 節的修正版（驗證不打亂、依筆數加權）讓每次比較都是同一個量尺，創新低才代表模型真的進步；本章的「幸運分組」就不會發生。
  • 存檔時連同訓練狀態一起存。常見的格式是一個字典：{'model': model.state_dict(), 'optimizer': optimizer.state_dict(), 'epoch': epoch, 'best_loss': best_loss}。optimizer 的 state_dict 包含 5.4 節的 momentum buffer，少了它，中斷後接著訓練時 momentum 要重新累積。通常也會另外存一份「最後一個 epoch」，和「最佳」分開。
  • 建目錄用 os.makedirs(path, exist_ok=True)（或 pathlib.Path(...).mkdir(parents=True, exist_ok=True)）一行完成，取代第 40–41 行的先檢查再建立；多層目錄也能一次建好。

5.8　early stopping：連續 400 次沒進步就停

early_stop_count 記的是「距離上次創新低已經幾個 epoch」：創新低時歸零（第 90 行），否則加 1（第 92 行）。第 94 行檢查它是否達到 config 的 early_stop（400），達到就印出訊息、return 離開 trainer()，主程式也隨之結束。訊息字串開頭的 \n 是換行，所以第 0 章的 log 裡，這句話前面有一行空白。

原版的過程：第 1483 個 epoch 創新低、計數歸零，之後第 1484 到第 1883 個 epoch 每次加 1，第 1883 個 epoch 結束時計數到 400，停止。這就是第 0 章 1483 + 400 = 1883 的來歷。

early stop 的用意是：valid loss 很久沒有進步，再訓練下去多半只是在訓練集上越練越熟（train loss 繼續降、valid loss 不再降甚至上升），浪費時間。400 就是「多久算很久」，它和 n_epochs 一起決定了訓練最長跑多久：

  • n_epochs（3000）是硬上限，不管有沒有進步，跑滿就停。第 3 章動手做第 4 項修好量法後的訓練，就是一直到第 3000 個 epoch 都還在創新低，跑滿上限才停。
  • early_stop（400）是耐心。設得太小，會在進步變慢的高原期誤停；設得太大，就要多跑很多無用的 epoch。從上一節的存檔紀錄可以推算：原版在第 1260 個 epoch 之後隔了 223 個 epoch 才再創新低，所以如果 early_stop 設成 200，訓練會在第 1260 + 200 = 1460 個 epoch 停下，最佳停在第 1260 個 epoch（第 1260 個之前，存檔間隔最長是第 686 到第 860 個 epoch 的 174，不到 200）。本機實際把 early_stop 改成 200 跑了一次，結果正是如此：最後一次存檔是 Epoch [1260/3000]: Train loss: 1.7980, Valid loss: 1.7165，最後一個 epoch 是第 1460 個，共存檔 48 次（原版的 49 次少了第 1483 個那一次）。

還要注意：early stop 看的是 valid loss，所以它和存檔一樣受第 3 章的雜訊影響。原版的 1.661 是靠一組幸運的分組量到的低值，之後的 400 個 epoch 裡，模型就算真的進步一點，也很難在雜訊下打破這個偏低的紀錄。第 3 章修好量法後不再 early stop，正是這個原因的反面證據。

  • 多記幾條曲線。學習率（若有使用學習率排程，也就是讓 lr 隨訓練進度逐步變小的做法）、梯度範數、每個 epoch 花的時間都是常見的記錄項目；5.10 節 lr 1e-4 的情況，光看 loss 曲線看不出模型已經只會輸出常數，多記一條「預測值的標準差」就一目了然。
  • 今天也常用 Weights & Biases、MLflow 這類記錄服務，概念和 add_scalar(tag, value, step) 一樣。

lr 1e-4：模型壞到只會輸出一個常數

學習率只大了 10 倍，結果完全崩壞。第 1 個 epoch 的 train loss 是 2,005,349.0116（兩百萬），valid 112.8123；第 2 個 epoch 是 67.2213／64.5274，之後停在 40 左右。一個 epoch 的 train loss 是 9 個 batch 的平均，平均兩百萬，代表這個 epoch 裡至少有一個 batch 的 loss 達到兩百萬以上：崩壞發生在最初的幾步。

從 5.4 節可以推算為什麼。第一步時 buf 就是 grad，而第一步的 grad 和學習率無關（同樣的初始權重、同樣的第一個 batch），所以 lr 1e-4 的第一步就是原版第一步的 10 倍：id 欄的權重一步移動約 0.87，將近初始範圍的 10 倍。id 動輒上千，乘上這樣的權重，第一層的加權總和一下子被推到幾百、幾千的量級，正負都有可能。

結局是本機實測的：第一層 16 個單元全部永遠輸出 0，這是第 4 章 4.7 節 dying ReLU 推到極端的樣子。第一層全死，第二層收到的永遠是 16 個 0，它和最後一層只剩 bias 在起作用，整個模型對每一筆輸入都輸出同一個數字：本機實測是 9.731，預測的標準差是 0。

既然只能輸出常數，訓練能做的就只剩把那個常數調到讓 MSE 最小的位置，也就是訓練集答案的平均。9.731 和訓練集答案的平均 9.7404（第 2 章）幾乎相同。它的真實 MSE 44.5095，和「永遠猜訓練集平均」的 44.5021、驗證集答案本身的變異數 44.346 幾乎一樣：這個模型等於什麼都沒學到。

log 看不出模型已經死了

lr 1e-4 的訓練照樣存檔 13 次、照樣 early stop，log 的格式和原版一模一樣，印出的最佳 36.157 看起來只是「比較差」。從 stdout 完全看不出模型已經只會輸出常數。這再次說明目錄頁「先做 baseline」的價值：只要知道「永遠猜平均」的 MSE 是 44.5，看到 36（以及它的真實值 44.5）就會立刻起疑。檢查預測值的標準差，或像第 4 章那樣數一數沒在工作的單元，都只要幾行程式。

lr 1e-6 與 momentum 0：走得太慢

學習率小 10 倍的那組，沒有崩壞，但真實 MSE 2.2601 比原版差：每步太小，同樣的時間內走不到那麼遠。它的最佳 epoch 和原版同是 1483，原因在 5.7 節。

拿掉 momentum（momentum 0，每一步就是單純的 w − lr × grad）的那組，進步慢很多：3,000 個 epoch 都沒觸發 early stop，表示它一直到上限都還在緩慢創新低，最後真實 MSE 2.9992，是三組正常訓練裡最差的。同樣的學習率下，momentum 讓有效步伐在方向一致時放大，這組對照就是它的效果。

四組實驗同時在一張 GPU 上跑，各花了 38.6 秒（原版）、19.3 秒（lr 1e-4，只跑到第 798 個 epoch）、38.1 秒（lr 1e-6）、56.8 秒（momentum 0，跑滿 3000）；單獨跑原版是 34.2 秒（第 0 章）。所花的時間大致和跑了幾個 epoch 成正比。

這四組只是單一變因的對照，不是在找最好的設定。真正要改進模型，第 4 章與第 2 章都指向同一個方向：先處理輸入的尺度（id 與標準化），再調學習率、換優化器。那是第 7 章的工作。

本章重點

  • trainer() 先準備一次（MSELoss、SGD、SummaryWriter、models/、計數器），再對每個 epoch 做四件事：訓練 9 個 batch（更新 9 次）、驗證 3 個 batch（不更新）、創新低就存檔、連續 400 次沒進步就停。
  • 梯度是 loss 對每個參數的斜率，存在 .grad、形狀和參數相同；梯度下降讓每個參數往斜率的反方向走一小步。五步驟：zero_grad 清掉累加的梯度 → .to(device) 與 model(x) 算預測並建出計算圖 → criterion 算 loss → backward 用連鎖律反向算出全部梯度並釋放計算圖 → step 依 buf ← 0.9·buf + grad、w ← w − lr·buf 改權重。
  • 第一層權重的梯度和它所乘的輸入成正比：第 1 個 batch 裡 id 欄的梯度約是其他欄的 108 倍，第一步就讓 id 欄的權重移動 0.0869，幾乎一整個初始範圍。
  • train loss 是 9 個「一路在變的模型」的 batch loss 平均，第 1 個 epoch 因此是 134 而 valid 是 107；後段兩者的落差變小（第 1483 個 epoch 印出 1.8014，checkpoint 的真實 train MSE 1.7938）。
  • model.train()／eval() 只切換 training 旗標，HW01 沒有受影響的層；torch.no_grad() 才是停止建計算圖的那一個。
  • 存檔只存 state_dict、每次覆寫同一個檔；49 次存檔越來越稀疏，第 1483 個 epoch 之後 400 次沒進步而停止。第 1483 個 epoch 的分組在 1,883 組裡排第 7 幸運，lr 1e-6 的訓練也選中同一個 epoch：最佳 epoch 有一部分是分組決定的。
  • TensorBoard 的兩條曲線來自第 68、83 行的 add_scalar，橫軸是更新次數 step（每個 epoch 9），不是 epoch。
  • lr 1e-4 讓第一層 16 個單元全死，模型只會輸出 9.731（≈ 訓練集答案平均），真實 MSE 44.5；log 卻和正常訓練一樣。lr 1e-6 與 momentum 0 則是走得太慢。

自我測驗

1. 把第 54 行 optimizer.zero_grad() 刪掉，程式會報錯嗎？訓練會變成什麼樣子？

不會報錯。backward 會把梯度加到 .grad 上而不是覆寫，所以每一步 step 用的是「從訓練開始到現在所有 batch 的梯度總和」，而且 momentum 還會再把它累積一次。步伐會越來越大、方向越來越被很久以前的梯度主導，很容易像 lr 1e-4 那樣崩壞。本機的累加實驗：同一個 batch backward 兩次，梯度剛好變 2 倍。

2. 為什麼第 1 個 epoch 的 train loss（134.2442）比 valid loss（107.2155）高？這代表模型在驗證集上比較準嗎？

不代表。train loss 是 9 個 batch 的 loss 平均，每個 batch 量的是「當時」的模型：第 1 個 batch 時模型還沒訓練（loss 509），第 9 個時已經更新 8 次（60.4）。valid loss 則是 epoch 結束後、更新 9 次的模型量的。train loss 被 epoch 開頭那幾個很差的模型拉高了。

3. 驗證迴圈裡如果忘了寫 with torch.no_grad():，valid loss 的數值會變嗎？如果忘了寫 model.eval() 呢？

忘了 no_grad：數值不變，只是多建了沒用的計算圖，浪費記憶體與時間；驗證迴圈沒有 backward 與 step，權重也不會被改。忘了 eval()：在 HW01 也不變（本機實測兩種模式輸出完全相同，因為沒有 Dropout、BatchNorm），但模型一旦加了這類層，驗證就會在訓練模式下進行，數值會不同。而且下一個 epoch 開頭的 model.train() 仍然要寫，兩者是成對的。

4. 只把 config 的 early_stop 改成 200，其他不動，訓練會在第幾個 epoch 停？存下來的是第幾個 epoch 的模型？

early_stop 只影響何時停，不影響停之前的任何計算（亂數、權重、分組都相同），所以存檔紀錄和原版一模一樣，直到停止為止。原版的存檔 epoch 中，第一個超過 200 的間隔是第 1260 到第 1483 個 epoch 的 223，所以會在第 1260 + 200 = 1460 個 epoch 停止，存下的是第 1260 個 epoch 的模型。這是依 5.7 節的存檔紀錄推算的，本機也實際跑過一次確認（5.8 節）。想自己驗證：照動手做第 4 項的方式備份 config.py，把第 16 行的 400 改成 200，執行 ../.venv/bin/python train.py 2>/dev/null > es200.log，再用 grep -B1 Saving es200.log | tail -2 看最後一次存檔（應是 Epoch [1260/3000] 那行），grep Epoch es200.log | tail -1 看最後一個 epoch（應是 Epoch [1460/3000]）。做完照第 4 項末尾的方法還原 config.py 並重跑原版。

5. 在 TensorBoard 上，橫軸 step 900 附近的點是第幾個 epoch？如果 batch_size 改成 128 呢？

batch_size 256 時每個 epoch 9 個 batch，step 900 是第 100 個 epoch 結束時寫入的點。batch_size 128 時，2160 ÷ 128 = 16.875，無條件進位是 17 個 batch（第 3 章），step 900 約是第 53 個 epoch（17 × 53 = 901）。橫軸是更新次數，換 batch_size 就換了比例。

6. lr 1e-4 的模型印出最佳 36.157。你手上只有 stdout 的 log，怎麼判斷它是「比較差」還是「完全壞掉」？

拿它和最簡單的 baseline 比：永遠預測訓練集答案平均的 MSE 是 44.5（驗證集答案的變異數 44.346），36～44 這個量級等於什麼都沒學到；再考慮第 3 章說印出值偏低，真實值只會更高（實測 44.5095）。要確認，就載入 checkpoint 看預測的標準差（實測是 0，全部輸出 9.731）或數第一層沒在工作的單元（16/16）。

這是 2022 年的作業

動手之前，請先讀目錄頁的〈先說在前面：用 2026 年的眼光讀 2022 年的作業〉：哪些已經過時（環境與 API、部分方法）、哪些沒有（訓練流程的觀念），以及一個值得記住的實測結果——在同一個驗證集上，直接拿第 4 天的陽性率當預測（MSE 1.313），就贏過範例程式的神經網路（2.069）。

0.1　作業要預測什麼

資料來自卡內基美隆大學 Delphi 研究群：他們從 2020 年 4 月起透過 Facebook 每天在美國各州發問卷，問受訪者有沒有發燒咳嗽、最近有沒有戴口罩、有沒有去餐廳、心情焦不焦慮等問題，再把每州每天的回答統計成百分比。其中一個欄位 tested_positive 是「受檢者中檢驗陽性的比例」，也是我們要預測的目標。

作業把資料整理成這樣：每一筆（一列）代表某一州、連續 5 天的統計。前 4 天的所有欄位（包含 tested_positive）都給你，第 5 天則只給問卷欄位、不給 tested_positive。你的模型要根據這些數字，輸出第 5 天的 tested_positive——一個實數。輸出是連續值而不是類別，所以這叫迴歸（regression）。

成績怎麼算？作業投影片寫明評估指標是均方誤差（Mean Squared Error, MSE）：

MSE = (1/N) · Σ (預測值i − 真實值i)²

差距平方後取平均，所以越小越好；預測偏 1 個百分點貢獻 1，偏 3 個百分點貢獻 9，大錯會被重罰。你在 Kaggle（一個舉辦資料科學競賽的網站，課程在上面開了這份作業的排行榜）上傳 pred.csv，網站用隱藏的正確答案算出你的 MSE；助教事先設了 simple／medium／strong／boss 四條分數門檻（基準線），每超過一條就多拿分。助教提供的範例程式能過 simple；後面三條要靠第 7 章的改進。本書不談上傳流程，只談程式。

一句話記住這個作業

輸入：一列 117 個數字（1 個編號 id、37 個代表「哪一州」的欄位、5 天的問卷統計，第 1 章逐欄拆給你看）。輸出：第 5 天的陽性率（1 個數字）。訓練目標：讓預測和真實值的 MSE 盡量小。

重點在第 14–20 行：nn.Sequential 把五個元件依序串起來，資料從上往下流過。只有兩種元件：

  • nn.Linear(a, b)（全連接層）：把 a 個輸入數字各乘上一個權重再加總、加上一個偏差（bias），算出 b 個輸出。每個輸出都連到全部輸入，所以叫「全連接」。權重與偏差就是模型要學的參數。

0.3　環境：為什麼不能照原本的 requirements 裝

先認識兩個名字。PyTorch（套件名 torch）是用來建立與訓練神經網路的 Python 函式庫，本作業的模型就是一個小型神經網路。CUDA 是 NVIDIA 提供的一套讓程式在顯卡上做運算的平台（驅動程式之上的函式庫與編譯工具）；PyTorch 要用顯卡，就是透過 CUDA。所以 GPU 版 PyTorch 的版本號會連帶標明它是用哪一版 CUDA 編譯的，例如 cu116 就是 CUDA 11.6。

本 repo 原本的 requirements.txt 第一行是 pip install torch==1.13.1+cu116 …，也就是 2022 年課程當時的 PyTorch 1.13 搭 CUDA 11.6。這組版本在這台機器上有兩個無法繞過的問題：

  1. 顯卡太新。本機是 NVIDIA RTX PRO 4000 Blackwell，運算能力（compute capability）是 12.0，PyTorch 的說法叫 sm_120。這個數字不是效能分數，而是顯卡架構世代的版本號：同一世代的指令集相同，新世代會有舊程式不認得的指令。PyTorch 的 GPU 程式（kernel）是事先針對特定 sm 版本編譯好放進安裝包的；1.13 的安裝包裡根本沒有 sm_120 的 kernel，CUDA 11.6 也不認識這代架構。要支援 Blackwell，至少要 CUDA 12.8 版的安裝包（cu128）。
  2. Python 太新。本機是 Python 3.12，而 PyTorch 1.13 沒有為 3.12 發布過安裝包，pip 會直接找不到可裝的版本。

所以這次改用 PyTorch 2.11 的 cu128 版本，並把 requirements 改成實際安裝的版本：

重點在第 3–5 行。一般套件從 PyPI 下載；但 GPU 版 PyTorch 放在 PyTorch 自己的伺服器上，依 CUDA 版本分目錄，--extra-index-url 告訴安裝工具「除了 PyPI 之外也去 cu128 那個目錄找」。版本號後面的 +cu128 就是指定「CUDA 12.8 編譯的那一份」。其餘套件各司其職：numpy／pandas 處理表格、tqdm 畫進度條、tensorboard 記錄並顯示訓練曲線、matplotlib 畫圖，torchvision 是 PyTorch 的影像工具包（這兩個 HW01 都用不到，其他作業會用；torchvision 必須和 torch 版本配對，所以也要從 cu128 目錄裝）。

建立環境

這個 repo 有八份作業，大多可以共用同一個環境，所以虛擬環境（venv，一個與系統 Python 隔開的獨立套件目錄）建在 repo 根目錄的 .venv。這裡用 uv 這套比 pip 快很多的安裝工具。以下指令都在 repo 根目錄執行；第一行的 ~/poyi/GitHubPoyi/ML2022-Spring-pytorch 是作者機器上的位置，請換成你自己 clone 這個 repo 的目錄：

$ cd ~/poyi/GitHubPoyi/ML2022-Spring-pytorch
$ uv venv .venv --python 3.12
$ UV_HTTP_TIMEOUT=600 uv pip install --python .venv -r requirements.txt

UV_HTTP_TIMEOUT=600 把下載逾時放寬到 600 秒。這種「變數=值 指令」的寫法是 shell 語法：只替後面這一條指令設定環境變數，指令結束就失效，不必先 export。GPU 版 PyTorch 會連帶下載十幾個 NVIDIA 函式庫，其中 cuFFT、cuDNN 等單檔就有數百 MB；在這台機器的網路上用預設逾時，第一次安裝就卡在 cuFFT 失敗過。裝好之後確認 PyTorch 真的看得到顯卡：

$ .venv/bin/python -c "import torch; print(torch.__version__, torch.cuda.is_available(), torch.cuda.get_device_name(0), torch.cuda.get_device_capability(0)); print(torch.cuda.get_arch_list())"
2.11.0+cu128 True NVIDIA RTX PRO 4000 Blackwell (12, 0)  «1»
['sm_75', 'sm_80', 'sm_86', 'sm_90', 'sm_100', 'sm_120']  «2»
  1. 1版本確實是 cu128；is_available() 為 True；(12, 0) 就是 compute capability 12.0，即 sm_120。
  2. 這份 PyTorch 內建了哪些架構的 kernel。最後一個 sm_120 正是本機需要的——這一行就是「cu128 才能用」的直接證據。

現在的做法：pyproject.toml + uv.lock

requirements.txt 只記下「直接」用到的套件版本；torch 自己又依賴十幾個 NVIDIA 函式庫，那些的版本沒被記下來，換一台機器重裝可能就不一樣。2026 年常見的做法是把專案寫成 pyproject.toml，由 uv 產生一份 uv.lock，鎖住每一個相依套件（含間接相依）的確切版本與來源。以 torch 為例：

$ uv init --bare --python 3.12
$ uv add "torch==2.11.0" --index pytorch-cu128=https://download.pytorch.org/whl/cu128
$ uv sync

uv add 會把相依與套件來源一起寫進 pyproject.toml：

[project]
dependencies = [
    "torch==2.11.0",
]

[tool.uv.sources]
torch = { index = "pytorch-cu128" }

[[tool.uv.index]]
name = "pytorch-cu128"
url = "https://download.pytorch.org/whl/cu128"

同時產生的 uv.lock 裡記著 torch 2.11.0+cu128 來自 cu128 那個目錄，連同其他 29 個間接相依套件的版本（在空目錄實測：共解析出 30 個套件）。uv sync 依照 lock 檔建出 .venv，任何人、任何時候執行都得到同一組版本。本 repo 為了貼近課程原貌仍用 requirements.txt，但新專案建議直接用這套。

0.4　config.py：全專案的設定中心

跑之前先看一眼設定檔，因為它決定了你等一下會看到的所有數字：

先解釋一個會反覆出現的詞：驗證集（validation set）。訓練時模型只從訓練集學；另外保留一小部分有答案、但模型訓練時沒看過的資料，專門拿來打分數，藉此判斷模型是「真的學會」還是「只是背下訓練資料」。這一份就是驗證集，valid_ratio 決定切多少出來。測試集則是作業給的、沒有答案的那 1078 筆，只用來產生要上傳的預測。

注意第 12 行的註解寫 validation_size = train_size * valid_ratio，但這和實際行為不符：程式是用切分前的全部資料乘以 0.2（2699 × 0.2 → 539），不是訓練集 2160 × 0.2 = 432。等一下的輸出會印出 539，第 2 章再對照程式碼說明。

下半部的 config 字典是超參數（hyperparameter）：由人決定、不靠訓練學出來的設定。其中 seed（亂數種子）是亂數產生器的起點：訓練中有好幾處需要亂數（模型權重的初始值、資料切分、每個 epoch 打亂資料順序），固定 seed 就讓每次抽出的亂數序列都一樣。每一項後面各章都會講到——seed 與 valid_ratio 在第 2 章、batch_size 在第 3 章、learning_rate、n_epochs、early_stop 在第 5 章、select_all 在第 2 章與第 7 章。現在只要知道：想調整訓練行為，先來這裡改。

上半部的 device 決定模型與資料放在哪個裝置上計算。'cuda' 代表 NVIDIA 顯卡，'cpu' 代表處理器。

設計選擇：沒有 CUDA 就立刻失敗

第 3 行被註解掉的那一句是官方原版的寫法：有 GPU 就用 cuda，沒有就退回 cpu。本 repo 刻意改成第 4 行的 device = "cuda"，並在第 6–7 行印出 GPU 狀態：這份程式就是要在 GPU 上跑，沒有 CUDA 就應該立刻、大聲地失敗（fail fast and loud），而不是默默退回 CPU、用慢上許多的速度跑完才讓人發現。具體行為有兩點：

  • 沒有可用的 NVIDIA 顯卡時，程式在讀資料之前就結束。第 7 行的 torch.cuda.current_device() 會直接拋出 RuntimeError: No CUDA GPUs are available（用 CUDA_VISIBLE_DEVICES="" 把顯卡藏起來就能重現）。
  • 每支 import config 的程式都會先印兩行。這是 import 的特性：Python 第一次 import 一個模組時，會把它從頭執行一遍，模組層級的 print 也跟著執行。所以等一下 train.py 與 predict.py 的輸出開頭都是 True 與 0——這兩行就是「GPU 確實在」的確認。

動手做：親手驗證本章的三個說法

以下指令都在 HW01/ 裡執行。每一個都只要幾秒到半分鐘，做完你就不必相信本書，而是相信自己的終端機。

  1. 可重現性：再跑一次 ../.venv/bin/python train.py 2>/dev/null | tail -3，最後一個 epoch 應該仍是 Epoch [1883/3000]，數字與 0.5 節完全相同。接著把 config.py 的 'seed' 改成別的數字再跑，停止的 epoch 會變；再跑一次第 3 項的指令，最佳 loss 也不再是 1.661。做完記得把 seed 改回 5201314，並再跑一次 train.py，讓 models/model.ckpt 回到 1.661 那一份——後面各章的數字都以它為準。
  2. 沒有 GPU 時會怎樣：執行 CUDA_VISIBLE_DEVICES="" ../.venv/bin/python -c "import config"。這個環境變數讓 PyTorch 看不到任何顯卡，模擬一台沒有 GPU 的機器；你會先看到 False，接著是 RuntimeError: No CUDA GPUs are available。
  3. 最後一次存檔在哪：執行 ../.venv/bin/python train.py 2>/dev/null | grep -B1 Saving | tail -2，-B1 讓 grep 連同前一行一起印，你會看到 Epoch [1483/3000] 與 Saving model with loss 1.661...。

2>/dev/null 把 stderr（tqdm 進度條）丟掉，否則管線只接住 stdout，進度條仍會灌滿螢幕。第 1、3 項每跑一次都會覆寫 models/model.ckpt，並在 runs/ 多一個目錄；只要 seed 是 5201314，覆寫後的權重和原本相同。

0.8　六個檔案的分工地圖

官方原版是一份 Jupyter／Colab 筆記本（.ipynb，把程式切成一格一格、在瀏覽器裡從上往下依序執行的檔案）；本 repo 把它按職責拆成六個檔案。下圖是資料在它們之間流動的方向：

CPU 端的資料處理 在 GPU 上運算 磁碟檔案 設定

這張圖有兩個值得記住的地方。第一，train.py 和 predict.py 是兩個獨立的程式：訓練結束後 Python 行程就結束了，記憶體裡的模型也跟著消失；預測時要用 model.py 重建一個同樣形狀的空模型，再從 model.ckpt 把權重填回去。另外，predict.py 不經過 train.py：它自己 import utils 與 data_loader，自己讀 CSV。第二，這些檔案之間靠 import * 連在一起：

from X import * 會把模組 X 裡所有公開的名字（函式、類別、變數，以及 X 自己 import 進來的東西）倒進目前的命名空間。所以 train.py 裡直接寫 config['seed']、device、My_Model、same_seed 都能用，不必加前綴。這樣寫很方便，代價是讀程式時看不出某個名字從哪來——例如 train.py 自己沒有 import torch，卻能使用 torch.optim.SGD，因為 config.py、utils.py、data_loader.py 都 import torch，torch 這個名字就跟著 import * 一起進來了；同理，train.py 用到的 nn.MSELoss 的 nn，來自 model.py 第 1 行的 import torch.nn as nn。遇到「這個名字哪來的？」就回頭查這張圖。另外，第 21 行的 from tqdm import tqdm 在第 9 行（train.py:9，註解 # For Progress Bar 底下）已經出現過一次，重複 import 無害，只是多餘。

現在的做法：明確寫出 import 的名字

今天的 Python 風格指南（PEP 8）與常見的程式檢查工具（例如 Ruff 的 F403 規則）都不建議在程式裡用 from X import *。改成明確列出要用的名字，例如 from utils import same_seed, train_valid_split, select_feat、from model import My_Model，讀程式的人一眼就知道每個名字從哪來，也不會發生「兩個模組都有同名函式、後 import 的悄悄蓋掉前一個」的問題。本書引用的程式碼維持原樣，後面各章遇到「這個名字哪來的」時，會回頭對照圖 0.2。

本章重點

  • HW01 是迴歸問題：用一列 117 個數字（id、州別、5 天的問卷統計）預測第 5 天的陽性率，以 MSE 評分。
  • Blackwell 顯卡（sm_120）需要 cu128 以上的 PyTorch；repo 根目錄的 .venv 是 Python 3.12 + PyTorch 2.11.0+cu128。
  • 所有程式都要在 HW01/ 裡執行，Python 用 ../.venv/bin/python。
  • 實測：訓練約 34 秒，第 1483 個 epoch 印出最佳驗證 loss 1.661（真實 MSE 2.069，見第 3 章），第 1883 個 epoch early stop；predict 產生 1078 筆預測。
  • config.py 刻意把 device 設為 cuda：沒有 GPU 就在 import 時立刻失敗（fail fast），不會默默退回 CPU。
  • train 與 predict 是兩個獨立程式，透過 models/model.ckpt 交接。

自我測驗

1. 為什麼這台機器不能安裝原本指定的 torch==1.13.1+cu116？請說出兩個理由。

一、顯卡是 Blackwell（sm_120），PyTorch 1.13 的安裝包沒有編譯 sm_120 的 kernel，CUDA 11.6 也不支援這代架構，至少要 cu128。二、本機是 Python 3.12，而 PyTorch 1.13 沒有發布 3.12 的安裝包。

2. 在一台沒有 NVIDIA 顯卡的筆電上執行 train.py，程式會在哪裡失敗？為什麼還沒開始讀資料就失敗了？

在 config.py 第 7 行 torch.cuda.current_device()。train.py 開頭的 from config import * 會先把 config.py 整個執行一遍，模組層級的程式碼在 import 時就跑了，而讀 CSV 的程式碼還在後面。

3. 輸出中 valid_data size 與 test_data size 前面為什麼多了 4 個空白？

那三行是用一個三引號 f-string 印的，第 2、3 行在原始碼裡有縮排，而三引號字串會原樣保留換行與縮排。

4. 訓練設定是 3000 個 epoch，為什麼停在 1883？從哪兩個數字可以驗證？

early stopping：最佳驗證 loss 出現在第 1483 個 epoch，之後連續 400 個 epoch（config 的 early_stop）都沒有更好，1483 + 400 = 1883，程式便停止。

5. tqdm 進度條顯示 loss=60.4，stdout 卻印 Train loss: 134.2442，兩者都是第 1 個 epoch，為什麼不同？

進度條顯示的是當下這個 batch 的 loss，跑完時就是最後一個 batch 的值；stdout 印的是這個 epoch 9 個 batch 的 loss 平均。第 1 個 epoch 裡 loss 下降得很快，前面的 batch loss 很大，把平均拉高了。

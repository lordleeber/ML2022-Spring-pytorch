第 4 章　模型：117 → 16 → 8 → 1

第 0 章 0.2 節已經畫過這個模型的架構、算過 2,033 個參數。本章逐行讀 model.py，回答前面幾章延後的四個問題：為什麼要呼叫 super().__init__()、forward 是誰呼叫的、squeeze(1) 少了會怎樣、117 這個數字怎麼決定第一層的 1,888 個參數。最後打開訓練好的模型，看兩件只有實測才看得到的事：第一層 16 個輸出單元裡有 10 個從不輸出，以及 id 這一欄在第一層裡壓過其他欄約 400 倍。

4.2　類別外殼：nn.Module 與 super().__init__()

第 10 行和第 3 章的 class COVID19Dataset(Dataset) 是同一個句型：定義新類別 My_Model，繼承 nn.Module。第 3 章說過，PyTorch 的 Dataset 幾乎是空的，繼承它主要是表明身分；nn.Module 正好相反，它是 PyTorch 裡最有份量的類別之一，所有模型、所有層（包括等一下的 nn.Linear、nn.ReLU、nn.Sequential）都是它的子類別。繼承它，My_Model 就免費得到一整套能力：

  • model.parameters()、model.named_parameters()：列出模型裡所有要學的參數（第 0 章用它數出 2,033；第 5 章交給優化器的也是它）。
  • model.to(device)：把所有參數一次搬到 GPU（4.5 節）。
  • model.state_dict()／model.load_state_dict()：把全部參數打包成一個字典存檔、再填回來（4.3、4.8 節）。
  • model.train()／model.eval()：切換訓練／評估模式（第 5 章）。這個開關只影響訓練與評估時行為不同的層（例如之後作業會用到的 Dropout）；HW01 只有 Linear 與 ReLU，兩種模式算出的結果相同。
  • print(model)：印出第 0 章看過的那個樹狀結構。
  • model(x)：讓物件可以像函式一樣被呼叫，背後再去呼叫 forward（4.5 節）。

這些方法要能運作，有一個前提：模型得知道自己有哪些子元件。My_Model 只寫了 self.layers = … 一行指定，parameters() 是怎麼找到藏在 layers 裡面那 2,033 個數字的？

指定屬性時，nn.Module 會順手登記

答案在 nn.Module 改寫了「指定屬性」這個動作。一般的 Python 物件，self.layers = 某個東西 就只是把東西存起來；nn.Module 則攔下每一次指定（它改寫了 __setattr__ 這個特殊方法，第 3 章說過，特殊方法是 Python 在對應語法出現時代為呼叫的方法），檢查被指定的值：如果是另一個 nn.Module，就把它登記到自己內部的一本「子模組名冊」（名叫 _modules 的字典）裡，名字就是屬性名 layers；如果是參數（nn.Parameter，一種專門裝模型參數的 tensor，4.3 節），就登記到參數名冊。之後 parameters()、to()、state_dict()、print() 全都是沿著這本名冊一層一層往下走。

名冊要先存在，才能往裡登記。建立名冊的工作，就在 nn.Module 自己的 __init__ 裡。這就是第 12 行的用途：在指定任何子模組之前，先執行父類別 nn.Module 的 __init__，把名冊這些內部結構準備好。

忘了這一行會怎樣？本機實測，自訂一個 nn.Module 子類別、不呼叫 super().__init__() 就指定子模組，建立物件的當下就會失敗：

AttributeError: cannot assign module before Module.__init__() call

訊息說得很直白：「在 Module.__init__() 被呼叫之前，不能指定 module」——名冊還不存在，登記無處可記。這是好事：PyTorch 選擇在建立物件時就大聲失敗，而不是讓你得到一個 parameters() 是空的、怎麼訓練都不會變的模型。

super(My_Model, self) 與 super()

super(…) 回傳一個代理物件，透過它呼叫的方法會去父類別找，所以 super(My_Model, self).__init__() 的意思是「對 self 執行 My_Model 的父類別（也就是 nn.Module）的 __init__」。第 0 章寫的 super().__init__() 是 Python 3 的簡寫，在類別裡面寫時，Python 會自動補上「目前這個類別」與 self，兩者意思完全相同。原程式這種把類別名稱寫出來的形式，是從 Python 2 時代沿用下來的寫法（Python 2 必須這樣寫）。

現在的做法：super().__init__()

今天的 PyTorch 官方教學與大部分程式碼都寫成 super().__init__()。除了短，它還少一個出錯點：類別改名時，帶名字的寫法要跟著改兩處，忘了改舊名字就會出錯；簡寫則永遠指向「目前這個類別」。功能上兩者沒有差別，本書引用時保持原樣。

第 11 行：input_dim 從哪裡來

__init__(self, input_dim) 比 nn.Module 多要一個參數 input_dim：輸入有幾欄。模型自己不知道資料長什麼樣，得由建立它的人告訴它。告訴它的就是 train.py 第 126 行：

x_train.shape[1] 是 x_train 的欄數。第 2 章 2.4 節看過，select_all=True 時它是 117，train.py 第 117 行印出的 number of features: 117 也是這個值。這一行先做 My_Model(input_dim=117)，Python 建立物件、呼叫 __init__，然後對建好的模型呼叫 .to(device)。.to(device) 留到 4.5 節；先看 __init__ 剩下的部分，117 是在那裡被用掉的。

4.3　nn.Sequential 與 nn.Linear：117 怎麼變成 1,888 個參數

nn.Sequential 是一個「容器模組」：建立時依序傳入幾個模組，它就依序把它們登記成自己的子模組，名字是 0、1、2…；被呼叫時，把輸入交給第 0 個，第 0 個的輸出交給第 1 個，一路傳到最後（4.5 節）。第 0 章 print(model) 印出的 (0): Linear(…)、(1): ReLU() 就是這些名字。本機實測 len(model.layers) 是 5，也可以用 model.layers[0] 這樣的索引取出單一元件。

第 13 行的 TODO 是給學生的提醒：改結構時「注意維度」。所謂維度，就是相鄰兩個 Linear 的大小必須接得上：Linear(input_dim, 16) 輸出 16 個數字，下一個 Linear 的第一個參數就必須是 16；它輸出 8 個，再下一個就得是 8。ReLU 逐個數字作用、不改變個數，所以可以夾在中間不影響維度。最後一層輸出 1 個數字，因為我們只要預測一個值。

nn.Linear 裡面存了什麼

第 0 章說 Linear(a, b) 有 a × b 個權重加 b 個偏差（bias）。本機用 named_parameters()（列出每個參數的名字與內容）實測，它們實際的存放方式是：

參數名稱形狀個數
layers.0.weight(16, 117)1,872
layers.0.bias(16,)16
layers.2.weight(8, 16)128
layers.2.bias(8,)8
layers.4.weight(1, 8)8
layers.4.bias(1,)1
合計2,033（第一層佔 92.9%）

這張表有三個值得停下來的地方。

第一，名字就是名冊的路徑。layers.0.weight 讀作「layers 這個子模組裡、名叫 0 的子模組裡、名叫 weight 的參數」。名字裡跳過了 1 和 3：那兩個位置是 ReLU，本機實測 layers[1] 的參數數量是 0。ReLU 只是一條固定的規則 max(0, x)，沒有東西要學，但它仍佔一個編號。

第二，weight 的形狀是 (輸出, 輸入)，不是 (輸入, 輸出)。nn.Linear(117, 16) 的參數順序是「先輸入、後輸出」，存起來的 weight 卻是 (16, 117)。這不是隨便排的：weight 的每一列就是一個輸出單元的全部權重。第 0 列的 117 個數字，決定第 0 個輸出怎麼由 117 欄加權而成；第 1 列決定第 1 個輸出；共 16 列。一次處理一整個 batch 時，nn.Linear 算的是

輸出 ＝ x · WT ＋ b
(256, 117) · (117, 16) ＋ (16,) → (256, 16)；WT 是 W 的轉置（列與欄互換：原本的第 j 列變成第 j 欄），b 對每一筆都加一次

所以 117 決定的是每一列有多長：16 列 × 117 個 = 1,872 個權重，加上 16 個 bias，就是第 0 章圖 0.1 的 1,888。input_dim 每多一欄，第一層就多 16 個參數。本機實測：拿掉 id、輸入改成 116 欄時，模型總參數是 2,017，正好少 16 個。這也是第 2 章那句「改 feat_idx 會自動改變模型第一層的大小」的具體意思。

模型參數（在 GPU 上運算） 乘在 id 欄上的那一欄權重

第三，名字也是存檔時的鑰匙。本機實測 model.state_dict() 的 key 依序是 'layers.0.weight'、'layers.0.bias'、'layers.2.weight'、'layers.2.bias'、'layers.4.weight'、'layers.4.bias'——和上表一模一樣。train.py 第 88 行存檔時存的就是這個字典（第 5 章），所以 model.ckpt 裡面是「名字 → tensor」的對照。第 0 章 0.7 節看過這個檔案是 11,005 bytes；其中參數本身佔 2,033 × 4 = 8,132 bytes（每個 float32 佔 4 bytes，第 3 章），其餘是 key 名稱、形狀等格式資訊。

全部參數都是 float32，而且 requires_grad=True：這個旗標告訴 PyTorch「之後要替這個 tensor 算梯度」。梯度簡單說就是「這個參數往哪個方向改一點，loss 會降多少」，訓練時優化器就是依梯度修改參數（第 5 章細講）。資料的 tensor 預設沒有這個旗標，參數有，這是兩者在 PyTorch 眼中的根本差別。

維度接不上、型別對不上：兩個錯誤訊息

形狀 (輸出, 輸入) 與「x · WT」這個算法，在錯誤訊息裡看得最清楚。本機實測兩種故意寫錯的情況：

怎麼寫錯錯誤訊息（逐字）
把 116 欄的輸入（4 筆）餵給 117 欄的模型RuntimeError: mat1 and mat2 shapes cannot be multiplied (4x116 and 117x16)
輸入是 float64RuntimeError: mat1 and mat2 must have the same dtype, but got Double and Float

mat1、mat2 是矩陣乘法的左右兩個矩陣。第一個訊息裡，mat1 是輸入 4x116，mat2 是 117x16——正是 WT，不是存起來的 (16, 117)。矩陣乘法要求左邊的欄數等於右邊的列數，116 ≠ 117，所以失敗。這就是第 13 行 TODO 要你「注意維度」的原因，也是 predict.py 必須用和訓練時同一個 input_dim 建模型的原因（4.8 節）。

第二個訊息兌現了第 3 章 3.2 節的說法：把 float64 的輸入直接餵給 float32 的模型，PyTorch 不會自動轉換，而是報錯。Double 是 float64、Float 是 float32。COVID19Dataset 在一開始就用 torch.FloatTensor 把資料轉成 float32，所以 HW01 不會碰到這個錯誤。

4.4　初始權重：2,033 個數字從哪裡來

__init__ 執行完，模型已經有 2,033 個參數，而且每個都有值——還沒訓練，值是哪來的？nn.Linear 在建立時就替自己的 weight 與 bias 抽亂數，預設從均勻分布 U(−1/√in, 1/√in) 抽，in 是這一層的輸入個數。本機照 train.py 的順序先呼叫 same_seed(5201314) 再建立模型，所以下面就是 train.py 開始訓練那一刻的權重：

層in範圍上限 1/√in實測
第一層 layers[0]1170.0925weight −0.0924～0.0924；bias −0.0891～0.065
第二層 layers[2]160.25weight −0.2459～0.2499
第三層 layers[4]80.35368 個 weight：0.1932、−0.168、0.1907、0.1301、−0.2984、−0.0179、−0.3317、0.1277；bias 0.0609

實測值都落在各自的範圍內，而且第一層的 1,872 個 weight 多到幾乎碰到兩端。第一層 weight 第 0 列的前 5 個是 0.0081、0.0874、0.0613、−0.0031、0.0789（圖 4.1 那一列）。

為什麼範圍要隨 in 縮小？一個輸出單元是 in 個「輸入 × 權重」的總和。如果每個輸入的大小都差不多，加總的項越多，總和就越容易變大；把權重的範圍按 1/√in 縮小，可以讓不同寬度的層，輸出的大小落在差不多的範圍，訊號不會一層一層放大或縮小。所以 117 個輸入的第一層，權重比只有 8 個輸入的最後一層小得多。

注意這個推論的前提：「每個輸入的大小差不多」。HW01 的輸入不滿足它。第 1 章 1.4 節看過，州別欄只有 0 和 1，cli 在 0～3 之間，id 卻從 0 到 2699（2,699 列，中間缺一號，第 1 章 1.6 節）。初始權重只按「有幾欄」縮放，管不到「每欄有多大」；id 乘上一個 0.09 量級的權重，一筆資料就可能貢獻兩百多（2699 × 0.0924），其他欄加起來都比不上。4.7 節會看到，訓練之後這個失衡不但沒消失，還更嚴重。

這些亂數抽自第 2 章表格裡的 PyTorch 全域產生器：My_Model 先在 CPU 上建立、在建立時抽亂數，再由 .to(device) 搬上 GPU。第 3 章 3.4 節提過後果：建立模型時抽走多少亂數，決定了 DataLoader 從哪裡接著抽，所以改了模型的層數或寬度，連每個 epoch 的 batch 順序都會跟著變。

4.5　forward：model(x) 怎麼走到這裡

forward 定義「資料進來之後怎麼算」：第 23 行交給 self.layers，第 24 行用 squeeze(1) 改形狀（4.6 節），第 25 行回傳。奇怪的是，整個 HW01 沒有任何一行寫 model.forward(x)。訓練與預測都寫 pred = model(x)（train.py 第 56、76 行，predict.py 第 16 行）——把物件當成函式呼叫。

這也是一個特殊方法：Python 看到 model(x)，實際呼叫的是 model.__call__(x)。My_Model 沒有定義 __call__，所以用的是從 nn.Module 繼承來的那一個。nn.Module.__call__ 做一些準備（最重要的是執行 hook：使用者可以掛在模組上、在 forward 前後自動執行的函式，常用來印出中間結果或做除錯），然後呼叫 self.forward(x)，把結果交回來。

本機實測，在同一個 batch 上 model(x) 和 model.forward(x) 的結果完全相同（torch.equal 為 True）——HW01 沒有掛任何 hook，__call__ 那層準備工作沒有改變結果。但慣例永遠寫 model(x)：直接呼叫 forward 會跳過那層機制，在有 hook 的程式裡就會出現「同一個模型，兩種呼叫結果不同」的怪事。

第 23 行的 self.layers(x) 也是同樣的機制：nn.Sequential 也是 nn.Module，呼叫它一樣經過 __call__，再進到 Sequential 自己的 forward。Sequential 的 forward 就是一個迴圈：依名冊順序，把資料交給每個子模組，再把輸出交給下一個。每個子模組被呼叫時，又各自經過自己的 __call__ 與 forward。本機拿驗證集的第一個 batch（shuffle=False，256 筆，在 GPU 上）逐層記錄形狀：

控制：呼叫機制 GPU 上的運算（模型的層） 預測值

這個 batch 用的是訓練好的 model.ckpt。前 5 筆的預測是 15.9939、5.0906、9.6055、3.0774、8.2978，對應的真值是 13.4923、3.7415、11.25、1.875、8.8235：大方向對了，每筆差了 0.5～2.5 個百分點不等，和真實 MSE 2.069 的量級相符。

train.py:126 的 .to(device)

回到第 126 行後半的 .to(device)。它把模型的所有參數搬到 device，也就是 config.py 的 "cuda"；本機實測搬完之後參數的 device 是 cuda:0（第 0 張 GPU）。它能「一次搬全部」，靠的又是 4.2 節的名冊：.to() 沿著名冊走遍每一個子模組，把每個參數都搬過去。

有一個和第 3 章不同的地方要注意。第 3 章說搬上 GPU 是「複製」：x.to(device) 對 tensor 回傳一個在 GPU 上的新 tensor，原本的 x 還留在 CPU，所以訓練迴圈要寫 x = x.to(device) 把結果接住。model.to(device) 對 模組則是原地搬移：模型自己的參數被換成 GPU 上的版本，回傳的是同一個模型物件。第 126 行把回傳值指定給 model，寫法和 tensor 的版本一樣，但就算不接回傳值，模型也已經搬過去了。

行尾的註解「把模型和資料放在同一個計算裝置上」點出了規則：一次運算的所有 tensor 必須在同一個裝置上，模型在 GPU、資料在 CPU 時，PyTorch 會報錯而不是自動搬。所以模型在這裡搬一次，資料則在訓練迴圈裡每個 batch 搬一次（第 5 章）。

4.6　squeeze(1)：少了它，loss 從 1.78 變成 89

第 0 章、第 2 章、第 3 章都說過同一件事：最後一層輸出 (B, 1)，第 24 行把它壓成 (B,)，為的是和 y 的形狀一致。squeeze(1) 的意思是「如果第 1 維（0 起算）的長度是 1，就把這一維拿掉」：(256, 1) 變成 (256,)，數值完全不動，只是少了一層包裝。第 24 行的註解 # (B, 1) -> (B) 寫的就是這件事，B 代表 batch 大小。

為什麼 Linear 會輸出 (256, 1)？因為 Linear 對每一筆輸出 out_features（建立時的第二個參數）個數字，這一層是 1 個，所以每筆是長度 1 的向量，256 筆疊起來是 (256, 1)。而 y 是第 2 章取 train_data[:, -1] 得到的一維陣列，經過第 3 章的 collate 疊成 (256,)。兩者裝的都是「每筆一個數字」，差別只在有沒有那一層長度 1 的維度。

看起來只是形狀的潔癖。本機拿同一個 batch、同一個 model.ckpt 做了對照：

送進 MSELoss 的預測和 y (256,) 相減後的形狀loss
有 squeeze：(256,)(256,)1.7758
沒有 squeeze：(256, 1)(256, 256)89.0963

同一組預測，loss 差了 50 倍。原因是 PyTorch 的廣播（broadcasting）規則：兩個形狀不同的 tensor 做逐元素運算時，PyTorch 會從最後一維開始對齊，長度為 1 的維度（或缺少的維度）會被「複製展開」去配合對方。(256, 1) 與 (256,) 對齊後是 (256, 1) 對 (1, 256)，兩邊各自展開，相減的結果就成了 (256, 256)：

預測值 答案 y（CPU 端資料搬上來的） 正確的配對

1.7758 是正確的值：這 256 筆的預測誤差平方平均。89.0963 是 65,536 個差值的平方平均，其中 65,280 個是「第 i 筆的預測減第 j 筆的答案」——等於問「這個預測和驗證集裡隨便一筆答案差多少」。答案本身在 0.3～30 之間散得很開，這個量自然很大，而且和模型好不好幾乎無關。

更麻煩的是，這不會讓程式停下來。本機實測，PyTorch 只跳出一則警告（UserWarning），逐字是：

UserWarning: Using a target size (torch.Size([256])) that is different to the input size (torch.Size([256, 1])). This will likely lead to incorrect results due to broadcasting. Please ensure they have the same size.

「target 的大小和 input 不同，這很可能因為廣播導致錯誤的結果，請確保兩者大小相同。」程式照常往下跑：loss 照算、梯度照算、權重照更新，只是優化的目標變成了「讓每個預測都接近所有答案」——最好的策略是讓每筆都預測同一個數字（大約是所有答案的平均）。警告印在 stderr，而第 0 章的跑法常用 2>/dev/null 把 stderr 丟掉，連這唯一的線索都會看不到。

為什麼是 squeeze(1) 而不是 squeeze()

不帶參數的 squeeze() 會拿掉所有長度為 1 的維度。平常這和 squeeze(1) 結果一樣，但 batch 只有 1 筆時就不同了。本機實測，只送 1 筆資料時：

形狀
最後一層的原始輸出(1, 1)
squeeze(1)(1,)：一筆、一個數字，仍是一維
squeeze()()：0 維 tensor（第 3 章），batch 那一維也被拿掉了

指定維度 1，只拿掉「每筆一個數字」的那一維，batch 維永遠保留，所以比較安全。HW01 的每個 batch 最少也有 27 筆（第 3 章，valid 的最後一批），實際上碰不到這個情況；但同一段模型程式拿去做單筆預測時就會碰到。

現在的做法：讓形狀不符變成錯誤，而不是警告

  • 在算 loss 前檢查形狀。在自己的訓練迴圈裡加一行 assert pred.shape == y.shape, (pred.shape, y.shape)，形狀一不對就當場停下，而不是靠一則可能被丟掉的警告。
  • 或者讓兩邊都保持 (B, 1)。另一個常見的做法是不 squeeze 模型輸出，改把 y 變成 (B, 1)（例如 y.unsqueeze(1)，unsqueeze 是 squeeze 的反向操作，在指定位置插入一個長度 1 的維度）。重點不是選哪一種，而是兩邊一致，並且有一行程式負責確認。
  • HW01 的寫法把這個責任放在模型的 forward 裡，這也沒錯，只要記得：改模型時如果動到第 24 行，loss 不會報錯，只會悄悄變大。

4.7　打開訓練好的模型：沒在工作的單元與壓倒性的 id

前面幾節講的都是模型的「形狀」。這一節打開 model.ckpt（訓練時印出 1.661、真實 MSE 2.069 的那一份，第 3 章 3.5 節），看訓練完的 2,033 個數字長什麼樣。先看整體輸出：本機實測，模型在驗證集上的預測落在 1.8327～28.2623，真值落在 0.3448～29.8157，範圍大致對得上。接下來的兩個發現，從 stdout 的 loss 完全看不出來。

16 個單元裡，有 10 個從不輸出

第一層 Linear 有 16 個輸出單元，每個都接著一個 ReLU。ReLU 把負數變成 0：某個單元的加權總和只要是負的，這一筆在這個單元上的輸出就是 0。偶爾是 0 很正常；但如果一個單元對所有資料的加權總和都是負的，它就永遠輸出 0，下游完全收不到它的訊息。這種單元常被稱為死掉的 ReLU（dying ReLU）。

本機實測，把訓練集與驗證集全部送進訓練好的模型：

模型第一層：永遠輸出 0 的單元第一層輸出中 0 的比例第二層：永遠輸出 0 的單元
剛初始化（訓練前）2 / 1646.6%（train）
訓練好的 model.ckpt10 / 1681.5%（train）、81.7%（valid）1 / 8
拿掉 id 後訓練的模型（第 2 章動手做）7 / 1656.2%2 / 8

（「永遠輸出 0」以訓練集加驗證集全部資料判定；初始化那一列的第二層沒有量。）

訓練好的模型，第一層 16 個單元只剩 6 個在工作；第一層所有輸出裡超過八成是 0。剛初始化時只有 2 個這樣的單元，所以大部分是訓練過程中才變成這樣的。

為什麼死了就回不來？訓練時，每個權重依「改動它能讓 loss 降多少」來調整（這個量叫梯度，第 5 章）。ReLU 在輸入為負時輸出固定是 0，輸入稍微變大或變小輸出都還是 0，所以對一個在所有資料上都輸入為負的單元來說，改動它的權重不會讓 loss 有任何變化，梯度是 0，權重就不再被資料推動。它停在那裡，參數還在，卻不貢獻任何東西。

這帶出一個實際的意思：0.2 節算的「第一層 1,888 個參數」，在訓練好的模型裡有 10 列（10 個單元的權重與 bias）對輸出毫無影響，卻照樣存在 model.ckpt 裡、照樣佔參數量。參數量是模型能表達多複雜關係的上限（容量），不是它實際用上的量。拿掉 id 的模型死得少一些（7 / 16），但仍將近一半；單憑這兩組數字，還不能說 id 是唯一的原因。第 7 章換模型結構、調學習率時，這是值得回頭量的指標。

id 這一欄，在第一層裡大了約 400 倍

第 2 章的結論是：id 拖累訓練的主因是數值尺度，id 最大到 2699，其他欄最大不到 90，程式又沒有標準化，所以 id 在第一層的加權總和裡壓過其他欄。當時那是從「拿掉 id、或把 id 除以 2699，loss 都大幅改善」推出來的。現在可以直接打開權重驗證。本機實測訓練好的第一層 weight（也就是圖 4.1 那個 (16, 117) 矩陣）：

id 欄（第 0 欄）其他 116 欄的平均比值
weight 的平均絕對值 |w|0.226430.05002約 4.5 倍
乘上驗證集該欄的平均值後的平均 |w·x|309.130.7558約 400 倍（309.13 ÷ 0.7558 ≈ 409）
id 欄 其他 116 欄（州別與問卷） 初始化範圍的上限

兩個觀察：

  • 訓練把 id 的權重推大了，不是壓小。4.4 節看過，第一層的初始權重落在 ±0.0925 之內，均勻分布在這個範圍內的平均絕對值大約是上限的一半（約 0.046）。其他欄的 0.05002 和這差不多，表示它們在訓練中沒怎麼動；id 欄的 0.22643 則是初始範圍上限 0.0925 的兩倍多。第 1 章 1.4 節說過，一欄的梯度和它的數值大小成正比，數值大的欄位權重被推得猛——這張表就是那句話的結果。
  • 真正壓倒其他欄的是「權重 × 數值」。權重只大 4.5 倍，但 id 的數值動輒上千，其他欄多半是個位數到幾十，相乘之後 id 對第一層的平均貢獻是其他欄的約 400 倍。對第一層的每個單元來說，加權總和幾乎就是「id × 某個係數」加上一點點其他資訊。

回想第 1 章：id 在訓練集裡隱含時間，在測試集裡卻是從 0 重新編號的另一套。一個主要靠 id 做判斷的第一層，學到的東西有很大一部分換到測試集就失效了。這也從另一個方向解釋了第 2 章的實驗：拿掉 id（或把它縮到 0～1），其他 116 欄才有機會被第一層「聽見」，真實 MSE 從 2.069 降到 1.24～1.26。

現在的做法：先處理輸入的尺度，再談模型

  • 標準化輸入。第 1 章「現在的做法」框裡的標準化（只用訓練集的平均與標準差），正好滿足 4.4 節初始化公式的前提「每個輸入大小差不多」。這是今天訓練神經網路的固定前處理，比調任何模型細節都優先。
  • 量一下有多少單元沒在工作。像本節這樣數「永遠輸出 0 的單元」花不了幾行程式，訓練完順手量一次，比只看 loss 多知道很多。
  • 需要時換激活函數。LeakyReLU（負數時保留一個很小的斜率）、GELU（形狀接近 ReLU、但在 0 附近是平滑曲線）等激活函數在負數區不會讓梯度完全變成 0，比較不容易出現整個單元死掉的情況。但在輸入沒有標準化之前換激活函數是治標；HW01 的情況，先處理 id 與尺度才是根本。第 7 章會實際比較。

4.8　predict.py：重建同樣的模型，再填回權重

第 0 章 0.8 節說過，train.py 結束時 Python 行程也結束了，記憶體裡的模型跟著消失。predict.py 要用模型，只能重建一個，再把 model.ckpt 的數字填回去：

兩行各做一件事：

  • 第 39 行和 train.py 第 126 行幾乎一字不差（少了行尾註解）：建立一個 My_Model，搬上 GPU。這時模型裡是 4.4 節那種初始化的亂數權重——predict.py 沒有呼叫 same_seed，所以每次執行抽到的都不一樣，但沒關係，下一行會全部蓋掉。
  • 第 40 行先用 torch.load 讀出存檔的字典，也就是 4.3 節那個「名字 → tensor」的 state_dict；再用 load_state_dict 依名字把每個 tensor 的數值複製進模型裡同名的參數。

「依名字對應」決定了這兩行的前提：重建的模型必須和存檔時的模型有同樣的名字、同樣的形狀。名字由 model.py 的結構決定（self.layers 與 Sequential 裡的順序），形狀由 input_dim 與各層大小決定。predict.py 第 39 行為了拿到 input_dim，用的是 x_train.shape[1]：它必須和 train.py 一樣讀進訓練資料、切分、選特徵，才能算出 117——第 0 章 0.6 節說的「多餘的步驟」就是為了這一個數字，第 6 章會討論更好的做法。

如果兩邊對不上，例如訓練時用了 116 欄、預測時用 117 欄建模型，load_state_dict 會在載入時報錯，指出哪個參數的形狀不符，而不會默默載入錯的權重。

載入之後，predict.py 在 predict() 裡呼叫 model.eval()，再對每個 batch 做 model(x)——和 4.5 節的呼叫鏈完全相同，只是這次 forward 裡用的是填回去的權重。預測迴圈與 pred.csv 的格式是第 6 章的內容。

現在的做法：載入時把裝置與安全性寫清楚

  • torch.load(path, map_location=device, weights_only=True)。目錄頁提過，PyTorch 2.6 起 weights_only 預設為 True：只允許載入 tensor 與基本容器，不執行檔案裡夾帶的任意 Python 物件。state_dict 正好只有 tensor，所以 HW01 的 model.ckpt 在新版照樣能載入；明寫出來，換版本時行為不會變。map_location 指定載入到哪個裝置，讓在 GPU 上存的檔案也能在別台機器上讀。
  • 把建模型需要的設定一起存。常見做法是存成 {'input_dim': 117, 'state_dict': model.state_dict()} 這樣的字典，預測時先讀出 input_dim 再建模型，就不必為了一個數字重讀訓練資料（第 6 章）。

4.9　動手做

動手做：親手看名冊、形狀與 squeeze

以下指令都在 HW01/ 裡執行。第 1、2 項只 import model 或 torch.nn，不 import config，所以輸出開頭不會有 True、0 兩行，也不需要 GPU；第 3、4 項要載入 model.ckpt、在 GPU 上算，會 import config。第 3、4 項需要 models/model.ckpt 是 1.661 那一份（第 2、3 章動手做的提醒）。

  1. 名冊裡有什麼：

  2. 忘了 super().__init__()：

  3. 逐層形狀與 squeeze 的對照： 
    $ ../.venv/bin/python -c "

    print('with squeeze', round(mse(pred, y).item(), 4))
    print('without     ', round(mse(model.layers(x), y).item(), 4))
"
    True、0 之後，前五行依序是 Linear、ReLU、Linear、ReLU、Linear 與圖 4.2 的五個形狀；下一行是 (256,) 與 True（model(x) 和 model.forward(x) 相同）；最後兩行是 4.6 節的 1.7758 與 89.0963。最後一行算 loss 時，stderr 會多出 4.6 節那則 UserWarning。next(iter(…)) 是「只從 loader 拿第一個 batch」的寫法；with torch.no_grad(): 與 model.eval() 和第 3 章動手做第 3 項一樣，是只做預測、不訓練時的固定寫法（第 5 章）。
  4. 數一數沒在工作的單元：在第 3 項的 Python 程式碼最後、收尾的 " 之前加這幾行再跑（縮排從行首開始）： 
    xs = torch.cat([COVID19Dataset(x_tr).x, COVID19Dataset(x_va).x]).cuda()
with torch.no_grad():
    h1 = model.layers[1](model.layers[0](xs))
print('dead units', (h1 == 0).all(dim=0).sum().item(), '/ 16')
print('zero ratio', round((h1 == 0).float().mean().item(), 3))
    torch.cat 把 train 的 2160 列與 valid 的 539 列上下接成一個 (2699, 117) 的 tensor；h1 是第一層 ReLU 之後的輸出，形狀 (2699, 16)。(h1 == 0).all(dim=0) 對每個單元（每一欄）問「是不是所有資料都等於 0」，加總就是永遠輸出 0 的單元數，應該是 4.7 節的 10。第二行是所有輸出中 0 的比例；這裡把 train 與 valid 合在一起算，所以會介於 4.7 節的 81.5% 與 81.7% 之間。

本章重點

  • My_Model 繼承 nn.Module，因而有 parameters()、to()、state_dict()、eval() 等能力。它們都靠「指定屬性時自動登記子模組」的名冊運作；名冊由 nn.Module.__init__ 建立，所以第 12 行的 super().__init__() 必須在指定子模組之前呼叫，忘了會得到 cannot assign module before Module.__init__() call。
  • nn.Linear(117, 16) 的 weight 形狀是 (輸出, 輸入) = (16, 117)，每一列是一個輸出單元的權重；計算是 x · WT + b。input_dim 決定每列的長度：117 → 1,872 + 16 = 1,888 個參數；改成 116 欄，總數變成 2,017。
  • 參數名稱（layers.0.weight…）就是名冊路徑，也是 state_dict 與 model.ckpt 的 key；ReLU 沒有參數，所以沒有 layers.1、layers.3。初始值從 U(−1/√in, 1/√in) 抽，來自 PyTorch 全域產生器。
  • 程式只寫 model(x)，由 nn.Module.__call__ 呼叫 forward；Sequential 再依序呼叫五個子模組，形狀 (256,117) → (256,16) → (256,8) → (256,1)，squeeze(1) 壓成 (256,) 以對齊 y。model.to(device) 是原地搬移所有參數。
  • 少了 squeeze，(256,1) 與 (256,) 經廣播變成 (256,256)，同一個 batch 的 loss 從 1.7758 變成 89.0963，PyTorch 只給一則 UserWarning。用 squeeze(1) 而不用 squeeze()，batch 只有 1 筆時才不會連 batch 維一起拿掉。
  • 訓練好的模型第一層有 10/16 個 ReLU 單元在所有資料上都輸出 0（初始化時只有 2/16）；id 欄對第一層的平均貢獻約是其他欄的 400 倍，實際印證第 2 章「數值尺度」的結論。

自我測驗

1. 把第 15、17 行改成 nn.Linear(input_dim, 32) 與 nn.Linear(32, 8)，其他不動，輸入仍是 117 欄。模型有幾個參數？layers.0.weight 的形狀是什麼？

第一層 117 × 32 + 32 = 3,776；第二層 32 × 8 + 8 = 264；第三層不變 9。合計 4,049。layers.0.weight 是 (輸出, 輸入) = (32, 117)。注意兩行要一起改：只改第 15 行，第 17 行還是 Linear(16, 8)，第一次 forward 就會因為 32 接不上 16 而報 mat1 and mat2 shapes cannot be multiplied。

2. 如果在 Sequential 裡多插一個 nn.ReLU()，放在最後一個 Linear 之後，參數名稱會怎麼變？存好的 model.ckpt 還能載入嗎？

參數名稱不變：多出來的 ReLU 是 layers.5，沒有參數，前面五個的編號都沒動，所以 state_dict 的 key 一樣，model.ckpt 能載入。但模型的行為變了：最後的輸出會被 ReLU 截掉負數。反過來，如果把 ReLU 插在中間，後面 Linear 的編號會往後移（例如 layers.2 變成 layers.3），舊的 checkpoint 就對不上名字了。

3. 同學把第 24 行刪掉，訓練照樣跑完沒有報錯，印出的 loss 很大但也在下降。哪裡出了問題？怎麼發現？

模型輸出 (B, 1)、y 是 (B,)，MSELoss 經廣播算的是 (B, B) 個差值的平均，絕大多數是「第 i 筆預測減第 j 筆答案」，loss 量的不是模型誤差（本機同一個 batch：1.7758 變 89.0963）。程式不會停，只會在 stderr 印 UserWarning；如果用 2>/dev/null 丟掉 stderr，就完全看不到。最可靠的發現方法是在算 loss 前 assert 兩邊形狀相同。

4. 訓練好的模型第一層有 10 個單元永遠輸出 0。把這 10 個單元從模型裡拿掉，預測結果會變嗎？

在訓練集與驗證集上不會：它們在這些資料上永遠輸出 0，乘上第二層的權重也是 0，對下游毫無貢獻。這正是「參數量是容量上限，不是實際用上的量」的意思。（對沒看過的資料，原則上可能有某筆讓它的加權總和變成正的，所以嚴格說只能保證在量過的資料上不變。）

5. 為什麼 predict.py 不直接寫死 My_Model(input_dim=117)，而要用 x_train.shape[1]？如果 config 的 select_all 改成 False 再訓練，predict.py 要跟著改什麼？

load_state_dict 依名字把參數一一複製回去，形狀必須相同；第一層 weight 的形狀是 (16, input_dim)，所以 input_dim 必須和訓練時一樣。select_all=False 時特徵只有 5 欄，model.ckpt 裡的第一層是 (16, 5)。predict.py 不必改：它用 x_train.shape[1] 算 input_dim，而它讀的是同一個 config，會選出同樣的 5 欄，建出 (16, 5) 的模型——這正是它重讀訓練資料的理由。

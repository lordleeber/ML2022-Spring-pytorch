第 3 章　Dataset 與 DataLoader

第 2 章結束時，資料是五個 NumPy 陣列。本章看它們怎麼變成模型吃得下的形式：data_loader.py 的 COVID19Dataset 把陣列轉成 PyTorch 的 tensor，DataLoader 再把資料切成一批 256 筆、每個 epoch 重新打亂。最後回答前面幾章一直延後的問題：為什麼訓練時印出的最佳驗證 loss 是 1.661，存下來的模型真實 MSE 卻是 2.069。

3.2　COVID19Dataset：三個方法

data_loader.py 整個檔案只有 28 行，就是一個類別（class）。分兩段看，先看前半：

第 5 行的 """# Dataset""" 是一個沒有被指定給任何變數的字串，執行時什麼都不做。它是從原版 Jupyter 筆記本拆檔時留下的：筆記本裡這是一個 Markdown 小標題「Dataset」，轉成 .py 時變成了字串。train.py 第 24 行的 """# Training Loop""" 也是同一回事。

第 8 行：繼承 Dataset

class COVID19Dataset(Dataset) 的意思是：定義一個新類別 COVID19Dataset，它繼承（inherit）第 1 行 import 的 Dataset。繼承讓新類別自動擁有父類別的一切，並且「算是一種」父類別。本機實測 isinstance(train_dataset, Dataset) 為 True。

第 2 章 2.3 節把 Dataset 粗略定義成「能用 len() 問長度、能用 [i] 取第 i 筆的資料容器」。這就是 PyTorch 對它的全部要求：PyTorch 的 Dataset 類別本身幾乎是空的，真正的內容由子類別補上兩個方法——__getitem__ 與 __len__。繼承它主要是表明身分，讓讀程式的人（和工具）一眼看出「這是一個資料集」。

第 14–19 行：__init__ 把 NumPy 陣列轉成 tensor

__init__ 是建立物件時自動執行的方法。train.py 第 119 行寫 COVID19Dataset(x_train, y_train)，Python 就建立一個新物件，然後呼叫 __init__(self, x_train, y_train)；self 是這個新物件本身，self.x = … 就是把東西存成物件的屬性，之後其他方法還拿得到。

存進去的不是原本的 NumPy 陣列，而是 torch.FloatTensor(x) 的結果。tensor 是 PyTorch 的多維陣列，用法跟 NumPy 陣列很像（有 shape、能用 [i] 取值、能切片），但多了兩個 NumPy 沒有的能力：可以放在 GPU 上運算，以及自動計算梯度（第 5 章）。模型只吃 tensor，所以資料遲早要轉過來，這個類別選在一開始就一次轉好。

torch.FloatTensor(x) 做了兩件事，都經本機實測：

  1. 把 float64 轉成 float32。第 1 章看過，.values 得到的是 float64（64 位元浮點數）；FloatTensor 是 32 位元浮點數（float32），每個數字佔 4 bytes 而不是 8 bytes。x_train 的 2160 × 117 個數字，NumPy 版佔 2,021,760 bytes，tensor 版佔 1,010,880 bytes，剛好一半。
  2. 複製一份。建立之後再去改 NumPy 陣列，tensor 不會跟著變。對照組 torch.from_numpy(x) 則和原陣列共用同一塊記憶體（改一邊、另一邊跟著變），而且 dtype（資料型別）維持 float64。

為什麼要轉成 float32？因為 PyTorch 建立的模型參數預設就是 float32，GPU 對 float32 的運算也快得多；把 float64 的輸入直接餵給 float32 的模型，PyTorch 會報 dtype 不符的錯，不會自動幫你轉。轉換的代價是精度：float32 大約只有 7 位有效數字。本機實測 x_train 全部數值轉換後的最大絕對誤差是 3.81 × 10−6，最大相對誤差（誤差除以原值）5.94 × 10−8。以第一筆答案為例，float64 是 3.7109291，float32 存成 3.7109291553497314——多出來的尾數是 float32 能表示的最接近值，不是原資料。對一個預測誤差以「百分點」計的問題，這種誤差完全可以忽略。

第 15–18 行處理 y。y=None 是預設值：呼叫時不給 y，它就是 None。docstring 那句「if none, do prediction」說的就是這個用途——predict.py 只有特徵、沒有答案，所以只傳 x（3.4 節）。這時第 16 行 self.y = y 存的就是 None（直接寫 self.y = None 意思相同，只是比較明白）。本機實測：train 的 Dataset，self.x 是 (2160, 117) float32、self.y 是 (2160,) float32；只給 x 建立的 test Dataset，self.y 是 None。

前後各兩條底線的方法

__init__、__getitem__、__len__ 這種名字前後各有兩條底線的方法，是 Python 的特殊方法（special method），俗稱 dunder（double underscore）方法。你通常不會直接呼叫它們，而是由 Python 在對應的語法出現時代為呼叫：

你寫的Python 實際呼叫的本機實測（train 的 Dataset）
COVID19Dataset(x, y)__init__(self, x, y)建立物件
len(train_dataset)train_dataset.__len__()2160（valid 539、test 1078）
train_dataset[0]train_dataset.__getitem__(0)一個長度 2 的 tuple：x 與 y

第 2 章說 duck typing 只看「你會不會做這些動作」，這兩個特殊方法就是「會做」的具體意思：有 __len__ 就能被 len()，有 __getitem__ 就能被 [i]。

__getitem__ 回傳什麼

有答案時，第 25 行回傳 self.x[idx], self.y[idx]——逗號隔開的兩個值在 Python 裡就是一個 tuple（不可修改的序列）。本機實測 train_dataset[0]：

  • tuple 長度 2。
  • x 的 shape 是 (117,)：一筆資料的 117 個特徵。前 3 個值是 696.0、0.0、0.0——第一個是 id 696，正是第 2 章圖 2.2 裡訓練集的第一個列號；後面兩個是 AL、AK 兩州的 one-hot。
  • y 的 shape 是 ()，值 3.7109。shape 是空的，表示這是一個 0 維 tensor：只裝一個數字的 tensor，沒有任何軸。從一維的 self.y 用單一整數取一個元素，得到的就是 0 維 tensor。這個「每筆答案是 0 維」的事實，3.3 節疊成 batch 時會變成 (256,)。

沒有答案時，第 23 行只回傳 self.x[idx]：本機實測 test_dataset[0] 是單獨一個 shape (117,) 的 tensor，不是 tuple。所以同一個類別會依照有沒有 y，回傳兩種不同結構的東西，使用它的程式要配合：train.py 寫 for x, y in …，predict.py 寫 for x in …。

因為 idx 直接拿去索引 tensor，凡是 tensor 接受的索引這裡都接受。本機實測切片 train_dataset[0:3] 回傳 x (3, 117) 與 y (3,)；負數索引 train_dataset[-1] 取最後一筆，它的 y 是 2.1545。不過 DataLoader 只會用單一整數來要資料，這些用法只在你自己檢查資料時方便。

__len__：以 x 的列數為準

第 28 行 len(self.x) 對二維 tensor 回傳第一維的大小，也就是列數。用 x 而不是 y 是對的：test 的 Dataset 沒有 y，只有 x 永遠存在。__len__ 看起來不起眼，但 DataLoader 需要它來決定要產生 0 到多少的索引、總共切成幾批。

現在的做法：TensorDataset 與明確的 dtype

像 HW01 這種「資料已經全部在記憶體裡、每筆就是一列」的情況，PyTorch 內建的 TensorDataset 可以取代整個 COVID19Dataset：

import torch
from torch.utils.data import TensorDataset

train_dataset = TensorDataset(torch.tensor(x_train, dtype=torch.float32),
                              torch.tensor(y_train, dtype=torch.float32))
test_dataset = TensorDataset(torch.tensor(x_test, dtype=torch.float32))
  • torch.FloatTensor(…) 是舊式寫法。PyTorch 文件建議用 torch.tensor(data, dtype=…)（一定複製）或 torch.from_numpy(data).float()，dtype 寫在明處，讀的人不必記得「FloatTensor 等於 float32」。
  • TensorDataset 的回傳永遠是 tuple。上面 test_dataset[0] 回傳的是只有一個元素的 tuple，所以預測時要寫 for (x,) in loader（把只有一個元素的 tuple 拆開）或 for batch in loader: x = batch[0]——比 COVID19Dataset 多一點點麻煩，換來的是訓練和預測的結構一致。
  • 自己寫 Dataset 類別仍然是正確的技能：資料太大放不進記憶體、每筆要從磁碟讀圖片或文字、要在取資料時做轉換，都得自己寫 __getitem__。後面的作業（影像、語音）就是這種情況。

3.3　DataLoader：每個 epoch 為什麼是 9 個 batch

Dataset 一次只給一筆；訓練卻要一次處理一批（第 0 章：batch 是一次餵給模型的一小批資料）。在兩者之間把單筆組成一批的，就是 DataLoader。

一個 batch 是怎麼組出來的

每次訓練迴圈要「下一個 batch」，DataLoader 做三件事：

  1. 決定要哪幾筆。由一個叫 sampler（取樣器）的物件產生索引：shuffle=False 時依序產生 0、1、2…；shuffle=True 時是一個打亂過的順序（3.4 節）。一次拿 batch_size 個索引。
  2. 逐筆向 Dataset 要資料。對每個索引呼叫一次 dataset[i]，也就是 __getitem__——一個滿的 batch 就是 256 次呼叫。
  3. 疊起來。這一步叫 collate（整理、合併）。預設的做法是把 256 個 x（各為 (117,)）疊成 (256, 117)，把 256 個 y（各為 0 維）疊成 (256,)。

本機實測一個 batch 的樣子：型別是 list（不是 tuple），長度 2；第一個元素 x 是 (256, 117) float32，第二個 y 是 (256,)。__getitem__ 回傳 tuple，DataLoader 疊完卻交回 list，這是預設 collate 函式的固定行為，不影響使用：for x, y in train_loader 對 list 和 tuple 一樣能拆成兩個變數。

y 的形狀 (256,) 值得記住。第 0 章 0.2 節看過，模型最後一層輸出 (256, 1)，再用 squeeze(1) 壓成 (256,)——就是為了和這裡的 y 形狀一致，第 4 章會細講。

9、3、5：無條件進位

batch_size 是 config 的 256。資料筆數除以 256 通常除不盡，最後一批就是剩下的零頭。本機實測：

batch（CPU 端資料） valid 的 27 筆零頭

零頭 batch 可以丟掉。DataLoader 有一個 drop_last 參數，預設 False（保留最後不滿的一批）；設成 True 時，本機實測 train 的 len 從 9 變成 8，那 112 筆在這個 epoch 不會被看到。訓練時丟零頭有時是為了讓每批大小一致；但驗證與預測絕對不能丟：驗證少算 27 筆就不是在全部驗證集上評估，預測少 54 筆就交不出 1078 行答案。

還有一個沒寫出來的預設值：num_workers，本機實測為 0，意思是上面那三件事都在主程式自己的行程（process，作業系統裡一個正在執行的程式）裡做，沒有另開行程平行準備資料。資料在記憶體裡、每筆只是取一列 tensor，這樣最快；需要從磁碟讀圖片、做轉換的作業才會開多個 worker。

3.4　shuffle、pin_memory，以及不打亂的 test loader

shuffle=True：每個 epoch 一個新順序

shuffle=True 時，DataLoader 用的 sampler 是 RandomSampler（本機實測）。每個 epoch 開始迭代時，它產生一個新的隨機排列，依這個順序分批。因為 train.py 沒有給 DataLoader 的 generator 參數指定一個自己的亂數產生器（第 2 章的 torch.Generator；和 Python 用 yield 寫的 generator 無關），它的亂數來自第 2 章表格裡的 PyTorch 全域產生器——那張表在「誰在用它」一欄寫的「DataLoader 每個 epoch 打亂資料順序（第 3 章）」，指的就是這裡。

本機照 train.py 的實際順序執行（same_seed → 切分 → 建立模型 → 開始迭代），train_loader 第一個 batch 的前 8 個 id：

第一個 batch 的前 8 個 id
第 1 個 epoch2285、2508、1402、559、1361、2114、469、1572
第 2 個 epoch385、383、712、792、821、1382、971、665

每個 epoch 順序都不同；但因為全域產生器的起點被 same_seed 固定了，整串順序每次執行都一樣，這是第 0 章兩次訓練結果完全相同的另一個原因。注意「建立模型」也在這串流程裡：模型的初始權重是從同一個全域產生器抽的（第 2 章），抽走多少亂數，就決定了 DataLoader 從哪裡接著抽。所以改了模型的層數或寬度，連 batch 的順序都會跟著變。

為什麼訓練資料要打亂？訓練時模型每看完一個 batch 就更新一次權重（第 5 章）。如果每個 epoch 的 batch 都由同樣的 256 筆、依同樣的順序組成，模型每次都朝同一串方向走；資料若還照某種規律排列（例如同一州的列擠在一起），某些 batch 就只代表一小部分資料。每個 epoch 重新打亂，讓每個 batch 都比較接近整體資料的縮影。

驗證就不一樣了：驗證時模型不更新，打不打亂都在算同一個模型在同一批 539 筆上的表現，順序本來不該有任何影響。HW01 的 valid_loader 也設了 shuffle=True，而 3.5 節會看到，在這份程式的算法下，順序確實會影響結果。

pin_memory=True：讓 batch 放在可以直接傳給 GPU 的記憶體

GPU 有自己的一塊記憶體（顯示記憶體），GPU 上的運算只能讀那裡的資料，所以每個 batch 都要從主記憶體複製過去——這就是「搬上 GPU」。作業系統可以把一般記憶體暫時搬到磁碟上（換頁，paging），需要時再搬回來。GPU 從主記憶體讀資料時，不能讀到一塊可能被搬走的記憶體，所以一般記憶體裡的資料要傳上 GPU，CUDA 會先把它複製到一塊「不會被搬走」的暫存區，再從那裡傳。這種被鎖定、不會被換頁的記憶體叫 pinned memory（也叫 page-locked memory）。

pin_memory=True 讓 DataLoader 把組好的 batch 直接放進 pinned memory，省掉那一次中轉複製；搭配 .to(device, non_blocking=True)，傳輸還能和 CPU 的其他工作同時進行。本機實測，設了之後 batch 的 is_pinned() 是 True，但 device 仍是 cpu——pin 只是換一種記憶體，不會替你搬上 GPU；不設時 is_pinned() 是 False。

效果呢？本機實測迭代 10 個 epoch、每個 batch 都 .cuda()（搬上 GPU 的簡寫）：pin 0.038 秒、不 pin 0.039 秒。這份資料一個 batch 才 256 × 117 個 float32，大約 120 KB，傳輸時間本來就微不足道，量不出差別；HW01 的訓練迴圈也沒有用 non_blocking=True。pin_memory 是資料量大（例如一批影像）時才看得出效果的設定，這裡寫著無害。

3.5　為什麼印出的 1.661 比真實的 2.069 低

目錄頁、第 0 章、第 2 章都留了同一個問題：train.py 印出的最佳驗證 loss 是 1.661，但把當時存下的 models/model.ckpt 拿到全部 539 筆驗證資料上一次算完 MSE，得到的是 2.069（更精確是 2.0685）。同一個模型、同一批資料，差了 0.4。原因有三層，逐層看。

先看驗證 loss 是怎麼算的。完整的訓練迴圈留給第 5 章，這裡只看每個 epoch 結尾計算驗證 loss 的這一段：

只需要知道四件事：第 73 行從 valid_loader 一次拿一個 batch；第 77 行的 criterion 是 nn.MSELoss(reduction='mean')（train.py 第 29 行），算出這一個 batch 的 MSE；第 79 行把它（.item() 把 0 維 tensor 取成一個 Python 數字）記進 loss_record；第 81 行把 3 個 batch 的 MSE 加總再除以 3。with torch.no_grad() 與 .to(device) 是第 5 章的內容，這裡不影響推理。

第一層：最後 27 筆的份量被放大了將近 10 倍

真實的驗證 MSE 是 539 個平方誤差的平均，每筆在平均裡的份量都是 1/539（這裡的「份量」是平均時的加權比例，和模型的權重無關）。第 81 行算的卻是「平均的平均」：

真實 MSE ＝ (256 · L1 ＋ 256 · L2 ＋ 27 · L3) ／ 539
第 81 行 ＝ (L1 ＋ L2 ＋ L3) ／ 3
L1、L2、L3 是三個 batch 各自的 MSE

在真實 MSE 裡，最後一個 batch 只佔 27/539 ≈ 5% 的份量；在第 81 行的算法裡，它和兩個 256 筆的 batch 一樣佔 1/3。換算到每一筆：落在滿 batch 的一筆，份量是 1/(3 × 256) = 1/768；落在最後一批的一筆，份量是 1/(3 × 27) = 1/81，大了約 9.5 倍。

如果最後那 27 筆每次都是固定同一組，這只會造成一個固定的偏移。本機用 shuffle=False 實測 model.ckpt：三個 batch 的平均是 2.0690，和一次算完的 2.0685 幾乎一樣——固定那 27 筆時，偏移小到可以忽略。問題出在第二層。

第二層：valid_loader 打亂，所以同一個模型每次量到不同的值

valid_loader 設了 shuffle=True，哪 27 筆落進最後一批，每個 epoch 都不一樣。這 27 筆碰巧都是好預測的，第 81 行的結果就偏低；碰巧混進幾筆誤差大的，就偏高——而且因為它們的份量被放大了 9.5 倍，影響很明顯。

本機拿同一個 model.ckpt，不改任何權重，只換 valid_loader 的打亂順序重算第 81 行：

量法結果
539 筆一次算完（真實 MSE）2.0685
shuffle=False 的 batch 平均2.0690
shuffle=True，換 20 種順序1.7670～2.4477，平均 2.0699；前 5 次是 1.9214、1.973、2.1159、2.0788、1.8774
shuffle=True，換 200 種順序最小 1.7069、第 5 百分位 1.8095、中位數 2.0528、最大 2.8467

（第 5 百分位：把 200 個值由小排到大，有 5% 的值比它小；中位數：剛好排在正中間的那個值。）

這裡要分清兩種「不準」：一種是每次量都往同一個方向偏（例如總是偏低），叫系統性偏差；另一種是每次量的結果上下亂跳，但平均起來在真值附近，叫雜訊。平均起來，打亂的量法沒有系統性偏低：20 次的平均 2.0699 和真實的 2.0685 幾乎一樣。但單次量測的起伏很大：同一個模型，一次可能量到 1.77，下一次 2.45。第 0 章看過的 stdout 結尾就是活生生的例子：第 1881～1883 個 epoch 印出的驗證 loss 是 2.3940、2.0718、2.5030，相鄰 epoch 的模型只差一次更新，量到的數字卻跳了 0.4。

第三層：在將近 1900 個有雜訊的數字裡挑最小的

第 85 行 if mean_valid_loss < best_loss 只在創新低時存檔（第 5 章細講）。訓練一共跑了 1883 個 epoch，每個 epoch 量一次，也就是將近 1900 個量測值，每一個都帶著第二層的雜訊。從一堆有雜訊的數字裡挑最小的，挑中的幾乎必然是「模型不錯、而且這次分組又特別幸運」的那一次——雜訊往下偏的量測比較容易勝出，所以被挑中的數字系統性地比該模型的真實表現低。這個現象在統計上叫選擇偏差（selection bias），也常被稱作「贏家的詛咒」（winner's curse）。

1.661 就是這樣產生的：它是第 1483 個 epoch（第 0 章的 log）那個模型、在那一次特定的打亂順序下量到的值。存下來的權重正是那個模型，但把它換 200 種順序重量，最小值也才 1.7069——1.661 比這 200 次裡最幸運的一次還低。這不矛盾：重量時只抽了 200 次，訓練過程卻抽了 1883 次（每次量的是略有不同的模型），抽的次數越多，越容易碰到極端偏低的那一次，而 best_loss 專門把那一次留下來。真實的表現，是一次算完的 2.069。

同一個模型、不同打亂順序的量測 一次算完的真實 MSE best_loss 挑出的值（控制邏輯）

三層合起來：第一層讓單次量測很容易受最後 27 筆影響（份量放大），第二層讓這個影響每個 epoch 都不一樣，第三層專挑偏低的那一次。少了任何一層，偏差都會小很多：不打亂，量測就是固定的 2.0690；依筆數加權，最後 27 筆就只佔 5%，打亂也晃不了多少；不挑最小值，就不會系統性偏低。

還有一個副作用：挑選本身也被雜訊影響。best_loss 比較的是帶雜訊的數字，所以被存下來的 checkpoint，不一定是 1883 個 epoch 裡真實表現最好的那一個。

同樣的偏差也出現在第 2 章的實驗裡

第 2 章動手做的兩個改良版本，印出的最佳 loss 也是同樣挑出來的。本機用同樣的方法重量它們的 checkpoint：

如果拿印出的 0.982 來比，會得出「改良後的 DNN 贏過線性迴歸」的錯誤結論；真實數字顯示它還差一截。

train loss 也有同樣的問題：train 的最後一個 batch 是 112 筆，第 67 行一樣是各 batch 平均再平均；而且 train loss 是一邊更新權重一邊記錄的，9 個 batch 的 loss 來自 9 個略有不同的模型，本來就不是某一個固定模型的 MSE。第 5 章講訓練迴圈時會再提。

現在的做法：驗證不打亂，依筆數加權

修法只要動兩處。第一，valid_loader 改成 shuffle=False（和 test loader 一樣）；第二，累加每個 batch 的平方誤差總和，最後除以總筆數，而不是平均各 batch 的平均：

valid_loader = DataLoader(valid_dataset, batch_size=config['batch_size'], shuffle=False, pin_memory=True)

model.eval()
total, n = 0.0, 0
with torch.no_grad():
    for x, y in valid_loader:
        x, y = x.to(device), y.to(device)
        pred = model(x)
        total += nn.functional.mse_loss(pred, y, reduction='sum').item()
        n += len(y)
mean_valid_loss = total / n
  • model.eval() 與 torch.no_grad() 是原程式本來就有的（train.py 第 71、75 行，第 5 章講），不是這次修改的一部分。
  • reduction='sum' 讓一個 batch 回傳平方誤差的總和而不是平均，加總後除以 539，數學上就等於一次算完的 MSE，與 batch 怎麼切無關。也可以寫 criterion(pred, y).item() * len(y)，把平均乘回總和。
  • 只有 shuffle=False 不加權：量測固定了（每個 epoch 都是同一組 27 筆），對 HW01 的 model.ckpt 來說是 2.0690，離真值很近。但固定的偏移仍在，換一個資料集或 batch_size 可能就不小。兩處一起改才正確。
  • 驗證集只有 539 筆時，更簡單的做法是驗證用 batch_size=len(valid_dataset)，一個 batch 一次算完。驗證不算梯度、佔的記憶體小，batch 可以比訓練時大很多。
  • 修好量法，第三層的「挑最小值」仍然存在，只是不再被打亂的雜訊放大。今天的習慣是：用驗證集挑模型，最後的成績用沒有參與挑選的資料來報告。HW01 的測試集答案不在我們手上，這一步由 Kaggle 代勞：上傳 pred.csv 後，Kaggle 用它保留的答案算分。
  • 現成的工具也是這樣算的，例如 TorchMetrics 的 MeanSquaredError 會跨 batch 累加平方誤差與筆數，最後才相除。

本章重點

  • COVID19Dataset 繼承 Dataset，只做三件事：__init__ 把 NumPy float64 轉成（並複製成）float32 tensor，__getitem__ 回傳第 i 筆（有答案時是 x、y 的 tuple，沒答案時只有 x），__len__ 回傳列數。
  • DataLoader 用 sampler 決定索引、逐筆呼叫 dataset[i]、再 collate 疊成一批：x (256, 117)、y (256,)，型別是 list。
  • batch 數是筆數 ÷ 256 無條件進位：train 9（最後 112 筆）、valid 3（256、256、27）、test 5（最後 54 筆）。drop_last 預設保留零頭，驗證與預測都不能丟。
  • shuffle=True 的順序來自 PyTorch 全域產生器，每個 epoch 不同、每次執行相同；test loader 必須 shuffle=False，因為 save_pred 依順序編 id。pin_memory 在這份小資料上量不出差別。
  • 印出的 1.661 偏低有三層原因：各 batch 平均再平均讓最後 27 筆在平均裡的份量放大約 9.5 倍；valid 也打亂，同一個模型每次量到 1.77～2.45 不等；再從將近 1900 個量測裡挑最小值。真實 MSE 是 2.069，比較模型時要用一次算完的數字。

自我測驗

1. 如果把 config 的 batch_size 改成 100，train、valid、test 三個 loader 各有幾個 batch？valid 最後一批有幾筆？

無條件進位：train 2160 ÷ 100 = 21.6 → 22 個；valid 539 ÷ 100 = 5.39 → 6 個；test 1078 ÷ 100 = 10.78 → 11 個。valid 最後一批是 539 − 500 = 39 筆。

2. train_dataset[0] 的 y 是 0 維 tensor，為什麼 DataLoader 給出的 batch 裡 y 是 (256,) 而不是 (256, 1)？

collate 把 256 個形狀為 () 的 tensor 疊在一起，新增的那一維就是 batch 維，所以是 (256,)。若 __getitem__ 回傳的 y 是 (1,)，疊出來才會是 (256, 1)。模型最後要 squeeze(1) 成 (256,)，就是為了和這個 y 對齊（第 4 章）。

3. 把 predict.py 第 37 行改成 shuffle=True，模型算出的預測值會變嗎？上傳的成績呢？

每一筆的預測值不變，模型是同一個，只是順序被打亂。但 save_pred 用 enumerate 依順序編 id，打亂後每個預測都被貼到錯的 id 上，成績會差到像亂猜。

4. 只把 valid_loader 改成 shuffle=False、不改第 81 行的平均方式，1.661 那種偏低還會發生嗎？

大幅減輕。不打亂時同一個模型每次量到同一個值（對 model.ckpt 是 2.0690，離真值 2.0685 很近），第二層的雜訊消失，第三層「挑最小值」就沒有隨機的好運可挑。但最後 27 筆份量放大的固定偏移還在，所以正確做法是連平均方式一起改成依筆數加權。

5. 同學說：「我的 DNN 印出 0.982，線性迴歸是 1.166，所以 DNN 比較好。」哪裡錯了？

兩個數字的量法不同。0.982 是各 batch 平均再平均、驗證集又打亂、再從一千多個 epoch 裡挑出的最小值，系統性偏低；1.166 是 539 筆一次算完的 MSE。把同一個 checkpoint 一次算完是 1.240，仍然輸給線性迴歸。

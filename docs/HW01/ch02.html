2.2　same_seed：把亂數固定住

第 0 章說過，seed 是亂數產生器的起點，固定 seed 就讓每次抽出的亂數序列都一樣；第 0 章也實測過，train.py 重跑兩次，最佳 loss 1.661、停在第 1883 個 epoch，結果完全相同。做到這件事的就是這 8 行：

一支程式裡有好幾個亂數產生器

電腦產生的亂數其實是偽亂數（pseudo-random）：一個演算法從某個起始狀態出發，每呼叫一次就算出下一個數字、更新一次狀態。數字看起來雜亂，但只要起始狀態相同，算出來的序列就一模一樣。seed 就是用來設定這個起始狀態的。

關鍵在於：一支 Python 程式裡通常不只一個亂數產生器，每個函式庫各有各的，彼此獨立，設定其中一個不會影響其他。這也是為什麼 same_seed 要連續設好幾個。每個函式庫都有一個全域產生器：程式各處呼叫該函式庫的亂數函式、又沒有另外指定產生器時，大家共用的就是這一個。下表把 HW01 會碰到的亂數產生器全部列出來，對照「誰設定了它」與「誰在用它」：

亂數產生器由誰設定HW01 裡誰在用
Python 內建 random 模組沒有人設定沒有人用（HW01 沒有 import random）
NumPy 的全域產生器第 11 行 np.random.seed沒有人用（整個 HW01 只有第 11 行出現 np.random）
PyTorch 的 CPU 全域產生器第 12 行 torch.manual_seed模型權重的初始值（My_Model 先在 CPU 上建立，再 .to(device) 搬上 GPU）；DataLoader 每個 epoch 打亂資料順序（第 3 章）
每張 GPU 各自的產生器第 13–14 行 torch.cuda.manual_seed_all沒有人用（模型裡沒有需要在 GPU 上抽亂數的元件）
random_split 專用的 torch.Generatorutils.py 第 22 行自己設定切分訓練／驗證集（2.3 節）

這張表說明了一件事：真正影響 HW01 結果的只有兩個——第 12 行設定的 PyTorch 全域產生器，以及 2.3 節那個切分專用的產生器。其餘幾行是通用的範本，寫來保險，換到用得到它們的作業就會生效。

第 12 行到底固定了什麼，可以直接觀察。本機實測：呼叫 same_seed(5201314) 之後立刻抽 3 個亂數，再重設 seed 重抽一次：

呼叫 same_seed(5201314) 後抽出的 3 個數重設 seed 再抽一次
torch.rand(3)0.5436、0.9728、0.8315完全相同
np.random.rand(3)0.6076、0.9134、0.281完全相同

torch.rand(3) 與 np.random.rand(3) 都是「抽 3 個 0～1 之間的均勻亂數」，但兩組數字完全不同——兩個函式庫用同一個 seed，各自的演算法算出各自的序列，印證了上表「彼此獨立」那一點。而同一個函式庫、同一個 seed，重來一次就分毫不差。模型的 2,033 個初始權重（第 0 章 0.2 節）就是從 PyTorch 這條序列裡抽出來的，所以每次訓練都從同一組起點出發。

第 9–10 行：cuDNN 的兩個開關

cuDNN 是 NVIDIA 為深度學習提供的 GPU 函式庫，負責卷積（convolution）這類運算。同一個運算，cuDNN 常有好幾種演算法可選，兩個開關就是在管這件事：

  • benchmark = True 會在第一次遇到某種輸入形狀時把幾種演算法都試跑一遍，挑最快的。代價是「最快」可能每次量出來不一樣，選到的演算法不同，結果的小數尾數就可能不同。第 10 行把它設成 False，不做這種挑選。
  • deterministic = True 要求 cuDNN 只用確定性（deterministic）的演算法，也就是同樣的輸入保證得到逐位元相同的輸出。有些較快的演算法為了平行化，加總的順序每次不固定；浮點數加法的順序不同，尾數就會不同（每加一次都會四捨五入到有限的位數，先加哪兩個，捨去的誤差就不一樣）。

本機實測這兩個旗標的值：呼叫 same_seed 之前是 deterministic=False、benchmark=False，之後是 deterministic=True、benchmark=False。也就是說 benchmark 預設就是關的，第 10 行只是把預設值明白寫出來；真正改變狀態的只有第 9 行。

不過，HW01 的模型只有 nn.Linear 與 nn.ReLU（第 0 章 0.2 節），沒有卷積。Linear 在 GPU 上是矩陣乘法，由另一個函式庫 cuBLAS 處理，不經過 cuDNN。所以這兩行在 HW01 裡其實沒有作用的對象——它們和 NumPy 那一行一樣，是為之後用到卷積的作業準備的範本。HW01 兩次訓練結果完全相同，靠的是第 12 行與 2.3 節的切分產生器，加上同一台機器、同一版軟體。

第 12–14 行與一個小瑕疵

第 13–14 行先檢查 torch.cuda.is_available() 才設定 GPU 的 seed，所以在沒有 GPU 的機器上，same_seed 本身不會報錯（本機實測）。但 HW01 不會走到這一步：第 0 章說過，沒有 GPU 時 import config 就已經以 RuntimeError 結束了。另外，現在的 PyTorch 文件寫明 torch.manual_seed 會設定所有裝置的產生器（含 GPU），所以第 13–14 行和第 12 行重複，無害但多餘。

最後看第 8 行的說明字串（docstring，寫在函式第一行、用來說明函式用途的字串）。仔細數，開頭是四個引號 """"：Python 把前三個當成字串的開頭，第四個就變成字串內容的第一個字元。本機實測 same_seed.__doc__ 的值是：

'" Fixes random number generator seeds for reproducibility. '

開頭多了一個 "。__doc__ 是 Python 存放 docstring 的屬性；用 help(same_seed) 查說明時看到的就是它。這不影響程式執行，只是筆誤，但它是個好例子：程式碼「能跑」不代表每個字元都是作者想要的。

現在的做法：一次設齊、用區域產生器、需要時強制確定性

same_seed 的思路在 2026 年仍然正確，但常見的寫法多做了三件事：

import random, os
import numpy as np
import torch

def seed_everything(seed):
    random.seed(seed)                          # Python 內建 random 也設
    np.random.seed(seed)
    torch.manual_seed(seed)                    # 已涵蓋所有 GPU
    os.environ['CUBLAS_WORKSPACE_CONFIG'] = ':4096:8'   # 文件指定的值，讓 cuBLAS 可以確定性地運算
    torch.use_deterministic_algorithms(True)   # 沒有確定性版本的運算直接報錯

# NumPy 的新式寫法：建立自己的產生器，不動全域狀態
rng = np.random.default_rng(5201314)
x = rng.random(3)
  • 把 Python 的 random 也設上。今天用不到，不代表之後加進來的程式（或某個函式庫）不會用。
  • torch.use_deterministic_algorithms(True) 比 cuDNN 的旗標管得更廣：它涵蓋 cuBLAS 在內的所有 PyTorch 運算，遇到沒有確定性實作的運算會直接拋出錯誤，而不是悄悄給出不同的尾數。依 PyTorch 文件，在 GPU 上使用時還要設定環境變數 CUBLAS_WORKSPACE_CONFIG。代價是可能變慢，所以通常只在除錯或需要逐位元重現時打開。
  • 用區域產生器取代全域狀態。NumPy 官方建議 np.random.default_rng(seed) 建立自己的產生器，np.random.seed 屬於舊式介面。PyTorch 這邊的同一個想法，HW01 已經用在切分上了（下一節）。

許多訓練框架也內建了同樣的函式，例如 PyTorch Lightning 的 seed_everything、Hugging Face transformers 的 set_seed。

2.3　train_valid_split：539 是怎麼來的

train.py 第 106 行傳進來的是 train_data（2699 × 118 的 NumPy 陣列）、config['valid_ratio']（0.2）、config['seed']（5201314）。逐行看。

第 19–20 行：先算大小

len(data_set) 對二維陣列回傳列數 2699。0.2 * 2699 在數學上是 539.8，但浮點數無法精確表示 0.2，本機實測算出來是 539.8000000000001。接著 int() 把它變成整數——int() 是直接截掉小數部分，不是四捨五入，所以得到 539，不是 540。第 20 行再用 2699 − 539 = 2160 算出訓練集大小。用減法而不是另外乘 0.8，保證兩份加起來剛好是 2699，一列都不會少。

讀 code 不盡信文件：config.py 的註解算錯了對象

config.py 第 12 行在 'valid_ratio': 0.2 後面註解 validation_size = train_size * valid_ratio。照這個公式，驗證集應該是 2160 × 0.2 = 432 筆。但第 19 行乘的是 len(data_set)，也就是切分前的全部 2699 列，所以實際是 539 筆。正確的註解應該寫成 validation_size = len(train_data) * valid_ratio（train_data 指切分前的那一份）。第 0 章 0.4 節提過這個不一致，這裡是它的出處。

第 21–22 行：random_split 與它自己的 Generator

random_split 是 PyTorch 提供的切分函式（utils.py 第 4 行從 torch.utils.data import 進來）。它的做法是：

  1. 產生 0～2698 這 2699 個列號的一個隨機排列（PyTorch 內部用 torch.randperm）。
  2. 依照第二個參數 [2160, 539]，把排列的前 2160 個位置分給第一份、接下來的 539 個分給第二份。
  3. 回傳兩個 Subset 物件。

Subset 不複製資料，它只記住兩樣東西：原始資料的參照，以及一串列號 indices。要第 i 筆時，它回頭去原始資料拿 indices[i] 那一列。本機實測，兩個 Subset 的長度是 2160 與 539，indices 的前 10 個如下：

訓練集的前 10 個列號是 696、2073、909、1475、2165、2487、479、1795、2150、2588，順序是亂的；驗證集的前 10 個是 1995、1042、86、1667、464、481、1040、85、423、788。這 10 列的 id 也正是這 10 個數字——但別把「id 等於列號」當通則，第 1 章看過 id 在 2239 有一個缺號。

還有一個細節：random_split 原本設計來切 PyTorch 的 Dataset（第 3 章的主題；現在只要知道它是「能用 len() 問長度、能用 [i] 取第 i 筆」的資料容器），但這裡傳進去的 data_set 是 NumPy 陣列，它卻照樣能切。因為 Subset 只需要對原始資料做兩件事——len() 與 [i]——而 NumPy 陣列兩件都支援。Python 不檢查「你是不是某個類別」，只看「你會不會做這些動作」，這種風格叫 duck typing。

為什麼要另外建一個 Generator

第 22 行的 torch.Generator() 建立一個全新、獨立的 PyTorch 亂數產生器，.manual_seed(seed) 設定它的 seed 並回傳它自己，所以可以寫在同一行傳給 generator=。random_split 只從這個產生器抽亂數，不碰 2.2 節的全域產生器。本機實測了四種情況：

做法切分結果
同一個 seed（5201314）再切一次和原本完全相同
改用 seed 1不同：訓練集前 10 個變成 1659、792、971、1755、777、408、450、248、1528、1631
切之前先執行 torch.manual_seed(0) 改掉全域 seed和原本完全相同——全域 seed 管不到這個產生器
不傳 generator，改用全域產生器全域 seed 相同，切分就相同；全域 seed 不同，切分就不同

第三列是這個設計的重點：切分結果只由「資料、比例、seed」三樣東西決定，和程式其他地方抽過幾次亂數、全域 seed 設成什麼都無關。predict.py 就是受益者：它沒有呼叫 same_seed（第 0 章看過，它的輸出在兩行 True／0 之後直接是資料大小），全域產生器的狀態每次都不一樣，但它重切出來的訓練／驗證集和 train.py 的一模一樣，印出的大小也一樣。

反過來說，如果第 22 行不傳 generator（第四列），train.py 因為先呼叫了 same_seed，每次切分仍然相同；但 predict.py 每次執行都會切出不同的兩份。在 HW01 裡這碰巧不影響預測結果（predict.py 只用測試集），但在需要「訓練和評估用同一個驗證集」的程式裡，這就是一個很難察覺的 bug。

附帶一提，train.py 第 12 行 from torch.utils.data import DataLoader, random_split 也 import 了 random_split，但 train.py 自己從頭到尾沒有呼叫它——切分是在 utils.py 裡做的。這是從原版筆記本拆檔時留下的痕跡，無害。

第 23 行：Subset 變回 NumPy 陣列

np.array(train_set) 收到的是一個 Subset 物件。NumPy 看到它有 len() 又能用 [i] 取值，就把它當成一個序列：從第 0 筆取到第 2159 筆，每一筆都是原始陣列的一列（118 個 float64），再把這 2160 列疊成一個新的二維陣列。本機實測結果是 (2160, 118)、float64，和 train.py 印出的大小一致。這一步會複製資料：回傳的是一個新陣列，不再是 Subset 那種「參照 + 列號」。

同樣的事有更直接的寫法：data_set[train_set.indices]，用 NumPy 的整數陣列索引（fancy indexing）一次取出那些列：中括號裡放一個列號的列表，就依列表的順序取出那些列（2.4 節取欄時會再用到同一招）。本機實測兩種寫法的結果完全相同（np.array_equal 為 True），耗時分別約 0.0015 秒與 0.0012 秒——這份資料太小，看不出差別。差別在可讀性：後者明白寫出「依列號取列」，前者要讀者知道 NumPy 會怎麼處理一個 Subset。

切出來的驗證集長什麼樣

隨機切分有一個好處：每一州都有機會進驗證集。本機實測，539 筆驗證資料裡 37 州全部出現，每州 7～25 列。答案欄的分布也和訓練集相近但不相同：

平均差了約 0.4 個百分點，這是抽樣造成的自然落差。但第 1 章 1.6 節指出的問題仍然在：資料是滑動視窗，同一州相鄰兩列共享 4 天；隨機切分讓驗證集的每一列，前後鄰居多半落在訓練集裡。圖 2.2 那種「打亂再切」的做法，正是讓驗證集被「偷看」的機制。第 1 章的「現在的做法：照時間切驗證集」框已經示範過替代方案，這裡不再重複。

現在的做法：用比例切、直接用索引

2022 年的範例手動算出兩份的大小再傳給 random_split。PyTorch 1.13 起，random_split 可以直接收比例：

train_set, valid_set = random_split(data_set, [0.8, 0.2],
                                    generator=torch.Generator().manual_seed(seed))
train, valid = data_set[train_set.indices], data_set[valid_set.indices]

本機實測，[0.8, 0.2] 切出來的大小也是 2160 與 539（依 PyTorch 文件，比例乘出來的小數部分被捨去後，剩下的筆數從第一份開始輪流各補 1 筆，所以總數一定等於原資料：2159 + 539 = 2698，差的 1 筆補給第一份，得到 2160）。第二行用 indices 直接取列，取代 np.array(Subset)。表格資料在 PyTorch 之外，最常見的切分工具是 scikit-learn 的 train_test_split；但對這份時間序列資料，更重要的是第 1 章說的「照時間切」，而不是換一個隨機切分的函式。

2.4　select_feat：x 與 y，以及被當成特徵的 id

機器學習的慣例是：模型的輸入叫 x（特徵，features），要預測的答案叫 y（目標，target）。這個函式就是把 2.3 節切好的三份資料拆成 x 和 y。第 1 章 1.5 節說過，.values 之後欄名全部消失，程式只能用位置指稱欄位——這個函式通篇都在用位置。

第 28–29 行：答案是最後一欄，其餘是 x

  • train_data[:, -1]：每一列的最後一欄，也就是第 5 天的 tested_positive。結果是一維陣列 (2160,)，不是 (2160, 1)——這個形狀在第 4 章講 squeeze(1) 時會再出現。
  • train_data[:, :-1]：每一列「從頭到倒數第二欄」，118 − 1 = 117 欄。
  • raw_x_test = test_data：測試集本來就沒有答案欄，117 欄直接整份拿來用，不必切。

這裡有一個沒寫出來、但程式完全依賴的前提：訓練集的前 117 欄和測試集的 117 欄，排列順序一模一樣。第 1 章圖 1.1 驗證過這件事；本機實測兩邊的第 116 欄（0 起算的最後一欄）都是 worried_finances.4。如果測試集的欄位順序和訓練集不同，模型會把 A 欄學到的權重套在 B 欄上，程式不會報錯，只會默默給出錯的預測。

第 31–34 行：feat_idx 決定模型看哪幾欄

feat_idx 是一串欄號，第 36 行用 raw_x[:, feat_idx] 從三份 x 裡挑出這些欄。這就是 2.3 節看過的整數陣列索引，只是放在逗號後面，取的是欄而不是列。兩個分支的結果：

id（編號） 輸入特徵（州別與問卷） 答案

本機實測兩個分支回傳的形狀：

select_allfeat_idxx_trainx_validx_testy_trainy_valid
True（config 的設定）0～116(2160, 117)(539, 117)(1078, 117)(2160,)(539,)
False[0, 1, 2, 3, 4](2160, 5)(539, 5)(1078, 5)(2160,)(539,)

第 32 行寫的是 range(raw_x_train.shape[1])，用 x 的實際欄數產生欄號，而不是寫死 117——資料多一欄少一欄，這行都不用改。train.py 第 117 行印的 number of features: 117 就是 x_train.shape[1]，而第 126 行建立模型時用的 input_dim=x_train.shape[1] 也是同一個值。所以改 feat_idx 會自動改變模型第一層的大小，模型那邊不必跟著動手改（第 4 章會看到 117 這個數字怎麼決定第一層的 1,888 個參數）。

第 36 行用同一個 feat_idx 去挑三份 x，這保證訓練、驗證、測試三份的欄位一一對應。答案 y 則不經過 feat_idx，一定只有一欄。

讀 code 不盡信文件：「Selects useful features」其實什麼都沒挑

第 27 行的 docstring 說這個函式「挑出有用的特徵」，但兩個分支都沒有在挑：

  • select_all=True（預設，也是 config 的設定）把答案以外的 117 欄全部拿走，包含第 0 欄的 id。第 1 章已經說明為什麼 id 不該是特徵：它在訓練集裡隱含時間（和答案相關 0.264），但測試集的 id 是從 0 重新編號的另一套，同一個數字代表的時間點毫無關係。
  • select_all=False 的 [0, 1, 2, 3, 4] 只是佔位用的範例，旁邊的 TODO 註解就是在說「這裡請你自己填」。對照欄位版圖，這 5 欄是 id 加上 AL、AK、AZ、AR 四個州的 one-hot——沒有任何一欄是問卷或陽性率。拿這 5 欄訓練，模型只知道「這列是不是這四州之一」以及一個不能用的編號。

id 到底拖累多少？先看線性模型：目錄頁〈先說在前面〉的線性迴歸用的是拿掉 id 的 116 欄，在和範例程式同一個驗證集上的驗證 MSE 是 1.166；本機另外實測，把 id 加回去、用 117 欄是 1.172。範例神經網路在同一個驗證集上的真實 MSE 是 2.069。注意要用這個數字比，不能用訓練時印出的 1.661，原因第 3 章會解釋。至於範例的神經網路（DNN）拿掉 id 會怎樣，留給下面的動手做，答案附在題目後面。填好 feat_idx 正是作業提示裡通過 medium 基準線的方法，第 7 章會正式處理。

本章重點

  • train.py 第 101、106、114 行依序呼叫 same_seed、train_valid_split、select_feat，三者都在 utils.py。
  • 一支程式裡有好幾個彼此獨立的亂數產生器。影響 HW01 結果的只有 PyTorch 全域產生器（模型初始權重、DataLoader 打亂）與切分專用的 torch.Generator；NumPy、cuDNN、GPU seed 那幾行在 HW01 沒有作用對象，Python 的 random 沒有被設定。
  • 驗證集大小是 int(0.2 × 2699) = 539（截斷，不是四捨五入），乘的是切分前的全部資料；config.py 的註解寫成 train_size * valid_ratio 是錯的。
  • random_split 先打亂列號再依序切開，回傳只記列號的 Subset；用獨立的 Generator，所以切分只由資料、比例、seed 決定，連沒呼叫 same_seed 的 predict.py 都切得一模一樣。
  • select_feat 以最後一欄為 y、其餘 117 欄為 x；預設 select_all=True 會把 id 也當成特徵，False 分支的 [0, 1, 2, 3, 4] 是 id 加四個州，只是佔位用的 TODO。

自我測驗

1. 如果把 valid_ratio 改成 0.25，驗證集與訓練集各有幾筆？

0.25 × 2699 = 674.75，int() 截掉小數得 674；訓練集 2699 − 674 = 2025。注意不是四捨五入成 675。

2. 呼叫 same_seed 後，torch.rand(3) 與 np.random.rand(3) 用的是同一個 seed，為什麼抽出的數字不一樣？

PyTorch 與 NumPy 各有自己的亂數產生器與演算法，彼此獨立。同一個 seed 只保證「同一個產生器」每次產生相同的序列，不保證不同產生器之間的序列相同。

3. 假設把 utils.py 第 22 行的 generator=... 參數刪掉。train.py 每次執行的切分還會相同嗎？predict.py 呢？

train.py 會：它在切分前呼叫了 same_seed，全域產生器的起點固定，切分就固定。predict.py 不會：它沒有呼叫 same_seed，全域產生器的起點每次不同，每次切出的兩份都不一樣。在 HW01 裡碰巧不影響預測（predict.py 只用測試集），但這正是用獨立 Generator 的理由。

4. HW01 的模型只有 Linear 與 ReLU。same_seed 裡設定 cuDNN 的兩行，在 HW01 有作用嗎？

沒有作用對象。cuDNN 負責卷積這類運算；Linear 在 GPU 上是矩陣乘法，由 cuBLAS 處理。另外 benchmark 的預設值本來就是 False。這兩行是給之後有卷積的作業用的範本。

5. select_all=False 時模型的輸入是哪 5 欄？為什麼這 5 欄幾乎不可能訓練出好模型？

0 起算的第 0～4 欄：id、AL、AK、AZ、AR。id 在測試集是另一套編號，不能當特徵；另外 4 欄只表示「這列是不是這四州之一」，完全沒有問卷或前幾天陽性率的資訊，而第 1 章看過，和答案最相關的正是前幾天的陽性率。

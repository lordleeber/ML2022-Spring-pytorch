ML2022 Spring · HW04 讀碼教材

第 5 章　預測與 output.csv

test.py 只有 91 行：讀 8,000 句測試資料，一次一句、整句送進模型，把 600 個分數裡最高的那個翻回說話者名稱，寫成 output.csv。這一章逐行讀它，並回答幾個問題：為什麼一次只能送一句？只看過 128 格的模型，怎麼處理長達 4,940 格的句子？想一次送一批，補值會不會改變答案？第 4 章的 deepcopy bug 和忘了 model.eval()，在交出去的檔案上留下多少痕跡？本章的數字都是實測，量測程式在 docs/tools/hw04_facts.py ch05。

5.1　測試集：InferenceDataset

第 15–18 行讀 testdata.json，取出 "utterances" 清單：8,000 筆，每筆只有 feature_path 與 mel_len，沒有說話者（第 1 章）。__getitem__ 讀進那一句的 mel（形狀 (長度, 40)），連同檔名一起回傳（第 28 行）。檔名之後會寫進 output.csv 的 Id 欄，所以要一路帶著。

和訓練用的 myDataset.__getitem__（dataset.py:34-49）比，少了兩件事：沒有標籤，也沒有切段。訓練時長於 128 格的句子會被隨機切出 128 格（dataset.py:40-44），這裡整句原封不動。測試句的長度是 214 到 4,940 格，中位數 538 格（第 1 章），也就是 2.1 到 49.4 秒。實測第 0 句是 (813, 40)、第 1 句是 (738, 40)。

投影片前後不一致：4,000 還是 8,000 句？

投影片 p.5 說測試資料是「4000 processed audio features (public & private)」，p.20 的繳交格式卻說標題列之後要有 8000 行。testdata.json 實際有 8,000 句，output.csv 也必須是 8,000 行答案加 1 行標題。比較可能的解釋是 Kaggle 把 8,000 句分成 public、private 各 4,000 句，p.5 寫的是其中一半——這是本書的推測，投影片沒有說明。以資料檔為準：8,000 句。

5.2　torch.stack 與 batch_size=1

DataLoader 每次拿到 batch_size 個 (檔名, mel)，交給這個函式。第 33 行的 zip(*batch) 把「一串配對」拆成「一串檔名」和「一串 mel」，兩者都是 tuple。第 35 行用 torch.stack 把 mel 疊成一個 3 維 tensor。torch.stack 要求每個 tensor 的形狀完全相同，而測試句長短不一。本書把第 0、1 句一起丟進去：

RuntimeError: stack expects each tensor to be equal size, but got [813, 40] at entry 0 and [738, 40] at entry 1

所以 test.py:62 只能設 batch_size=1：一批只有一句，torch.stack 只是在前面加一維，得到 (1, 813, 40)，檔名是長度 1 的 tuple。訓練時沒有這個問題，因為 train.py 的 collate_batch 用的是 pad_sequence，而且句子已經切成最多 128 格（第 2 章）。

想一次送一批：補值與 mask

一次一句很慢嗎？本書把 8,000 句先讀進記憶體、只計模型的時間：batch 1 跑完全部是 3.03 秒。如果照訓練的做法，把句子補到同一批最長的長度（補 −20），一批 32 句，可以快很多。但第 3 章 3.6 節說過：這個模型沒有 padding mask，補進去的 −20 會被注意力看到，也會被 mean pooling 平均進去。補值會不會改變答案？實測（依長度排序後每 32 句一批）：

做法8,000 句的時間（只算模型）和 batch 1 預測不同的句數
test.py 的做法：batch 1、不補值3.03 秒—
依長度排序、每批 32 句、補 −20、不加 mask0.59 秒91 句
依長度排序、每批 32 句、補 −20、加 mask2.31 秒0 句

已經依長度排序了，32 句的長度非常接近，補值只占全部格子的 0.6%，答案還是變了 91 句。本書挑了一批長度 538–539 格的句子（每句最多補 1 格）：不加 mask，logits 和 batch 1 的最大差距是 0.178；加了 mask，最大差距只有 2.29e-05，是浮點數誤差的大小。一格 −20 就足以改動 logits，因為 −20 遠小於正常的 mel 值（第 1 章：平均約 −2），經過 prenet 之後是一個很突出的向量。如果不排序、照檔案順序每 32 句一批，補值會占 62.7% 的格子，答案會亂得多。

「加 mask」要改兩個地方：注意力不能看補的格子，平均時也只能平均真實的格子。本書量測用的寫法如下（這不是 repo 裡的程式）：

def fwd_masked(model, x, lens):
    out = model.prenet(x).permute(1, 0, 2)
    mask = torch.arange(x.shape[1], device=x.device)[None, :] >= lens[:, None]  # True = 補的格子
    out = model.encoder_layer(out, src_key_padding_mask=mask).transpose(0, 1)
    keep = (~mask).unsqueeze(-1).float()
    return model.pred_layer((out * keep).sum(1) / keep.sum(1))

src_key_padding_mask 讓注意力把補的格子的分數設成負無限大，softmax 之後權重是 0；最後一行只把真實格子的輸出加起來、除以真實的長度。這個版本的答案和 batch 1 完全一樣，但在本機只比 batch 1 快一點（2.31 秒對 3.03 秒），比不加 mask 慢了將近 4 倍；為什麼加了 mask 會慢這麼多，本書沒有追究。對 8,000 句來說，3 秒本來就不是瓶頸（5.6 節），batch_size=1 是簡單又正確的選擇。

5.3　載入模型與 model.eval()

第 0 章 0.6 節已經讀過 main() 的前半，這裡只看建模型的四行。第 70 行用 mapping.json 的 id2speaker 有幾個鍵來決定輸出幾類：600。第 71 行建一個和訓練時一模一樣的 Classifier，第 72 行把 model.ckpt 裡的 state_dict 填進去。load_state_dict 預設是嚴格的：名字或形狀對不上就報錯，所以 classifier.py 一改架構，舊的 model.ckpt 就載不進來。

第 73 行 model.eval() 把 dropout 關掉（第 3 章：encoder layer 裡有 4 個 dropout，p = 0.1）。忘了這一行會怎樣？本書用同一份權重、讓 dropout 開著再預測一次：

model.eval()忘了 eval()（dropout 開著）
驗證集 5,667 句，整句準確率0.857070.8583
測試集 8,000 句，和 eval() 預測不同的句數—396 句
換一個亂數種子再跑一次，兩次彼此不同的句數0（每次都一樣）405 句

準確率幾乎沒變，在這次量測裡甚至高了一點點——dropout 只有 0.1，整句又夠長，平均起來把雜訊壓掉了大半。真正的問題在第三列：同一個檔案、同一份權重，每跑一次 output.csv 就不一樣，約 5% 的答案在跳。這種錯誤看準確率不容易發現，比對兩次的輸出才看得出來。

5.4　預測迴圈與 output.csv

第 76 行先放標題列 ["Id", "Category"]，這是投影片 p.20 規定的格式。第 78 行 torch.no_grad() 告訴 PyTorch 不要記錄計算圖，省記憶體也省時間；它和 model.eval() 是兩回事：一個管梯度，一個管 dropout 這類層的行為，兩者都要。

第 80–81 行：一句話進去，出來 (1, 600) 的分數；argmax(1) 取最高分的編號，搬回 CPU 轉成 NumPy 陣列。第 83 行把編號翻成說話者名稱，這裡有一個容易漏看的 str()：

pred type int64 np.int64(292) | str(pred) -> '292' | id2speaker[str] id03196
id2speaker[pred] -> KeyError: np.int64(292)

JSON 的鍵一定是字串，所以 id2speaker 的鍵是 "0" 到 "599"（第 1 章）；而 pred 是 NumPy 的 int64。不轉成字串直接查，就是 KeyError。本書也檢查過 speaker2id 與 id2speaker 對 600 個編號都互為反函數，訓練時的「編號 292」和這裡翻出來的 id03196 指的是同一個人。第 82 行的內層迴圈是為了 batch 不只一句時也能用；batch 1 時它只跑一次。

第 85–87 行用 csv.writer 一次寫出所有列。open(..., newline='') 是 Python csv 模組文件要求的寫法：讓 csv 自己決定換行字元。它的預設是 \r\n，所以本機產生的 output.csv 每一行結尾都是 \r\n（共 8,001 行），這是 CSV 標準（RFC 4180）的換行，一般的 CSV 讀取器都能處理。重跑 test.py 的輸出逐位元組相同：本書用實驗工具重現的權重算出的檔案，md5 和第 0 章那份 output.csv 一樣。

5.5　只看過 128 格的模型，怎麼看整句？

訓練時模型看到的每一筆都是 128 格（只有 2 句更短，第 1 章）；測試時它要看 214 到 4,940 格。為什麼不會出錯？第 3 章的兩個性質：模型沒有位置編碼，注意力只看「格子之間的相似度」，和序列多長無關；最後的 mean pooling 不管幾格都平均成一個 80 維的向量。架構裡沒有任何東西綁定長度 128，所以整句送進去，形狀照樣是 (1, 長度, 40) → (1, 600)。

能跑不代表一樣準。第 4 章已經量過：同一份權重，整句 0.857、128 格片段 0.686。本書再把驗證集依長度分成六組，看準確率怎麼隨長度變化：

長度（格）驗證句數整句固定 128 格測試句數
400 以下6960.81610.6580948
400–4991,6410.81050.64352,435
500–6491,4180.85120.70032,048
650–8991,0280.90270.71791,393
900–1,2995910.92720.7343760

整句的準確率隨長度上升：400 格以下約 0.81，1,300 格以上 0.94。句子越長，模型看到的證據越多，平均出來的向量越穩。固定片段則一直在 0.64 到 0.73 之間，因為不論句子多長，它都只看 128 格；它也隨長度稍微上升，可能是長句子裡同一個人的聲音比較一致、片段切到靜音或雜音的機會比較少，這一點本書沒有驗證。最右邊那組只有 293 句，片段的 0.703 比前一組低，不要過度解讀。

測試集的長度分布和驗證集很接近（最後一欄；中位數 538 對 541），所以從「整句 0.857」推測測試集的表現，至少在長度這一點上沒有偏差。但第 0 章提過，驗證集和訓練集是同一批 600 人、同一批錄音隨機切的，可能比測試集容易得多，所以 0.857 不能直接當成 Kaggle 的分數。

5.6　deepcopy 的 bug 改了幾個答案

第 4 章 4.5 節：model.ckpt 存的是第 70,000 步的權重，log 卻說它是第 68,000 步那一份。在驗證集上，兩份權重的整句準確率只差 1 句。換到測試集看，本書用兩份權重各預測一次 8,000 句：

  • 測試集：82 句的答案不同（1.0%）。
  • 驗證集：22 句的答案不同，對錯互相抵銷，淨差 1 句（0.85707 對 0.85724）。

測試集沒有答案，不知道這 82 句裡哪一份猜對比較多；從驗證集的情形看，兩份的分數應該很接近。這一節要說的是：「log 上的準確率對應哪一份權重」這件事錯了，交出去的檔案就真的不一樣，只是這一次差得很少。

5.7　推論要多久

第 0 章實測 test.py 整支跑完是 11.36 秒，進度條顯示迴圈本身約 9 秒。下面量到模型本身只要大約 3 秒，所以多出來的時間應該花在啟動 Python、載入 PyTorch 與 CUDA，以及 8 個 worker 從磁碟讀 8,000 個檔、把資料傳回主行程——這是推測，本書沒有逐項計時。逐句量模型的時間（batch 1，mel 已在記憶體裡，每次先同步 GPU 再計時）：

長度（格）句數每句時間（中位數）最慢的一句
500 以下3,3830.37 ms1.28 ms
500–9993,7510.38 ms1.06 ms
1,000–1,9997630.41 ms0.94 ms
2,000–2,999820.62 ms0.72 ms
3,000–4,940210.78 ms1.37 ms

注意力的計算量和長度的平方成正比，最長那句的注意力矩陣有 186 MiB（第 3 章），但在這張 GPU 上，一句 4,940 格也只要 1.37 ms。1,000 格以下幾乎都是 0.37 ms 左右：這時的時間主要花在「從 Python 呼叫一次模型、啟動一連串 GPU kernel」的固定開銷，而不是計算本身。這也是 5.2 節一次送 32 句能快 5 倍的原因：固定開銷分攤給 32 句。最慢的那幾句並不是最長的句子（500 格以下也有 1.28 ms 的），應該是量測時的偶發延遲。

現在的做法：批次推論與說話者向量

要大量推論時，今天的做法是依長度分組、補值、加 mask 一次送一批（5.2 節），並用 torch.inference_mode() 取代 no_grad()（再省一點開銷）；PyTorch 的 TransformerEncoder 在 batch_first=True 時還能用 nested tensor 直接跳過補的格子。任務本身也變了：HW04 是「封閉集」的辨識，600 個人是固定的，來了第 601 個人就只能猜錯。實際的說話者辨識系統大多訓練一個說話者向量（speaker embedding）模型，例如 x-vector、ECAPA-TDNN，或在 WavLM 這類自監督模型上微調；推論時把一句話變成一個向量，和已登錄的人比 cosine 相似度。這樣新的人只要登錄一句話，不必重新訓練。第 8 章用到的 AM-Softmax 就是為了讓這種向量更好比較而設計的 loss。

本章重點

  • InferenceDataset 回傳（檔名, 整句 mel），不切段、沒有標籤；測試集 8,000 句（投影片 p.5 寫 4,000，以資料檔為準）。
  • inference_collate_batch 用 torch.stack，長短不同的句子疊不起來，所以只能 batch_size=1。補值成批不加 mask 會改變 91 句答案（一格 −20 就讓 logits 差 0.18）；加了 mask 就和 batch 1 完全一樣。
  • 忘了 model.eval()：準確率幾乎不變，但每跑一次約 5% 的答案不同。
  • argmax 出來的是 np.int64，id2speaker 的鍵是字串，所以要 str(pred)。output.csv 是 8,001 行、以 \r\n 換行。
  • 沒有位置編碼 + mean pooling ⇒ 只看過 128 格的模型可以吃任何長度。整句的準確率隨長度上升（0.81 → 0.94），128 格片段則一直在 0.64–0.73。
  • deepcopy 的 bug 在測試集上改了 82 句的答案。模型推論 8,000 句只要約 3 秒，test.py 的 11 秒大多花在啟動與讀檔。

自我測驗

1. 把 test.py:62 改成 batch_size=2，會發生什麼事？在哪裡出錯？

第一批就會出錯：inference_collate_batch 的 torch.stack 收到兩個長度不同的 tensor（第 0 句 813 格、第 1 句 738 格），丟出 RuntimeError: stack expects each tensor to be equal size。因為 num_workers=8，collate 是在 worker 行程裡跑的，錯誤會在 worker 裡發生、再由 DataLoader 包裝後在主行程重新丟出，訊息裡會說是哪一個 worker。要支援 batch 大於 1，得改用 pad_sequence，而且要加 mask（5.2 節），否則答案會變。

2. 為什麼第 83 行要寫 mapping["id2speaker"][str(pred)]，不能直接用 pred？

mapping.json 是 JSON，JSON 物件的鍵只能是字串，所以讀進來的 id2speaker 鍵是 "0"–"599"。pred 是 argmax(1).cpu().numpy() 的元素，型別是 numpy.int64；用它查字典會找不到，丟出 KeyError: np.int64(292)。str(pred) 把它變成 '292' 才查得到。

3. 同學說：「我忘了 model.eval()，但驗證準確率沒變，所以沒關係。」哪裡不對？

準確率沒變，不代表輸出沒變。dropout 開著時，每次 forward 都隨機丟掉一些值，同一句話每次跑出來的分數都不同。本書實測，兩次預測 8,000 句有 405 句答案不同，output.csv 不再能重現。這次的準確率剛好差不多（dropout 只有 0.1、整句又長），換一個 dropout 比較大的模型或比較短的輸入，準確率也可能明顯下降。

4. 依長度排序後每批 32 句，補值只占 0.6%，為什麼不加 mask 還是有 91 句答案改變？

因為只要補一格，就同時影響了兩個地方：注意力會把那一格 −20 當成一個真實的格子去看（每個真實格子的輸出都被改了一點），mean pooling 又把那一格的輸出平均進去。−20 和正常的 mel 值差很多，經過 prenet 後是一個很突出的向量，所以只補一格，logits 就差了 0.178。原本兩個說話者分數很接近的句子，這點差距就足以讓 argmax 換人。

5. 模型訓練時只看過 128 格，測試時卻要看最長 4,940 格。如果模型有位置編碼（例如只學了 128 個位置的可學習位置向量），test.py 還能照原樣跑嗎？

不能照原樣跑。只學了 128 個位置，第 129 格以後就沒有位置向量可加，程式會在形狀或索引上出錯；要嘛把測試句也切成 128 格的片段再合併結果，要嘛改用能外推的位置編碼（例如正弦位置編碼或相對位置）。這份程式沒有位置編碼（第 3 章），所以長度不受限制；代價是模型完全不知道格子的順序，好在說話者是誰主要看聲音的特徵，不太需要順序。

延伸閱讀

  • PyTorch 文件 TransformerEncoderLayer：src_key_padding_mask 的格式（True 表示要忽略的位置）與 batch_first 的快速路徑；以及 torch.inference_mode。
  • Python 文件 csv：為什麼開檔要 newline=''，以及 lineterminator 預設是 \r\n。
  • Snyder 等，〈X-Vectors: Robust DNN Embeddings for Speaker Recognition〉（ICASSP 2018）：把說話者辨識做成「抽向量、比相似度」的代表作。
  • Desplanques 等，〈ECAPA-TDNN〉（Interspeech 2020），arXiv:2005.07143：常用的說話者向量模型，也用了第 8 章會看到的 attentive pooling 的變形。

ML2022 Spring · HW04 讀碼教材

第 2 章　切段、補齊與 DataLoader

第 1 章的 myDataset 只記得 56,666 個檔名。這一章看它怎麼在被取用時讀檔、隨機切出 128 格；collate_batch 怎麼把 32 句疊成一個 batch；random_split 切出了什麼樣的驗證集；以及 train.py 為什麼用「步」而不是 epoch 來數訓練，8 個背景行程的亂數又是怎麼被固定的。

2.1　__getitem__：每次取用都切不同的 128 格

DataLoader 每要一句話，就呼叫一次 __getitem__(index)。第 35 行從第 1 章那張清單拿出 [檔名, 編號]，第 37 行才真的讀檔，得到一個 (T, 40) 的 tensor。接下來分兩種情況：

  • 比 128 格長（第 40–44 行）：從 0 到 T − 128 之間隨機挑一個起點，切出連續的 128 格。random.randint(a, b) 是 Python 標準函式庫的函式，兩端都包含，所以一句 435 格的話有 435 − 128 + 1 = 308 種切法。56,666 句裡除了 2 句以外都走這條路（第 1 章 1.3 節）。
  • 不超過 128 格（第 45–46 行）：整句原封不動交出去，長度小於 128。全部資料只有 91 格與 116 格那 2 句會走這條路，2.2 節會看它們怎麼被補齊。

重點在「隨機」：這個起點是每次被取用時重新抽的，不是建立 Dataset 時決定好的。本書實測，連續取兩次 dataset[0]，拿到的是兩段不同的 128 格。所以 44 個 epoch 裡，同一句話被取用 44 次，模型幾乎每次都看到它不同的一段——這等於一種免費的資料增強（data augmentation）：訓練集只有 50,999 句，但模型看到的「片段」遠多於此。投影片第 9 頁「Segment during training」那張圖畫的就是這件事。

第 48 行把編號變成一個長度 1 的 int64 tensor：先用 torch.FloatTensor([speaker]) 做成浮點數，再 .long() 轉成整數。繞一圈浮點數是多餘的（0–599 的整數用 float32 表示不會有誤差，所以結果正確），直接寫 torch.tensor(speaker) 就好。第 44、46 行的 torch.FloatTensor(mel[...]) 也是同一種舊寫法：mel 本來就是 float32 的 tensor，本書實測 torch.FloatTensor(x) 回傳的新 tensor 和 x 共用同一塊記憶體，不是複本，也沒有轉換，等於什麼都沒做。

現在的做法：別用 torch.FloatTensor(...) 當轉換函式

torch.FloatTensor、torch.LongTensor 這類「型別名稱當建構函式」的寫法來自 PyTorch 很早期的版本，現在的文件已經不建議使用：它們只能產生 CPU 上的 tensor，遇到不同的輸入（list、numpy 陣列、另一個 tensor）時行為也不一致——像這裡傳入 tensor 就不複製、只共用記憶體。現在的寫法是：從 Python 資料建立用 torch.tensor(data, dtype=...)，已經是 tensor 要轉型別用 x.float()、x.long() 或 x.to(torch.float32)，想避免複製用 torch.as_tensor。

2.2　collate_batch：把 32 句疊成一個 batch

DataLoader 一次拿 32 個 (mel, speaker)，交給 collate_fn 疊成一個 batch。預設的疊法要求每個 tensor 形狀相同，但這裡的句子可能比 128 格短，所以 train.py 自己寫了一個：

第 72 行的 zip(*batch) 把「32 個 (mel, speaker) 對」拆成「32 個 mel」和「32 個 speaker」兩組。第 74 行的 pad_sequence 找出這一組裡最長的長度，把較短的在尾端補上 padding_value，再疊成一個 tensor；batch_first=True 讓 batch 那一維放在最前面，得到 (32, 長度, 40)。補的值是 −20，第 1 章 1.5 節說過，這幾乎就是資料裡「沒有聲音」的值。第 76 行把 32 個長度 1 的編號 tensor 合成一個 (32,) 的 int64 tensor——torch.FloatTensor 收到一個裝滿單元素 tensor 的 tuple 也能處理，又是那種繞一圈浮點數的舊寫法。

把 train.py 的第一個 batch 拿出來看（和 train.py 同樣的種子、同樣的順序，所以這就是訓練第 1 步用的 batch）：

mels   (32, 128, 40) torch.float32
labels (32,) torch.int64   前 8 個：[257, 50, 560, 538, 336, 338, 415, 594]
補值 -20 的格數：0

32 句都切到了 128 格，沒有任何一格是補的。因為幾乎每一句都比 128 格長，絕大多數的 batch 根本不需要補。要看到補值，得把那句 91 格的話（完整資料集的第 20,902 句）和其他句子湊成一批：

四句的形狀：[(91, 40), (128, 40), (128, 40), (128, 40)]
collate 之後：(4, 128, 40)
第一句尾端補了 -20 的格數：37      標籤：[534, 436, 436, 436]

91 + 37 = 128。那 2 句短句都在訓練集裡（2.3 節），每個 epoch 各出現一次，所以一個 epoch 1,593 個 batch 裡最多只有 2 個需要補，70,000 步裡大約 88 個；驗證集最短的一句也有 152 格，驗證時從來不補。補值這段程式在別的資料集上很重要，在這份資料上幾乎是備而不用。

補的格子會被 mean pooling 平均進去

補值只是讓形狀對齊，模型並不知道哪些格子是補的：classifier.py 的 forward 沒有傳任何 padding mask 給 encoder，第 66 行的 out.mean(dim=1) 也是把 128 格（含補的 37 格）一起平均。所以那句 91 格的話，模型看到的其實是「91 格說話 + 37 格靜音」。在這份資料上只影響 2 句、每個 epoch 最多 2 個 batch，實際影響很小；但如果資料裡短句很多，就應該用 mask 讓注意力與 pooling 跳過補的格子。第 3 章會再談。

2.3　random_split：切出驗證集

第 84 行算出訓練集的大小 int(0.9 × 56,666) = int(50,999.4) = 50,999，剩下的 5,667 句當驗證集。第 86 行的 random_split 用 PyTorch 的全域亂數產生器打亂 0–56,665 這些 index，前 50,999 個給訓練、後 5,667 個給驗證，回傳兩個 Subset：它們不複製資料，只記得「我是原資料集的哪些 index」，取用時轉給原本的 myDataset。因為 train.py:32 在一開始就 set_seed(87)，這個切法每次都一樣；本書實測，驗證集的前五個 index 是 [43097, 46091, 22324, 24456, 274]。

切出來的驗證集長什麼樣？

  • 600 位說話者全部都在兩邊：訓練集與驗證集都有 600 人。驗證集每人 1–20 句，平均 9.45 句。這是好事，模型在驗證時不會碰到沒看過的人——作業本來就是閉集分類，測試集的說話者也都在訓練集裡。
  • 長度分布和全體一樣：驗證集平均 658.6 格、中位數 541、最短 152 格；那 2 句短於 128 格的話（index 20,902 與 32,767）都落在訓練集。
  • 切的單位是「句」，不是「人」或「影片」。同一位說話者的其他句子，甚至很可能同一支影片裡相鄰的句子，都在訓練集裡。VoxCeleb2 的句子是從影片裡切出來的，同一支影片的句子共用同樣的麥克風、房間迴音與背景。這讓驗證集可能比測試集容易——第 0 章 0.7 節那個「驗證集整句 0.857、Kaggle 卻只在 0.608 附近」的落差，這是最可能的解釋之一。本書拿不到每一句屬於哪支影片的資訊（檔名是隨機 ID），所以沒有辦法驗證。

2.4　兩個 DataLoader

兩個 DataLoader 的設定幾乎一樣，差在第 91 行：訓練集 shuffle=True，驗證集沒寫、用預設的 False。逐項看：

參數訓練驗證意思
batch_size3232一批 32 句
shuffleTrue（RandomSampler）False（SequentialSampler）訓練集每個 epoch 重新打亂順序；驗證集永遠照同一個順序
drop_lastTrueTrue最後湊不滿 32 句的那一批丟掉
num_workers888 個背景行程平行讀檔、切段（2.6 節）
pin_memoryTrueTrue把 batch 放在「鎖定」的主記憶體裡，複製到 GPU 比較快
collate_fncollate_batch（2.2 節）怎麼把 32 句疊成一批

算一下 batch 數：訓練集 50,999 = 1,593 × 32 + 23，所以一個 epoch 有 1,593 個 batch，每個 epoch 丟掉 23 句；因為每個 epoch 都重新打亂，被丟掉的是隨機的 23 句，長期下來每一句都會被用到。驗證集 5,667 = 177 × 32 + 3，177 個 batch，丟掉最後 3 句；但驗證集不打亂，所以每一次驗證丟掉的都是同樣的 3 句，這 3 句從頭到尾沒有被驗證過。這就是第 0 章進度條停在 5664/5667 的原因。

驗證集設 drop_last=True 其實沒有必要：驗證不更新參數，最後一批只有 3 句也無所謂。好在 177 批全都恰好是 32 句，所以 valid()「每批算一個準確率、再把 177 個數字平均」的做法，和「5,664 句裡答對幾句」完全相等（本書實測兩者都是 0.68591）——HW01、HW03 那種「最後一批比較小卻和其他批同權重」的偏差，在這裡不存在。真正的偏差在別的地方，第 4 章會講。

2.5　以「步」為單位：迭代器用完就重建

HW01–HW03 的訓練迴圈都是「跑 N 個 epoch，每個 epoch 把 DataLoader 從頭到尾跑一遍」。HW04 不一樣，它數的是步：

第 248 行在迴圈開始前就建好了 train_iterator = iter(train_loader)。每一步用 next() 拿下一個 batch；1,593 步之後迭代器用完了，next() 丟出 StopIteration，第 267 行就重建一個新的迭代器（新的打亂順序），再拿第一個 batch。所以 epoch 的邊界在這份程式裡是「看不見」的：70,000 步 = 70,000 ÷ 1,593 = 43.94 個 epoch，迭代器一共重建 43 次，第 44 個 epoch 只跑了 94% 就結束了。

以步為單位有兩個好處。第一，學習率排程（第 4 章）、驗證頻率（每 2,000 步）、存檔頻率（每 10,000 步）都直接用步數設定，換 batch 大小或資料量時不必重算「幾個 epoch」；Transformer 的論文與程式也習慣這樣寫。第二，最後一個 epoch 不必跑完，總步數就是總共更新幾次參數，比較實驗時很清楚。代價是要自己處理「迭代器用完」——就是第 264–268 行那個 try／except。

2.6　8 個 worker 與亂數

num_workers=8 讓 DataLoader 開 8 個背景行程（worker），每個 worker 各自呼叫 __getitem__ 讀檔、切段，主程式只管拿做好的 batch 送進 GPU。差多少？本書只讀資料、不跑模型，量 500 個訓練 batch：

num_workers500 個 batch每秒 batch 數
0（主程式自己讀）35.28 秒約 14
8（train.py 的設定）1.39 秒約 360

差了 25 倍。train.py 實際訓練時每秒約 350 步（第 0 章），和 8 個 worker 的供應速度差不多——資料讀取剛好跟得上 GPU。如果只用主程式讀，70,000 步光讀資料就要將近一個半小時。

worker 裡的 random 是怎麼固定的

__getitem__ 用的是 Python 標準函式庫的 random.randint，不是 PyTorch 的亂數，而它是在 8 個不同的行程裡執行的。set_seed(87) 只設了主程式的種子，worker 裡的 random 是誰設的？答案是 PyTorch 的 DataLoader：每建立一次迭代器，它先從主程式的 PyTorch 亂數抽一個 base_seed，再讓第 i 個 worker 用 base_seed + i 去設 Python random 與 PyTorch 的種子；如果有裝 NumPy，也用 base_seed 和 i 另外算出一組種子去設 np.random（本書讀過 PyTorch 2.11 的 torch/utils/data/_utils/worker.py）。本書寫了一個小 Dataset，讓每個 worker 回報自己的 id、種子和第一個 random.random()：

iterator 0: (worker id, seed, first python random*1e9): [(0, 2882565337522676045, 210487631), (1, 2882565337522676046, 232592194), (2, 2882565337522676047, 264303430)] ... python random == Random(seed)? True
iterator 1: (worker id, seed, first python random*1e9): [(0, 8391449358263599247, 914314671), (1, 8391449358263599248, 474064050), (2, 8391449358263599249, 751550641)] ... python random == Random(seed)? True

同一個迭代器裡，worker 0、1、2 的種子是連續的整數；換一個迭代器（2.5 節每個 epoch 重建一次），base_seed 就重抽一個。最後的 True 表示每個 worker 的第一個 random.random()，確實等於用那個種子新建的 random.Random(seed) 的第一個數。因為 base_seed 來自主程式的 PyTorch 亂數，而主程式的亂數被 set_seed(87) 固定了，所以 8 個 worker 的切段位置每次都一樣——這就是第 0 章兩次訓練得到逐位元組相同 model.ckpt 的資料面原因。

舊版 PyTorch 的陷阱

舊版的 PyTorch，DataLoader 只替 worker 設 PyTorch 與 Python random 的種子，沒有設 NumPy 的；在 __getitem__ 裡用 np.random 的程式，每個 worker 會從同一個狀態複製出來，抽到一模一樣的「隨機」數。這份程式用的是 Python random，不受影響；現在的 PyTorch 也已經修正。如果需要自己控制，可以傳 worker_init_fn 與 generator 給 DataLoader。

驗證集也在切段，而且每次切的位置不同

還有一件事容易漏看：valid_loader 用的是同一個 myDataset（2.3 節的 Subset 只是轉手），所以驗證時也會隨機切 128 格，而且每一次驗證都建新的迭代器、抽新的 base_seed，切到的位置都不同。換句話說，同一份權重在不同時間驗證，會量到不同的準確率。本書拿第 8 章基準組（就是 train.py 的設定）第 68,000 步的權重，在同一個驗證集上換 10 個種子、照 valid() 的做法各量一次：

[0.6854, 0.6843, 0.6774, 0.6741, 0.687, 0.6758, 0.6819, 0.6781, 0.6813, 0.688]
min 0.6741  max 0.688  mean 0.6813

同一份權重，準確率在 0.674 到 0.688 之間跳，相差 1.4 個百分點。訓練時印出的 0.6859 是其中偏高的一次。train.py 拿 35 次這樣的量測挑最高的一次當「最佳」，挑中的有一部分是運氣；第 4 章會把這件事和「切段 vs 整句」放在一起談。

本章重點

  • __getitem__ 每次被取用才讀檔，比 128 格長就從 0 到 T − 128 隨機挑起點（兩端都含）；同一句話每個 epoch 看到不同的一段，等於免費的資料增強。
  • collate_batch 用 pad_sequence 在尾端補 −20；因為只有 2 句短於 128 格，70,000 步裡只有約 88 個 batch 有補值，驗證時從不補。模型沒有 padding mask，補的格子會被 mean pooling 平均進去。
  • random_split 在種子 87 下切出 50,999／5,667；600 人兩邊都有，切的單位是句，同一人（可能同一支影片）的其他句子都在訓練集。
  • 訓練 1,593 批／epoch、每 epoch 隨機丟 23 句；驗證 177 批、永遠丟同樣的 3 句；177 批都是 32 句，所以平均再平均沒有偏差。
  • 訓練以步計：70,000 步 = 43.94 epoch，迭代器用完就重建。
  • 8 個 worker 讓讀資料快 25 倍；每個 worker 的 Python random 由 PyTorch 設成 base_seed + id，所以可重現。驗證也在隨機切段，同一份權重的 valid() 準確率在 0.674–0.688 之間跳。

自我測驗

1. 一句 129 格的話有幾種切法？一句 128 格的話呢？

129 格：len(mel) > 128 成立，起點是 random.randint(0, 1)，0 或 1 兩種。128 格：128 > 128 不成立，走 else，整句交出去、不切，只有一種，而且不需要補。注意第 40 行用的是 > 不是 >=，剛好 128 格的句子不會進到 randint；如果寫成 >=，randint(0, 0) 也只會回傳 0，結果一樣。

2. 把 valid_loader 的 drop_last 改成 False，印出的驗證準確率會怎樣？

會多出第 178 批，只有 3 句。valid() 把每一批的準確率平均，這一批的權重和其他 32 句的批一樣大，它的準確率只能是 0、1/3、2/3 或 1，會讓平均值偏移最多約 1/178 ≈ 0.56 個百分點；進度條會停在 5696/5667，超過總數（因為 update 每批加的是 batch_size 32，不是實際句數，178 × 32 = 5,696）。另外，這 3 句終於會被驗證到。本書沒有實際跑這個修改，這是從程式推論的；2.6 節量到的隨機切段造成的跳動（1.4 個百分點）比這大得多。

3. 只把 n_workers 從 8 改成 0，訓練結果會和原本逐位元相同嗎？

不會。num_workers=0 時 __getitem__ 在主程式裡執行，random.randint 用的是主程式的 Python random（被 set_seed(87) 設過），而不是 worker 的 base_seed + id，切段位置全部不同；（DataLoader 照樣會從 PyTorch 亂數抽一個 base_seed，只是沒有 worker 用它。）結果仍然可以重現（每次跑都一樣），但和 8 個 worker 的版本不同，也會慢很多（2.6 節：讀資料慢 25 倍）。本書沒有完整跑這個版本的訓練。

4. 為什麼說 random_split 切出的驗證集「可能比測試集容易」？要怎麼切才比較公平？

它以「句」為單位隨機切，同一位說話者的其他句子、甚至同一支影片的句子都留在訓練集，驗證句和訓練句共用相同的錄音環境。如果測試集的句子來自不同的影片，模型就不能靠「記住這個房間的聲音」答對。比較公平的切法是以影片（或錄音場次）為單位切，讓驗證集的影片完全不出現在訓練集；這份資料沒有影片資訊，做不到。這個解釋是推論，本書無法驗證。

5. 70,000 步裡，訓練集的某一句話平均被模型看過幾次？看到的都是同一段嗎？

70,000 步 × 32 句 = 2,240,000 次取用，分給 50,999 句，平均每句約 43.9 次（扣掉每個 epoch 隨機丟掉的 23 句，大致就是 43–44 個 epoch 各一次）。每次的起點都重新抽，一句 541 格的話有 414 種切法，所以 44 次裡幾乎不會重複；只有那 2 句不超過 128 格的話每次都一樣。

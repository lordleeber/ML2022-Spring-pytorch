第 4 章　訓練迴圈、學習率與驗證

資料（第 1、2 章）和模型（第 3 章）都備齊了，這一章看 train.py 怎麼把它們接起來：AdamW 與「先升後降」的學習率、一步更新做了哪幾件事、valid() 印出來的準確率到底量的是什麼，以及第 0 章留下的那個問題——log 說「存下最佳模型（0.6859）」，存下的卻不是那一步的權重。本書把同一次訓練的 35 份權重全部存下來，用三種量法各量一次，把這些問題攤開來看。

4.1　優化器：AdamW

train.py:253 只有一行：optimizer = AdamW(model.parameters(), lr=1e-3)。學習率之外全用預設值，本書在 PyTorch 2.11 上印出來是：

AdamW defaults: {'lr': 0.001, 'betas': (0.9, 0.999), 'eps': 1e-08, 'weight_decay': 0.01, 'amsgrad': False}

Adam 替每一個參數維護兩個移動平均：梯度的平均（betas[0] = 0.9，像動量）與梯度平方的平均（betas[1] = 0.999），更新量是「平均梯度 ÷ 平均梯度大小」再乘上學習率，所以每個參數的步伐會自動依它的梯度尺度調整。AdamW 的 W 是 weight decay：每一步把參數乘上 (1 − lr × 0.01)，讓權重慢慢往 0 縮。它和 HW03 用的 Adam(..., weight_decay=1e-5) 不一樣：Adam 的 weight decay 是加進梯度裡、跟著 Adam 的縮放走，AdamW 是直接從參數上扣（decoupled weight decay），後者在 Transformer 上效果比較好，也是今天訓練 Transformer 的預設選擇。注意程式裡沒寫 weight_decay，0.01 是 AdamW 的預設值，不是作者的選擇。

4.2　學習率：warmup 加 cosine

LambdaLR（第 162 行）是 PyTorch 的排程器：它每一步呼叫一次 lr_lambda(目前的步數)，把回傳的倍數乘上優化器原本的學習率 0.001。所以 lr_lambda 回傳的是 0 到 1 之間的比例：

  • warmup（第 152–153 行）：前 1,000 步，比例從 0 線性升到 1，學習率從 0 升到 0.001。
  • cosine 衰減（第 155–160 行）：之後算出「已經走了剩下路程的幾成」progress（0 到 1），比例是 0.5 × (1 + cos(π × progress))，從 1 沿著半個餘弦降到 0。num_cycles 預設 0.5，math.pi * 0.5 * 2.0 * progress 就是 π × progress；max(0.0, ...) 防止超過總步數時變成負的。

本書用 docs/tools/hw04_facts.py sched 逐步算過：第 500 步 0.0005、第 1,000 步 0.001（最高）、第 10,000 步 0.000959、第 35,500 步恰好 0.0005（warmup 之後剩下 69,000 步的一半）、第 60,000 步 0.0000509、第 68,000 步 0.0000021、第 70,000 步 0。最後一萬步的學習率已經小到參數幾乎不動，這也是第 8 章會看到「最後幾次驗證差不多」的原因。

為什麼要 warmup

train.py:133-139 的說明文字寫：「對 Transformer 架構，學習率排程的設計和 CNN 不同；先前的研究顯示 warmup 對訓練 Transformer 有用。」原因和第 3 章 3.3 節的 post-norm 有關：剛初始化的 post-norm Transformer，最初幾步的梯度可能很大、方向也很亂，加上 Adam 一開始的二階動量估計還不準，大學習率很容易一步把參數推到很糟的地方。先用很小的學習率走幾百步，讓 Adam 的統計量穩定下來，再放大。第 3 章引用的 Xiong 等人（2020）的論文分析的就是這件事，也說明 pre-norm 對 warmup 比較不敏感。第 8 章那組 3 層、寬 256 的 post-norm Transformer 學不起來，換成 pre-norm 或把學習率降到 3e-4 就好了，是同一件事在更大的模型上發作。

第一步的學習率是 0

一個細節：LambdaLR 在建立的時候就會呼叫一次 lr_lambda(0)，把學習率設成 0.001 × 0 = 0。所以訓練迴圈的第一個 optimizer.step() 用的學習率是 0，第二步才是 1e-6。本書實測：

lr used by the 1st optimizer.step(): 0.0
parameters unchanged after the 1st step? True | Adam state exp_avg nonzero? True
lr used by the 2nd step: 1e-06
changed after the 2nd step? True

第一步參數一個都沒變（更新量與 weight decay 都乘上了學習率 0），但 Adam 的移動平均已經記下了第一個 batch 的梯度。所以第一個 batch 不是白跑：它沒有改參數，卻讓 Adam 的統計量先熱身了一步。70,000 步裡少一步更新，對結果沒有影響；但這說明了排程器的「第幾步」和迴圈的 step 差了一個：迴圈第 step 次更新用的是 lr_lambda(step)。

4.3　一步做了什麼

model_fn 訓練與驗證共用：把 batch 搬上 GPU（第 176–177 行），forward（第 179 行），cross entropy（第 181 行），再算這一批的準確率（第 184–186 行，32 句裡答對的比例）。回傳的 loss 還連著計算圖，accuracy 是一個沒有梯度的 tensor。

第 271–272 行用 .item() 把 loss 和準確率變成 Python 的浮點數，順便讓 CPU 等 GPU 算完。第 275–278 行是標準的四步：backward 算梯度、optimizer.step() 更新參數、scheduler.step() 把學習率推到下一步、zero_grad 清掉梯度。後兩行的順序 PyTorch 1.1 以後規定是先 optimizer.step() 再 scheduler.step()，這份程式寫對了，所以沒有警告。zero_grad 放在最後而不是最前面，效果一樣，因為下一步 backward 之前梯度已經清掉了。

第 282–286 行把 batch_loss、batch_accuracy 印在進度條上。這是最後一個 batch的值，不是平均：第 0 章看到的 accuracy=0.06, loss=4.01, step=2000 是第 2,000 個 batch 那 32 句的結果，下一段的 0.22 是第 4,000 個 batch 的。32 句的準確率只能是 0/32、1/32……，跳動很大，所以進度條上的數字只能看個大概。本書的實驗工具另外記了每 2,000 步的平均訓練 loss：第一段 5.192，最後一段 1.002（4.4 節的表）。

4.4　驗證：valid() 印出來的是什麼

第 199 行切到評估模式（關掉 dropout，第 3 章 3.3 節），第 217 行切回訓練模式。中間把 177 個驗證 batch 各丟進 model_fn，累加每一批的 loss 與準確率，最後第 219 行回傳「準確率的平均」。驗證 loss 只顯示在進度條上（第 211–214 行），沒有回傳，所以 train.py 挑最佳模型只看準確率。第 202 行進度條的總數是 len(dataloader.dataset) = 5,667，第 210 行每批卻加 batch_size 32，加 177 次停在 5,664——第 2 章 2.4 節解釋過那 3 句。

這個函式本身沒有寫錯，177 批都是 32 句，平均再平均也沒有偏差（第 2 章）。問題在它量的東西：驗證集經過的是和訓練一樣的 myDataset.__getitem__，每句隨機切 128 格。本書替 4.5 節重跑了一次 train.py（實驗工具，逐位元相同），在 35 次驗證的時間點各存一份權重，再用三種方法量每一份：

  1. 印出的：train.py 自己印的值，5,664 句、每次隨機切 128 格、逐批平均。
  2. 固定片段：全部 5,667 句，每句切 128 格，但每一份權重都切同樣的位置（用固定種子的 Python 亂數），所以不同時間點可以公平比較。
  3. 整句：全部 5,667 句，整句送進模型、一次一句，就是 test.py 的做法（第 5 章）。

圖 4.2 一次看出三件事。

一、片段和整句差了一大截

綠線（整句）從頭到尾都在另外兩條上面：第 2,000 步差 6 個百分點，第 70,000 步差 17 個百分點（0.857 vs 0.686）。模型越好、差距越大。原因第 0 章 0.7 節講過：128 格只是 1.28 秒，平均只看到一句話的 23%（第 1 章）；整句話給了模型多得多的證據，mean pooling 平均起來穩得多。valid() 量的是「拿一段 1.28 秒的片段猜是誰」，test.py 做的卻是「拿整句話猜是誰」。兩者都沒錯，但 train.py 印出來的數字不能拿來預估 test.py 的表現。

二、印出的值會隨機跳動

藍線（印出的）和橘色虛線（固定片段）量的都是「片段」，差別只在印出的那條每次切的位置不同、而且少了 3 句。兩條線大致重疊，但藍線一直在橘線上下抖：第 2 章 2.6 節用同一份權重換 10 個種子，量出 0.674 到 0.688，就是這個抖動的大小。第 28,000 步藍線往下掉，橘線和綠線也都掉了一點，所以那一次是模型真的變差了一點；但第 44,000 步藍線往下掉時，固定片段反而是上升的——那一次的下跌只是切到的片段不同。

三、挑「最高的一次」會挑到運氣

train.py 拿 35 個會抖動的數字，挑最大的那一次當「最佳」。最大值天生偏高：印出的最佳是第 68,000 步的 0.6859，而同一份權重在固定片段上是 0.6847、換 10 個種子平均是 0.6813（第 2 章）。三種量法的「最佳」也不在同一步：

量法最高的一次那一步
印出的（隨機片段）0.6859第 68,000 步
固定片段0.6859第 66,000 步
整句0.85724第 64,000 步與第 68,000 步（相同）

好在最後兩萬步學習率已經很小，三種量法在 60,000 步以後都差不多平，挑到哪一步差別都不大：整句的準確率在第 60,000–70,000 步之間只在 0.8528 到 0.8572 之間變動。在訓練初期就停下來、或學習率還很大的情況下，「挑最高的一次」的偏差會大得多。比較好的做法是用固定、完整的驗證方式（例如整句），而且只把驗證集當作「選模型」的依據，最後的成績另外用一份沒參與挑選的資料來報告。

4.5　存檔：沒有 deepcopy 的「最佳模型」

第 295–297 行：驗證準確率比目前最好的高，就記下準確率，並把 model.state_dict() 存進 best_state_dict。第 302–304 行：每 10,000 步把 best_state_dict 寫進 model.ckpt，印出「best model saved」。意圖很清楚——第 294 行的註解寫「keep the best model」——但第 297 行少了一個 copy.deepcopy。

state_dict() 回傳的是一個有序字典，值是模型參數本身的 tensor（只是脫離了計算圖），不是複本。本書實測：

sd = model.state_dict(); after optimizer.step(): sd tensor changed? True | same storage as the parameter? True

拿到 sd 之後再做一次 optimizer.step()，sd 裡的值跟著變了，因為它和參數共用同一塊記憶體。所以 best_state_dict 只是「指向模型參數的一張清單」，之後每一步訓練都會改到它；第 303 行存檔時，寫進去的永遠是存檔當下的權重。log 上的準確率卻是 best_accuracy，那個數字是當初記下的、不會變。結果就是：log 說的和檔案裡存的，可能不是同一份權重。

什麼時候會出問題？只有在「存檔那一刻，最近一次驗證不是最佳」的時候。對照 4.4 節的表，7 次存檔裡有兩次是這樣：

存檔log 印的準確率（來自）實際存下的權重本該存的權重兩者的整句準確率
第 10,000–50,000 步（5 次）當下那一步當下那一步同左相同，bug 沒有作用
第 60,000 步0.6698（第 58,000 步）第 60,000 步第 58,000 步存下的 0.85601，本該存的 0.85371
第 70,000 步（最後的 model.ckpt）0.6859（第 68,000 步）第 70,000 步第 68,000 步存下的 0.85707，本該存的 0.85724

bug 是真的：最後的 model.ckpt 是第 70,000 步的權重，不是 log 說的那一份；本書比對過，它和第 70,000 步的權重逐位元相同，和第 68,000 步的不同。但在這次訓練裡，它的影響小到看不出來：整句準確率只差 0.00017，也就是 5,667 句裡的 1 句；第 60,000 步那次甚至存到了比較好的權重。原因同樣是學習率：最後幾千步參數幾乎不動，第 68,000 步和第 70,000 步的模型本來就很像。換一個情境——學習率固定不衰減、模型在中途過擬合、最佳出現在很早的時候——存下的權重就可能比 log 說的差很多，而你從 log 上完全看不出來。

修法有兩種，一行就夠：

best_state_dict = copy.deepcopy(model.state_dict())
# 或者
best_state_dict = {k: v.detach().clone() for k, v in model.state_dict().items()}

第 8 章的實驗工具每一組都同時記了兩份：deepcopy 的「真正最佳」與 train.py 會存的那一份，兩者的整句準確率在 12 組實驗裡差距都在 0.0016 以內，有一半的組甚至是 train.py 的那一份比較高。這個 bug 在這份作業裡是一個「程式錯了、運氣很好」的例子。

另一個存檔的盲點

第 302 行只在步數是 10,000 的倍數時存檔。如果把 total_steps 改成 75,000 而最佳出現在第 72,000 步，迴圈結束時不會再存一次，最佳模型就永遠不會被寫進檔案。比較穩當的寫法是在迴圈結束後（第 306 行之後）再存一次，或者每次找到新的最佳就立刻存檔。本書沒有實際跑這個修改，這是讀程式得到的結論。

4.6　逐位元重現

set_seed(87) 在 import 之後、任何東西建立之前就執行（第 32 行），固定三種亂數：NumPy（這份程式沒用到）、Python random（主程式沒用到，worker 的由 PyTorch 另外設，第 2 章）、PyTorch（CPU 與每一張 GPU）。第 28–29 行要求 cuDNN 不要自己挑最快的演算法、只用確定性的演算法；這個模型主要是矩陣乘法，應該幾乎沒有用到 cuDNN，這兩行在這裡大概作用不大，但留著無害。

這次訓練用到 PyTorch 亂數的地方，依序是：random_split（第 2 章）、第一個訓練迭代器的打亂順序與 worker 的 base_seed、模型的初始權重（第 251 行）、每次驗證的 worker base_seed、每個 epoch 重建迭代器、以及 GPU 上的 dropout。只要這個順序不變，結果就逐位元相同：第 0 章兩次跑 train.py 的 model.ckpt md5 一樣，本書的實驗工具 docs/tools/hw04_exp.py 重現出來的權重也和它逐位元相同。HW03 的教材遇過一個進度條改變亂數順序的例子（tqdm.auto 偷偷多呼叫一次 iter()）；這份程式用的是一般的 tqdm，而且進度條沒有包住 DataLoader，所以不受影響。

本章重點

  • AdamW，學習率 0.001，其餘預設（betas 0.9／0.999、weight decay 0.01）。
  • 學習率：前 1,000 步 0 → 0.001，之後半個餘弦降到 0；第 35,500 步是一半。第一次 optimizer.step() 的學習率是 0，參數不變，但 Adam 的統計量已經更新。
  • 進度條上的 loss／accuracy 是最後一個 batch 的值。
  • valid() 量的是「隨機 128 格片段」：比整句低 6–17 個百分點、每次切的位置不同會抖動約 ±0.7 個百分點，挑 35 次裡最高的一次又會偏高。三種量法的「最佳」不在同一步。
  • best_state_dict = model.state_dict() 是參照：第 60,000 與 70,000 步存下的都是當下的權重，不是 log 說的那一份。這次整句準確率只差 1 句，因為最後的學習率很小；修法是 copy.deepcopy。
  • 種子 87 + 固定的亂數使用順序 ⇒ 逐位元重現。

自我測驗

1. 如果把 warmup_steps 改成 0，第一步的學習率是多少？

是 0.001。current_step < 0 永遠不成立，第 0 步直接走 cosine 那一段，progress = 0，比例 0.5 × (1 + cos 0) = 1。第 156 行的 max(1, num_training_steps - num_warmup_steps) 也照常是 70,000。本書沒有實際訓練這個版本；對這個單層、post-norm 的小模型，不 warmup 不一定會壞，但第 8 章那組 3 層的 post-norm 模型連 1,000 步 warmup 都撐不住。

2. 一位同學把第 297 行改成 best_state_dict = model.state_dict().copy()，這樣修好了嗎？

沒有。dict.copy() 是淺複製：新的字典，但裡面的值還是同樣那些 tensor，和參數共用記憶體，之後的訓練一樣會改到它們。要複製 tensor 本身，必須用 copy.deepcopy(model.state_dict()) 或對每個值 .clone()。

3. 圖 4.2 裡，第 2,000 步的訓練 loss（平均 5.192）比驗證 loss（4.114）還高，這是過擬合的相反嗎？

不是。訓練 loss 是第 1–2,000 步的平均，包括一開始幾乎在亂猜、loss 約 6.4 的那幾百步；驗證 loss 是第 2,000 步結束時的模型量的，那時模型已經學了 2,000 步。兩個數字量的不是同一個時間點的模型。另外訓練時開著 dropout，驗證時關掉，也會讓訓練 loss 偏高。到了最後一段，訓練 loss 1.002 低於驗證 loss 1.443，才是正常的樣子。

4. 為什麼說「印出的最佳 0.6859」是偏高的估計？

因為它是 35 個會隨機抖動的量測裡最大的那一個。每一次驗證都隨機切片段，同一份權重的準確率會在約 ±0.7 個百分點內跳（第 2 章：0.674–0.688）；從一堆有雜訊的數字挑最大的，挑到的通常是「真實值 + 正的雜訊」。同一份權重在固定片段上是 0.6847，10 個種子的平均是 0.6813，都比 0.6859 低。

5. 想讓 train.py 印出的驗證準確率直接代表 test.py 的做法，最少要改哪裡？

讓驗證集不切段、整句評估。例如另外建一個驗證用的 Dataset，__getitem__ 不切；DataLoader 用 batch_size=1（或依長度分組再補齊並加 mask）；valid() 照舊。代價是每次驗證變慢：本書的實驗工具在訓練結束後整句評估一份權重，5,667 句大約要十幾秒，35 次就是幾分鐘，比整個 70,000 步的訓練（約 4 分鐘）還久。本書沒有改 train.py 這樣跑，第 8 章是在訓練結束後才對挑出的權重做整句評估。

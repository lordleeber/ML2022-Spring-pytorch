第 3 章　Transformer encoder 逐行

第 0 章只看了 Classifier 的外形。這一章把它拆開：prenet 對每一格做什麼、nn.TransformerEncoderLayer 這一行裡面藏了哪些運算，本書再用二十行程式把它重寫一遍、和 PyTorch 的輸出比對到小數點後五位。然後做三個實驗：把一句話的格子順序打亂、看補值對預測的影響、看沒被用到的 dropout 參數。第一個實驗的結果會讓你重新想一想這個模型到底學到了什麼。

3.1　建構子：三個元件

第 0 章看過這三個元件的形狀與參數量，這裡看它們各自的角色。

prenet（第 34 行）：nn.Linear(40, 80)。nn.Linear 只對輸入的最後一維做矩陣乘法，前面有幾維都照樣保留，所以 (32, 128, 40) 進去、(32, 128, 80) 出來：128 格的每一格各自乘上同一個 40 × 80 的矩陣，格與格之間沒有任何交流。它的工作只是把 40 個 mel 數值「翻譯」成 Transformer 要的寬度 d_model。為什麼不直接讓 encoder 吃 40 維？因為多頭注意力要把寬度平均分給每個頭，而且寬一點表達力比較好；80 是範例程式選的，第 8 章會試 160 與 256。

encoder_layer（第 38–40 行）：一層 nn.TransformerEncoderLayer，只傳了三個參數 d_model=80、dim_feedforward=256、nhead=2，其他全用預設值。3.2–3.3 節把它拆開。

pred_layer（第 44–48 行）：Linear(80, 80) → ReLU → Linear(80, 600)。它吃的是 pooling 之後、一句話一個的 80 維向量，輸出 600 個 logits。第一層加 ReLU 讓它不只是一個線性分類器。最後一層的 600 × 80 權重可以想成 600 個「說話者的範本向量」，logit 就是這句話的向量和每個範本的內積加上偏差；第 8 章的 Additive Margin Softmax 會把這個內積換成餘弦相似度。

還有兩行沒用到的東西。第 31 行的參數 dropout=0.1 沒有傳給任何一層（3.7 節）；第 41 行被註解掉的 nn.TransformerEncoder 是「把這一層疊 N 次」的容器（3.5 節）。檔案開頭第 1–23 行是一段 Model 說明的字串，和 train.py:109-131 那一段一字不差，是 notebook 拆檔時兩邊都留了一份。

3.2　自注意力：每一格去看其他每一格

TransformerEncoderLayer 的第一個子層是多頭自注意力（multi-head self-attention），它是這個模型裡唯一讓不同格子互相交流的地方。先看一個頭（head）做什麼。輸入是 L 格、每格 d 維的矩陣 X（這裡 L = 128、d = 80）：

Q = X WQ + bQ，K = X WK + bK，V = X WV + bV
A = softmax( Q KT ⁄ √dhead )　　（形狀 L × L，每一列加起來是 1）
輸出 = A V

每一格產生三個向量：query（我在找什麼）、key（我有什麼）、value（我要提供的內容）。第 i 格的 query 和每一格的 key 做內積，得到 L 個分數，除以 √dhead 之後做 softmax，變成 L 個加起來是 1 的權重；第 i 格的輸出就是所有格子 value 的加權平均。所以第 i 格的新向量是「整句話裡，和我相關的那些格子的混合」——任兩格不管隔多遠，都只差一步，這是 self-attention 比 RNN 擅長長距離關係的原因（投影片第 3 頁）。

多頭就是把這件事做好幾份。nhead=2 時，80 維被切成兩份各 40 維，每個頭用自己那 40 維的 Q、K、V 各算一個 L × L 的注意力，兩個頭的輸出（各 40 維）接回 80 維，再乘一個 80 × 80 的輸出矩陣 out_proj。所以頭數不改變參數量（第 0 章 0.2 節），只改變「一次能同時注意幾種不同的關係」，以及每個頭的寬度 dhead = 80 ÷ 2 = 40；縮放因子 1/√40 = 0.1581。

PyTorch 把 WQ、WK、WV 三個 80 × 80 的矩陣疊成一個 in_proj_weight，形狀 (240, 80)，前 80 列是 Q、中間 80 列是 K、最後 80 列是 V；偏差 in_proj_bias 同理是 240 個數。這就是 0.2 節 PyTorch 印出 MultiheadAttention 19440 的那一份。

用二十行程式重寫一次

讀文件不如自己算一次。下面這段是本書寫的驗證程式（不屬於 repo，在 docs/tools/hw04_facts.py 的 ch03 段），拿第 8 章基準組訓練好的 encoder_layer，只用矩陣乘法、softmax 和 layer_norm 重算一次 3.2–3.3 節的公式，輸入是隨機的 (128, 4, 80)（長度在前，原因見 3.5 節）：

W, b = el.self_attn.in_proj_weight, el.self_attn.in_proj_bias
q, k, v = (x @ W[i*80:(i+1)*80].T + b[i*80:(i+1)*80] for i in range(3))   # (L, B, 80) each
def heads(t): return t.reshape(128, 4, 2, 40).permute(1, 2, 0, 3)       # (B, h, L, 40)
qh, kh, vh = heads(q), heads(k), heads(v)
att = torch.softmax(qh @ kh.transpose(-1, -2) / math.sqrt(40), dim=-1)   # (B, h, L, L)
ctx = (att @ vh).permute(2, 0, 1, 3).reshape(128, 4, 80)
sa = ctx @ el.self_attn.out_proj.weight.T + el.self_attn.out_proj.bias
h1 = F.layer_norm(x + sa, (80,), el.norm1.weight, el.norm1.bias, el.norm1.eps)
ff = F.relu(h1 @ el.linear1.weight.T + el.linear1.bias) @ el.linear2.weight.T + el.linear2.bias
out = F.layer_norm(h1 + ff, (80,), el.norm2.weight, el.norm2.bias, el.norm2.eps)

hand-written == encoder_layer (eval): True max diff 2.6226043701171875e-06
attention (4, 2, 128, 128) row sums 0.9999997615814209 1.000000238418579 scale 1/sqrt(40) = 0.15811388300841897

手寫版和 el(x) 的輸出最多差 2.6 × 10−6，是浮點數運算順序不同造成的誤差，可以說完全相同。注意力的形狀是 (batch, 頭, L, L) = (4, 2, 128, 128)，每一列加起來是 1；用 need_weights=True, average_attn_weights=False 向 PyTorch 要它自己算的注意力權重，和手寫的也一樣。這個比對是在評估模式（eval()）下做的，因為訓練模式有 dropout（3.3 節）。

注意力的成本是長度的平方

注意力矩陣是 L × L：訓練時 128 格，一個頭是 16,384 個數，很便宜。但第 5 章的 test.py 送的是整句，最長一句 4,940 格，兩個頭的注意力矩陣是 2 × 4,940 × 4,940 個 float32 = 186 MiB；這份資料只有 8,000 句、一次一句，GPU 吃得下。如果句子再長十倍，記憶體就是一百倍。這是 Transformer 處理長序列最大的限制，第 6 章介紹的幾種變體，有一部分就是為了解決它。

3.3　encoder layer 的其餘部分：殘差、LayerNorm、FFN、dropout

把手寫程式的最後四行寫成公式，就是一層 TransformerEncoderLayer（PyTorch 預設 norm_first=False 的版本）：

h = LayerNorm1( x + Dropout1( SelfAttention(x) ) )
out = LayerNorm2( h + Dropout2( Linear2( Dropout( ReLU( Linear1(h) ) ) ) ) )
  • 殘差連接（residual connection）：兩個子層都是「輸入 + 子層的輸出」。HW03 的第 7 章講過它的好處：梯度可以沿著「+」直接往回傳，網路比較好訓練。
  • FFN（position-wise feed-forward network）：linear1 80 → 256、ReLU、linear2 256 → 80。和 prenet 一樣只作用在最後一維，所以是每一格各自過同一個兩層網路。注意力負責格與格之間的交流，FFN 負責每一格自己的非線性變換。dim_feedforward=256 是中間層的寬度，PyTorch 的預設是 2,048，範例程式改小了。
  • LayerNorm：對每一格的 80 維各自做正規化（減平均、除以標準差，再乘上、加上可學習的 80 個 weight 與 80 個 bias），eps 是 1e-5。和 HW03 的 BatchNorm 不同，它不跨樣本統計，所以訓練與評估時的算法一樣、和 batch 大小無關。
  • Dropout：一共四處，機率都是 0.1：注意力權重本身（在 MultiheadAttention 裡面，不是獨立的模組）、注意力之後的 dropout1、FFN 中間的 dropout、FFN 之後的 dropout2。0.2 節 print(model) 看到的是後三個。訓練模式下同一個輸入算兩次，本書實測輸出最多差 5.96；評估模式下 dropout 關掉，每次都一樣。

LayerNorm 放在殘差相加之後，叫做 post-norm，這是 2017 年原始論文的做法；把 LayerNorm 移到子層之前（x + SelfAttention(LayerNorm(x))）叫做 pre-norm，用 norm_first=True 打開。這個差別在一層的時候不太重要，疊深了就很重要：第 8 章有一組 3 層、寬 256 的 Transformer，用 post-norm 與學習率 1e-3 訓練，整句驗證準確率只有 0.521，只改成 pre-norm 就變成 0.951。

3.4　沒有位置編碼：模型看不出順序

回頭看 3.2 節的公式：注意力權重只取決於「兩格的內容」，和它們在第幾格無關；FFN、LayerNorm、prenet 都是每一格各自做。所以如果把輸入的 128 格打亂順序，每一格的輸出向量會跟著一起被打亂，但每個向量本身不變。原始的 Transformer 論文為了讓模型知道順序，在輸入上加了一組位置編碼（positional encoding）——一個隨位置變化的向量。classifier.py 沒有加：prenet 之後直接進 encoder。

再加上第 66 行的 mean pooling 把所有格子平均——平均和順序無關——結論是：這個模型的輸出和格子的順序完全無關，它看到的是一袋（bag of）沒有順序的格子。本書用訓練好的權重實測，把 5,667 句驗證語句的每一句整句送進模型三次：原本的順序、時間倒過來、隨機打亂：

full-length valid acc, frames in order / reversed / shuffled: {'orig': 0.85724, 'reversed': 0.85724, 'shuffled': 0.85724} max |logit diff| orig vs shuffled 1.52587890625e-05

三種順序的準確率一模一樣，5,667 句裡每一句的 logits 最多只差 1.5 × 10−5（浮點數加法順序不同的誤差）。把一句話倒著播、甚至把每 10 毫秒剪下來隨便亂排，模型給的答案都不會變。

這聽起來很糟，但對說話者辨識來說其實不算太離譜：認一個人的聲音，靠的主要是聲音的「質地」——音高的範圍、共振峰的位置、說話的音色——這些是每一格（或短短幾格）就看得出來的統計特性，不太需要知道字的先後順序。第 1 章 1.7 節看圖得到的直覺也是這樣。但「完全不知道順序」終究丟掉了資訊：一個音怎麼滑到下一個音、語速與節奏，都要跨好幾格才看得出來。給模型這種「局部順序」最直接的方法是卷積——這正是報告第 2 題、第 7 章的主題，Conformer 的卷積模組就是做這件事的；第 8 章的實驗裡，同樣寬 160、2 層，把 Transformer 換成 Conformer，整句驗證準確率從 0.918 升到 0.937。

注意力本身不知道順序，是很多人第一次讀 Transformer 時漏掉的事

文字的 Transformer 一定要加位置編碼，因為「狗咬人」和「人咬狗」是同一袋字。後來的模型發展出很多種位置編碼：原論文的正弦函數、BERT 的可學習位置向量、Conformer 用的相對位置編碼、現在大型語言模型常用的旋轉位置編碼（RoPE）。HW04 的範例程式全都沒有，第 8 章本書實作的 Conformer 也沒有加位置編碼，局部順序完全靠卷積提供。

3.5　forward：permute 與 batch_first

第 58 行 prenet，第 69 行 pred_layer，3.1 節講過。中間有兩次換軸：第 60 行 permute(1, 0, 2) 把 (batch, 長度, 80) 換成 (長度, batch, 80)，第 62 行過 encoder，第 64 行 transpose(0, 1) 換回來。為什麼要換？因為 nn.TransformerEncoderLayer 有一個參數 batch_first，預設是 False，代表它要的輸入是「長度在前」（第 61 行的註解）。這是早年 PyTorch 跟著 RNN 的慣例留下來的。permute(1, 0, 2) 和 transpose(0, 1) 在三維 tensor 上做的是同一件事（交換前兩維），兩行用了兩種寫法。

如果忘了換軸會怎樣？encoder 會把 batch 那一維當成長度，讓同一批裡不同句子的同一格互相注意，而不是同一句話裡的不同格；形狀完全對得上，程式不會報錯，只會悄悄地學錯東西。這是 batch_first 最常見的坑。

把第 41 行打開會怎樣

第 41 行被註解掉的 nn.TransformerEncoder(self.encoder_layer, num_layers=2)，會把傳進去的那一層深複製成 2 份疊起來（每一層有自己的參數）。但只拿掉第 41 行的 # 並不會讓模型變成兩層：forward 第 62 行呼叫的仍然是 self.encoder_layer，self.encoder 建好了卻從來沒被用到，只是多了一份不會被訓練的參數（第 0 章自我測驗第 4 題）。要真的用兩層，第 62 行也要改成 out = self.encoder(out)。

另外，打開第 41 行，建立模型時 PyTorch 2.11 會印出一個警告（本書實測）：

UserWarning: enable_nested_tensor is True, but self.use_nested_tensor is False because encoder_layer.self_attn.batch_first was not True(use batch_first for better inference performance)

意思是：TransformerEncoder 有一條推論用的快速路徑（把補值的部分用 nested tensor 跳過不算），但只在 batch_first=True 時才能用，所以它提醒你這條路徑被關掉了。這只影響速度、不影響結果。原狀的程式只用一層 TransformerEncoderLayer、沒有 TransformerEncoder，所以不會印這個警告。第 8 章的實驗工具 --layers 2 就是「打開第 41 行並改好第 62 行」的版本，整句驗證準確率從 0.857 升到 0.897。

現在的做法：batch_first=True、norm_first=True，以及 SDPA

2022 年以後寫 Transformer，大多直接設 batch_first=True，省掉兩次換軸，也才能用上 PyTorch 的快速路徑；疊好幾層時多半用 pre-norm（norm_first=True），比較好訓練（3.3 節、第 8 章）。PyTorch 2.0 起還有 torch.nn.functional.scaled_dot_product_attention（SDPA），把 3.2 節那幾行 softmax 與矩陣乘法交給 FlashAttention 這類融合核心來算，長序列時快很多、省很多記憶體——3.2 節那 186 MiB 的注意力矩陣，FlashAttention 根本不會完整存下來。nn.MultiheadAttention 在條件符合時已經會自動使用它。

3.6　mean pooling 與補值

第 66 行 stats = out.mean(dim=1) 在長度那一維取平均，把 (32, 128, 80) 變成 (32, 80)：一句話一個向量。它簡單、沒有參數、可以吃任何長度，但有兩個弱點。第一，每一格的權重都一樣，一段停頓和一段清楚的母音同樣重要；第 8 章的 Self-Attention Pooling 讓模型自己學每一格的權重。第二，它不知道哪些格子是補的。

第 2 章看過，全部資料只有 2 句短於 128 格，訓練時會被補上 −20。補的格子經過 prenet、encoder 之後也會變成 80 維的向量，而且會參與注意力（其他格子會去「注意」這些補的格子），最後被平均進去。本書拿那句 91 格的話（說話者編號 534）、用訓練好的權重實測兩種情況：

送進模型的形狀模型的答案正確答案 534 的機率
原本的 91 格(1, 91, 40)534（對）0.8627
補 37 格 −20 到 128 格（訓練時的樣子）(1, 128, 40)534（對）0.2007

兩次都猜對，但補了之後，模型對正確答案的把握從 86% 掉到 20%：37 格「靜音」占了平均的 29%，把這句話的向量往「靜音」的方向拉了一大段。這句話在訓練集裡，所以影響的是訓練時的梯度，不是驗證或測試的分數；而且全部只有 2 句，對整體結果的影響可以忽略。但這個例子說明了補值不是無害的。正確的做法是告訴模型哪些格子是補的：

  • 給 encoder 一個 src_key_padding_mask（形狀 (batch, 長度)，補的位置是 True），注意力就不會看那些格子；
  • pooling 時只平均真正的格子：把補的位置乘 0 再加總，除以每句的真實長度，而不是一律除以 128。

這需要 collate_batch 多回傳每句的長度。在這份幾乎不用補的資料上沒有必要，本書的實驗也沒有加。

3.7　沒有用到的 dropout 參數

第 31 行 def __init__(self, d_model=80, n_spks=600, dropout=0.1) 收了一個 dropout，但第 38–40 行建 encoder layer 時沒有傳 dropout=dropout，pred_layer 裡也沒有任何 dropout。所以這個參數是裝飾用的。本書實測：

Classifier(dropout=0.5): encoder dropout p = 0.1

傳 0.5 進去，encoder 裡的 dropout 仍然是 PyTorch 的預設值 0.1。剛好預設值和參數的預設值一樣，所以原本的程式行為正確；但如果有人想調 dropout、改了 Classifier(dropout=0.3)，會以為自己改了什麼，其實什麼都沒變。這類「參數收了卻沒用」的錯誤，Python 不會有任何警告，只能靠讀程式或像上面這樣實測抓出來。要修，就在第 38–40 行加上 dropout=dropout。

本章重點

  • prenet、FFN、LayerNorm、pred_layer 都是每一格（或每一句）各自做；只有自注意力讓格與格交流。
  • 自注意力：Q、K、V 由一個 (240, 80) 的 in_proj 產生；2 個頭各 40 維，softmax(QKT/√40)V；注意力矩陣是 L × L，最長的測試語句要 186 MiB。本書手寫一次，和 PyTorch 差不到 3 × 10−6。
  • 一層是 post-norm：LayerNorm(x + Dropout(SA(x)))，再 LayerNorm(h + Dropout(FFN(h)))；dropout 有四處，都是 0.1。疊深時 pre-norm 比較好訓練。
  • 沒有位置編碼 + mean pooling ⇒ 模型和格子順序完全無關：倒放、打亂，準確率都是 0.85724。局部順序要靠卷積（第 7 章）。
  • batch_first 預設 False，所以要 permute；打開第 41 行還要改第 62 行，並會印 nested tensor 的警告。
  • 補的 −20 會被注意力看到、被平均進去：91 格那句補到 128 格後，正確答案的機率從 0.863 掉到 0.201。dropout 參數沒被用到。

自我測驗

1. 把 nhead 從 2 改成 4，參數量會變嗎？改成 3 呢？

改成 4，參數量不變（還是 125,896），每個頭變成 80 ÷ 4 = 20 維。改成 3 會在建立模型時報錯：AssertionError: embed_dim must be divisible by num_heads（本書實測），因為 d_model 80 不能被 3 整除，而每個頭的寬度必須相同。本書第 8 章的組合都選了能整除的頭數（160 配 4 個頭、256 配 8 個頭）。

2. 3.4 節說模型和順序無關。那為什麼訓練時「隨機切一段連續的 128 格」，而不是隨機挑 128 個不連續的格子？

對這個模型而言，片段裡的格子怎麼排列確實沒有差別；但「挑哪些格子」仍然有差：連續的 128 格是 1.28 秒的一段話，內容集中；隨機挑 128 個分散的格子，會從整句各處取樣，涵蓋的音更多，平均起來可能更像整句話（這可能也會讓切段與整句的準確率差距變小）。連續切段的好處是任何模型都適用——換成有位置編碼或卷積的模型（Conformer）時，局部順序就重要了。本書沒有實際跑「隨機挑格子」的實驗，以上是推論。

3. 如果把第 60 行和第 64 行都刪掉（不換軸），程式會報錯嗎？會發生什麼？

不會報錯。encoder 會把 (32, 128, 80) 當成「長度 32、batch 128」，讓同一批 32 句話的「第 t 格」互相注意，每一句話內部的 128 格之間反而完全沒有交流；輸出形狀仍是 (32, 128, 80)，mean pooling 和 pred_layer 照常運作。模型還是能學到一些東西（每一格各自的特徵），但等於把注意力浪費在不同句子之間；而且驗證、測試時 batch 的組成不同（測試時 batch 只有 1），行為也會跟著變。本書沒有實際訓練這個版本。

4. 評估模式下，同一個 batch 送進去兩次，輸出會一樣嗎？訓練模式呢？

評估模式下一樣：model.eval() 關掉所有 dropout，而這個模型沒有 BatchNorm 之類會隨 batch 改變的層，所以計算是確定的。訓練模式下不一樣：四處 dropout 每次隨機丟掉 10% 的值，本書實測同一個輸入算兩次，輸出最多差 5.96。train.py 的 valid() 開頭呼叫 model.eval()、結尾呼叫 model.train()，就是為了這個（第 4 章）。

5. 3.6 節那句 91 格的話補值後機率大跌，但第 0 章說模型可以吃任何長度。為什麼訓練時不乾脆不補、讓每個 batch 的長度不同？

因為一個 batch 必須是一個長方形的 tensor，32 句的長度要一樣才能疊起來。訓練時每句都切成 128 格，剛好解決了這件事，只剩那 2 句短句要補。另一個辦法是把長度相近的句子分在同一批（bucketing），或者每批切成這批最短那句的長度；測試時 batch_size=1 則完全不需要補（第 5 章）。

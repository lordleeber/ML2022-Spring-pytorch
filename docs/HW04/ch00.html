第 0 章　任務、環境與模型總覽

先弄清楚作業要什麼、規則禁止什麼、分數怎麼算；再看一眼模型——一段 128 格、每格 40 個數字的聲音，經過一層 Transformer encoder、取平均，變成 600 個分數；最後把 train.py 和 test.py 實際跑一遍，逐行讀它們印出來的東西，並看到一個本書會反覆回來的問題：印出來的驗證準確率 0.6859，和用 test.py 的做法量出來的 0.857，為什麼差這麼多。

0.1　作業要做什麼

HW04 是一個說話者辨識（speaker identification）問題：輸入一段話，輸出說這段話的人是 600 位說話者裡的哪一位。投影片第 4 頁把它歸類為多類別分類（multiclass classification）——和 HW02 的音素分類、HW03 的食物分類是同一種問題，只是類別有 600 個，而且輸入是一段長短不一的聲音。第 3 頁寫明這份作業的目標：「Learn how to use Transformer」。

資料來自 VoxCeleb2，一個從網路影片裡收集名人說話片段的資料集。助教從裡面隨機挑了 600 位說話者，把聲音事先轉成 mel-spectrogram（第 1 章會說明這是什麼），所以資料集裡沒有任何原始聲音檔，只有一個個存著二維 tensor 的 .pt 檔。數量如下：

資料句數有沒有標籤用途
訓練語句（metadata.json）56,666有程式再切成訓練 50,999 句、驗證 5,667 句（第 2 章）
測試語句（testdata.json）8,000沒有交給 Kaggle 評分

本書在本機數過，兩個數字和 json 檔一致。投影片這裡有一處前後不一：第 5 頁說測試資料是「4000 processed audio features (public & private)」，第 20 頁卻要你交 8,000 行答案；實際的 testdata.json 是 8,000 句，比較合理的讀法是 public 與 private 各 4,000 句。第 5 章會再回來看這件事。

規則：不准用額外資料與預訓練模型（投影片第 25 頁）

第 25 頁列了幾條禁令，和技術有關的是兩條：不准搜尋或使用額外的資料，不准用預訓練模型（pretrained model）。另外每天最多上傳 5 次到 Kaggle。所以這份作業和 HW03 一樣，模型要從亂數開始訓練，只能用這 56,666 句話。目錄頁的「現在的做法」框說明了今天的說話者辨識為什麼幾乎都從預訓練的語音模型出發。

0.2　模型總覽：128 × 40 個數字，經過一層 encoder 變成 600 個分數

本 repo 的模型在 classifier.py，類別名稱是 Classifier，和原版範例程式的模型一模一樣（只差縮排從 tab 換成空白）。投影片第 10 頁把它畫成四段：輸入的特徵 → Encoder → Pooling Layer → Linear Layer → 600 維的預測。這一節只看整體：有哪些層、資料的形狀怎麼變、參數在哪裡。每一層內部怎麼算，留給第 3 章逐行拆。

__init__ 建了三樣東西，forward 依序用它們：

  • self.prenet（第 34 行）：一層 nn.Linear(40, d_model)，把每一格的 40 個 mel 數值變成 d_model = 80 個數字。Transformer 裡的每一層都在同一個寬度上運算，這個寬度就叫 d_model。
  • self.encoder_layer（第 38–40 行）：PyTorch 內建的 nn.TransformerEncoderLayer，只有一層。參數是寬度 80、前饋網路（feed-forward network，FFN）中間層 256、注意力頭（head）2 個。第 41 行把「疊 2 層」的 nn.TransformerEncoder 註解掉了，第 35–37 行的 TODO 則提示把它換成 Conformer。
  • self.pred_layer（第 44–48 行）：兩層全連接，80 → 80 → 600，中間夾一個 ReLU。最後的 600 個數字還沒經過 softmax，叫做 logits；分數最大的那一位就是模型的答案。

forward 裡有兩個新東西。第 60 行的 permute(1, 0, 2) 把形狀從「batch、長度、寬度」換成「長度、batch、寬度」，因為 TransformerEncoderLayer 預設要的就是長度在前（第 61 行的註解）；第 64 行再換回來。第 66 行的 out.mean(dim=1) 是 mean pooling：把 128 格的向量平均成一個，這樣不管一句話多長，最後都只剩一個 80 維的向量代表「這段聲音是誰」。第 31 行的參數 dropout=0.1 其實沒有被用到（第 38–40 行沒有傳給 encoder layer），這件事第 3 章再說。

注意整張表裡，只有 mean pooling 會改變「長度」那一維。在它之前，128 格的每一格都各自保有一個向量；encoder 讓每一格「看到」其他格，但不會把它們合併。這也是為什麼同一個模型可以吃 128 格（訓練）也可以吃 4,940 格（測試時最長的一句）：除了 pooling，沒有任何一層的參數和長度有關。本書在 PyTorch 2.11 上實際把一句 (1, 4940, 40) 送進模型，輸出就是 (1, 600)。

參數量：先手算，再讓 PyTorch 數

這個模型有兩種有參數的層：nn.Linear 與 nn.LayerNorm。多頭自注意力裡面其實也是 Linear。公式：

Linear(i, o) 的參數 = i × o（權重）+ o（偏差 bias）
LayerNorm(d) 的參數 = 2d（每一維一個縮放 weight、一個平移 bias）
多頭自注意力的參數 = 3 × Linear(d, d)（產生 Q、K、V）+ Linear(d, d)（輸出投影），和頭數無關
  • prenet：40 × 80 + 80 = 3,280。
  • 自注意力：PyTorch 把產生 Q、K、V 的三個 80 × 80 矩陣疊成一個 in_proj_weight，形狀 (240, 80)：240 × 80 + 240 = 19,440；輸出投影 out_proj 80 × 80 + 80 = 6,480。合計 25,920。2 個頭只是把 80 維切成兩份各 40 維分開算注意力，不增加參數（第 3 章）。
  • FFN：linear1 80 × 256 + 256 = 20,736；linear2 256 × 80 + 80 = 20,560。
  • LayerNorm：norm1、norm2 各 2 × 80 = 160。encoder 合計 25,920 + 20,736 + 20,560 + 160 + 160 = 67,536。
  • pred_layer：80 × 80 + 80 = 6,480；80 × 600 + 600 = 48,600。
  • 合計：3,280 + 67,536 + 6,480 + 48,600 = 125,896，大約十二萬六千個。

和 HW03 的 CNN（一千兩百八十萬個參數）比，這個模型小了一百倍。最後一層 Linear 80 → 600 就占了 39%，因為它要替 600 個人各準備一組 80 維的權重——第 8 章的 Additive Margin Softmax 改的就是這一層。接著讓 PyTorch 自己數。在 HW04/ 裡執行（只建模型，不需要 GPU）：

$ cd HW04
$ ../.venv/bin/python -c "
from classifier import Classifier
m = Classifier()
for name, mod in m.named_modules():
    n = sum(p.numel() for p in mod.parameters(recurse=False))
    if n:
        print(name, mod.__class__.__name__, n)
print('total', sum(p.numel() for p in m.parameters()))
"

和手算一致。recurse=False 讓每個模組只數「直接屬於自己」的參數，所以容器被跳過，ReLU 與 dropout 沒有參數也被跳過。兩個細節：第一，in_proj 的 19,440 個參數直接掛在 MultiheadAttention 身上，不是一個獨立的 Linear；第二，out_proj 的類別名稱是 NonDynamicallyQuantizableLinear，它就是一個 nn.Linear，只是多了一個「不要被動態量化」的標記，計算上沒有差別。

0.5　執行 train.py

兩支腳本都要在 HW04/ 裡面執行，因為資料路徑寫成相對路徑 ./Dataset，相對的是「目前所在的資料夾」，不是腳本所在的資料夾。先看設定：

和 HW03 用 epoch 計算不同，這份程式以「步」（step）為單位：一步就是拿一個 batch（32 句）更新一次參數，總共 70,000 步（第 235 行）。每 2,000 步在驗證集上量一次準確率（第 232 行），每 10,000 步把「目前最好的」權重存成 model.ckpt（第 234 行）。第 233 行的 warmup 是前 1,000 步讓學習率從 0 慢慢升上去（第 4 章）。一個 epoch 是 1,593 步，所以 70,000 步大約是 44 個 epoch（第 2 章）。n_workers 8 是讀資料的背景行程數。

第 247 行建 DataLoader（第 2 章），第 251 行建模型，n_spks 是從資料裡數出來的 600。第 252 行用 cross entropy 當 loss，第 253 行用 AdamW 優化器、學習率 0.001，第 254 行套上學習率排程（第 4 章）。三個 print 分別在第 245、249、255 行。第 260 行開了第一個進度條，注意它的 unit="step" 沒有前導空白，等一下的輸出看得出來。第 262 行以後是訓練迴圈，留給第 4 章。執行：

跑多久：本書在 GPU 上沒有任何其他程式時，用 /usr/bin/time -v 量完整的 train.py：wall clock（牆上時鐘實際經過的時間）3 分 53 秒，再跑一次 3 分 59 秒。投影片估計 Colab 上要 30–40 分鐘，差了將近十倍，主要差在硬體：Colab 免費方案給的 GPU 與 CPU 都比本機這台弱。同一份紀錄裡，CPU 使用率 353%，也就是平均有三、四個核心在忙——8 個背景行程在讀 .pt 檔、切段、補齊；主程式本身最多用到約 1.5 GB 的主機記憶體。

同樣的程式，同樣的結果

本書在兩個不同的資料夾裡各跑一次 train.py，兩次存下的 model.ckpt 逐位元組相同（md5 都是 0eef2229…）。這不是理所當然的：資料由 8 個背景行程平行讀取，每個行程都用 Python 的 random 隨機切段，PyTorch 替每個行程設好了種子，train.py:21-32 又固定了主程式的種子並要求 cuDNN 使用確定性的演算法，結果才會每次一樣（第 2、4 章）。所以只要環境相同，你跑出來的每一行數字都會和上面一樣。repo 裡被忽略的那份舊 model.ckpt（2026-10-03）是更早用不同設定跑的，和今天的不同；本書不用它。

錄輸出時的小陷阱：進度條消失了

如果你把 train.py 的輸出導到檔案或管線，例如用 script -qc "..." log.txt 錄下來，可能會發現檔案裡只有三行 [Info]、7 行存檔訊息和一堆空行，進度條全不見了。原因是 tqdm 會先問終端機有多寬，再決定進度條畫多長；在沒有真正終端機的環境裡，寬度是 0，tqdm 就什麼都不畫。本書錄上面那段輸出時，先執行 stty cols 120 把寬度設好。這件事和程式的結果無關，只影響你看得到什麼。

0.7　本 repo 的成績落在哪裡

本機沒有測試集的答案，能量的只有驗證集。把驗證集上的數字和投影片的四條基準線放在一起：

同一個模型、同一份權重、同一批驗證語句，只因為「每句看 128 格」還是「看整句」，準確率就從 0.686 跳到 0.857，差了 17 個百分點。原因不難想：一個 128 格的片段只有 1.28 秒，平均只占一句話的 23%（第 2 章），資訊少得多；整句話裡同一個人的聲音特徵出現很多次，平均起來就穩得多。train.py 的 valid() 拿的是和訓練時一樣的切段資料，test.py 卻送整句，所以訓練時印出的數字並不是 test.py 那種做法的準確率。第 4 章會把這兩種量法並排拆開，第 8 章的每一組實驗也都會同時報這兩個數字。

驗證集不是 Kaggle 的測試集

表裡有兩種數字：基準線是 Kaggle 測試集上的分數，本 repo 的是本機驗證集上的準確率，兩者是不同的資料。所以本書不會說本 repo「過了哪一條基準線」。而且有一個跡象顯示驗證集比測試集容易很多：投影片說 Simple 基準線就是「跑範例程式」，本 repo 就是範例程式，在 Kaggle 上大概就在 0.608 附近；同一份程式送整句到本機驗證集卻有 0.857。一個合理的解釋是：驗證集是從同一批 56,666 句裡隨機分出來的，同一位說話者、甚至同一支影片的其他句子都在訓練集裡，錄音環境、麥克風都一樣；測試集的句子可能來自不同的影片。這只是推論——本書拿不到測試集的答案，無法驗證。能確定的是：驗證集上的數字只適合拿來互相比較（第 8 章），不適合拿來預測 Kaggle 的分數。

本章重點

  • HW04 是 600 位說話者的多類別分類，輸入是已經轉成 mel-spectrogram 的語句；不准用額外資料與預訓練模型；四條基準線從「跑範例程式」到「Conformer + Self-Attention Pooling + AM-Softmax」。
  • Classifier：prenet 40 → 80、一層 TransformerEncoderLayer（2 個頭、FFN 256）、mean pooling、80 → 80 → 600。共 125,896 個參數，手算與 PyTorch 一致；只有 pooling 會消掉長度那一維，所以模型吃任何長度都可以。
  • train.py 以步計：70,000 步、每 2,000 步驗證、每 10,000 步存檔，本機 3 分 53 秒，兩次跑出逐位元組相同的 model.ckpt；test.py 一次一句、送整句，11 秒寫出 8,001 行的 output.csv。
  • 進度條上的 accuracy／loss 是最後一個 batch 的值；驗證停在 5664/5667 是因為 drop_last=True。
  • 印出的 0.6859 是「切 128 格」的準確率；同一份權重送整句是 0.857。兩者都是驗證集上的數字，不能拿來宣稱過了 Kaggle 的哪一條基準線。

自我測驗

1. 不改 classifier.py，模型要多少個參數才能處理一句 4,940 格的測試語句？比處理 128 格時多還是少？

一樣多，都是 125,896 個。prenet、encoder 裡的 Linear 與 LayerNorm、pred_layer 都只對「每一格的 80 維」或「pooling 後的 80 維」運算，參數和格數無關；自注意力會讓 4,940 格兩兩互看，計算量與記憶體跟著長度平方成長，但參數不變。真正把長度消掉的是沒有參數的 mean pooling。本書實測把 (1, 4940, 40) 送進模型，輸出就是 (1, 600)。

2. 訓練第 1 步的進度條印 loss=6.40。這個數字為什麼合理？

剛初始化的模型對 600 位說話者給的分數差不多，softmax 之後每一位的機率接近 1/600；cross entropy 是「正確答案的機率取負對數」，所以約等於 −ln(1/600) = ln 600 ≈ 6.397。印出來的 6.40 就是這個值，表示一開始模型確實在亂猜。

3. 驗證的進度條為什麼停在 5664/5667，而不是 5667/5667？

驗證集有 5,667 句，DataLoader 一批 32 句、設了 drop_last=True：5,667 = 177 × 32 + 3，最後 3 句湊不成一整批就被丟掉。進度條的總數是 len(dataloader.dataset) = 5,667，每一批 update(dataloader.batch_size) 加 32，177 批加到 5,664 就結束了（第 2 章）。

4. 把 classifier.py:41 的註解拿掉，模型會變成兩層嗎？

不會。第 41 行只是建了一個 self.encoder，但 forward 第 62 行用的仍然是 self.encoder_layer，所以實際計算還是一層，只是多了一組永遠沒用到的參數。要真的用兩層，第 62 行也要改成 self.encoder(out)。打開之後 PyTorch 還會印一個和 batch_first 有關的警告，第 3 章會看到；改成兩層的實測結果在第 8 章。

5. 本 repo 印出的驗證準確率 0.6859 高於 Simple 的 0.60824、低於 Medium 的 0.70375。可以說「本 repo 過了 Simple 基準線」嗎？

不行。基準線是 Kaggle 測試集上的分數，0.6859 是本機驗證集上、而且每句只看 128 格的準確率，兩者量的是不同資料、不同做法。同一份權重整句送進去，驗證集上是 0.857，反而高過 Strong 基準線——但範例程式在 Kaggle 上應該就在 Simple 附近，這表示驗證集比測試集容易很多。驗證集的數字只能拿來比較不同的模型。

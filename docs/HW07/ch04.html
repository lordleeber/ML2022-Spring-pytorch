第 4 章　評估與後處理：同一個模型，只改挑答案的規則

模型輸出的只是每個視窗的兩排分數，「答案」是後處理的規則挑出來的。這一章全部用同一個訓練好的模型（第 0 章那個 dev 0.416 的 checkpoint），一次訓練都不重跑，只改挑答案的方式：先修掉範例的 bug，再改評估視窗的 doc_stride。前者讓 EM 漲了 1 個百分點，後者讓 EM 從 0.416 漲到 0.6 以上，原因又回到第 2 章的「答案總在中央」。

4.1　範例的 evaluate

規則只有三步：每個視窗裡，start 分數最高的位置當起點、end 分數最高的位置當終點（第 15–16 行）；兩個分數相加當這個視窗的分數（第 19 行）；所有視窗裡分數最高的那個，用 decode 把起點到終點的 token 換回文字（第 22–25 行）。這就是投影片 p.14 的表：window 1 總分 0.9、window 2 總分 1.0，選 window 2。

第 6 行的註解說這裡「有一個 bug，還有改進空間」，第 7 行提示「打開預測檔看看哪裡錯了」。順帶一提，第 10 行的變數叫 max_prob、第 18 行的註解說「答案的機率」，但 output.start_logits 是 logits（沒有經過 softmax），兩個 logits 相加也不是機率。這不只是命名問題，4.5 節會看到，改成真正的機率反而會更差。

4.2　打開預測檔

照提示做：把第 0 章那個模型對 dev 的預測逐題攤開（stride 150，範例規則，EM 0.416），找出規則本身造成的錯誤。有四種：

空字串最常見：135 題，佔 dev 的 3.3%。原因是 start 與 end 各自取最大值，沒有任何規則要求終點在起點之後（第 3 章 3.1 節：兩排分數是獨立打的）。更糟的是，這種「不合法」的組合照樣參加視窗之間的比較：第 0 章的 dev 第 0 題，終點在起點之前的那個視窗分數最高，答案就成了空字串。這就是投影片 p.21 點名的 bug（end_index < start_index）。

4.3　規則一：只在合法的範圍內挑

修法是把「各自取最大」改成「在所有合法的 (起點, 終點) 組合裡，取 start 分數 + end 分數最大的一對」。合法的條件有三個：起點 ≤ 終點；兩者都在文章的部分（不在問題、特殊符號或 padding 上）；答案長度不超過一個上限。上限取 30 個 token：dev 答案的第 99 百分位是 23 個 token，30 足夠寬鬆。寫成程式：

關鍵在第 16–19 行：pair[i, j] 是「起點 i、終點 j」這個組合的分數，一次算出文章裡所有組合（最多 150 × 150 個）；triu() 留下 i ≤ j 的上三角，~triu(30) 再去掉 j ≥ i + 30 的部分，剩下一條寬 30 的帶狀區域。第 12–15 行用 token_type_ids 算出這個視窗的文章有幾個 token，只取文章部分的分數，問題與 padding 就自然被排除了。拿 dev 4,131 題實際跑一次，EM 是 0.42677（1,763 題），和實驗工具 docs/tools/hw07_post.py 的結果完全相同。

全部加起來，多答對 45 題，沒有任何一題從對變錯。分類一下這 45 題：原本是空字串的 27 題、含 [UNK] 的 9 題、答案過長的 6 題、其他 3 題。135 個空字串全部消失了，但只有 27 題變成正確答案；其餘的 108 題換成了另一個合法、但錯誤的答案。這說明規則能修的是「明顯不合理」的輸出，修不了模型本身的判斷：第 3 章的分類裡，「選錯視窗」與「視窗對、位置錯」合計 2,331 題，後處理碰不到它們的大部分。

4.4　規則二：從原文切出答案

第 1 章算過：就算位置全對，用 decode 還原，dev 有 44 題對不上；改用 offsets 從原文切，只剩 1 題。evaluate_v2 的第 25 行就是這件事：視窗 k 裡的第 i 個文章 token，是整篇文章的第 k × doc_stride + i 個 token，查它的 offsets 得到字元位置，直接從原文字串切。原文是什麼樣子，答案就是什麼樣子，[UNK]、大小寫、原文中的空白都保留。

實際的收穫比 44 題小：單獨加上「從原文切」只多答對 11 題（範例的選擇，0.41588 → 0.41854），因為這 44 題裡，模型多半本來就沒有指對位置。後處理的上限由模型決定，但後處理錯了，模型再準也拿不到分數。在第 7 章換成 hfl 與 luhua 的模型時，這一條會變得更重要：它們的 tokenizer 會轉小寫，decode 出來的英文全是小寫，和標準答案的大小寫對不上。

4.5　視窗之間怎麼比：logits 還是機率

4.1 節提到，範例比的是 logits 的和，不是機率。直覺上，換成真正的機率應該比較合理：每個視窗各自做 softmax，取 log P(起點) + log P(終點) 來比。實測（合法組合、長度 ≤ 30、從原文切，只改比較方式）：

視窗之間比較的分數stride 150stride 32
start logit + end logit（範例的作法）0.426770.57153
log softmax(start) + log softmax(end)（各視窗分別正規化）0.375700.44275

機率版本差了 5 到 13 個百分點。原因在於 softmax 是在每個視窗內部正規化的：機率加起來一定是 1，所以就算一個視窗根本沒有答案，它最可能的位置照樣可以拿到很高的機率。logits 沒有這個限制，它的絕對大小保留了「模型有多確定」的訊息：含答案的視窗，範例規則的分數（max start + max end）平均是 8.09，不含答案的視窗平均只有 0.76。正規化把這個差距抹掉了。

這也點出這個模型的根本限制：它從來沒有被訓練過「這個視窗沒有答案」（第 3 章 3.5 節），logits 的大小只是碰巧帶有這個訊息。SQuAD 2.0 之後的標準做法，是讓模型在沒有答案時指向 [CLS]，把「沒有答案」也當成一個要學的選項。

4.6　評估的 stride：一個不用重新訓練的大改進

第 2 章說過，doc_stride 只影響評估，可以不重新訓練就調整，並且算出 stride 100 時被切斷的答案從 74 題變成 0 題。用同一個模型實際評估各種 stride：

回想第 2 章 2.3 節：訓練時有 52.4% 的答案中點正好落在視窗的第 75 個位置。模型會不會因此特別相信「視窗中央的答案」？量模型在 dev 上的預測位置：對每一個 dev 視窗，取範例規則挑出的 span 中點，看它落在文章部分（150 個 token）的哪裡：

stride 150 的所有視窗2,5931,5351,3921,2191,1064,0236844282378524
stride 32 的所有視窗7,5195,6195,1945,0674,89519,7593,3192,0591,112457135

中央那一格（70–80，寬 11 個位置）的預測數量，換算成每個位置的密度，是左邊相鄰那一格（60–69，寬 10）的 3.3 倍（stride 150）與 3.7 倍（stride 32）。視窗後半段（90 以後）的預測則越來越少。模型確實學到了訓練資料的形狀：答案若不是在中央，就是在前段，很少在後段（第 2 章：在後半的訓練答案只佔 13.7%）。

這解釋了 stride 的效果。stride 150 時，每個答案只出現在一個視窗裡，位置是隨機的，多半不在中央；stride 越小，同一個答案出現在越多個視窗裡，其中總有一個視窗讓它接近中央，而模型對中央的答案最有把握，那個視窗就會勝出。換句話說，小 stride 是在評估時把「答案在中央」這個條件重新造出來，讓評估更像訓練。stride 從 150 改成 32，答對的題目多了 842 題、變錯的有 244 題，淨增 598 題；選中的視窗含有答案的題數也從 2,734 題增加到 3,213 題。

代價是計算量：視窗數和 stride 大致成反比，stride 16 要算 8 倍的視窗（111,762 個），stride 8 要 16 倍（221,409 個），評估時間也差不多按比例增加。另一個更好的解法是從源頭消除偏差：讓訓練視窗的位置隨機，模型就不會偏好中央，第 6 章實測。到時候也能驗證本節的解釋：如果偏差真的是原因，用隨機視窗訓練的模型，從小 stride 得到的好處應該會小很多。

4.7　報告第 1 題怎麼寫

報告第 1 題（投影片 p.30）問：模型預測出起點、終點的機率之後，你用什麼規則決定最後的答案範圍？規則必須和範例不同。根據本章，一份有根據的答案大致是：

  • 在每個視窗裡，只考慮起點 ≤ 終點、兩者都在文章部分、長度不超過 30 個 token 的組合，取 start logit + end logit 最大的一對（修掉 end < start 與答案落在問題裡的情況）。
  • 視窗之間比較 logits 的和，不做 softmax（4.5 節：正規化會讓沒有答案的視窗也顯得很有把握）。
  • 答案用 offsets 從原文切出，不用 decode（修掉 [UNK] 與空白）。
  • 評估時用重疊的視窗（較小的 doc_stride），並附上本章的實測數字。

現在的做法：pipeline 已經內建這些規則

transformers 的 pipeline("question-answering") 把本章的後處理都包好了：它在每個視窗裡對合法的 (起點, 終點) 組合排序、限制答案長度（參數 max_answer_len，預設 15 個 token）、用 offsets 從原文切出答案，還能用 top_k 回傳前幾名的候選答案（n-best），視窗重疊則由 doc_stride 參數控制。它還支援 handle_impossible_answer=True：把 [CLS] 的分數當成「沒有答案」的分數一起比較，這需要模型在 SQuAD 2.0 這類有「無答案」題目的資料上訓練過。到了 LLM 時代，生成式問答不需要這些規則，但 RAG 的檢索階段又回到同樣的問題：每個 chunk 的相關度分數能不能互相比較，要不要正規化。

本章重點

  • 範例的 evaluate 讓 start、end 各自取最大值，可能 end < start（dev 135 題回答空字串）、可能落在問題裡、可能過長；答案用 decode 還原，[UNK] 會原樣出現。
  • 改成「在 i ≤ j、文章內、長度 ≤ 30 的組合裡取最高分，並用 offsets 從原文切」，同一個模型多答對 45 題（0.416 → 0.427），沒有任何一題變錯。
  • 視窗之間要比 logits，不要比各視窗分別正規化的機率（0.427 → 0.376）：logits 的大小帶有「這個視窗有沒有答案」的訊息。
  • 評估的 stride 從 150 縮到 8，同一個模型的 EM 從 0.416 漲到 0.627（範例規則；evaluate_v2 0.632），不用重新訓練，代價是 16 倍的視窗。主因不是救回被切斷的答案，而是模型偏好視窗中央：預測中點在中央的密度是旁邊的 3 倍多，小 stride 讓每個答案都有機會落在某個視窗的中央。

自我測驗

1. 一個視窗的 start logits 最大值在位置 50（分數 6.0），end logits 最大值在位置 48（分數 5.5）；位置 48、50 的另一排分數分別是 start[48] = 5.0、end[50] = 4.0。範例規則與 evaluate_v2 各會選出什麼？

範例：起點 50、終點 48，視窗分數 11.5，decode 出空字串。evaluate_v2 要找 i ≤ j 的最佳組合：(48, 48) 是 5.0 + 5.5 = 10.5，(50, 50) 是 6.0 + 4.0 = 10.0，(48, 50) 是 5.0 + 4.0 = 9.0；如果其他位置的分數都比這些低，會選 (48, 48)，也就是單一個 token。注意這個視窗在範例裡拿 11.5 分，在 evaluate_v2 裡只拿 10.5 分，所以視窗之間的勝負也可能改變。

2. 為什麼「長度 ≤ 30」只多答對 7 題（0.42242 → 0.42411），卻沒有讓任何題目變錯？如果把上限設成 3 呢？

dev 的答案 99% 不超過 23 個 token，30 的上限幾乎不會排除正確答案，只排除模型偶爾挑出的超長片段，所以只會修正、不太會改錯。上限設成 3，所有超過 3 個 token 的答案（例如「暖溫帶大陸性季風氣候」）都不可能答對，EM 會明顯下降。上限要依資料的答案長度分布來定。（上限 3 的情形是推論，本書沒有實測。）

3. stride 越小 EM 越高。那 stride 設成 1（每個位置都開一個視窗）是不是最好？

視窗數會變成大約「文章長度」那麼多個，dev 會有大約 170 萬個視窗，是 stride 150 的 125 倍，評估要好幾個小時。EM 可能還會再漲一點，但 4.6 節的分析告訴我們，這是在用計算量彌補訓練資料的偏差。更划算的做法是修正偏差本身（第 6 章），讓模型在任何位置都能找到答案，這樣中等的 stride 就夠了。

4. 有人主張：「logits 不是機率，不能跨視窗比較，應該先 softmax 才公平。」用本章的數據回應。

實測先 softmax 會讓 EM 從 0.427 掉到 0.376（stride 150），從 0.572 掉到 0.443（stride 32）。原因是 softmax 在每個視窗內部正規化，抹掉了「這個視窗整體有多可信」的訊息：含答案的視窗分數平均 8.09，不含的平均 0.76，正規化後兩者都會有一個機率很高的位置。logits 確實沒有嚴格的機率意義，但它的大小在這裡是有用的訊號。根本的解法是訓練模型明確地預測「沒有答案」。

5. 把 stride 從 150 改成 32，有 244 題從答對變成答錯。這可能是怎麼發生的？

stride 小了，每題的視窗變多，其中不含答案的視窗也變多；只要某個不含答案的視窗裡，模型在中央附近找到一個看起來很像答案的片段、分數又比原本的正確視窗高，答案就被換掉了。小 stride 讓每個位置都有機會「站在中央」，對錯誤的候選人也一樣。淨效果是正的（+842、−244），但不是只有好處。

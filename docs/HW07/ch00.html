ML2022 Spring · HW07 讀碼教材

第 0 章　全貌：一篇文章、一個問題、兩排分數

這一章先把整份作業跑一遍：題目要什麼、資料長什麼樣子、模型由哪些零件組成、指令怎麼下、跑多久、印出什麼。讀完這章，你手上會有一個 101,678,594 個參數、在 dev 上答對四成多的模型，也會知道一件讓人不安的事：同一份程式、同一個種子，跑兩次分數就不一樣。後面八章會一層一層拆開這個模型為什麼答錯，以及怎麼讓它答對更多。

0.1　題目：從文章裡框出答案

HW07 的任務叫 extractive question answering（抽取式問答）。給模型一段文章和一個問題，答案保證是文章裡的一段連續文字，模型只要指出這段文字的起點和終點。投影片 p.8 的例子：

投影片 p.8 的例子

文章：新加坡、馬來西亞的華文學術界在 1970年代後開始統一使用簡體中文；然而繁體字在媒體中普遍存在著，例如華人商店的招牌、舊告示及許多非學術類中文書籍……

問題：新加坡的華文學術界在哪個年代後開始使用簡體中文？　答案：1970
問題：馬來西亞的華人商店招牌主要使用什麼文字？　答案：繁體字

「抽取式」三個字限制了模型能做的事：它不能用自己的話回答，也不能回答「文章沒提到」；它輸出的永遠是原文的某一段。這讓問題變得很好定義。模型對文章的每一個位置打兩個分數：這裡是答案起點的分數（start），和這裡是答案終點的分數（end）。選出最好的一對起點與終點，中間的文字就是答案。整份作業從頭到尾都在處理這「兩排分數」：怎麼讓模型打出好的分數（第 3、5、6、7 章），以及怎麼從分數挑出答案（第 4 章）。

評分用 Exact Match（EM，完全相符）：預測的字串和標準答案一個字都不差才算對，差一個字、多一個空白都算錯。投影片 p.26 把它稱為 accuracy，本書統一叫 EM。這個標準很嚴：標準答案是「64所」，回答「64」就是錯。

規則、基準線與報告

Kaggle 的測試集有 4,957 題，public 與 private 排行榜各約一半（p.26），一天最多上傳 5 次（p.32）。只能用 Hugging Face 上公開的預訓練模型，不准用額外資料，也不准手動修改預測檔，違規的話學期成績乘 0.9（p.20、p.32）。評分共 10 分（p.25）：四條基準線各在 public、private 拿 0.5 分，共 4 分；程式碼 2 分；報告 4 分。

報告有兩題（p.30），各 2 分。第 1 題：模型預測出起點、終點的分數之後，你用什麼規則決定最後的答案範圍，而且規則必須和範例不同（第 4 章）。第 2 題：換一個 Hugging Face 上的預訓練模型，例如從 BERT 換成 BERT-wwm-ext 或 RoBERTa，說明它的表現，以及它和 BERT 在架構、預訓練目標上的差別（第 7 章）。

本書只報 dev 的 EM

測試集沒有答案（投影片 p.7：Testing: No answer!），本機算不出 Kaggle 分數。本書一律報 dev（4,131 題、有答案）上的 EM。dev 和測試集的組成不同：測試集有 1,464 題來自 ODSQA，是語音辨識轉出來的文字，帶著辨識錯字（例如把「梵語」辨識成「當犯人」），dev 裡沒有這種題目。所以本書不說「過了哪條基準線」，只說「dev 上到了多少」。

0.2　資料：DRCD 與它的語音版

資料來自三個資料集（p.6）。DRCD（Delta Reading Comprehension Dataset，台達閱讀理解資料集）是台達電子整理的繁體中文閱讀理解資料，文章取自中文維基百科，問題由人工撰寫。DRCD-TTS 把 DRCD 的文章用語音合成（text-to-speech）念出來，再用語音辨識轉回文字，所以文字裡帶著辨識錯誤。ODSQA（Open-Domain Spoken Question Answering）是另一份語音問答資料。三個檔的組成與規模：

檔案來源（p.6）文章問題文章平均 token文章最長
hw7_train.jsonDRCD + DRCD-TTS10,52431,690390.21,679
hw7_dev.jsonDRCD + DRCD-TTS1,4904,131414.41,126
hw7_test.jsonDRCD + ODSQA1,5864,957416.7950

每個檔都是一個 JSON 物件，裡面有兩個清單：paragraphs 是文章字串，questions 是題目。一篇文章平均配 3 題左右，題目用 paragraph_id 指到文章。dev 的第 1 題長這樣：

{"id": 1, "paragraph_id": 428, "question_text": "1338年白蓮教徒起義的結果是?",
 "answer_text": "失敗", "answer_start": 206, "answer_end": 207}

answer_start 與 answer_end 是答案在文章字串裡的字元位置，兩端都包含：第 428 篇文章的第 206、207 個字就是「失敗」（原文：「1338年江西袁州彭和尚、周子旺等白蓮教徒起義失敗，彭和尚逃至淮西」）。實測三萬多題訓練資料，answer_text 和原文切片全部一致。測試集的這三欄是空的：前 3,493 題是 null，後 1,464 題是字串 'null'，這 1,464 題就是 ODSQA 的口語題。

表中的 token 是 BERT 的 tokenizer 切出來的單位。中文幾乎是一個字一個 token，所以「文章平均 414 個 token」大約就是 414 個字。這個數字很關鍵：BERT 一次最多只能讀 512 個 token，範例程式更只給文章 150 個 token 的空間，所以幾乎每一篇文章都放不進模型（dev 100% 的文章超過 150 個 token），必須切成好幾段「視窗」分別處理。這是第 2 章的主題。

0.3　模型總覽：BERT-base 加一個 768→2 的線性層

模型在 train.py 的兩行裡建好：

bert-base-chinese 是 Google 在 2018 年隨 BERT 論文釋出的中文模型，用中文維基百科預訓練（簡體與繁體都有）。BertForQuestionAnswering 是 Hugging Face transformers 套件裡的一個類別：BERT 本體，加上一個把每個位置的 768 維向量變成 2 個數（start 分數、end 分數）的線性層。這個線性層在預訓練的權重裡不存在，所以載入時會被隨機初始化，transformers 也會印出一份報告提醒你（0.4 節）。整個模型的資料流：

參數可以手算。設定檔寫著詞表 21,128 個 token、隱藏維度 768、12 層、12 個注意力頭、feed-forward 中間層 3,072、位置上限 512、句子類型 2 種。一個線性層 Linear(a, b) 有 a·b 個權重加 b 個偏差；一個 LayerNorm 有 768 個縮放加 768 個平移。

用 sum(p.numel() for p in model.parameters()) 實際數一次，得到的也是 101,678,594（工具 docs/tools/hw07_ch00.py，輸出在 hw07_ch00.txt）。這張表有兩件事值得記住。第一，真正為這份作業新學的參數只有 1,538 個，其他一億多個都是預訓練好的，微調只是在它們的基礎上小幅調整。第二，詞嵌入就佔了 16%：中文詞表有兩萬多個字，每個字一個 768 維的向量。常聽到的「BERT-base 有 1.1 億參數」是英文版（詞表 30,522）再加上 pooler 的數字；問答模型用不到 pooler（判斷兩句是否相連用的那一層），所以這裡沒有它。

在本機的 RTX PRO 4000（24 GB）上，訓練 991 步花 4 分 26 秒（每秒 3.7 步），dev 4,131 題花 56 秒；test.py 對 4,957 題推論花 1 分 7 秒。投影片估計在 Colab 的 T4 上要 20 分鐘（p.16）。存下來的 saved_model/model.safetensors 是 406,737,656 bytes，正好是 101,678,594 個 32 位元浮點數（每個 4 bytes）再加一點檔頭。

訓練的 acc 是「在含答案的那個視窗裡，start 和 end 兩個位置都猜對」的比例，最後幾百步在 0.74 左右；dev 的 acc（就是 EM）卻只有 0.416。差了三成多，不是因為過擬合（只看過每題一次），而是兩者量的根本不是同一件事：訓練時模型拿到的視窗保證含有答案，而且答案剛好在視窗正中央；dev 要在 3、4 個視窗裡自己找出答案在哪，還要把 token 正確地換回文字。這個落差是第 2、3、6 章的主線。

0.5　同一份程式跑兩次，分數就不一樣

train.py 一開頭就固定了所有的亂數種子：

照理說，種子固定，結果就應該固定。實際跑了四次：

執行dev EM說明
notebook 原樣（參照版）0.445一般模式
train.py0.464一般模式，和上一列是同一份程式碼
notebook 原樣（參照版）0.416決定性模式
train.py0.416決定性模式，和上一列逐位元相同

一般模式下，同樣的程式碼、同樣的種子，dev EM 一次 0.445、一次 0.464。再把同一支程式只跑 100 步、跑兩次，所有權重加總分別是 −12803.044 與 −12797.275，loss 也一個 1.474、一個 1.471：第 100 步就已經分岔了。原因不在種子，而在 GPU 上的某些運算本身就不保證每次結果相同。叫 PyTorch 自己指認：開 torch.use_deterministic_algorithms(True, warn_only=True) 訓練幾步，它只對一個運算發出警告：「Memory Efficient attention defaults to a non-deterministic algorithm」。transformers 5 的 BERT 預設用 PyTorch 內建的 scaled_dot_product_attention 算注意力，GPU 上會挑一個叫 memory-efficient attention 的快速實作；它在反向傳播時由許多執行緒同時把梯度加到同一塊記憶體，加法的先後順序每次不同，浮點數的捨入誤差就不同。誤差極小，但經過幾百步的訓練會被放大。cudnn.deterministic = True 只管 cuDNN 的運算（主要是卷積），管不到注意力。

PyTorch 提供了全面的開關 torch.use_deterministic_algorithms(True)：所有運算都改用決定性的版本，沒有決定性版本的就直接報錯。本書寫了一個不改原檔就能套用的小工具 docs/tools/hw07_det.py：

$ CUBLAS_WORKSPACE_CONFIG=:4096:8 PYTHONPATH=. ../.venv/bin/python ../docs/tools/hw07_det.py train.py

開了之後，跑兩次 100 步，權重加總都是 −12801.912，完全相同；完整跑完的 dev EM 是 0.416。代價是變慢一點（1 個 epoch 從 4 分 26 秒變成 4 分 31 秒）。CUBLAS_WORKSPACE_CONFIG 是 NVIDIA 的矩陣運算函式庫要求的設定，不設的話 PyTorch 會報錯提醒你。

這件事改變了全書的讀法

只因為 GPU 的加法順序不同，dev EM 就在 0.416 到 0.464 之間跳了將近 5 個百分點。這比很多「改良」帶來的進步還大。所以本書所有的實驗都開決定性模式（同一個設定跑兩次結果相同），並且每個設定換 3 個種子各跑一次：種子之間的差距，就是判斷「這個改良是不是真的有用」的尺。差距比種子之間的差距還小，就不算數。第 3 章會再回來看非決定性從哪裡來，第 5 章會量出種子之間到底差多少。

順帶一提，dev 0.416 低於 Simple 基準線 0.45139，但這不代表範例「過不了 Simple」：一來 dev 和測試集不同（0.1 節），二來同一份程式在一般模式下也跑出過 0.445 與 0.464。這個 repo 之前用 bert-base-chinese 在 Kaggle 上交過一次，拿到 0.49495（記在舊版 train.py 的註解裡；當時用了幾個 epoch、哪個種子，沒有留下紀錄）。

0.6　notebook 拆成哪些檔

原版是一份 Colab notebook。本 repo 把它拆成五個檔（目錄頁有對照表）：dataset.py、postprocess.py、legacy_adamw.py、train.py、test.py。改動只有兩處：from transformers import AdamW 換成從 legacy_adamw.py 匯入同一份程式（transformers 5 已經刪掉它），evaluate 多一個 tokenizer 參數（原本讀全域變數）。

拆完之後怎麼確定沒有改變結果？做法和前幾本書一樣：用 docs/tools/hw07_make_ref.py 把 notebook 的程式格原樣串成一支「參照」腳本（只註解掉 !gdown、!pip 這類 shell 指令，並改從 legacy_adamw.py 匯入 AdamW），跑一次；再跑拆好的 train.py 與 test.py，比對三樣東西：印出的每一行、存下的權重（每一個張量用 torch.equal 比）、result.csv（逐位元組比）。有了 0.5 節的教訓，這個比對必須在決定性模式下做；一般模式下，連參照版自己跑兩次都對不上。在決定性模式下，三樣全部相同。

還有一個不影響結果、但讀程式時會看到的小改動：原版註解說存檔會得到 pytorch_model.bin，現在的 transformers 預設存成 model.safetensors。safetensors 只存張量、不存任何 Python 物件，載入時不會執行任意程式碼，比舊的 pickle 格式安全，這幾年已經是 Hugging Face 的標準格式。

本章重點

  • HW07 是抽取式問答：答案是文章裡的一段連續文字，模型對每個位置打 start、end 兩個分數。評分用 Exact Match，一字不差才算對。四條基準線 0.451／0.658／0.781／0.844 是 Kaggle 測試集的數字，本書只報 dev 的 EM。
  • 資料是繁體中文的 DRCD 加上語音版 DRCD-TTS；測試集另含 ODSQA 的口語題（1,464 題，dev 沒有）。文章平均 400 多個 token，幾乎全部放不進範例給的 150 個 token，必須切視窗。
  • 模型是 bert-base-chinese 加一個 Linear(768, 2)：101,678,594 個參數，其中 encoder 佔 83.6%、詞嵌入 16%，新學的問答頭只有 1,538 個。
  • 原版訓練 1 個 epoch（991 步）4 分半，dev 評估 1 分鐘。訓練 acc 0.74，dev EM 只有 0.416：兩者量的不是同一件事。
  • 固定了種子，GPU 的非決定性運算仍讓 dev EM 在 0.416–0.464 之間變動。開 torch.use_deterministic_algorithms(True) 才能逐位元重現；全書的實驗都這樣跑，並用 3 個種子量雜訊。

自我測驗

1. 文章是「福岡市的兩大中心地區是中央區的天神地區和博多站附近的博多地區」，標準答案是「天神地區」。下面哪些回答會被 Exact Match 判為正確：「天神地區」「天神」「中央區的天神地區」「天神地區 」（後面多一個空白）？

只有「天神地區」。EM 要求字串完全相同，少字（天神）、多字（中央區的天神地區）、多一個空白都算錯。這也是為什麼範例的 evaluate 最後要 answer.replace(' ','')：tokenizer 把 token 換回文字時會在 token 之間插入空白，不拿掉就全部判錯（第 1、4 章）。

2. 如果把 bert-base-chinese 換成一個 24 層、隱藏維度 1,024、feed-forward 中間層 4,096、詞表一樣是 21,128 的模型（例如第 7 章的 RoBERTa-large），問答頭會有多少參數？encoder 一層大約多少參數？

問答頭是 Linear(1024, 2)：1,024 × 2 + 2 = 2,050。encoder 一層：attention 4 × (1,024² + 1,024) + 2,048 = 4,200,448；feed-forward (1,024 × 4,096 + 4,096) + (4,096 × 1,024 + 1,024) + 2,048 = 8,395,776；合計 12,596,224，24 層 302,309,376，約 3.02 億。這是手算，第 7 章會用 PyTorch 實際數一次。

3. 訓練時印出的 acc 到最後是 0.74，dev EM 是 0.416。有人說「這是過擬合，應該加 dropout」。對嗎？

不對。只訓練了 1 個 epoch，每題只看過一次，談不上把訓練資料背起來。兩個數字量的是不同的事：訓練 acc 是在「保證含答案、答案還在正中央」的單一視窗裡猜 start 與 end；dev EM 要在多個視窗裡自己找答案、處理 end 在 start 之前之類的情況、再把 token 換回一字不差的文字。要比較是否過擬合，得在 dev 上用和訓練相同的方式量（第 3 章）。

4. 你改了一行程式，dev EM 從 0.430 變成 0.445。能說這個改動有用嗎？

不能。在一般（非決定性）模式下，連一行都不改，同一份程式就跑出過 0.445 與 0.464。至少要在決定性模式下比較，並且換幾個種子各跑一次，看改動帶來的差距是否明顯大於種子之間的差距。

5. saved_model/model.safetensors 是 406,737,656 bytes。用參數量估算，這個大小合理嗎？如果改存成 16 位元（fp16），大約會變多大？

合理：101,678,594 個參數 × 4 bytes = 406,714,376 bytes，剩下的 23,280 bytes 是檔頭（記錄每個張量的名稱、形狀、位置）。改成 fp16 每個參數 2 bytes，約 203 MB。這是推算，沒有實際存過。

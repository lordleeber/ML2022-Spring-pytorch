ML2022 Spring · HW07 讀碼教材

第 3 章　模型與訓練迴圈：兩排分數是怎麼學出來的

這一章讀模型的最後幾行與訓練迴圈：768 維的向量怎麼變成 start、end 兩排分數，loss 怎麼算，優化器怎麼更新一億個參數。然後回答第 0 章留下的問題：訓練 acc 0.74、dev EM 只有 0.416，差的三成多去了哪裡。答案出乎意料：模型在 dev 上用訓練的量法也有 0.749，它沒有學壞，是「從視窗挑答案」這一步丟了分數。最後拆開 GPU 的非決定性：注意力不是唯一的來源。

3.1　從向量到兩排分數

BertForQuestionAnswering 的定義在 transformers 套件裡。BERT 本體處理完之後，每個位置是一個 768 維的向量（第 0 章圖 0.1），剩下的只有幾行：

qa_outputs 對每個位置各做一次同樣的線性轉換，把 768 維變成 2 個數，形狀從 (W, 193, 768) 變成 (W, 193, 2)；split(1, dim=-1) 把最後一維拆成兩份，squeeze 拿掉多餘的維度，得到兩個 (W, 193)。第一排是「這個位置是答案起點」的分數，第二排是「這個位置是答案終點」的分數。這些分數叫 logits：還沒經過 softmax 的原始分數，可以是任何實數，大小只有相對意義。

這個設計有兩個特點。第一，start 與 end 是各自獨立打分的：模型不知道「終點應該在起點之後」，這要靠後處理（第 4 章）。第二，193 個位置全部都有分數，包括 [CLS]、問題的每個字、[SEP]、甚至 padding；attention_mask 只讓其他 token 不去注意 padding，並不會把 padding 位置的 logits 遮掉。模型必須自己學會「答案不會在問題裡，也不會在 padding 上」。

一開始，問答頭的權重是隨機的（標準差 0.02、偏差 0），每個位置的分數都差不多，模型等於在 193 個位置裡平均亂猜。這時的 loss 應該接近 ln 193 = 5.263。實測：拿還沒訓練的模型，對訓練集前 256 題的訓練視窗算 loss，得到 5.221，非常接近。訓練的第 1 個 100 步之後，平均 loss 已經降到 1.474（第 0 章的輸出）：預訓練好的 BERT 本體已經懂中文，問答頭只要學會「看哪裡」就好，所以學得非常快。

3.2　loss：兩個 193 選 1 的分類題

loss 把問題看成兩道選擇題：193 個位置裡，哪一個是起點？哪一個是終點？各算一次 cross entropy，再取平均。cross entropy 在這裡的意思是：把 193 個 logits 做 softmax 變成機率，取正確位置那個機率的負對數。正確位置的機率是 0.5，loss 是 0.69；機率是 0.9，loss 是 0.11。訓練結束時 loss 在 0.57 左右，相當於正確位置的機率（取幾何平均）約 e−0.57 ≈ 0.57。

前三行處理一個這份作業碰不到的情況：如果答案位置超出輸入範圍（例如答案被截掉了），就把它設成 ignored_index（等於序列長 193），而 CrossEntropyLoss(ignore_index=193) 會跳過這些樣本。範例的訓練視窗保證包住答案，第 2 章也確認了答案最長 115 個 token、短於 150，所以這段程式在本作業裡從未被觸發。但第 6 章若要讓訓練視窗不一定含答案，就會用到它，或者改成另一種常見的做法：答案不在視窗裡時，把 start、end 都設成 0，也就是指向 [CLS]，表示「這個視窗沒有答案」。

3.3　訓練迴圈

流程是標準的：把一批資料搬到 GPU（第 84 行）；把 start_positions、end_positions 一起傳給模型，模型就會順便算好 loss（第 88 行）；取 start、end 各自的最大值當預測（第 91–92 行），兩個都對才算對（第 95 行）；反向傳播、更新、清空梯度（第 101–104 行）。第 107 行是 Medium 的 TODO：學習率衰減，第 5 章實作。

印出來的數字有三個小毛病，讀 log 時要知道：

  • 第一個 100 步其實只有 99 批。step 從 1 開始，每處理完一批才加 1，所以處理完第 99 批時 step 就是 100，觸發第一次印出；累積了 99 批的 loss，卻除以 100。之後每次都是完整的 100 批。
  • 最後 92 批沒有被印出。一個 epoch 有 991 批，最後一次印出是處理完第 899 批時，第 900 到 991 批的 loss 與 acc 累積起來，下一個 epoch 開始時就被歸零了。
  • train_loss 累加的是張量。output.loss 帶著計算圖，train_loss += output.loss 讓 100 個 loss 串成一條，到印出時才 .item()。結果沒錯，只是多佔一點記憶體；比較好的寫法是 train_loss += output.loss.item()。

這些都不影響訓練本身，只影響印出的數字。第 0 章那排 log 的最後一行（Step 900，loss 0.567、acc 0.742）就是「第 800 到 899 批」的平均。

3.4　兩種 AdamW

範例用的是 2022 年 transformers 內建的 AdamW。transformers 5 已經把它刪除，本 repo 原樣抄成 legacy_adamw.py。更新一個參數的核心是這幾行：

Adam 對每個參數維護兩個移動平均：梯度的平均 m（exp_avg）與梯度平方的平均 v（exp_avg_sq），更新量是 m / (√v + eps) 乘上學習率。因為 m、v 從 0 開始，前幾步會偏小，所以要除以 1 − βt 做偏差修正（第 96–99 行）。舊版和 PyTorch 內建的 torch.optim.AdamW 有三個差別：

舊版（legacy_adamw.py，範例用的）torch.optim.AdamW
eps 預設1e-61e-8
weight decay 預設0.0（不衰減）0.01
eps 加在哪√v + eps，再整體乘上 √(1−β₂t)√v / √(1−β₂t) + eps

第三點寫成式子：舊版的更新量是 lr · √(1−β₂t) / (1−β₁t) · m / (√v + eps)，等於把 eps 放大成 eps / √(1−β₂t) 再加到修正後的 √v̂ 上。訓練初期 β₂t 接近 1，這個放大倍數很大（第 1 步是 √(1/0.001) ≈ 31.6 倍），所以舊版在最初幾步的更新比較保守。這些差異會不會影響結果？這個 repo 之前把 from transformers import AdamW 直接換成 torch.optim.AdamW（commit 381aad0），等於同時改了三件事。把兩種各用 3 個種子訓練 1 個 epoch：

優化器（1 個 epoch、其他照範例）種子 0種子 1種子 2平均
舊版 AdamW（eps 1e-6、不衰減）0.4160.4820.4390.446
torch.optim.AdamW（eps 1e-8、weight decay 0.01）0.4520.4780.4440.458

（舊版那一列就是範例本身；三個種子是第 5 章 N 組的第 1 個 epoch。）同一個種子，換優化器之後的分數都不一樣，所以「直接替換」確實改變了結果；但平均只差 1.2 個百分點，而種子之間就差了 6.6 個百分點（0.416 到 0.482），兩組的範圍完全重疊。結論是：在這份作業的規模（991 步、學習率 1e-4）下，兩種 AdamW 沒有看得出來的好壞之分。這是一個值得記住的判讀方式：如果只跑種子 0，會看到「換成 PyTorch 版漲了 3.6 個百分點」，得出完全錯誤的結論。

3.5　訓練 acc 0.74、dev EM 0.416：差在哪裡

訓練時印的 acc 是「在一個以答案為中心的視窗裡，start 與 end 都猜對」的比例。dev EM 量的是另一件事。要比較兩者，得先用同一把尺量：拿訓練好的模型（決定性模式、種子 0），切換成 eval 模式，對 dev 的每一題也只切一個以答案為中心的視窗（就是把 dev 資料送進 QA_Dataset 的訓練分支），算一樣的指標；再對訓練集隨機抽 4,131 題做同樣的事（工具 docs/tools/hw07_ch03.py）：

資料（一個以答案為中心的視窗、eval 模式）start 對end 對兩者都對loss
dev 4,131 題0.7980.8380.7490.560
train 抽 4,131 題0.9200.9100.8720.287

dev 用訓練的量法是 0.749，和訓練最後印出的 0.74 幾乎一樣。所以第 0 章那個落差不是過擬合造成的：模型在沒看過的題目上，只要給它一個含答案的視窗，表現和訓練時相當。（訓練集上是 0.872，比 dev 高 12 點，代表模型對看過的題目確實記得比較清楚；但這和「印出的 acc 比 dev EM 高」是兩回事，印出的 acc 是邊訓練邊量的，每題被量的時候模型都還沒學過它。）

那麼 dev EM 掉在哪裡？用正式的評估視窗（stride 150）與範例的 evaluate，把 4,131 題逐題分類：

結果題數比例在哪一章處理
答對（EM）1,71841.6%
答案被視窗切斷，不可能答對721.7%第 2、4 章
選錯視窗：最高分的視窗不是答案所在的那個1,21529.4%第 4、6 章
視窗選對，起點或終點錯1,11627.0%第 4、5、7 章
位置全對，文字還原不了100.2%第 1、4 章

（另有 2 題答案被切斷卻答對了：答案的文字在文章別處也出現，模型指到了另一個位置。）最大的一塊是「選錯視窗」，將近三成。這和訓練方式直接相關：訓練時模型只看過「保證有答案」的視窗，從來沒看過「這個視窗沒有答案」的例子；評估時每題有 2 個以上的視窗不含答案，模型在這些視窗裡照樣會指出一個「最像答案」的地方，而且分數未必比較低。第 0 章 dev 第 0 題就是一例：不含答案的第 1 個視窗拿到最高分。範例的 evaluate 還會讓「終點在起點之前」的組合參賽：選中的視窗裡 end < start、回答空字串的有 135 題。這些是第 4 章後處理要修的；讓模型學會分辨「沒有答案的視窗」，則是第 6 章前處理的方向。

3.6　非決定性從哪裡來

第 0 章看到：同一份程式、同一個種子，跑兩次分數不同；開了 torch.use_deterministic_algorithms(True) 就會相同。哪些運算不是決定性的？PyTorch 提供 warn_only=True 模式：碰到非決定性的運算時只發警告、不報錯，可以用來列出嫌疑犯。對 BERT 問答模型做一次 forward 與 backward，它只發出一個警告：

UserWarning: Memory Efficient attention defaults to a non-deterministic algorithm.
(Triggered internally at /pytorch/aten/src/ATen/native/transformers/cuda/attention_backward.cu:900.)

transformers 5 的 BERT 預設用 PyTorch 內建的 scaled_dot_product_attention（SDPA）算注意力，GPU 上會挑 memory-efficient attention 這個實作，它的反向傳播是非決定性的。2022 年的 transformers 4.5 沒有 SDPA，注意力是用矩陣乘法一步一步寫出來的（現在叫 attn_implementation="eager"）。那麼換回 eager 就可以重現了嗎？用同樣的設定訓練 100 步，比較所有權重的總和（工具 docs/tools/hw07_eager_det.py）：

設定第 1 次第 2 次相同？
eager−12787.717−12787.707不同
eager ＋ CUBLAS_WORKSPACE_CONFIG=:4096:8−12787.710−12787.703不同
eager ＋ use_deterministic_algorithms(True)−12787.694937936982−12787.694937936982相同

eager 也不能重現，而且 warn_only 對它一個警告都不發。只設定 cuBLAS（NVIDIA 的矩陣運算函式庫）的工作空間也不夠。要把開關整個打開，兩次才相同。這代表有些運算在開關打開時，會默默換成另一個決定性的實作，PyTorch 認為這不需要警告。是哪一個（或哪幾個）運算，本書沒有逐一找出來；重點是結論：在 GPU 上，「固定種子」不等於「可以重現」，要重現就得打開這個開關，並接受一點速度代價（本作業 1 個 epoch 從 4 分 26 秒變 4 分 31 秒，約 2%）。

也要說清楚這件事的影響範圍。非決定性造成的是「同一個設定的結果有一個分布」，跟換種子造成的分布性質相同；它不會讓模型變好或變壞。所以研究上常見的做法不是追求逐位元重現，而是每個設定跑多個種子、報平均與範圍。本書兩件事都做：決定性模式讓「拆檔前後一致」這種比對有意義，多種子讓「改良有沒有用」的判斷有意義。

現在的做法：讓 Trainer 處理迴圈

手寫訓練迴圈適合教學，但每個專案都要重寫一次學習率排程、混合精度、梯度累積、定期評估、存最佳模型。今天微調 Hugging Face 模型，多半用 transformers 的 Trainer（或底層的 Accelerate）：這些都變成 TrainingArguments 裡的一個參數，例如 lr_scheduler_type="linear"、bf16=True、gradient_accumulation_steps=4，full_determinism=True 則會替你打開本節的決定性開關。Trainer 預設的優化器是 PyTorch 的 AdamW，搭配 eps 1e-8、weight decay 0，學習率排程預設就是線性衰減（transformers 5.18 的 training_args.py），和本章兩種 AdamW 的預設都不完全相同，換工具時要記得檢查。transformers 5 的 Trainer 需要另外安裝 accelerate。

本章重點

  • 問答頭是一個 Linear(768, 2)，對每個位置打 start、end 兩個 logits；兩者獨立，193 個位置（含問題與 padding）都有分數。
  • loss 是 start 與 end 各一個 193 選 1 的 cross entropy 取平均。未訓練時是 5.22（≈ ln 193），第 1 個 100 步之後就降到 1.47：BERT 本體已經懂中文。
  • 印出的 loss／acc 有三個小毛病：第一次只累積 99 批、最後 92 批沒印、累加的是帶計算圖的張量。都不影響訓練。
  • 舊版 AdamW 和 torch.optim.AdamW 的 eps、weight decay 預設與 eps 的位置都不同。直接替換會改變每個種子的結果，但 3 個種子的平均只差 1.2 個百分點（0.446 vs 0.458），比種子之間的差距（6.6）小得多。
  • dev 用訓練的量法（一個以答案為中心的視窗）是 0.749，和訓練 acc 一樣：模型沒有過擬合。dev EM 0.416 的損失主要在評估：選錯視窗 29.4%、視窗對但位置錯 27.0%、答案被切斷 1.7%。
  • 非決定性有兩種來源：SDPA 注意力（PyTorch 會警告），以及開關打開時被默默替換的運算（不警告）。要重現就打開 use_deterministic_algorithms，代價約 2%。

自我測驗

1. 如果問答頭的 start 機率在 193 個位置上完全平均，end 也一樣，loss 是多少？如果把 max_paragraph_len 改成 300 呢？

每個位置機率 1/193，cross entropy 是 ln 193 ≈ 5.263，start、end 平均後還是 5.263。序列長變成 1 + 40 + 1 + 300 + 1 = 343，均勻猜的 loss 變成 ln 343 ≈ 5.838。所以比較不同視窗長度的 loss 時，起點本來就不同。（第一個數字和實測的 5.221 吻合；第二個是推算。）

2. 模型對 padding 位置也會打分數。如果 padding 位置的 start logit 剛好最高，範例的 evaluate 會回答什麼？

decode 預設不會略過特殊符號（skip_special_tokens=False），實測 tokenizer.decode([1921, 4868, 0, 0]) 得到 '天 神 [PAD] [PAD]'，拿掉空白就是「天神[PAD][PAD]」；[CLS]、[SEP] 也一樣會原樣出現。這種回答一定錯，而且 span 根本不在文章裡。第 4 章的後處理會把起點、終點限制在文章範圍內。

3. 3.5 節說「dev 用訓練的量法是 0.749，所以沒有過擬合」。但同一個量法在訓練集上是 0.872。這不就是過擬合嗎？

訓練集比 dev 高 12 點，說明模型對看過的題目記得比較牢，這確實是一點過擬合（泛化落差）。但第 0 章的問題是「印出的訓練 acc 0.74 和 dev EM 0.416 差三成」，那個落差的成因不是過擬合：印出的 acc 每一批都是在模型學它之前量的，本質上也是「沒看過的題目」，所以和 dev 的 0.749 相當。兩件事要分開：泛化落差（0.872 vs 0.749）和量法不同造成的落差（0.749 vs 0.416）。

4. 選錯視窗的有 1,215 題。如果有一個「先知」告訴我們答案在哪個視窗，其他都照範例做，dev EM 最多能到多少？

這 1,215 題換成正確的視窗後，模型在那個視窗裡指得對不對還不知道。可以用 3.5 節的量法估：模型在含答案的視窗裡兩者都對的比例約 0.749，但那是「以答案為中心」的視窗，評估視窗裡答案不一定在中間，會再低一些。粗估 1,718 + 1,215 × 0.7 ≈ 2,570，EM 約 0.62。這是推算，沒有實測；第 4 章會實際量「在所有視窗裡用更好的規則挑答案」能拿回多少。

5. 你在 GPU 上跑同一份程式兩次，結果不同。下列哪些做法能讓它變得可以重現：(a) 再呼叫一次 torch.manual_seed(0)；(b) torch.backends.cudnn.deterministic = True；(c) 改用 eager attention；(d) torch.use_deterministic_algorithms(True) 並設定 CUBLAS_WORKSPACE_CONFIG？

只有 (d)。(a)、(b) 範例本來就做了；(c) 實測仍然不同（3.6 節的表）。(d) 會讓所有運算改用決定性實作，沒有決定性實作的運算會直接報錯，讓你知道。

延伸閱讀

  • Ilya Loshchilov、Frank Hutter，Decoupled Weight Decay Regularization（2017）：AdamW 的原始論文，解釋為什麼 weight decay 要和 Adam 的更新分開。
  • Diederik Kingma、Jimmy Ba，Adam: A Method for Stochastic Optimization（2014）：偏差修正與 eps 的原始寫法（Algorithm 1 與第 2 節最後的「更有效率的寫法」，正是舊版 AdamW 的 eps 位置）。
  • PyTorch 文件 torch.use_deterministic_algorithms：會被替換與會報錯的運算清單。

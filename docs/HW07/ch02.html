第 2 章　Dataset：一篇文章切成幾個視窗

文章平均 414 個 token，範例只給模型 150 個 token 的文章空間。QA_Dataset 用兩種完全不同的方式切文章：訓練時知道答案在哪，只切一個包住答案的視窗；評估時不知道，只好從頭到尾每隔 doc_stride 切一個。這一章逐行讀這個類別，量出兩種切法各自的副作用：訓練視窗的答案位置有一半以上固定在同一格，評估視窗則把 74 題的答案切成兩半。

2.1　為什麼要切視窗

BERT 的位置嵌入只有 512 個（第 0 章的 512 × 768），所以一次最多讀 512 個 token。投影片 p.12 還給了另一個理由：self-attention 讓每個 token 都和其他所有 token 計算一次關聯，計算量和序列長度的平方成正比，序列長兩倍，注意力的計算就變四倍。範例選了一個比 512 小很多的長度：

一個輸入序列 = [CLS] + 問題（最多 40）+ [SEP] + 文章（最多 150）+ [SEP]，總長 193。dev 的文章中位數是 407 個 token，一篇文章要切 3 段左右；同時塞得下問題與整篇文章的題目幾乎沒有。範例沒有說明為什麼選 150。可以確定的是代價的方向：序列短，訓練快、記憶體省（注意力的計算和長度平方成正比），但每個視窗看到的文章少，切出的視窗多。

2.2　一筆訓練資料

__getitem__ 依 split 分兩支。訓練那一支：

五個步驟。（1）第 41–42 行用第 1 章的 char_to_token 把答案的字元位置換成文章裡的 token 位置。（2）第 45 行算答案的中點 mid。（3）第 46 行讓視窗從 mid - 75 開始，也就是把答案放在 150 個 token 的正中央；外面那層 max(0, min(..., len - 150)) 是邊界保護：答案太靠近文章開頭時視窗從 0 開始，太靠近結尾時視窗對齊文章最後 150 個 token。（4）第 50–51 行切出文章片段，接上問題與特殊符號。（5）第 54–55 行把答案位置從「文章裡的第幾個 token」換成「這個輸入序列裡的第幾個 token」：減掉視窗起點，再加上前面問題部分的長度。

實際取一筆看。訓練集第 1 題「百濟國在哪一年建國?」，答案「公元前18年」：

train_set[1]
   input_ids, token_type_ids, attention_mask 的形狀都是 (193,)
   start = 85, end = 89 → ['公', '元', '前', '18', '年']
   前 12 個 token：['[CLS]', '百', '濟', '國', '在', '哪', '一', '年', '建', '國', '?', '[SEP]']
   token_type_ids：0 有 42 個、1 有 151 個
   attention_mask：1 有 163 個、0（padding）有 30 個

問題「百濟國在哪一年建國?」斷成 10 個 token（「?」是一個），加上 [CLS]、[SEP] 共 12 個；文章 150 個加結尾的 [SEP] 是 151 個，合計 163，剩下 30 個位置補 0。這裡有一個容易誤會的細節：token_type_ids 的 0 有 42 個，不是 12 個，因為 padding 的位置也填 0（2.6 節）。答案「公元前18年」的 5 個 token 在序列的第 85–89 個位置；扣掉問題部分的 12 個，是文章視窗裡的第 73–77 個，中點 75，正好是正中央。DataLoader 每次取 32 筆，疊成 (32, 193) 的張量，start、end 疊成 (32,)，這就是第 0 章圖 0.1 裡訓練時的 W = 32。

2.3　訓練視窗：答案真的都在正中央嗎

投影片 p.13 解釋了這樣切的理由：訓練時我們知道答案在哪，而回答問題需要的資訊通常就在答案附近，所以在答案周圍畫一個盡量大的視窗即可。但投影片 p.19 的 Strong 提示又說：「如何避免模型學到不該學的東西？（答案不總是在視窗中央附近）」。先量一量訓練集裡答案到底落在視窗的哪裡。把 31,690 題的答案中點在「文章視窗」（150 個 token）裡的位置分組：

結果不是「全部在中央」，而是兩種情況疊在一起。一半多一點（52.4%）的答案，中點正好在第 75 個位置，一格不差。其餘的是被邊界擋住的：答案在文章的前 75 個 token 內時，視窗只能從 0 開始，答案就落在視窗的前半（這種有 10,762 題，佔 34.0%，而且越靠前越多，0–14 這一格就有 12.3%）；答案在文章最後 75 個 token 內時，視窗對齊文章結尾，答案落在後半（4,331 題，13.7%）。

這對模型意味著什麼？一個只會說「答案在第 75 個位置」的模型，在訓練資料上就能猜對一半以上題目的大致位置。模型不必理解問題，只要學會這個位置的規律，loss 就能降很多。到了評估時，視窗是從文章開頭依序切的，答案在視窗裡的位置和「75」毫無關係（下一節）。這個捷徑能讓模型偏差多少，要看模型在 dev 上預測的位置分布，第 6 章會量，並試試把訓練視窗的位置隨機化。

2.4　評估視窗：每隔 doc_stride 切一個

評估時不知道答案在哪，只能把整篇文章切開，每一段都問一次：

第 66 行的 range(0, len(tokenized_paragraph), self.doc_stride) 產生每個視窗的起點：0、150、300……，直到超過文章長度。每個視窗都接上同一個問題，最後疊成 (視窗數, 193) 的張量回傳。所以評估時的一「筆」資料不是一個視窗，而是一題的所有視窗，視窗數每題不同。這就是 train.py 裡那段大寫警告的原因：

batch_size 為 1 時，DataLoader 會在最前面多加一個長度 1 的維度，張量變成 (1, 視窗數, 193)；train.py 在呼叫模型前用 squeeze(dim=0) 把它拿掉，postprocess.py 則用 data[0][0][k] 取第 k 個視窗。如果把 batch_size 改成 2，兩題的視窗數不同，DataLoader 疊不起來，會直接報錯。dev 4,131 題的視窗數：

每題視窗數2345678合計
題數3102,3891,31281211534,131 題、13,695 個視窗

最後一個視窗常常很短：它裝的是「文章剩下的部分」，平均 78 個 token，其中 12% 不到 20 個 token，258 題的最後一個視窗不到 10 個 token。第 0 章的 dev 第 0 題就是這樣：460 個 token 的文章，第 4 個視窗只有 10 個 token 的文章，其餘全是 padding。這種視窗幾乎沒有內容，模型卻照樣要在裡面指出一個答案，而且它的分數會和其他視窗放在一起比（第 4 章）。

答案落在哪個視窗也不平均。在沒有被切斷的 4,057 題裡，答案在第 1 個視窗的有 2,194 題（54%）、第 2 個 1,188 題、第 3 個 571 題，第 4 個以後只有 104 題；答案在所在視窗裡的位置也偏前（前 30 個 token 有 1,251 題，最後 30 個只有 505 題）。出題的人傾向從文章前段出題，這個規律對訓練和評估是一致的，不算捷徑。

2.5　doc_stride = 150：被切成兩半的答案

範例的 doc_stride 和視窗長度都是 150，所以視窗首尾相接、沒有重疊。答案如果剛好跨在第 149 和第 150 個 token 之間，前半在一個視窗、後半在下一個視窗，沒有任何一個視窗包含完整的答案，模型怎麼預測都不可能答對。投影片 p.18 畫的就是這個情況，提示用重疊的視窗。實測 dev 有幾題被切斷，以及代價是多少個視窗：

道理很簡單：相鄰視窗重疊 r 個 token 時，長度不超過 r + 1 的答案一定能完整落在某個視窗裡。重疊 50 保證救回 51 個 token 以內的答案；dev 最長的答案有 52 個 token，超過一點，但它沒有剛好落在最壞的位置，所以實測 stride 100 時一題都沒有被切斷。重疊 22 時還剩 3 題長答案被切斷。代價是視窗變多，評估時間大致跟著視窗數成正比，stride 100 要多算 43% 的視窗。

74 題佔 dev 的 1.79%，也就是說，光是 stride 這一個數字，就讓 EM 的上限少了將近 2 個百分點。但上限不等於實際：把 stride 調小之後，模型要在更多視窗之間挑答案，挑錯的機會也多了。實際能漲多少，第 4 章在同一個模型上量。另外要注意，doc_stride 只影響評估：訓練時每題只切一個視窗，根本用不到它。所以它不必重新訓練就能調，這是 Medium 的兩個提示裡最便宜的一個。

2.6　padding、token_type_ids 與 attention_mask

三個串列長度都是 193，對應投影片 p.11 的圖：

  • input_ids：問題、文章之後補 0 到滿 193。0 是 [PAD] 的 id。
  • token_type_ids：問題部分（含 [CLS] 與第一個 [SEP]）是 0，文章部分（含結尾的 [SEP]）是 1，padding 又是 0。模型把它查表成「句子類型嵌入」加到每個 token 上（第 0 章的 2 × 768）。
  • attention_mask：真的 token 是 1，padding 是 0。注意力計算時，mask 為 0 的位置會被加上一個極大的負數，softmax 之後權重是 0，其他 token 完全不會「看到」它們。

padding 浪費多少計算？dev 的 13,695 個視窗裡，padding 佔了所有位置的 21.5%。來源有兩個：問題不到 40 個 token 的空位（問題平均 21 個，每個視窗大約空出 19 個），以及最後一個視窗的文章不滿 150。這 21.5% 的位置照樣要算過 12 層 Transformer，只是結果不被使用。今天的做法是讓每個 batch 只補到該 batch 最長的那一筆（dynamic padding），或把多個短序列接成一條（packing）。

現在的做法：讓 tokenizer 切視窗，或乾脆用更長的模型

範例手寫的切視窗邏輯，transformers 早就內建：tokenizer(question, paragraph, truncation="only_second", max_length=..., stride=..., return_overflowing_tokens=True, return_offsets_mapping=True) 會自動切出互相重疊的視窗，每個視窗都帶著 offsets，答案可以直接從原文切出來（第 1 章的解法）。注意它的 stride 參數意思是「重疊多少個 token」，和範例的 doc_stride（相鄰視窗起點的距離）剛好相反。另一條路是用能讀長序列的模型：2024 年的 ModernBERT 可以一次讀 8,192 個 token，本作業任何一篇文章都塞得進去，視窗問題就消失了。在 RAG 系統裡，「把文件切成有重疊的塊」（chunking with overlap）仍然是標準做法，理由和本節一樣：怕重要的句子剛好被切在兩塊之間。

本章重點

  • 一個輸入是 [CLS] + 問題 ≤ 40 + [SEP] + 文章 ≤ 150 + [SEP]，共 193 個 token；文章平均 400 多個 token，必須切視窗。
  • 訓練時每題只切一個包住答案的視窗：52.4% 的答案中點正好在第 75 個位置，34.0% 因為靠近文章開頭而落在前半，13.7% 落在後半。模型可以學到「答案在中間」的捷徑（第 6 章）。
  • 評估時每隔 doc_stride 切一個視窗，一題就是一筆 (視窗數, 193)，所以 dev 的 batch_size 必須是 1。dev 平均每題 3.32 個視窗，最後一個常常只有幾個 token。
  • doc_stride = 150 讓視窗互不重疊，dev 有 74 題（1.79%）的答案被切斷、不可能答對；stride 100 時為 0，代價是多 43% 的視窗。stride 只影響評估，不必重新訓練。
  • padding 佔 dev 視窗位置的 21.5%；token_type_ids 區分問題與文章，attention_mask 讓模型忽略 padding。

自我測驗

1. 一篇文章 460 個 token，doc_stride 是 150，會切成幾個視窗？各涵蓋文章的哪些 token？改成 100 呢？

stride 150：起點 0、150、300、450，共 4 個，涵蓋 [0,150)、[150,300)、[300,450)、[450,460)，最後一個只有 10 個 token（就是第 0 章 dev 第 0 題）。stride 100：起點 0、100、200、300、400，共 5 個，最後一個 [400,460) 有 60 個 token。注意 range 只看起點有沒有超過文章長度，所以最後一個視窗可能很短，但不會漏掉文章結尾。

2. 訓練集第 1 題的答案在序列的第 85–89 個位置。如果把 max_question_len 從 40 改成 60，這一筆的 start、end 會變嗎？

不會。start、end 是「問題部分的實際長度 + 答案在文章視窗裡的位置」，問題只有 10 個 token，上限是 40 還是 60 都不會截，問題部分仍是 12；視窗的起點只和答案位置與 max_paragraph_len 有關。會變的是 max_seq_len（變成 213），padding 多出 20 個位置。這是依程式推論，沒有實際跑。

3. 有人把 dev 的 DataLoader 改成 batch_size=4 想加速評估，會發生什麼事？

多半會報錯。每一筆是 (視窗數, 193)，視窗數每題不同（2 到 8），DataLoader 預設的 collate 要把 4 筆疊成一個張量，形狀不一致就疊不起來。即使碰巧 4 題的視窗數相同，postprocess.py 也只看 data[0][0]，也就是 batch 裡的第一題，其他三題會被忽略。要加速，得自己把多題的視窗攤平成一批送進模型，再按題分回去。

4. 為什麼把 doc_stride 調小不需要重新訓練？有什麼「訓練時的設定」是必須和它一起考慮的嗎？

因為訓練分支只切一個以答案為中心的視窗，完全沒用到 doc_stride（它只出現在第 66 行的評估分支）。要一起考慮的是視窗長度 max_paragraph_len：它同時決定訓練視窗與評估視窗的大小，改了它就要重新訓練，因為模型學到的是在 150 個 token 的範圍內找答案。

5. 訓練時，答案在文章前 75 個 token 的題目有 34%。這些題目的視窗都從文章的第 0 個 token 開始。這對模型可能有什麼影響？

這些視窗裡，文章的開頭總是緊接在問題的 [SEP] 之後，答案又集中在視窗前段。模型可能學到「答案常在文章開頭附近」，而評估時第 1 個視窗正好是文章開頭，dev 也有 54% 的答案在第 1 個視窗裡，所以這個傾向和評估資料大致吻合，不像「正好在第 75 個位置」那樣是純粹的捷徑。兩種偏差各有多大影響，要看模型預測位置的分布（第 6 章）。

第 7 章　換預訓練模型，以及讓訓練變快的兩個技巧

投影片給 Strong 的另一個提示是「試試其他預訓練模型」，報告第 2 題也要你換一個模型、說明它和 BERT 的差別。這一章用同一套訓練方式（線性衰減、1 個 epoch、中心視窗）比較五個中文模型，各 3 個種子：四個和 bert-base-chinese 一模一樣大，只差在預訓練的方法與資料；一個大三倍。結果有好有壞，而且排名第一的那個「換模型的好處」，有很大一部分來自它早就學過閱讀理解。最後實測投影片建議的兩個訓練技巧：混合精度讓訓練快 2.7 倍，梯度累積省記憶體但不會變快。

7.1　換模型只要改兩行

模型在 train.py 的兩行裡載入（第 0 章 0.3 節）：

把 "bert-base-chinese" 換成 Hugging Face 上另一個模型的名字即可。本章的模型都是 BERT 架構，所以 BertForQuestionAnswering 照樣能用；比較通用的寫法是 AutoModelForQuestionAnswering，它會依模型的設定檔自動選對類別，實驗工具用的就是它。要確認三件事：

  • 詞表與特殊符號：dataset.py 把 [CLS]、[SEP] 寫死成 101、102（第 1 章 1.4 節）。本章五個模型的 vocab.txt 逐位元組相同（md5 都是 3b5b76c4…），所以不必改。換成詞表不同的模型（例如英文 RoBERTa 或多語言模型），這兩個數字就錯了。
  • tokenizer 的設定：ckiplab 的模型卡要求用 bert-base-chinese 的 tokenizer；hfl 與 luhua 的 tokenizer 雖然詞表相同，卻預設轉小寫（第 1 章 1.3 節），bert-base-chinese 不轉。換模型時順便換了前處理，7.5 節討論。
  • 模型大小：大模型需要更多記憶體與時間（7.6 節）。

五個模型都用第 5 章的設定（線性衰減、1 個 epoch、學習率 1e-4、中心視窗）各訓練 3 個種子。左邊是範例的評估（stride 150），右邊是第 4 章改良的評估：

先看同樣大小的四個模型。hfl RoBERTa-wwm-ext 穩定地比 bert-base-chinese 高：範例評估高 3.6 個百分點、改良評估高 2.8 個百分點，三個種子全部高於 bert-base-chinese 的平均。整詞遮罩、更多資料與更長的預訓練，在中文閱讀理解上確實有幫助。MacBERT 卻比 bert-base-chinese 低（0.514、0.674），而且三個種子差了 9 個百分點，是本章雜訊最大的一個。MacBERT 的論文（GitHub ymcui/MacBERT 的表格）報告 DRCD dev 的 EM：BERT-base 83.1、RoBERTa-wwm-ext 86.6、MacBERT-base 89.4（10 次的最高值），MacBERT 最好，這裡卻反過來。論文的 EM 也比本章高得多，因為微調方式完全不同：論文用的是完整的閱讀理解流程（較長的序列、多個 epoch、各自調過的訓練設定），本章則是範例的 193 個 token、學習率 1e-4、1 個 epoch。這是比較預訓練模型時常見的陷阱：同一組超參數未必對每個模型都公平，排名可能隨著微調設定改變；本章的結果只代表「在範例的設定下」。

ckiplab 與 luhua 是前兩名，但它們不是在和其他模型同一個起跑點比賽，下一節會說明。luhua 的 0.756 是全書最高的數字，代價是 3 倍的參數與 3 倍的訓練時間（7.6 節）。

兩個現象。第一，一次都沒訓練，ckiplab 用改良的評估就有 0.719，已經和本書用 bert-base-chinese 加隨機視窗、精心調過的最好結果（第 6 章，0.729）相當；我們花一個 epoch 微調它，只多了 2.5 個百分點。它的問答頭顯然在某個繁體中文閱讀理解資料上訓練過（DRCD 是最常見的繁體中文閱讀理解資料集），但模型卡沒有說明。luhua 不訓練也有 0.668，它的文件只說用了「大量中文 MRC 數據（包括公開的 MRC 數據集）」，沒有點名。我們無法確定它們有沒有看過 DRCD 的 dev 題目；如果看過，這些分數就有一部分是「背答案」。

第二，範例的評估把它們低估得很嚴重：ckiplab 從 0.694 掉到 0.415，luhua 從 0.655 掉到 0.369。原因是這兩個模型是用 SQuAD 2.0 的方式訓練的：視窗裡沒有答案時，start 與 end 都指向 [CLS]，表示「沒有答案」，而且這個分數往往很高。範例規則照樣拿它參加視窗之間的比較，結果 ckiplab 有 2,114 題、luhua 有 1,995 題的回答是字面上的「[CLS]」（另有 12、14 題是空字串）。第 4 章的規則只在文章範圍內挑答案，[CLS] 自然被排除了。這再一次說明後處理不是細節：換了模型，模型輸出的「習慣」也跟著換，後處理要能處理各種情況。

回到換模型的問題：ckiplab 從 bert-base-chinese 的 0.693 漲到 0.744，看起來是「換模型」帶來 5 個百分點；但其中大部分在換上去的那一刻就已經有了，來自它過去的問答訓練，而不是更好的預訓練。在報告裡比較模型時，應該把「有沒有先在閱讀理解資料上微調過」分開說明。

7.5　轉小寫的對照

第 1 章發現，hfl 與 luhua 的 tokenizer 預設轉小寫，bert-base-chinese 不轉。換成 hfl 的模型，同時也換了這個前處理。為了分開兩者，本書加跑了一組「bert-base-chinese 加轉小寫」的對照（使用者核可）。這組對照有一個設計上的缺陷要先說清楚：它用的是範例的設定（不衰減），而不是本章的設定（線性衰減），所以只能和不衰減的範例比：

bert-base-chinese，1 epoch，不衰減種子 0種子 1種子 2平均
不轉小寫（範例）0.4160.4820.4390.446
轉小寫0.4750.4700.4190.455

平均只差 0.9 個百分點，而這個設定的種子雜訊高達 6.6 個百分點（第 5 章 5.6 節），兩組的範圍幾乎完全重疊，看不出轉小寫有什麼作用。另外要注意，轉小寫之後，範例的 evaluate 用 decode 還原答案，英文答案會變成小寫而判錯，對轉小寫的模型不利；改用從原文切答案的 evaluate_v2（stride 150），種子 0 是 0.491（範例設定的種子 0 是 0.427），其他兩個種子是 0.488、0.434，仍然被雜訊淹沒。能說的只有：轉小寫的影響在這份資料上不大（英文在 DRCD 裡畢竟少），不足以解釋 hfl RoBERTa 相對 bert-base-chinese 的優勢；要精確量出它的貢獻，得在線性衰減的設定下重做，本書沒有做。

7.6　混合精度：快 2.7 倍

投影片 p.22 建議用 automatic mixed precision（自動混合精度，AMP）：大部分運算改用 16 位元的浮點數，速度約快 1.5 到 3 倍。範例的寫法是 accelerate==0.2.0 的 Accelerator(fp16=True)（train.py:29–32），這個參數在新版 accelerate 已經改名為 mixed_precision="fp16"，本機也沒有安裝 accelerate。PyTorch 本身就內建混合精度，實驗工具用的是它：

torch.autocast 讓區塊內的矩陣乘法等運算自動改用 16 位元，LayerNorm、softmax、loss 這類對精度敏感的運算仍用 32 位元。參數與優化器的狀態一律保持 32 位元，所以叫「混合」。16 位元有兩種：fp16 的指數位元少，能表示的最小數字大約是 6e-8，很小的梯度會直接變成 0（underflow），所以要用 GradScaler 先把 loss 放大（例如乘以 65,536）再反向傳播，更新前再除回來；bf16（bfloat16）的指數位元和 fp32 一樣多，範圍夠大，不需要 scaler，代價是有效位數更少。bf16 需要 Ampere（2020 年）以後的 NVIDIA GPU，2022 年 Colab 的 T4 不支援，這是投影片只提 fp16 的原因。

投影片估計 T4 加 fp16 大約快 2.5 倍（Simple 從 20 分鐘變 8 分鐘），和這裡的 2.7 倍相近。快的原因是現代 GPU 有專門做 16 位元矩陣乘法的硬體（Tensor Core），速度是 32 位元的好幾倍。

7.7　梯度累積：省記憶體，不省時間

投影片 p.23 的另一個技巧是梯度累積（gradient accumulation）：GPU 記憶體不夠放一個 batch 時，把 batch 拆成幾份，每份都做 forward 與 backward，但梯度先累加、不更新，等全部做完才更新一次。上面那段程式的第 162 行把 loss 除以累積的次數（讓累加起來的梯度等於大 batch 的平均），第 168 行只在累積滿了才更新參數與學習率。用 batch 16 × 累積 2 次，模擬原本的 batch 32：

設定（種子 0）訓練時間GPU 記憶體峰值dev EM
batch 32272 秒4.91 GB0.528
batch 16 × 累積 2283 秒3.44 GB0.542

記憶體從 4.91 GB 降到 3.44 GB，時間略增（每一筆資料的計算量不變，但小 batch 的 GPU 利用率較低）。dev EM 0.542 與 0.528 不同，但都在種子雜訊的範圍內：理論上等價的兩種寫法，浮點運算的順序與 dropout 的隨機遮罩不同，結果就不會逐位元相同（自我測驗 4）。所以梯度累積是「GPU 不夠大時的替代品」，不是加速技巧。本作業的 bert-base 只用不到 5 GB，用不到它；換成 large 模型、或把視窗加長時才需要。

7.8　報告第 2 題與 Kaggle 的史料

報告第 2 題（投影片 p.30）要求：換一個 Hugging Face 上的預訓練模型，說明（1）用了哪個模型、（2）它的表現、（3）它和 BERT 的差別（架構、預訓練的 loss 等）。根據本章，以 hfl/chinese-roberta-wwm-ext 為例，一份有根據的回答包含：架構與 BERT-base 完全相同（12 層、768 維，101,678,594 個參數），差別在預訓練——整詞遮罩（中文先斷詞、整個詞一起遮）、拿掉 NSP、更多資料與更長的訓練；在相同的微調設定下，dev EM 平均從 0.552 提高到 0.588（3 個種子，範例的評估），改良的評估下從 0.693 到 0.721。如果選 ckiplab 或 luhua，則必須說明它們已經在閱讀理解資料上微調過，並附上不訓練時的分數。

現在的做法：先查模型卡，再看自己的評估

今天 Hugging Face 上的中文模型多到數不清，選模型的第一步是讀模型卡：架構、預訓練資料、授權，以及有沒有在你的評估資料上訓練過。本章的 ckiplab 與 luhua 就是例子：它們的高分有一部分來自「早就學過閱讀理解」，模型卡卻沒寫清楚用了哪些資料；如果訓練資料包含 DRCD 的 dev 或測試題，分數就會虛高。這個問題在大型語言模型時代更嚴重，稱為資料污染（data contamination）：評估用的題目可能早就在預訓練語料裡。做法是一樣的：先查文件，再用自己沒有公開過的資料評估，並且像本章一樣，用「不訓練直接評估」看看模型的起跑點。至於 BERT 這類 encoder，2024 年的 ModernBERT 等新一代模型把上下文長度拉到 8,192 個 token，也改用更新的訓練配方，換模型的選擇比 2022 年多了很多。

本章重點

  • 換模型只要改模型名稱；但要確認詞表與特殊符號（本章五個模型的 vocab.txt 相同）、tokenizer 是否轉小寫、以及模型大小。
  • 同樣大小的模型裡，hfl RoBERTa-wwm-ext 穩定地比 bert-base-chinese 高約 3 個百分點；MacBERT 在這組超參數下反而較差、雜訊也最大。同一組超參數不一定對每個模型公平。
  • ckiplab 與 luhua 載入時已有問答頭：不訓練就有 0.719 與 0.668（改良評估、stride 32），換模型的好處大部分來自它們過去的問答訓練；範例的評估會嚴重低估它們（0.415、0.369）。
  • 轉小寫的對照（不衰減的設定）只差 0.9 個百分點，被種子雜訊淹沒，不足以解釋 hfl 的優勢。
  • 混合精度（fp16 + GradScaler，或 bf16）讓訓練快 2.6–2.7 倍、大模型快 3.3 倍，dev EM 不變；梯度累積省記憶體（4.91 → 3.44 GB），不省時間。

自我測驗

1. 想把模型換成英文的 roberta-base 來做這份作業，除了改模型名稱，還有什麼一定要改？

至少三件：dataset.py 寫死的 101、102 要改成該 tokenizer 的 cls_token_id、sep_token_id（英文 RoBERTa 的 <s> 是 0）；RoBERTa 沒有句子類型嵌入（type_vocab_size 是 1），token_type_ids 不能有 1；它的詞表是英文的 byte-level BPE，中文會被拆成很多位元組 token，150 個 token 裝不了多少字。更根本的問題是它沒有學過中文，效果一定很差。

2. 為什麼 hfl RoBERTa 與 MacBERT 和 bert-base-chinese 的參數量一模一樣，表現卻不同？

參數量只描述架構，表現取決於參數的值，而值是預訓練決定的：用什麼資料、什麼任務（逐字遮、整詞遮、相似詞替換）、訓練多久。這三個模型的架構相同，差在預訓練，所以它們的差異是「預訓練方法與資料」的差異。但本章也看到，一次 1 個 epoch 的微調、3 個種子，排名不一定穩定（MacBERT 的種子差距很大），要下「哪種預訓練比較好」的結論，需要更多種子與不同的微調設定。

3. 用 fp16 訓練時忘了 GradScaler，可能會發生什麼事？bf16 呢？

fp16 的範圍小，很多很小的梯度在反向傳播時會變成 0（underflow），模型學得比較差，嚴重時 loss 不降反升，或出現 inf／NaN。bf16 的指數範圍和 fp32 相同，不會 underflow，通常不需要 scaler。本書沒有實測「fp16 不加 scaler」的情形。

4. 梯度累積的 batch 16 × 2 和 batch 32 在數學上等價，為什麼 dev EM 不完全相同？

資料順序是一樣的（DataLoader 的隨機排列和 batch 大小無關，16 個一組的兩組正好就是原本的 32 個），loss 也有除以 2。但兩次各 16 筆的 forward 與一次 32 筆的 forward，dropout 每次抽的隨機遮罩不同，矩陣運算的加法順序也不同，浮點數的捨入誤差經過幾百步就會讓結果分岔，和第 0 章的非決定性是同一件事。另外，31,690 不是 32 的倍數，最後一批 10 筆在累積模式下湊不滿兩份，會被丟掉。

第 2 章　策略網路與取樣：擲一顆不公正的骰子

第 0 章看過策略網路的架構；這一章看它怎麼被使用。每一步，網路把狀態變成四個機率，Categorical 照機率擲一次骰子，順手留下這個動作的 log 機率給之後的學習用。這一章逐行讀 sample()，看一個沒訓練過的網路擲出的骰子有多公正、訓練過的又有多偏，再解釋為什麼在這份作業裡，把網路搬到 GPU 上反而會變慢。

2.1　sample()：五行做完一個決定

代理人類別 PolicyGradientAgent 包住策略網路，提供兩個方法：sample() 決定動作，learn() 更新網路（第 3 章）。訓練與測試都只透過 sample() 和網路打交道：

  1. torch.FloatTensor(state)：環境回傳的狀態是 NumPy 的 float32 陣列，形狀 (8,)，轉成 PyTorch 的張量。一次只送一個狀態，沒有 batch 維度；第 0 章的 nn.Linear 兩種形狀都吃。
  2. self.network(...)：前向計算，得到形狀 (4,) 的機率，四個數加起來是 1。
  3. Categorical(action_prob)：把這四個機率包成一個「類別分布」物件。它本身不做任何隨機的事，只是記住「動作 0 的機率是多少、動作 1 是多少……」。
  4. action_dist.sample()：照這個分布抽一個動作。這是整份作業裡唯一用到 torch 亂數的地方（第 1 章的表）。
  5. action_dist.log_prob(action)：抽到的那個動作的機率取自然對數。它還連著計算圖：之後對它 backward()，梯度會一路流回網路的權重。

最後回傳兩樣東西：action.item() 把只有一個元素的張量變成 Python 的整數，交給 env.step()；log_prob 則被訓練迴圈收進一個串列，一批 5 局收了幾百個（第 0 章的「log_probs looks like (508,)」）。

2.2　還沒訓練的網路：一顆幾乎公正的骰子

網路剛建好時，權重是隨機的小數字，輸出的機率會長什麼樣子？本書的 docs/tools/hw12_ch02.py 照 train.py 的順序建立網路（fix() 設了 torch 的種子 543，探索格沒有用到 torch 的亂數，所以這就是範例訓練一開始的那個網路），餵它 train.py 印出的第一個狀態：

first state [-0.0013  1.3985 -0.1278 -0.5538  0.0015  0.029   0.      0.    ]
probs [0.313  0.2289 0.2666 0.1915] sum 1.0 entropy 1.3700436353683472 max entropy ln4 1.3862943611198906   «1»
one sample: 3 log_prob -1.652858853340149 = log(p[a]) -1.652858853340149                                  «2»
100000 draws, frequency [0.3131 0.2281 0.2668 0.192 ]                                                      «3»
  1. 1四個機率在 0.19 到 0.31 之間，接近均勻的 0.25。熵（entropy，−Σ p log p）衡量一個分布有多「平」：四個動作完全均勻時是 ln 4 ≈ 1.386，永遠只選同一個動作時是 0。這個網路的熵是 1.370，幾乎是最大值。一開始的策略近似隨機亂按——這正是我們想要的：還不知道什麼好，就每個都試試看。
  2. 2抽到動作 3，它的 log_prob 是 −1.6529，正好等於 log(0.1915)。
  3. 3同一個分布抽 10 萬次，四個動作出現的比例和機率吻合到小數第三位。Categorical.sample() 做的就是這件事：照機率擲骰子。

為什麼留 log 機率而不是機率本身？兩個理由。數學上，策略梯度定理（第 3 章）推出來的就是 ∇ log π(a|s)。數值上，一局幾百步的機率連乘會變成極小的數，取 log 之後變成加總，不會下溢。Categorical 內部其實先把機率轉成 logits 再算 log_prob，比自己寫 torch.log(p[a]) 更穩定：當某個機率被訓練到非常接近 0 時，直接取 log 會得到 −∞。

2.3　訓練過的網路：一顆很偏的骰子

訓練 2,000 局之後，骰子變得很偏。拿範例（種子 543）訓練完的網路，在它自己的 5 局測試裡逐步檢查每一個狀態的輸出：

judge rewards (same as test.py): [-34.25, -161.82, -170.98, 257.59, -22.56] steps 1534
max prob: mean 0.850 median 0.912; share of steps with max prob > 0.9: 0.525, > 0.99: 0.186      «1»
entropy: mean 0.354 (ln4 = 1.386); sampled action == argmax on 0.836 of the steps (251 of 1534)     «2»
  1. 11,534 步裡，最可能的那個動作平均有 0.85 的機率；一半以上的步數（52.5%）超過 0.9，近五分之一超過 0.99。第 1 章那一局成功降落的軌跡就是例子：開局時動作 3 的機率 0.997，停在地上時動作 0 的機率 0.919。
  2. 2平均熵從 1.37 降到 0.354。照機率取樣時，有 251 步（16.4%）抽到的不是最可能的那個動作。

這解釋了第 0 章的觀察：閉迴路 greedy（永遠選最可能的動作）比 stochastic（照機率擲骰子）平均高 36 分。在一局幾百步裡，大約每六步就有一步「擲歪了」；對一艘正在減速的小艇，該開主引擎的那一步沒開，可能就摔了。

反過來說，訓練時必須擲骰子。策略梯度只能從自己做過的動作學習：如果永遠選最可能的動作，就永遠看不到其他動作的結果，也就無法發現它們可能更好。照機率取樣是範例裡唯一的探索（exploration）機制，而且它會隨著訓練自動減少——機率越偏，探索越少。這是一把雙面刃：機率太早變得極端，策略就會卡住，再也試不到別的做法。第 3 章會看到，學習率太大的範例會把某個動作的機率推到接近 1，從此只會做那一件事；第 6 章的熵正則化就是用來對抗這件事的。

測試時要擲骰子還是選最大？

範例的 test.py 照樣呼叫 sample()，所以交出去的動作序列是擲骰子擲出來的。這不算錯：策略梯度訓練出來的本來就是一個機率分布，它在訓練時也是這樣被使用的。但它讓 judge 的分數多了一層運氣，同一個策略重跑一次測試就可能差上百分（第 7 章）。改成 greedy 通常會比較好（第 0 章平均高 36 分），但不是一定：第 4 章會看到 greedy 讓小艇懸停在半空中。

2.4　從 log_prob 到梯度：被抽到的動作被推高多少

第 3 章要讀的 loss 是 -(log_prob × 權重).sum()。在讀它之前，先看單獨一個 log_prob 的梯度長什麼樣子。網路最後一層輸出 4 個 logits z（softmax 之前的數字），機率 p = softmax(z)。對被抽到的動作 a，

∂ log pa ／ ∂ zk ＝ 1[k = a] − pk

被抽到的那個動作的 logit 梯度是 1 − pa（正的），其他三個是 −pk（負的），四個加起來是 0。hw12_ch02.py 用 autograd 在 2.2 節那個沒訓練的網路上驗證（抽到動作 3）：

probs [0.313  0.2289 0.2666 0.1915] grad wrt logits [-0.313  -0.2289 -0.2666  0.8085] onehot(3) - probs [-0.313  -0.2289 -0.2666  0.8085]
weight +1.0: descent direction of the logits [-0.313  -0.2289 -0.2666  0.8085]     «1»
weight -1.0: descent direction of the logits [ 0.313   0.2289  0.2666 -0.8085]     «2»
  1. 1loss 是 −權重 × log_prob。權重是正的時候，梯度下降沿著「+梯度」的方向走：動作 3 的 logit 被推高 0.81 倍學習率，其他三個依它們目前的機率被壓低。下次遇到同樣的狀態，動作 3 更可能被選中。
  2. 2權重是負的時候，方向整個反過來：動作 3 被壓低，其他三個被抬高。

這就是策略梯度的全部機制：每一步的權重決定被抽到的動作要被推高還是壓低，以及推多少；網路其他層的梯度，只是把這 4 個 logits 的推力透過反向傳播分給 484 個參數。兩個推論：一、權重的正負號比大小更重要，全部都是正的權重會把每一個做過的動作都推高（範例因此要先標準化，第 3 章）。二、機率已經很高的動作，1 − pa 很小，再推也推不了多少；機率很低的動作一旦被抽到，推力接近 1。剩下的問題只有一個：每一步的權重該怎麼算——那是第 3 到第 6 章的主題。

2.5　train() 與 eval() 在這裡沒有作用

範例在訓練前呼叫 agent.network.train()，測試前呼叫 agent.network.eval()。在 HW03、HW10、HW13 裡，這兩個呼叫非常重要：它們切換 Dropout 與 BatchNorm 的行為，忘了切就會量錯。這個網路只有三個 Linear：

identical outputs: True | modules: ['PolicyGradientNetwork', 'Linear', 'Linear', 'Linear']

同一批輸入在兩種模式下的輸出逐位元相同。範例寫這兩行是好習慣，不寫也不會出錯。另一個在這裡同樣沒有作用的是 model.py 裡 PolicyGradientAgent.forward()：整份程式從來沒有呼叫它，訓練迴圈直接用 sample()，learn() 也不會再做一次前向計算——它用的是 sample() 時留下的 log_prob，計算圖一直保留到那一批更新為止。

還有兩處「留著沒用」的東西：StepLR 被 import 了卻沒有建立排程器（看得出助教原本想讓學生試試學習率排程），優化器是最基本的 SGD、學習率 0.001。第 3 章會看到，這個學習率對範例的「瞬時獎勵 + 加總」的 loss 來說其實相當敏感：調大 10 倍會崩潰，調小 10 倍學不動。

2.6　為什麼這份作業用 CPU

投影片 p.13 說「HW12 won't use GPU by default」。前幾本書都在 GPU 上跑，這一本為什麼不用？因為訓練迴圈的形狀：每一步只送一個狀態進網路，拿到動作之後才能交給環境走下一步，下一個狀態要等環境算完才知道。整份訓練是 50 萬次「網路算一次、環境走一步」的循環，沒有任何可以一次大量平行的地方。本書的 docs/tools/hw12_timing.py 量了一步的成本（單執行緒；第一次重複用來暖機，取最後一次）：

每一步時間（µs）
策略網路在 CPU：前向 + Categorical 取樣 + log_prob + .item()85.8
同樣的事在 GPU（RTX PRO 4000 Blackwell）667.5
LunarLander 的一步物理模擬（Box2D，CPU）18.4

（在全部實驗結束、機器閒置時量的，docs/tools/hw12_timing.txt。）

GPU 慢了 7.8 倍，原因是每一步都要付固定成本：把 8 個數字從 CPU 記憶體搬到 GPU、啟動三次矩陣乘法與 softmax 的 kernel、等 GPU 算完、再把一個整數搬回來交給 CPU 上的環境。這些固定成本每次是幾十微秒，而真正的計算——484 個參數的乘加——小到可以忽略。GPU 擅長的是一次算很多，例如一次送進幾千個狀態；這份作業的迴圈一次只有一個。

另一個有趣的數字是：網路比物理還貴。Box2D 模擬一步只要 18.4 微秒，策略網路加上取樣卻要 85.8 微秒，是 4.7 倍。大部分時間花在 Python 與 PyTorch 的固定開銷上：建立張量、建立 Categorical 物件（它預設還會檢查參數是否合法）、記錄計算圖。範例訓練 2,000 局（約 52 萬步）要 2 分多鐘，物理模擬只佔其中一小部分，大部分花在這五行 sample() 與每批一次的更新。

現在的做法：向量化環境，一次跑很多局

現在的 RL 函式庫（例如 Stable-Baselines3、CleanRL）訓練 LunarLander 時，通常同時開 8 到 16 個環境（Gymnasium 的 VectorEnv），每一步把所有環境的狀態疊成一個 batch 一次送進網路。網路的固定開銷被 16 個環境分攤，GPU 也才有東西可以平行。第 6 章的 PPO 收集資料的方式已經比較接近這個樣子（先收一大批，再一次用很多個 minibatch 更新），但本書為了和範例對照，環境仍然一次只開一個。

本章重點

  • sample()：狀態 → 網路 → 4 個機率 → Categorical 擲骰子 → 動作，並留下帶著計算圖的 log_prob。
  • 沒訓練的網路幾乎是均勻分布（熵 1.370，最大 1.386）；訓練 2,000 局後平均熵 0.354，一半以上的步數最可能的動作超過 0.9。
  • 測試時擲骰子，約 16% 的步數會選到不是最可能的動作；這是 greedy 平均比 stochastic 高 36 分的原因之一。訓練時必須擲骰子，那是範例唯一的探索。
  • ∂ log pa／∂ zk ＝ 1[k = a] − pk：權重為正，被抽到的動作被推高、其他被壓低；權重為負就反過來。
  • 網路沒有 Dropout 與 BatchNorm，train()／eval() 不影響結果；forward() 與 StepLR 都沒用到。
  • 一次只算一個狀態，GPU 的固定成本遠大於計算，反而比 CPU 慢；一步之中，網路與取樣比物理模擬還貴。

自我測驗

1. 一個動作的機率是 0.997，它的 log_prob 是多少？機率是 0.001 的動作呢？訓練時抽到後者，對梯度有什麼影響？

log(0.997) ≈ −0.003，log(0.001) ≈ −6.91。∇ log π 的大小和 1/π 有關：很少被抽到的動作一旦被抽到，它的梯度會很大，策略會被大幅推動——往哪個方向推，取決於那一步的權重是正是負（第 3 章）。

2. 如果把 sample() 改成永遠回傳 argmax（但仍回傳那個動作的 log_prob），訓練會怎樣？

策略失去探索：一開始選到哪個動作最可能，就一直選它，永遠看不到其他動作的結果。梯度只會增減那一個動作的機率，而它已經是最大的，argmax 幾乎不會改變——訓練會卡在一個固定動作的策略上（第 1 章的固定動作策略都在 −130 到 −883 之間）。這是推論，本書沒有實際跑。

3. 為什麼範例不必在測試前加 torch.no_grad() 也能正確運作？加了有什麼好處？

測試時不呼叫 backward()，計算圖只是被建立、然後丟掉，不影響結果。加上 no_grad() 可以省下建立計算圖的時間與記憶體。本書的實驗工具評估時就包了 no_grad()；兩者抽到的動作完全相同，因為取樣用的亂數和有沒有計算圖無關。

4. 把 2.6 節的 GPU 版本改成一次送 1,000 個狀態，你預期每個狀態的平均時間會怎麼變？為什麼範例沒辦法這樣做？

固定成本被 1,000 個狀態分攤，每個狀態的平均時間會大幅下降，GPU 很可能就比 CPU 快了。範例做不到，是因為它只開一個環境，下一個狀態要等這一步做完才知道；要一次送很多個狀態，就得同時開很多個環境（向量化環境）。這是推論，本書沒有量。

5. 熵是 0.354 的分布，大概像什麼樣子？請舉一個四個機率的例子。

例如 (0.93, 0.03, 0.02, 0.02)：熵 = −(0.93 ln 0.93 + 0.03 ln 0.03 + 2 × 0.02 ln 0.02) ≈ 0.067 + 0.105 + 0.156 ≈ 0.33，接近 0.354。也就是說「九成多選同一個動作，其餘三個平分剩下的」。

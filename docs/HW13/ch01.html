ML2022 Spring · HW13 讀碼教材

第 1 章　程式結構與訓練迴圈

這一章讀「模型以外」的程式：notebook 怎麼拆成檔案、怎麼證明拆完沒變；老師模型為什麼即使不用也得建、而且要建在原來的位置；影像怎麼轉成張量；一步訓練做了哪些事；印出來的驗證準確率可不可信；八分鐘花在哪裡。最後一節的結論會跟著全書走：在這份作業裡，只是換一條亂數流，10 個 epoch 的準確率就能差一個百分點以上。

1.1　從 notebook 到六個檔

原版的範例程式是一份 32 格的 notebook（文字格與程式格各半），放在 Kaggle 比賽頁與 Colab。官方 GitHub 上的 HW13 資料夾只有資料，沒有程式，所以本 repo 是從投影片 p.2 的 Colab 連結下載 notebook，存成 HW13/HW13.ipynb，再拆成六個檔。對照表在目錄頁，這裡講拆法和驗證。

拆的原則是「能照抄就照抄」：每個檔的開頭註解寫著它來自 notebook 的哪幾格，程式碼逐字搬過來，只去掉行尾空白。真正改動的地方只有三處：kd.py 的 TODO（第 4 章）、老師的建法（1.2 節），以及把 Medium 的「手動取消註解」換成命令列選項。最後一項的樣子是這樣：

原版要跑 Medium，得把 config.py 的 'loss_fn_type' 改成 'KD'，再到訓練迴圈裡把六行標著 # MEDIUM BASELINE 的註解打開。本 repo 把那六行包進 if use_kd:，用 --loss_fn_type KD 一次切換。三個選項不給的時候，cfg 完全不動，第 48 行印出的設定和原版一字不差。

拆完怎麼知道沒有改壞？光看程式碼對不對是不夠的，要讓兩邊實際跑出同樣的東西。做法分三步：

  1. 用 docs/tools/hw13_make_ref.py 把 notebook 的程式格原樣串成一支腳本，當作「參照版」。它只動兩種行：!wget、!tar 這種 shell 指令（資料已經在本機）註解掉；torch.hub.load 那一行換成本機 torchvision（1.2 節）。其他一字不改，連印資料夾檔案數的那一格都保留。
  2. 在另一個資料夾跑參照版，再跑本 repo 的 train.py 與 test.py。
  3. 比對三樣東西：stdout 的每一行（diff）、存下的學生權重（每個張量用 torch.equal）、submission.csv（cmp 逐位元組）。

結果：stdout 只差一行——One ./food11-hw13/evaluation sample ... 從 train.py 搬到了 test.py 印，因為建測試集那一格本來就屬於推論；權重 30 個張量全部相等；submission.csv 位元組相同。這種「逐位元一致」的檢查看起來嚴格得過頭，其實是最省事的：只要有一個位元不同，就知道拆的時候改到了會影響結果的東西，不必再猜是哪裡。1.2 節就是這個檢查抓到的例子。

1.2　老師要建在哪裡：不用它，也得建它

原版 notebook 建老師的那一行是：

teacher_model = torch.hub.load('pytorch/vision:v0.10.0', 'resnet18', pretrained=False, num_classes=11)

torch.hub.load 會在執行時從 GitHub 下載 pytorch/vision 這個 repo 在 v0.10.0 標籤的原始碼，存進 ~/.cache/torch/hub/，再從裡面的 hubconf.py 呼叫 resnet18。這在 2022 年的 Colab 上很方便，但有三個問題：每次換環境都要連網下載；執行的是一份和你安裝的 torchvision 不同版本的程式碼；pretrained=False 這個參數在新版 torchvision 已經移除，改成 weights=None。本 repo 改成直接用已安裝的 torchvision.models.resnet18(weights=None, num_classes=11)（第 0 章引用過的 model.py 第 68 行）。兩者的架構相同，助教的 checkpoint 載得進去、122 個 key 全部對上，驗證準確率 0.87143（第 3 章）。

沒有驗證的地方

torchvision 0.10.0 和本機的 0.26.0 建 ResNet-18 時，初始化權重各用掉多少亂數，本書沒有實測（要先下載舊版才能比）。如果兩者用掉的亂數不同，2022 年在 Colab 上跑出來的學生，和本書的參照版就不會逐位元相同。本書的「參照版」指的一律是「notebook 原樣、但老師用本機 torchvision 建」的版本。

Simple baseline 根本不用老師：loss 只有 cross entropy，老師連 .to(device) 都沒做。那麼拆檔時，能不能乾脆在 CE 模式下不建老師？

不行，因為建模型會用到全域的亂數產生器。resnet18(...) 在 __init__ 裡替每個卷積與全連接層隨機初始化權重，這些亂數取自第 33 行 torch.manual_seed(myseed) 設定的那一個產生器。model.py 第 71 行雖然馬上用助教的權重蓋掉，但亂數已經用掉了。之後 DataLoader 要洗牌、RandomHorizontalFlip 要決定翻不翻，用的都是同一個產生器的「下一段」亂數，所以有沒有建老師，學生看到的資料順序就不同。

實測兩種情況（都照 train.py 的順序設種子、建資料、建學生）：

建老師（原版）不建老師
學生第一層的初始權重相同（torch.equal：學生在老師之前建）
之後的亂數產生器狀態不同
第一個訓練 batch 的前 12 個標籤[7, 1, 8, 0, 7, 8, 0, 3, 1, 10, 6, 3][5, 5, 2, 3, 9, 9, 10, 2, 6, 9, 2, 2]
最佳驗證準確率（10 個 epoch）0.50408（第 9 個 epoch）0.51720（第 10 個 epoch）

最後一列是照字面改的：在 scratchpad 複製一份 HW13，只把 train.py 第 68 行註解掉，其他一字不動，完整跑 10 個 epoch。準確率差了 1.3 個百分點，而且不是因為少了老師——老師在 CE 模式下本來就沒參與訓練。這 1.3 個百分點純粹是「另一條亂數流」造成的。1.6 節會再看到同樣量級的差異，並說明這對後面每一個實驗意味著什麼。

所以 train.py 第 66–67 行留了註解：老師不管用不用，都建在 notebook 原來的位置。這和 HW14 教材遇到的 example = Model() 是同一件事：一行看起來「只是建個物件」的程式，也會改變結果。

1.3　資料：從 JPEG 到 (3, 224, 224)

print(test_tfm) 的實際內容是 Resize(size=256, interpolation=bilinear, max_size=None, antialias=True)、CenterCrop(size=(224, 224))、ToTensor()、Normalize(...) 四步：

  • Resize(256) 給的是一個整數，意思是「把短邊縮到 256、長邊等比例」，不會把照片壓扁。HW03 用的是 Resize((128, 128))，給一個 tuple，就是硬壓成正方形。
  • CenterCrop(224) 從中間裁出 224×224。照片四周的 32 像素以上被丟掉，長邊丟得更多。
  • Normalize 用的平均值 [0.485, 0.456, 0.406] 與標準差 [0.229, 0.224, 0.225] 是 ImageNet 的統計值，不是 Food-11 的（HW03 教材量過 Food-11 的通道平均是 [0.5549, 0.4509, 0.3436]）。這裡用 ImageNet 的值不是錯，而是一個約定：torchvision 的分類模型都是這樣訓練的，助教訓練老師時也用了同一套轉換。

第 11 行與第 21–23 行的註解是重點：老師是在 224×224、這種正規化的輸入上訓練的。學生的輸入可以改，但如果要做知識蒸餾，老師和學生吃的是同一個 imgs（train.py 第 122、124 行），改了大小或正規化，老師的輸出就可能變差，學生學到的是一個變笨的老師。第 5 章加資料增強時會遇到這個限制。

訓練的轉換只比測試多一個 RandomHorizontalFlip()：一半的機率左右翻轉。這幾乎是最弱的增強；HW03 教材第 8 章實測過：沒有增強的模型 40 個 epoch 就停在 0.674，加上一組較強的增強（隨機裁切、旋轉、色彩抖動）訓練 200 個 epoch 能到 0.765。第 5 章會把那一套搬過來。

FoodDataset 和 HW03 的幾乎一樣：第 33 行列出資料夾裡所有 .jpg 並排序；__getitem__ 每次被取一張時才開檔、轉換（第 44–45 行），所以「讀圖」的成本在每個 epoch、每張圖都會重付一次；第 47 行從檔名切出類別，evaluation/ 的檔名沒有底線，int("0000.jpg") 拋例外，就回傳 −1。第 47 行用 "/" 切路徑，在 Windows 上路徑分隔符是反斜線，這行會在整個訓練集都回傳 −1；HW03 的版本改用了 os.path.basename，這裡照原版保留。

訓練集 shuffle=True、驗證集 shuffle=False，兩者都是 num_workers=0：讀圖全部在主行程裡做，GPU 每一步都要等 CPU 解完 64 張 JPEG。1.6 節會量這個代價。

1.4　一步訓練

CE 模式下，一步就是標準的五件事：前向（第 124 行）、算 loss（第 131 行）、清掉上一步的梯度（第 133 行）、反向傳播（第 136 行）、更新（第 142 行）。KD 模式多了第 120–122 行：在 torch.no_grad() 底下讓老師也看同一批圖，產生 teacher_logits 傳給 loss。老師不需要梯度，no_grad 讓 PyTorch 不必記錄老師的計算圖，省記憶體也省時間；老師的權重也不在 optimizer 裡（第 93 行只交了 student_model.parameters()），本來就不會被更新。

第 139 行是 gradient clipping（梯度裁剪）：先算出所有參數梯度合起來的長度（L2 範數），如果超過 grad_norm_max（10），就把所有梯度等比例縮小到長度剛好是 10。它防的是偶發的巨大梯度把權重一下子推太遠。這個保護在 Simple 的訓練裡用到了幾次？本書另外寫了一支 docs/tools/hw13_gradnorm.py，照同樣的設定跑 10 個 epoch、記下每一步裁剪前的範數（它用 16 個 worker 讀資料，亂數流和 train.py 不同，但分布可以參考）：

統計值
總步數（155 步 × 10 個 epoch）1,550
範數超過 10、真的被裁剪的步數6（0.39%）
平均／中位數4.061／4.059
最大值16.875（第 8 個 epoch）
每個 epoch 的最大值4.6、5.7、10.1、11.1、8.0、13.2、14.7、16.9、9.9、12.6

第 1 個 epoch 的範數都在 2 左右，之後慢慢變大，中位數 4，偶爾有超過 10 的尖峰。所以 clipping 在這裡是「保險」，絕大多數的步驟都沒有作用。順帶一提，第 139 行把回傳值存進 grad_norm，之後卻沒有用到；印出來或記進 log，就是最便宜的訓練健康檢查。

第 93 行的 optimizer 是 Adam(..., weight_decay=1e-5)。要注意 torch.optim.Adam 的 weight_decay 是把 wd·θ 加進梯度（L2 正則化），再經過 Adam 的自適應縮放；這和 AdamW 的「直接把權重往 0 拉」不是同一件事。1e-5 很小，在這份作業裡兩者差別不大。

第 145 行算這個 batch 答對幾張，結果是一個放在 GPU 上的張量；第 150 行把它 append 進串列，第 154 行加總。這種寫法每一步都不需要把數字搬回 CPU，比 .item() 快一點；train_loss 那一邊用的是 loss.item()（第 149 行），每一步會同步一次 GPU。兩種寫法並存，是範例程式從 HW3 一路修改下來的痕跡。

1.5　驗證、存檔，以及印出的數字可不可信

驗證迴圈（第 161–196 行）和訓練迴圈同構，只是先 student_model.eval()（BatchNorm 改用訓練時累積的平均與變異數，不再用當前 batch 的統計）、前向放在 no_grad 裡、不更新。第 199–200 行把逐 batch 的「loss × 張數」與「答對張數」加總，再除以總張數。

前幾本書都在這裡踩過雷：HW01 印出的驗證 loss 和真實值差了 0.4，HW04 的驗證只取每句話的一個隨機片段。所以每本書在 Phase 0 都會檢查：用最佳的權重，在整個驗證集上重新算一次，和訓練時印出的數字比對。HW13 的條件很乾淨——驗證集 shuffle=False、沒有 drop_last、每一張都算到、轉換沒有隨機成分——重算的結果是 0.50408（1,729 / 3,430）、CE 1.47539，和第 9 個 epoch 印出的數字完全相同。本書之後引用的驗證準確率，都可以當成「整個驗證集上的真實準確率」。

存檔的規則是「驗證準確率創新高就存」（第 209–213 行），所以 student_best.ckpt 永遠是最好的那個 epoch，不是最後一個。用驗證集挑 epoch，本身就是在驗證集上做了一次選擇，選出來的準確率會略為偏高；在這份作業裡，Kaggle 測試集才是最後的裁判。patience 是 300，對 10 個、甚至 200 個 epoch 的訓練都等於不會提早停止（第 215–218 行）。

印出的行同時寫進 outputs/<exp_name>/log.txt（第 43–46 行的 log）。要注意 torchsummary 的表格與資料夾的檔案數是用 print 印的，不會出現在 log.txt 裡；報告第 1 題要貼的 torchsummary 結果，得從終端機複製。

1.6　八分鐘花在哪裡，以及本書的實驗怎麼跑

Simple 跑完 10 個 epoch 要 8 分 19 秒，大約每個 epoch 50 秒。把時間拆開：

量測時間說明
只讀訓練集一遍，num_workers=021.1 s不做任何計算，只有開檔、解碼、縮放、裁切、轉張量
同上，num_workers=162.3 s16 個子行程同時讀
一個 epoch 的訓練，num_workers=034.8–46.1 s工具在預設設定下的實測（與 train.py 逐位元一致）
一個 epoch 的訓練，num_workers=1612.5–13.9 sA 組第一次實驗（A10_ce）
一次驗證，num_workers=0 → 1610.3–19.3 s → 3.0–4.1 s同上
整個 10 個 epoch8 分 19 秒 → 163.5 s3 倍快

單一行程時，訓練一個 epoch 有大約一半的時間花在 CPU 讀圖。開 16 個 worker 之後，讀圖幾乎被藏到 GPU 計算的背後，剩下的 12.5 秒大部分是學生模型本身的計算：學生雖然只有 8 萬多個參數，前兩層卻在 222×222 的解析度上做 32 通道的卷積，算得並不少（第 2 章）。參照版跑的時候 CPU 使用率是 1567%，PyTorch 預設會開滿所有核心做 CPU 上的運算，這對讀圖這種小運算反而不划算（HW03 教材量過，OMP_NUM_THREADS=1 能快 18%）。

所以本書的實驗（第 4、5 章，加起來幾十個小時的訓練量）一律用 16 個 worker。但這有代價：worker 的數量會改變亂數的用法。多行程的 DataLoader 在建立時，就會先替每個 worker 抽亂數種子並預取資料（HW03 教材第 4 章拆過這件事），所以同一個種子、只改 num_workers，資料順序與翻轉就不同，結果也不同：

設定第 5 個 epoch最佳驗證準確率在第幾個 epoch
train.py（num_workers=0）0.442860.504089
train.py，不建老師（1.2 節）0.465890.5172010
實驗工具，num_workers=16（A10_ce）0.400000.5154510

三組的程式、超參數、種子都一樣，只是亂數的用法不同，最佳準確率就分布在 0.504 到 0.517 之間，中途的某個 epoch 甚至能差 6 個百分點（0.400 對 0.466）。這給了全書一把尺：10 個 epoch 的實驗，差距在 1–2 個百分點以內，就分不出是方法的效果還是亂數的運氣。第 4 章拿 KD 和 CE 比的時候，A10 兩組只差 0.2 個百分點（0.51720 對 0.51545），在這把尺之下等於沒有差別；要看出差別，得訓練更久、或跑多個種子。

實驗工具 docs/tools/hw13_exp.py 的設計就是為了這件事：不加任何選項時，它和 train.py 逐位元一致（Phase 1 驗證過：20 行輸出相同、權重每個張量相等），所以它的程式路徑可以信任；加上 --nw 16 才換成多 worker，並且全書所有正式實驗都在同一個 --nw 16 的條件下比較。它另外記錄每個 epoch 的驗證 cross entropy 與訓練、驗證各花的秒數，這些額外的計算都不碰亂數產生器。

現在的做法：讀圖的瓶頸

2022 年的範例用 num_workers=0，在 Colab 與 Kaggle 那種只有兩個 CPU 核心的機器上，多開 worker 的好處有限。現在的訓練程式通常會把 num_workers 設成 CPU 核心數附近，加上 persistent_workers=True（每個 epoch 不重建子行程）；資料量大時，會先把影像預先解碼、縮放成固定大小存起來（例如存成 numpy 陣列或 WebDataset 的分片），或用 NVIDIA DALI 把 JPEG 解碼搬到 GPU 上做。本書的工具開了 persistent_workers，結果踩到一個坑：Python 3.12 下行程在結束時會卡住，所以工具最後用 os._exit(0) 直接離開。

1.7　拆檔時順便看到的小問題

  • test.py 的 squeeze()：推論時用 list(logits.argmax(dim=-1).squeeze().cpu().numpy()) 把一個 batch 的預測轉成串列。如果最後一批剛好只有 1 張，squeeze() 會把形狀 (1,) 壓成 0 維，list() 就拋出 TypeError: iteration over a 0-d array（實測）。這份測試集有 3,347 張，3,347 除以 64 餘 19，所以不會觸發；換一個讓 3,347 除以 batch size 餘 1 的設定（例如 batch size 2）就會。把 .squeeze() 拿掉就安全了。
  • 寫死的路徑：train.py 第 50 行列資料夾檔案數時用的是 './food11-hw13'，不是 cfg['dataset_root']。改了 dataset_root 之後，這一段什麼都不印，也不會報錯。
  • if files != None（dataset.py 第 34 行）：和 None 比較應該用 is not None。如果 files 是 numpy 陣列，!= 會逐元素比較，if 就會報錯。範例程式從來沒傳過 files，所以沒事。
  • 沒有用到的 grad_norm：見 1.4 節。

這幾個都不影響本書的數字，本 repo 照原版保留，好讓 train.py 能和 notebook 逐位元比對。

本章重點

  • notebook 照抄拆成六個檔，用「參照版」逐位元比對 stdout、權重與 submission.csv 來證明拆完沒變。--loss_fn_type KD 取代手動取消註解。
  • torch.hub.load 會在執行時從 GitHub 下載 torchvision 0.10.0 的原始碼；本 repo 改用本機的 torchvision.models.resnet18。建老師會用掉全域亂數，所以即使 CE 模式用不到，也要建在原位置；照字面拿掉那一行，最佳準確率從 0.50408 變成 0.51720。
  • 轉換：短邊縮到 256、中央裁 224、ImageNet 的正規化；訓練只多一個水平翻轉。老師是在這種輸入上訓練的，蒸餾時學生和老師吃同一批圖。
  • 一步訓練：前向、loss、清梯度、反向、clip 到 10、Adam 更新。實測 1,550 步只有 6 步真的被裁剪。
  • 印出的驗證準確率就是整個驗證集的真實準確率（重算得到同樣的 0.50408）。
  • 讀圖佔了單一行程時大約一半的時間；16 個 worker 讓 10 個 epoch 從 8 分 19 秒變成 163.5 秒，但會改變亂數流。只換亂數流，10 個 epoch 的最佳準確率就在 0.504–0.517 之間：差距 1–2 個百分點以內的比較，不能當真。

自我測驗

1. 有人想讓 CE 模式省一點記憶體，把 train.py 第 68 行改成 if cfg['loss_fn_type'] == 'KD': teacher_model = get_teacher_model(...)。訓練結果會改變嗎？

會。CE 模式下不建老師，等於 1.2 節的「不建老師」：老師的權重初始化不再用掉亂數，之後的洗牌與翻轉都不同。本書照字面把那一行註解掉實際跑過，最佳驗證準確率從 0.50408 變成 0.51720。這不是「省了老師所以變好」，換一個種子也可能變差；重點是結果不再能和原版逐位元比對。

2. 把 test_tfm 的 Resize(256) 改成 Resize((256, 256))，會有什麼不同？

Resize(256) 把短邊縮到 256、保持長寬比；Resize((256, 256)) 把整張圖壓成正方形，長方形的照片會被擠扁。接著的 CenterCrop(224) 在前者只裁掉長邊多出來的部分，在後者則是裁一張變形過的圖。老師是在保持長寬比的輸入上訓練的，改成後者，老師的準確率很可能下降。本書沒有實際量這個改動。

3. 第 139 行的 gradient clipping 如果拿掉，Simple 的結果會差很多嗎？

從實測的分布判斷，影響應該很小：1,550 步裡只有 6 步的範數超過 10，其餘的步驟 clipping 本來就沒有作用。但那 6 步的更新會變大，之後的權重與訓練軌跡都跟著不同（clipping 不用亂數，所以資料順序不變），結果不會逐位元相同。本書沒有實際跑「拿掉 clipping」這一組。

4. 為什麼本書的正式實驗要全部用同一個 --nw 16，而不是讓其中幾組用 --nw 0（和 train.py 一致）？

worker 數會改變亂數流。如果 A 組用 16、B 組用 0，兩組之間的差異就混進了「換一條亂數流」的效果，而 1.6 節量過，光是這一項在 10 個 epoch 就能造成 1 個百分點以上的差距。所有實驗用同一個 worker 數，比較時才只剩下被改動的那一項。

5. 本章說「印出的驗證準確率可信」。那用驗證準確率挑出的最佳 epoch，它的準確率能代表模型在測試集上的表現嗎？

不完全能。印出的值確實是整個驗證集的真實準確率；但「創新高就存檔」是在 10 個（或更多）epoch 裡挑了驗證集上最好的一個，挑選本身會讓這個數字略為偏高。epoch 越多、每個 epoch 之間的起伏越大，偏高得越多。測試集上的準確率通常會略低一點。

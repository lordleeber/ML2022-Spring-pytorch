第 6 章　剪枝：把權重設成 0，會變快嗎

報告第 3 題要你對老師做剪枝：畫出剪枝比例和準確率的關係，再回答「教學裡的剪枝能不能加速推論」。這一章先讀 PyTorch 的剪枝工具到底對模型做了什麼，再量三種剪法的準確率曲線，然後在一張沒有其他工作的 GPU 上計時。答案是不會變快，有時反而更慢；要真的變快，得把通道整個拿掉、模型真的變小，而那需要重新訓練。

6.1　torch.nn.utils.prune 做了什麼

報告第 3-1 題附的範例 notebook（本 repo 存成 HW13/HW13_pruning_example.ipynb）只有幾行，核心是第 [3] 格：

ratio = 0.2 # specify the pruning ratio
for name, module in model.named_modules():
    if isinstance(module, torch.nn.Conv2d): # if the nn.module is torch.nn.Conv2d
        prune.l1_unstructured(module, name='weight', amount=ratio) # use 'prune' method provided by 'torch.nn.utils.prune' to prune the weight parameters in the nn.Conv2d layers
# Next, you just have to generize the above code to different ratio and test the accuracy on the validation set of food11-hw13.

對每一個 Conv2d，把它自己的權重裡絕對值最小的 20% 設成 0。這叫 unstructured pruning（非結構化剪枝）：被剪掉的是散落在各處的單一權重，不是整個通道或整個濾波器。「絕對值小的權重不重要」是最簡單的重要度標準（magnitude pruning），也是 l1_unstructured 名字裡的 L1。

它不是真的把權重刪掉。對剪過的老師檢查 conv1（剪 50%）：

剪之前剪之後
參數只有 weight參數變成 weight_orig（原本的權重，完整保留），另外多了一個 buffer weight_mask（0 與 1 組成的同形狀張量）
conv1.weight 是 nn.Parameterconv1.weight 不再是參數，而是一個普通屬性；模組多了 1 個 forward pre-hook，每次 forward 之前重新算一次 weight = weight_orig * weight_mask
numel 11,182,155；torchsummary 11,182,155都還是 11,182,155（被設成 0 的權重仍然算參數）
state_dict 122 個 key，存檔 44,806,605 bytes142 個 key，存檔 89,481,855 bytes（兩倍：原權重和 mask 各存一份）

所以剪枝之後，模型在每一個意義上都沒有變小：參數一樣多、計算一樣多，存成檔案還大了一倍。要把 mask 固定下來，得對每個模組呼叫 prune.remove(module, 'weight')：它把 weight_orig * weight_mask 的結果寫回一個普通的 weight 參數，拿掉 hook 與 mask。之後 state_dict 回到 122 個 key、44,807,627 bytes，零依然是零（50%），準確率不變——只是一個「一半是 0」的稠密模型。

想用稀疏格式存？把每個 4 維權重轉成 PyTorch 的 COO 稀疏張量（to_sparse()）再存，檔案變成 201,150,399 bytes，是原本的 4.5 倍：COO 格式每個非零元素要另外存 4 個 int64 的座標，50% 的稀疏程度遠不夠抵銷。

另一個實作上的副作用：剪過的模組不能 copy.deepcopy。本書的計時工具第一次這樣做時得到 RuntimeError: Only Tensors created explicitly by the user (graph leaves) support the deepcopy protocol at the moment.，因為 weight 變成了由兩個張量算出來的結果，不是使用者建立的 leaf 張量。要複製，得先 prune.remove，或對一份新載入的模型重新剪一次。

6.2　剪枝比例與準確率（報告第 3-1 題）

報告要求把範例推廣到不同比例，在驗證集上量準確率。本書的 docs/tools/hw13_prune.py 對老師和 Simple 學生各做三種剪法，比例從 0 到 0.95，全部不微調：

  • 逐層 L1（第 52 行）：範例的做法，每一層各自剪掉 r 比例。
  • 全域 L1（第 56 行）：prune.global_unstructured 把所有卷積的權重放在一起排序，用同一個門檻剪掉全體的 r 比例。有的層剪得多、有的層剪得少。
  • 整個通道（第 61 行）：prune.ln_structured(..., n=2, dim=0)，每一層剪掉 L2 範數最小的 r 比例個輸出通道（整個濾波器設成 0）。這是 structured pruning（結構化剪枝）；不過這裡仍然只是 mask，通道並沒有真的消失。

讀這張表：

  • 老師很耐剪。全域剪 30% 只掉 1.4 個百分點，剪 50% 還有 0.749。1,100 萬個參數裡有大量冗餘，這也是「大模型可以壓縮」的實證。
  • 全域比逐層好得多。剪 50% 時 0.749 對 0.522。逐層的做法對每一層一視同仁，包括只有 9,408 個參數的第一層、和三個 downsample 的 1×1 卷積；這些層小而關鍵，剪掉一半就傷筋動骨。全域的做法讓大的層（layer4 有 840 萬個參數）多剪一些、小的層少剪一些，自然地避開了這個問題。
  • 學生幾乎沒有冗餘。逐層剪 20% 就掉了 10 個百分點。全域剪到 30% 還能維持（0.517，比沒剪時的 0.504 還高，是雜訊範圍內的波動），但它的空間比老師小得多：8 萬多個參數，每一個都有用。
  • 整個通道的剪法一碰就崩。老師只剪 10% 的通道，準確率就從 0.871 掉到 0.224。6.4 節解釋為什麼，並說明真正有用的結構化剪枝長什麼樣子。

6.3　剪了會變快嗎（報告第 3-2 題）

第 3-2 題的兩個選項：(a) 剪枝之後神經元被移除，計算量變少，推論變快；(b) 教學裡的剪枝只是替模組加上 mask，計算量幾乎相同，推論時間也差不多。投影片鼓勵自己量。本書用 docs/tools/hw13_speed.py 在 GPU 上沒有任何其他程式時計時（前後各記一次 nvidia-smi，兩次都是空的），每種設定先暖機、再跑 100 次（CPU 20 次）取中位數：

老師GPU batch 64GPU batch 1CPU batch 1（4 執行緒）
原本16.531 ms1.115 ms9.386 ms
剪 50%，還掛著 mask16.761 ms1.468 ms12.751 ms
剪 50%，prune.remove 之後16.568 ms1.101 ms9.615 ms

答案是 (b)，而且比 (b) 說的還糟：

  • 計算量完全沒變。三種模型用 FlopCounterMode 量都是 1,813,566,976 MACs。一半的權重是 0，但卷積照樣把每一個 0 乘上去、加起來。
  • 掛著 mask 時反而更慢：GPU batch 1 慢了 32%，CPU 慢了 36%。每次 forward 之前，20 個卷積都要先做一次 weight_orig * weight_mask，那是額外的運算。batch 64 時這筆固定開銷被大量的卷積運算稀釋，只慢了 1.4%。
  • prune.remove 之後和原本一樣快（差距在量測誤差內）：它只是一個一半權重恰好是 0 的普通模型。

為什麼 0 不能跳過？GPU 和 CPU 的卷積實作（cuDNN、oneDNN）都是為稠密的矩陣運算最佳化的：資料連續地搬、成批地乘。要跳過散落各處的 0，得先檢查每個權重是不是 0、再決定算不算，這種不規則的分支在硬體上通常比直接乘還慢。稀疏要變快，需要兩個條件：零夠多（通常 90% 以上），而且硬體或函式庫支援那種稀疏格式。

現在的做法：硬體能跳過的稀疏，與大型語言模型的剪枝

NVIDIA 從 Ampere 架構（2020）開始支援 2:4 結構化稀疏：每連續 4 個權重裡恰好 2 個是 0，Tensor Core 可以只算另外兩個，理論上矩陣乘法快一倍。它是「非結構化」與「整個通道」之間的折衷：零的位置有規律，硬體才吃得下。PyTorch 用 to_sparse_semi_structured 支援這種格式（本書沒有實測）。在大型語言模型上，SparseGPT（2023）與 Wanda（2023）可以不重新訓練就把權重剪到 50%，再配合 2:4 格式加速；另一條路是整塊拿掉注意力頭、層或隱藏維度（例如 NVIDIA 的 Minitron，2024，剪完再用蒸餾把能力補回來）——和 6.4 節的「拿掉通道、再訓練」是同一個思路，也和第 4 章的蒸餾接上了。

6.4　真的變小：把通道拿掉，再訓練

6.2 節的「整個通道」剪法讓老師一剪就崩。先看原因。本書的 docs/tools/hw13_prune_bn.py 做了兩個實驗（老師，不微調）：

剪掉的通道比例只把卷積的通道設成 0連後面 BatchNorm 的 γ、β 也設成 0改用 BatchNorm 的 |γ| 挑通道
0.10.224490.383380.61895
0.20.144020.134690.24286
0.30.145770.135860.14431
0.50.145770.045190.12653

第一個問題是 BatchNorm。卷積的某個輸出通道設成 0 之後，緊接的 BatchNorm 仍用原本的統計量做正規化：(0 − μ) / σ · γ + β，輸出是一個常數，不是 0。剪 10% 時有 480 個這樣的「死通道」，每個都輸出一個絕對值平均 0.59、最大 2.4 的常數，傳到下一層去干擾。把 γ、β 也設成 0，讓死通道真的輸出 0，準確率從 0.224 回到 0.383。

第二個問題更根本：挑錯了通道。ln_structured 按卷積權重的 L2 範數挑，可是卷積後面接著 BatchNorm，BN 會把每個通道除以它自己的標準差、再乘上 γ：權重小的通道，輸出也小，標準差跟著小，正規化之後又被放大回來。所以卷積權重的大小幾乎不代表這個通道的重要性。改用 BatchNorm 的 |γ| 來挑（γ 才是正規化之後真正決定通道輸出大小的係數，這是 network slimming 的做法），剪 10% 的準確率回到 0.619。即使如此，剪到 20% 仍然只剩 0.243：不重新訓練，結構化剪枝的損失就是這麼大。

結構化剪枝的價值，在於剪完之後可以把通道真的拿掉，得到一個更小的稠密模型，所有的硬體都能直接加速。本書用 Simple 學生示範（它是單純的一條鏈，拿通道比 ResNet 容易得多）：

每個卷積依權重的 L1 範數留下前 keep 比例的輸出通道（第 15–16 行）；新的卷積只保留這些輸出通道、以及上一層留下來的輸入通道（第 17–18 行）；BatchNorm 的四組數字跟著挑（第 20–21 行）；最後的全連接層只保留留下來的輸入（第 27 行）。這裡用卷積權重的範數挑通道，正是上面說的那個不好的標準；本書保留它，是因為接著會重新訓練，挑選標準的影響會被訓練補回來。

最醒目的一格：範例學生在 GPU 上一次處理 64 張，比老師還慢（22.4 對 16.5 ms）。參數只有老師的 1/127，卻慢了 35%。第 2 章已經預告了原因：它的計算量是老師的 47%，而且集中在 220×220 的大特徵圖上，要搬的中間結果比老師多；老師的計算集中在小特徵圖、多通道的層，正是 GPU 最擅長的形狀。如果作業的目標是「在 GPU 上跑得快」，範例學生是一個比老師更差的模型。

一次只處理 1 張時，排名完全反過來：範例學生最快（0.30 ms），老師和 26 層的 mbv2 較慢。單張圖的工作量太小，GPU 的時間主要花在逐層啟動運算的固定開銷，層數少的模型佔便宜。CPU 上又是另一個排名：plain 最快、老師最慢，比較接近計算量的順序。哪個模型比較快，取決於硬體與 batch 大小；要部署，就要在部署的條件下量。

fp16 一欄是第 7 章的預告：同樣的模型改用 16 位元浮點數，GPU 上老師從 16.5 變成 7.4 ms，快了一倍多，而且第 7 章會看到準確率完全不變。和剪枝相比，這是不必重新訓練、就能真的加速的壓縮。

本章重點

  • prune.l1_unstructured 把權重拆成 weight_orig 與 weight_mask，每次 forward 前重算 weight；參數與計算量不變，存檔大一倍，模組不能 deepcopy。prune.remove 把它固定成一個帶 0 的稠密模型。
  • 剪枝比例對準確率（報告 3-1）：老師全域剪 50% 仍有 0.749，逐層剪只有 0.522；學生幾乎沒有冗餘；整個通道的 mask 剪法剪 10% 就崩到 0.224。
  • 剪 50% 的老師完全沒有變快（GPU b64 16.76 對 16.53 ms），掛著 mask 時 batch 1 還慢了 32%（報告 3-2 選 (b)）。0 散落各處，稠密的卷積實作照樣全部乘一遍。
  • 結構化剪枝要成功：死通道後面的 BatchNorm 要一起處理，挑通道要看 |γ| 而不是卷積權重的大小，而且要重新訓練。實體拿掉一半通道的學生參數剩 22,647、GPU 快一倍，微調後 0.544，比同寬度從頭訓練高 5.8 個百分點（但多訓練了 9 個 epoch）。
  • 範例學生在 GPU batch 64 時比老師還慢（22.4 對 16.5 ms）；batch 1 時卻最快。速度取決於硬體與 batch 大小，要在部署條件下量。

自我測驗

1. 剪枝之後用 torchsummary 數參數，Total params 會變少嗎？那報告第 1 題能不能用「先訓練一個大學生、再剪掉 90%」來過 100,000 的上限？

不會變少。conv.weight 仍然存在（由 weight_orig * weight_mask 算出來），torchsummary 照樣數它的元素數，設成 0 的權重也算；本章實測剪 50% 前後都是 11,182,155。所以 mask 式剪枝不能用來過參數上限；要變少，得像 6.4 節那樣把通道真的拿掉、建一個更小的模型。

2. 為什麼全域剪枝在老師上比逐層剪枝好那麼多？

逐層剪枝讓每一層都剪掉同樣比例，包括參數很少但很關鍵的層：第一個 7×7 卷積（9,408 個參數）、三個 downsample 的 1×1 卷積。這些層剪一半，資訊就被截斷了。全域剪枝用同一個門檻，參數多、冗餘多的層（layer4 佔 75% 的參數）會被剪得多，小而關鍵的層剪得少，整體損失就小很多：剪 50% 時 0.749 對 0.522。

3. 一個剪掉 50% 權重的模型，用 prune.remove 固定之後存成檔案，為什麼不會變小？要怎樣才會變小？

因為 PyTorch 預設用稠密格式存張量，0 也要佔 4 個 bytes。改用 COO 稀疏格式（to_sparse()）反而變成 4.5 倍大：每個非零元素要多存 4 個 int64 的座標，50% 的稀疏度遠不夠抵銷。要變小，可以把通道真的拿掉（6.4 節），或用壓縮率高的格式存（例如只存非零值與位元遮罩，再加上壓縮），或配合量化減少每個數的位元（第 7 章）。Deep Compression（2015）就是把剪枝、量化與霍夫曼編碼串起來做這件事。

4. 本章說「剪完微調」比「同寬度從頭訓練」好 4.5 到 5.8 個百分點。這個比較有什麼不公平的地方？

微調的起點是已經訓練了 9 個 epoch 的 Simple 學生，所以剪完微調的模型總共看過 29 個 epoch 的資料，從頭訓練的只有 20 個。第 4 章看過，這個學生在 50 個 epoch 之前都還在進步，多 9 個 epoch 本身就值好幾個百分點。公平的對照應該讓從頭訓練跑 29 個 epoch。本書沒有跑這一組，所以只能說「剪完微調在同樣的微調預算下比較好」，不能說剪枝留下的權重值多少個百分點。

5. 範例學生在 GPU batch 64 時比老師慢，batch 1 時卻比老師快 3.7 倍。如果你的應用是手機上一次辨識一張照片，你會根據哪一個數字選模型？

兩個都不適合直接拿來用。batch 1 的條件比較接近，但本書的 batch 1 是在桌機 GPU 上量的，手機的處理器、記憶體頻寬、支援的運算元都不同；本書在桌機 CPU（4 執行緒）上量到範例學生 5.70 ms、老師 9.39 ms、plain 0.93 ms，排名又和 GPU 不一樣。要在手機上用，就要匯出到手機的推論框架、在手機上量。本章的教訓就是：速度要在部署的條件下量。
